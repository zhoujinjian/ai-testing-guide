# 08｜质量度量科普：逃逸率、DRE、MTTR

> 核心要点：执行率、通过率说的是**测试阶段干得怎么样**，逃逸率、DRE、MTTR 说的是**测试的价值最终兑现了多少**——逃出去多少、拦住了几成、出事后多快摆平；三个指标都要用**上线后的结果**反过来算，算的时候口径先行。

## 打个比方

渔夫的鱼塘分两口：**苗塘**和**成鱼塘**。鱼苗进成鱼塘之前，要先过一道筛子，把病苗、弱苗筛出去。

渔夫关心三件事。一是**漏了多少**：筛过的苗放进成鱼塘，过几天还是发现有病苗——漏出去的会在大塘里传染，这就是逃逸。二是**筛子拦住了几成**：100 条病苗拦住 97 条、漏 3 条，和拦 70 漏 30，是完全不同的两把筛子。三是**发现了治得多快**：真有病苗漏进成鱼塘，半天捞出来处理掉，和拖一星期整塘感染，结局天差地别。

测试就是那道筛子，线上环境就是成鱼塘。**逃逸率**看漏了多少，**DRE（缺陷移除率）**看拦住几成，**MTTR（平均修复时长）**看漏出去的病苗多快被治好。漏得少是本事，漏了能快速止血，也是本事——两个本事一起练。

## 展开讲讲

### 逃逸缺陷率：漏出去多少

先定义：**逃逸缺陷** = 上线后由用户或监控发现的、本应在测试阶段发现的缺陷。需求上线后才变更、运营配置错误这类，算不算要提前约定，不然每次复盘都要吵一轮。

**公式：逃逸缺陷率 = 线上发现缺陷数 ÷（测试发现缺陷数 + 线上发现缺陷数）× 100%**

算例（上个版本 6.1.0）：测试阶段发现 41 个，上线后线上冒出 3 个：

3 ÷（41 + 3）= 3 ÷ 44 = **6.8%**

算例（本版本 6.2.0，购物车限购 99 改 200 那个版本）：测试发现有效缺陷 44 个，上线后线上 2 个：

2 ÷（44 + 2）= 2 ÷ 46 = **4.3%**

### DRE 缺陷移除率：筛子拦住了几成

DRE（Defect Removal Efficiency）和逃逸率是一枚硬币的两面：

**公式：DRE = 测试发现的缺陷数 ÷（测试发现 + 线上发现）× 100%**

算例：6.1.0 的 DRE = 41 ÷ 44 = **93.2%**；6.2.0 的 DRE = 44 ÷ 46 = **95.7%**。

数学上 DRE = 100% − 逃逸率，但两个数都要算、都要写——评审会上"逃逸率 4.3%"是问题视角，"DRE 95.7%"是能力视角，先后顺序影响听的人什么感受。读 DRE 还要带一个心眼：DRE 高，可能是测试真强，也可能是开发产出的缺陷太多、测试在拼命兜底——要和[缺陷密度](./04-core-metrics.md)对着看。

### MTTR 平均修复时长：漏了之后多快止血

MTTR（Mean Time To Repair，平均修复时长）衡量的是**从缺陷被发现到系统恢复正常**的平均耗时，是右移视角的指标——出了事不可怕，可怕的是恢复得慢。

**公式：MTTR = 每次故障（发现 → 恢复）耗时之和 ÷ 次数**

算例（6.2.0 上线后的两个线上缺陷）：

- 3 月 27 日 15:20，客服反馈"满 199 减 30 券与满减叠加时，购物车合计与结算页差 0.01 元"；16:05 定位为四舍五入规则不一致，17:50 热修上线——耗时 2.5 小时
- 3 月 29 日 10:11，用户反馈"收货地址改为偏远地区后运费未重算"；10:40 定位，11:26 热修上线——耗时 1.25 小时

MTTR =（2.5 + 1.25）÷ 2 = **1.9 小时**。资金和主流程类的线上问题，行业里普遍要求小时级恢复，1.9 小时算体面；如果算出来是两天，那要复盘的就不是测试，是整个应急机制。

### 三个指标怎么配合用

| 指标 | 回答什么 | 6.1.0 → 6.2.0 | 好的标准 |
| --- | --- | --- | --- |
| 逃逸率 | 漏出去多少 | 6.8% → 4.3% | 越低越好，和自己的基线比 |
| DRE | 拦住了几成 | 93.2% → 95.7% | 95% 以上算健康 |
| MTTR | 漏了之后多快恢复 | 无记录 → 1.9 小时 | 资金 / 主流程类小时级 |

单看任何一个都会被骗：DRE 95.7% 看着漂亮，若 MTTR 是 48 小时，用户照样流失光。**漏得少 + 漏了能快速止血**，合起来才是质量保障的完整能力。

最后提醒一个度量的天敌：指标一旦变成对个人的考核，就会有人把线上问题往"需求变更""运营配置"里塞、把发现时间往早里报——数字立刻失真。**度量用来改进流程，不用来给人排名。**

## 举个例子

把三个指标串成一次真实的复盘（4 月初的季度质量总结会）：

你先摆数据：6.1.0 逃逸 3 个，拆开看是弱网场景 2 个、Android 8 老机型 1 个；6.2.0 之前团队补了弱网专项和 12 款机型兼容回归（就是 6.2.0 测试报告里那两个专项），结果 6.2.0 的 2 个逃逸里弱网和机型类是零——**改进动作兑现成了指标改善**，逃逸率 6.8% 降到 4.3%、DRE 升到 95.7%。

再看 MTTR：6.1.0 时代线上问题没有记录时间线的习惯，MTTR 算不出来；6.2.0 开始要求"发现、定位、恢复"三个时间点必填，算出 1.9 小时。你在总结里写的下一步是："6.3.0 对金额计算类需求引入提测前对账校验，目标把 6.2.0 这类四舍五入逃逸再堵掉一层。"

——数据 → 归因 → 动作 → 下个版本验证，度量这才闭环。没有动作的度量，是挂在天花板上的装饰画。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 把逃逸率当个人考核指标 | 一考核就有人往"不算逃逸"的筐里塞问题，指标马上失真 |
| 逃逸口径不提前约定 | 需求变更、配置错误、第三方故障算不算，不约定就每次复盘吵一轮 |
| DRE 高就万事大吉 | DRE 高也可能因为开发缺陷太多、测试在兜底，要和缺陷密度对着读 |
| MTTR 只算修复不算发现 | 从用户反馈算还是从监控告警算，起点不同数字差一倍 |
| 指标看单点不看趋势 | 一个版本的 4.3% 说明不了什么，连续三个版本的走向才是信号 |
| 只统计不改进 | 度量的唯一目的是驱动改进动作，没有下一步的度量报告是装饰品 |

## 上手建议

1. **建一张逃逸清单**：每个线上缺陷记一行——现象、根因、本应何阶段发现、发现与恢复时间，三个指标的数据源全是它
2. **和团队约定口径写进文档**：逃逸算不算配置错误、MTTR 从哪个时间点起算，白纸黑字，复盘不吵
3. **MTTR 记到分钟**：发现、定位、恢复三个时间点当场记，事后补录必然失真
4. **每季度画一次三指标趋势图**：和上季度的改进动作对照，看动作有没有兑现成数字
5. **度量结果只进复盘会不进绩效表**：讨论的永远是"流程哪里改"，不是"谁背锅"
