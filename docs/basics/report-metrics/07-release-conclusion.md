# 07｜上线结论怎么下：质量评估的依据

> 核心要点：上线结论不是一句"可以上了"，而是三选一——**建议上线 / 有条件上线 / 不建议上线**，每个结论都要有四类依据撑着：出口标准达成情况、版本数据、遗留风险、历史对比；**测试给结论，决策归项目，但依据必须扎实、边界必须写清。**

## 打个比方

航班起飞前，签派员和机长要做**放行决策**。

他们不是凭感觉说"今天应该能飞"，而是过检查单：目的地天气、航路天气（外部条件）、油量（资源余量）、飞机机械状况（系统健康）、机组状态（团队状态）。每一项对着标准看，全部过线，才在放行单上签字。结论也只有三种：**正常起飞**、**推迟起飞**（等天气窗口或排故）、**取消或换机型**（短期内修不好）。

还有一个细节：签派员给评估意见，**机长签字担责**。签派说天气在边缘，机长可以结合航班任务决定飞或不飞——决策权在机长，但签派的专业评估必须给足、说清。

测试就是那个签派员：上线结论是你的专业输出，**最终拍板是项目组的事**（大促窗口、市场节奏都是业务考量）。你的专业体现在两件事上：结论有依据，边界说清楚。

## 展开讲讲

### 结论只有三档，别发明第四档

| 结论 | 适用情形 | 报告里怎么表述 |
| --- | --- | --- |
| 建议上线 | 出口标准全达成，遗留均为一般 / 轻微且规避就位 | "出口标准全部达成，遗留 3 个均不碰主流程，建议按期上线" |
| 有条件上线 | 个别条件未满足，但有补偿手段 | "全量回归覆盖率 90%，建议灰度 5% 起步、重点观察 48 小时后再全量" |
| 不建议上线 | 出口标准有硬伤：严重缺陷未修、主流程未通、关键数据缺失 | "2 个严重缺陷未修复且无规避方案，不建议本迭代上线，预计延期 2 天" |

"再测测看""应该没问题""基本差不多"——这些话都不算结论。评审会上与会者要的是一个能落进会议纪要的明确档位，模糊表述只会换来一轮追问。

### 依据从哪来：四个输入

1. **出口标准**：测试计划阶段就定好的准出线（执行率、通过率、严重缺陷清零、遗留受控），下结论时逐条对照。标准怎么定，见[准入与准出：什么时候开始测、什么时候能上线](../process/11-entry-exit-criteria.md)
2. **版本数据**：6.2.0 的实例——执行率 98.8%、通过率 94.1%、有效缺陷 44 个修复 41 个、严重 3 个全部修复回归
3. **遗留风险评估**：遗留表三条，均不碰主流程与资金、规避就位，见[遗留缺陷与风险评估怎么写](./06-remaining-risk.md)
4. **历史对比**：6.1.0 同期通过率 92.7%、线上逃逸 3 个；6.2.0 各项持平或更好——**和历史比是结论的底气来源**，孤零零的一版数据谁也说不清是好是坏

### 结论必须带边界

测试结论的标准句式："**在已执行 324 条用例及兼容、弱网专项范围内，未发现阻塞上线的缺陷。**"

这句话同时保护你和真相：4 条未执行的用例（2 条依赖大促数据、2 条 P3 移入下版本）、没来得及做的专项，都是边界，要在结论附近点名。没有边界的"可以上线"，等于替整个宇宙做了保证——谁也付不起这个责任。

### 决策权和专业权分开

你给出"不建议上线"，业务因为大促窗口执意要上，怎么办？把风险复述清楚、留下书面记录、准备好灰度和回滚预案——这不是认输，是专业。**红灯没亮是失职，红灯亮了没人踩刹车是决策**，两者在事后追责时是完全不同的责任。反过来，该亮红灯时你亮了绿灯，第一个被追责的就是你。

## 举个例子

6.2.0（购物车限购 99 改 200 等 6 个需求）3 月 23 日评审会，你的结论是**建议上线**，报告里摆了四条依据：出口标准六项全部达成；执行率 98.8%、通过率 94.1%；有效缺陷 44 个修复回归 41 个、严重 3 个全部关闭；遗留 3 个均不碰主流程、规避方案就位。

会上被挑战两次。第一次，产品指着遗留表问 BUG-1129 的卡顿会不会引发投诉，你按[遗留缺陷表](./06-remaining-risk.md)的三要素答完。第二次，领导问执行率为什么不是 100%，你答："2 条依赖的大促活动没开始、2 条 P3 经评审移入下版本，四条都列在报告里，这属于受控裁剪。"

最后会议纪要落字：**3 月 26 日 20:00 上线，灰度 10% 起步，观察订单转化率与崩溃率 24 小时后全量**。你结论里那句"弱网专项已执行、极限机型兼容 2 条用例移入下版本"的边界声明也被纪要原样保留——上线后一周，6.2.0 线上缺陷 2 个，都不在边界声明的范围内。结论闭环，专业信誉又厚了一层。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 结论含糊（"应该可以"） | 三档之外的表述都是没下结论，会议纪要没法写 |
| 结论只凭感觉（"测得差不多了"） | 每个结论至少挂两条数据依据，拍脑袋的结论一追问就穿帮 |
| 把"建议上线"当"保证没问题" | 你对"已测范围内未发现阻塞缺陷"负责，"上线后绝不出问题"谁也保证不了 |
| 不敢说"不建议上线" | 该亮红灯时亮绿灯，出事后第一责任在你；红灯被否决是决策，没亮是失职 |
| 结论不带边界 | 没测的、裁掉的、拿不准的都写进去，边界清晰结论才可信 |
| 数据前后打架 | 报告里 94.1%、会上说 94%，小误差毁掉的是整份报告的信任 |

## 上手建议

1. **结论措辞锁死三档**：从"建议上线 / 有条件上线 / 不建议上线"里选一个写，不自创新说法
2. **准出标准提前定**：测试计划阶段就把出口标准写死，下结论时逐条对照，别事后找标准凑数
3. **给结论预演两个追问**：最尖锐的问题通常是"为什么不是 100%"和"遗留谁负责"，答案提前写进报告
4. **结论段固定带边界句**：模板——"在……范围内，未发现……"，每个版本照着填
5. **结论被否决时留痕**：邮件或会议纪要复述风险与预案，专业且自保，这是测试的止损动作
