# 06｜遗留缺陷与风险评估怎么写

> 核心要点：遗留缺陷表五列一个不能少——**编号、严重度、影响、规避方案、负责人**；写风险要"敢写也敢扛"：敢写是把已知问题全部亮出来，敢扛是每条都有规避方案、负责人和时限，写完不管等于没写。

## 打个比方

体检报告上写着：甲状腺结节，3 类。

没到要手术的程度（不阻塞上线），但医生绝不会装没看见，而是给你一张**随访医嘱**：结节多大、什么性质（问题是什么）、目前不影响健康但需注意什么（影响多大）、平时少熬夜少吃碘（怎么规避）、半年后复查、有变化随时挂外科（找谁、什么时候）。四个要素齐了，这个"没好透的问题"才算是被管理起来了。

最怕两种医生：一种是查出来不说，等结节变大了才摊牌——**隐瞒风险**；另一种是说了不管，医嘱里连复查时间都没有——**写了不扛**。遗留缺陷表就是测试交给项目的随访医嘱，两种失职一种都不能沾。

## 展开讲讲

### 遗留缺陷表：五列模板

拿电商 App 6.2.0 版本（购物车限购 99 改 200 等 6 个需求）的三条遗留直接当模板：

| 编号 | 严重度 | 影响 | 规避方案 | 负责人 / 时限 |
| --- | --- | --- | --- | --- |
| BUG-1129 | 一般 | 低端机全选 50 种以上商品时，按钮响应延迟约 2 秒，不影响下单 | 6.3.0 优化列表渲染；期间客服话术已同步 | 开发·李工，6.3.0 |
| BUG-1137 | 轻微 | 深色模式下购物车金额文字对比度低，辨认吃力 | 6.3.0 随 UI 规范统一调整 | UI·王工，6.3.0 |
| BUG-1142 | 轻微 | 修改默认地址后，旧订单详情页地址标签不刷新 | 下拉刷新可恢复；已录入用户 FAQ | 开发·张工，待排期 |

对着表检查五列的含金量：**编号**让它可追溯（bug 系统里能点开详情）；**严重度**让决策者一眼排序；**影响**写的是用户视角的后果，不是代码术语；**规避方案**必须是"期间怎么办"加"什么时候根治"，只写"下版本修复"不算方案；**负责人**落到具体的人加时限，"开发会处理的"等于没人负责。

### 哪些缺陷够格遗留：一把尺子

四个条件全部满足，才有资格进这张表：

1. 不碰**主流程和资金**——下单、支付、金额计算出问题，一票否决
2. 严重度为**一般或轻微**——严重缺陷想遗留？先看[上线前一天发现严重 bug 怎么办](../../interview/testing-essentials/10-critical-bug-before-release.md)
3. 有明确的**规避或补偿方案**——有话术、有 FAQ、有监控，都算
4. 负责人和时限**落字**——口头承诺不算

卡尺的另一半：致命缺陷没有任何讨论空间，上线前必须清零。

### 敢写与敢扛

**敢写**：已知问题不进表，上线后炸出来，性质就从"已知风险"变成"隐瞒问题"——前者是项目共同决策，后者是你一个人的责任。表里每一行都是项目知情、你免责的证据。

**敢扛**：写进表不是终点。BUG-1129 写了"客服话术已同步"，你就得真去确认话术发了；写了"6.3.0 修复"，6.3.0 提测时就要验证关闭。遗留表是活文档，不是报告的装饰段落。

### 风险措辞三要素

每条风险的文字表述，用三要素自查：**触发条件 + 影响范围 + 应对**。

- 合格："若低端机用户在全选 50 种以上商品时，可能出现约 2 秒延迟（仅观感受影响、不影响下单），客服话术已备"
- 不合格："可能有点卡"

后者看起来"留了余地"，实际上一半是没帮决策（读的人不知道多严重），一半是没保护你（真出事时这句话挡不住任何追问）。

还有一类容易漏的风险：**没测到的部分**。被裁剪的 2 条 P3 兼容用例、没来得及做的专项，同样是风险，要和缺陷遗留并排列出——风险不只藏在发现的 bug 里，也藏在没走的用例里。

## 举个例子

6.2.0 版本 3 月 23 日评审会，产品经理翻到遗留表，指着 BUG-1129 问："这个卡顿，用户不会投诉吗？"

你按表格三要素答："触发条件是低端机、购物车里 50 种以上商品、点全选，三个条件同时满足才会出现；影响是延迟 2 秒、下单不受影响，我们查过 6.1.0 的客诉记录，同类体验问题月均反馈 2 起以内；应对是客服话术今天已同步、李工确认 6.3.0 修复，上线后一周我会盯着客服工单。"产品点头，结论维持"建议上线"。

上线一周后你复核：BUG-1129 收到 2 起客服反馈，和预判一致；6.3.0 提测当天你验证关闭了它，在群里发了句"1129 已关闭"。这份"敢写也敢扛"的记录，就是你下次再说"这条可以遗留"时的信用本钱——**遗留管理的口碑，是一条一条攒出来的。**

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 遗留 = 装看不见 | 不写不会消失，上线后炸出来，性质从"已知风险"变成"隐瞒问题" |
| "下版本修复"算交代 | 没有负责人和时限的承诺等于没有承诺，6.3.0 是排期不是话术 |
| 遗留清单一股脑全塞 | 真正需要项目知情的是影响决策的几条，十几条的清单没人看 |
| 措辞模糊求保险 | "可能有点卡"既帮不了决策也保护不了你，三要素缺一不可 |
| 只写缺陷不写"没测到的" | 裁掉的用例、没做的专项也是风险，要和缺陷遗留并排列出 |
| 写完就归档 | 每条有时限，到期跟进验证关闭，遗留表是活文档不是存档页 |

## 上手建议

1. **下个版本就换五列表**：编号、严重度、影响、规避方案、负责人，先别加别的列，用顺了再扩展
2. **每条措辞按三要素自查**：触发条件、影响、应对，读一遍，缺哪个补哪个
3. **遗留单在 bug 系统打标签**：统一打"遗留"标签加目标版本号，版本末期一键过滤出表，不用手工凑
4. **评审前逐条和开发对齐**：负责人和时限让本人确认，别在会上替开发拍承诺
5. **上线后按表逐条核销**：到期验证关闭、复核客服反馈量，让团队看到遗留管理是真的在管
