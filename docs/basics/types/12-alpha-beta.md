# 12｜Alpha 测试与 Beta 测试：正式上线前的两次试演

> 核心要点：**Alpha 是开发方内部的受控测试**——自己人先当一次用户；**Beta 是真实用户在真实环境里的小范围试用**——真观众进场收真实反馈。两者都是验收测试的组织形式，一个靠内部可控、一个靠真实多样，上线前的最后两道用户视角关卡。

## 打个比方

一部电影从拍完到正式上映，有两场试映：

**内部试映**：剪辑还没完全定稿，主创团队和片厂员工在小放映厅先看一遍——剧情逻辑通不通、有没有穿帮镜头、台词有没有硬伤。观众是自己人，看得认真、反馈专业，但身份太懂行，感受不了普通观众的笑点和泪点。**点映**：在几个城市放小规模场次，请真实观众买票进场——节奏拖不拖、结局接不接受、会不会推荐朋友来看，全由真观众用脚投票。片方根据口碑决定是重新剪辑结局还是扩大排片。

对应过来：**Alpha＝内部试映**（自己人、受控环境、挑硬伤），**Beta＝点映**（真用户、真实环境、收真实体验），**正式上映＝全量发布**。跳过两场试映直接全量，等于把首映当试映——翻车就是大型公开事故。

## 展开讲讲

### Alpha 测试：自己人先看一遍

- **时机**：系统测试中后期，功能基本完整、主流程稳定之后
- **谁参与**：公司内部员工，最好是**没参与过这个项目的人**——参与过的人看什么都说好，"自己孩子怎么看怎么俊"
- **环境**：受控的开发 / 测试环境，或专门的模拟环境
- **发现什么**：功能缺陷、明显的设计硬伤、易用性问题——内部观众的优势是敢提意见、能复述操作步骤，反馈质量高
- **谁来组织**：测试团队，Alpha 本质是把系统测试再包一层"准用户视角"

### Beta 测试：真观众进场

- **时机**：Alpha 通过后、正式发布前，功能已稳定
- **谁参与**：**真实用户**——公开招募志愿者或定向邀请种子用户，几百到几千人不等
- **环境**：用户自己的设备、自己的网络、真实的数据——这是 Alpha 永远替代不了的：公司内部清一色新手机和千兆 Wi-Fi，而真实用户里有三年前的安卓机、有地铁弱网、有一边充电一边抢红包的重度用户
- **发现什么**：兼容性问题（机型终于多样了）、真实场景问题（内部没人想到的使用姿势）、性能体感（真用户的耐心阈值）
- **形态**：游戏行业"公测"、App 内测分发渠道（TestFlight、各安卓应用商店内测版）、Web 产品"抢先体验"

### Alpha 与 Beta 对比

| 维度 | Alpha 测试 | Beta 测试 |
| --- | --- | --- |
| 时机 | 系统测试中后期 | Alpha 通过后、发布前 |
| 参与者 | 内部员工（非项目组优先） | 真实用户（招募或邀请） |
| 环境 | 受控环境 | 用户真实设备和网络 |
| 发现什么 | 功能缺陷、设计硬伤 | 兼容、真实场景、体验 |
| 可控性 | 高，反馈质量稳定 | 低，反馈杂、需要筛选 |

### 和灰度发布的区别（高频混淆点）

Beta 测试和**灰度发布**看着像——都是"先放一小部分人用"，但性质不同：**Beta 是发布之前的测试活动**，产品还没正式发布，目的是收反馈改问题；**灰度是发布策略**，版本已经正式发布，只是控制放量节奏（先放 5% 用户，观察无异常再逐步放大，详见[发布上线：灰度、放量与线上验证](../process/12-release-process.md)）。一句话分清：**Beta 是"要不要上"的参考，灰度是"怎么上"的节奏**。

## 举个例子

在线教育 App 新版本，核心功能"错题本"，两次试演完整走一遍：

**Alpha（内部，一周）**：通过公司内网分发，200 名非项目组同事参与，测试环境。收获一批高质量反馈：三年级以下的题库缺失（低学段用户进来就是空页）、错题导出 PDF 时公式乱码、反馈都能附带复现步骤——这是内部观众的红利，普通用户只会说"坏了"。两个问题全修复。

**Beta（外部，两周）**：应用商店内测渠道放出，5000 名种子用户（从老用户中报名招募），用户自己的设备。新发现三类问题：平板分辨率下排版挤成一团（公司内部几乎没人用平板测试）、某品牌手机拍照搜题闪退 47 例（内部没这机型）、家长反馈"孩子误触清空错题本且无法恢复"——加了二次确认加回收站。反馈通道两条：App 内置反馈入口 + 种子用户群，每天汇总分类。

**全量发布前**：Beta 期发现的问题全部处理完，崩溃率降到 0.05% 以下，种子用户群里主动好评变多，版本过验收（上线结论怎么下见[怎么判断版本测完了可以上线](../../interview/testing-essentials/18-release-exit-criteria.md)）。两周试演换来的，是正式发布当天没有翻车。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| Alpha 和 Beta 是两次重复的测试 | 参与者和环境完全不同：内部受控挑硬伤，外部真实捞兼容和体验 |
| Beta 阶段发现的问题上线再修也行 | Beta 的意义就是上线前最后一轮真实验证，带着已知问题全量等于赌运气 |
| Beta 用户越多越好 | 没有反馈通道和数据回收机制，人越多噪声越大；几千有效用户胜过几万沉默用户 |
| 灰度发布就是 Beta 测试 | 灰度是发布策略（怎么上），Beta 是测试活动（要不要上），时点在发布之前 |
| 内测渠道发的包不用测 | 内测包也是正式露脸的包，自测加冒烟不能省，第一批内测用户的信任最贵 |

## 上手建议

1. 团队发内测包时，把你们的冒烟用例在内测渠道上再真实跑一遍——内测包翻车一样丢人
2. Beta 前先搭好反馈回收三件套：内置反馈入口、用户群、问题分级表，别等用户进来才想怎么收集
3. Beta 期每天盯三个数：崩溃率、新功能使用率、卸载率——比看反馈口水战直观得多
4. 把 Beta 反馈按"功能 / 兼容 / 体验"三类归档，能复现的转成 bug，不能复现的记入[偶现 bug 处理流程](../bug-management/07-intermittent-bugs.md)
5. 争取旁观一次自己产品的灰度发布全流程，把"Beta 是测试、灰度是发布"这条分界线看实（见[发布上线：灰度、放量与线上验证](../process/12-release-process.md)）
