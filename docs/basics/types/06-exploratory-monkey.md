# 06｜探索性测试与猴子测试：用例之外的两条路

> 核心要点：**探索性测试**是带着目标和经验的有脑自由发挥——边设计边执行；**猴子测试**是工具生成随机操作的纯乱撞——跑量换崩溃。一个靠人的经验补用例的漏，一个靠随机量补人手的极限。

## 打个比方

去一座陌生城市玩，有三种走法：

**跟团**：攻略精确到分钟，几点集合、看什么景点、走什么路线，全按清单执行——这就是执行测试用例，覆盖有保证，但清单上没有的地方一步不去。**自由行**：你有个大方向（这次专逛老城区的小吃），具体路线边走边定，看见有意思的巷子就钻，钻进去发现一家攻略上没有的老店——这是探索性测试，**有目标、有经验、无固定路线**。**闭眼乱走**：拿个骰子决定每个路口往哪拐，走一整天，大概率绕圈，但万一撞进一片攻略和自由行都到不了的废墟花园呢——这是猴子测试，**无目标、无经验、纯随机**。

三者的关系不是替代：跟团保证下限，自由行抬高上限，乱撞碰极端运气。

## 展开讲讲

### 探索性测试：有脑子的自由行

探索性测试（Exploratory Testing）不是"乱点"，它是**一边设计一边执行的测试**：测试设计和测试执行同时进行，下一个测什么取决于上一个结果给你的启发。

它有三个和"乱点"划清界限的标志：

- **有目标（Charter）**：开始前用一句话写清本次探索的区域和目的，比如"这 90 分钟专攻订单取消的各种异常姿势"
- **有时间盒（Session）**：固定时长的一段探索，60~90 分钟一个回合，到点收工写记录
- **有假设驱动**：每一步都在验证一个猜想——"如果我在支付转圈时切到后台再回来，订单状态会怎样？"这和漫无目的的消磨时间完全是两回事

**它依赖什么**：对系统的熟悉程度和对易错点的嗅觉。同一个 App，老手探索一小时捞三个 bug，新手转一小时颗粒无收，差距全在经验——而经验的系统化版本，就是用例篇里的[错误推测法](../testcase-design/13-error-guessing.md)。

**和用例的关系**：互补而不是替代。用例保证可重复执行和覆盖下限；探索负责走用例没想到的路，抬上限。探索中发现的 bug 和路径，应该反哺成新的正式用例。

### 猴子测试：真正的乱走

猴子测试（Monkey Testing）用工具生成**大量随机操作序列**——随机点击屏幕随机坐标、随机滑动、随机输入——长时间跑下去，看应用崩不崩、无响应不响应、内存泄不泄漏。名字来自"无限猴子定理"：让猴子随机敲键盘，敲得够久总有一天能敲出莎士比亚。

- **代表工具**：Android 自带的 Monkey，名字最正宗，命令行一条就能跑（下文例子里有）
- **它擅长什么**：崩溃率、无响应（ANR）、内存泄漏这类**需要海量操作才撞得出来**的问题——人手点一万次不现实，随机工具跑一晚上轻轻松松
- **它撞不到什么**：业务逻辑错误。随机操作碰巧完成一次"先用券再退货"的完整流程并发现金额算错的概率，约等于零——逻辑问题还是人和用例的活

两者一张表对齐：

| 维度 | 探索性测试 | 猴子测试 |
| --- | --- | --- |
| 有没有目标 | 有明确 Charter 和时间盒 | 无目标，纯随机 |
| 靠什么 | 人的经验和怀疑精神 | 工具的随机量 |
| 谁来执行 | 人（测试工程师） | 工具（如 Monkey） |
| 典型产出 | 逻辑型、体验型 bug | 崩溃、ANR、内存泄漏等稳定性问题 |
| 什么时候用 | 用例执行完后的补漏、新功能快速摸底 | 提测当晚挂机跑、稳定性专项 |

## 举个例子

社交 App 上线"发布动态"功能，用例测完 60 条全部通过之后，你追加两个动作：

**一、90 分钟探索（Charter：动态发布和编辑的边角姿势）**：

- 发一条"9 图 + 定位 + @三个好友"的动态：正常
- 提交瞬间切到后台，10 秒后回来：草稿箱提示"已保存"，但回来发现内容真的还在——通过；换个姿势，提交瞬间直接杀进程，重新打开：草稿没了也没任何提示——bug 一个
- 弱网（工具限速 200ms）下连点两次"发布"：发出去了两条一模一样的动态——bug 两个，这种重复提交类问题用例很少覆盖，因为正常网络下你点不出第二次

**二、当晚挂 Monkey 跑 8 小时**：

```
adb shell monkey -p com.example.app --throttle 300 -s 500 200000
```

（`-p` 指定应用包名，`--throttle 300` 每个事件间隔 300 毫秒，`-s 500` 固定随机种子方便复现，`200000` 是事件总数）

第二天看崩溃报告：3 次崩溃，全部集中在图片浏览页，栈信息指向同一行代码。用例执行 60 条没碰到的页面深处，被二十万次随机操作撞了出来。

两条路捞到的 5 个问题，用例一条都没覆盖——这就是"用例之外"的价值。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 探索性测试＝乱点 | 有 Charter、有时间盒、有记录、有假设驱动；没有这四样只是消磨时间 |
| 会探索就可以少写用例 | 用例保证可重复和覆盖下限，探索抬高上限，砍掉哪个都是瘸腿 |
| 猴子测试没有技术含量 | 随机压力是人肉替代不了的，App 的崩溃率指标主要就靠它守 |
| 探索发现全靠天赋 | 探索的猜想可以沉淀：错误推测法就是经验的系统化，越攒越准 |
| 猴子跑一晚没崩＝应用稳定 | 随机只是概率覆盖，关键路径的稳定性还要定向长跑来验（见[性能测试全家桶](./08-performance-family.md)里的稳定性测试） |

## 上手建议

1. 每天给探索留一个固定时间盒（30~60 分钟），开始前写一句话 Charter，结束写三行记录——探了什么、发现了什么、打算怎么跟进
2. 探索捞到的每个 bug，追问"哪条用例本该覆盖它"，没有就补一条——这是探索反哺用例库的标准动作
3. Android 项目亲手跑一次 Monkey 命令，从安装到看崩溃报告走通一遍，下次提测就能挂机
4. 学看崩溃堆栈：第一行通常就告诉你崩在哪个类哪个方法，贴进 bug 单开发省一半排查时间
5. 攒一张"探索灵感清单"：断网时点提交、快速连点、切后台再回来、时间穿越（改系统时间）……每次探索前扫一眼，比临时想快得多
