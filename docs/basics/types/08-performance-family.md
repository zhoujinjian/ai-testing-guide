# 08｜性能测试全家桶：负载、压力、并发、稳定性、容量

> 核心要点：都说"性能测试"，细究起来是**五种问法**——负载问"预期压力下达标吗"、压力问"极限在哪"、并发问"瞬间冲击扛得住吗"、稳定性问"长时间跑会不会垮"、容量问"最多养得起多少用户"。看懂 RT、TPS、并发数三个指标，全家桶就懂了一半。

## 打个比方

一支长跑队的**体能测试**有五个科目：

**负载测试**是按日常训练配速跑 10 公里——用的正是比赛要求的速度，看心率、呼吸、步频是否全程平稳。**压力测试**是从慢到快逐步加速，一直加到跑崩为止——要的就是知道极限配速在哪、崩的时候人是什么状态、缓一缓还能不能站起来。**并发测试**是发令枪响那一瞬——上百人同时从起跑线冲出去，看会不会互相踩踏。**稳定性测试**是中速连续跑 3 小时——配速不难，难的是后半程会不会抽筋、掉速。**容量测试**是问"这条赛道最多能容纳多少选手同时开跑"——为下一届赛事报名规模做规划。

五个科目用的都是"跑步"这一件事，但每个科目回答的问题完全不同。

## 展开讲讲

### 先懂三个核心指标

| 指标 | 人话解释 |
| --- | --- |
| **RT（响应时间）** | 从你点"提交订单"到看到结果页的耗时。报指标通常说 P95 / P99：100 个请求里 95 个（99 个）要快于这个值 |
| **TPS（每秒事务数）** | 系统一秒钟能完整办完多少笔业务，比如 3000 TPS＝每秒处理 3000 笔下单 |
| **并发数** | 同一时刻同时压在系统上的请求数，比如 5000 个用户同一秒都在等系统响应 |

三者关系记一句话：**并发往上加，RT 先平稳后上升，TPS 先上升后掉头**——TPS 掉头的那个拐点，就是系统的"体力极限"。旁边还有两个配角：**错误率**（失败请求占比，一般要求低于 0.1%）和**资源利用率**（CPU、内存占用，撑到 90% 以上就危险了）。

### 五种类型对照表（本篇核心）

| 类型 | 加多大压力 | 回答什么问题 | 典型场景 |
| --- | --- | --- | --- |
| **负载测试** | 预期的日常峰值（如大促预估 5000 TPS） | 预期负载下，指标达不达标 | 大促前按预估流量验证 |
| **压力测试** | 从小到大持续加压，直到指标恶化或系统崩溃 | 极限在哪、崩的时候什么样、恢复得了吗 | 找系统拐点和容量上限 |
| **并发测试** | 瞬间大并发冲击（如 0 点同一秒 10 万个请求） | 瞬时洪峰会不会打垮系统、数据会不会错 | 秒杀、抢票、开学选课 |
| **稳定性测试** | 中等负载长时间运行（7×24 小时或连跑 3 天） | 长跑会不会内存泄漏、变慢、连接堆积 | 长期运行类系统的验收项 |
| **容量测试** | 不同负载等级逐级测一轮 | 多少用户量、数据量时必须扩容 | 年度扩容规划、双 11 备战 |

两点说明：一是边界在实战里有重叠——一场完整的压测常常从负载开始、自然加到压力，一份报告覆盖两问；二是**并发和负载最容易被混**：负载看重"持续的总量"，并发看重"同一瞬间的密度"，秒杀抢的从来不是总量是那一秒。

### 性能测试的大致流程

定指标（要多少 TPS、RT 上限多少）→ 造脚本（用 JMeter、Locust 等工具把业务操作录成可回放的请求）→ 设场景（怎么加压、加多久）→ 执行监控（跑起来盯三指标加资源曲线）→ 出报告（结论：达标 / 拐点在哪 / 建议）。新手现阶段不用会全套，**能看懂报告**就是合格起点。

## 举个例子

电商 618 大促备战，下单链路全套走一遍（指标要求：P95 RT < 500ms，5000 TPS 下错误率 < 0.1%）：

1. **负载测试**：按预估峰值 5000 TPS 持续压 30 分钟——P95 稳在 480ms，错误率 0.02%，达标
2. **压力测试**：从 1000 TPS 逐级加压，1000→3000→5000→6500→8000。加到 6500 时 RT 飙到 3 秒，再加 TPS 反而掉到 5200——拐点找到了：**系统极限 6500 TPS**。报告结论：离预估峰值只有 30% 余量，建议扩容或加限流
3. **并发测试**：模拟 0 点开抢，10 万用户同一秒点"立即抢购"。功能上抓到一个致命问题：限量 1000 件的商品卖出了 1037 件——**超卖**，这是并发测试独有的战果，负载测试总量再大也测不出这种"同一瞬间"的数据竞争
4. **稳定性测试**：3000 TPS（六成负载）连续压 24 小时。RT 全程平稳，但内存曲线从第 6 小时起缓慢爬升、从不回落——疑似内存泄漏，提单给开发，附上 24 小时监控曲线截图
5. **容量测试**：结合业务增速（月活每月涨 15%），推算当前配置能撑到 11 月中旬——留给扩容的时间窗口出来了

一轮下来，五个科目各交各的卷子：负载给"达标"、压力给"上限"、并发给"超卖"、稳定性给"泄漏"、容量给"扩容时间表"。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 性能测试＝把系统点快一点 | 性能测试的压力是工具造出来的，和手速无关；点击和压测是两码事 |
| 五个词是五种互斥的活动 | 一场完整压测常把它们串成一个剧本，边界有重叠 |
| 只看平均响应时间 | 平均值会骗人：99 个 100ms 加 1 个 30 秒，平均不到 400ms——看 P95/P99 才能兜住慢请求 |
| 压测通过＝线上稳 | 压测环境和真实流量有差距（流量模型、数据量、依赖服务），结论要打余量 |
| 性能是性能工程师的事，与我无关 | 功能测试最先撞见"慢"的体感 bug；把"很卡"说成"下单页 8 秒、接口 6.5 秒"，就是你的性能贡献 |

## 上手建议

1. 找性能组要一份最近的压测报告，对照本篇三指标逐行看懂——P95、TPS、拐点各在哪，看懂一份胜过背十篇概念
2. 把日常遇到的"慢"量化：页面几秒、接口几秒、什么时候开始慢，用数字提单而不是"有点卡"
3. 用接口工具给自己的模块做一次迷你对比：1 个请求和 50 个并发请求的 RT 差多少，亲手看一次 RT 上升曲线
4. 记住自家系统的关键口径：注册用户多少、日活多少、预估峰值 TPS 多少——面试聊性能先问的就是这些数
5. 想深入动手：从 JMeter 装起来、录一个接口、跑一次阶梯加压开始（完整学习路径见[第 8 章性能与稳定性测试](../../roadmap/08-performance-testing.md)）
