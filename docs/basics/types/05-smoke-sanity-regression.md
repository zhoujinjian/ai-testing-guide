# 05｜冒烟、Sanity 与回归测试的区别

> 核心要点：三个词都出现在提测之后，但分工完全不同——**冒烟**问"这个版本能不能测"，**Sanity** 问"这个小改动值不值得进入下一环节"，**回归**问"改的东西有没有把原来好的弄坏"。用目的、时机、范围、耗时、不通过怎么办五个维度一比，就再也不会混。

## 打个比方

把一次提测想象成一次进医院体检：

**冒烟测试**是急诊预检分诊——护士先花两分钟量血压、测体温，判断你"有没有生命危险"。血压都测不出读数，就直接推去抢救（版本打回），后面的常规体检一项都不用做。**Sanity 测试**是专项复查——上次体检血糖偏高，这周只复查血糖一个项目，十几分钟，看指标恢复了没有、值不值得预约下一次全套体检。**回归测试**是年度全身体检——所有项目从头到尾再来一遍，确认这一整年没有攒出新毛病。

三者共同点：都是"先花小钱确认值得花大钱"。区别在于：分诊面对的是一个新病人（新提测的版本），复查面对的是一个老病人的新变化（小改动），全身体检面对的是"整体没被时间改坏"。

## 展开讲讲

### 冒烟测试：版本的准入检查

冒烟测试（Smoke Testing）的名字有真实出处：早年测电路板，先通电看冒不冒烟——冒烟说明有致命短路，后面的细测不用做了。软件沿用至今：

- **测什么**：系统最核心的主流程。电商就是登录、搜索、加购、下单、支付这一条链，通常固定 20~50 条用例
- **定位**：提测后第一件事，验证的是"**这个版本有没有资格被细测**"，不是验证功能对不对
- **不通过**：整个版本打回，开发修复后重新提测，冒烟从头再跑

### Sanity 测试：小改动后的快速确认

Sanity 测试（健全性测试，中文常直译）专对付**小改动**：

- **典型场景**：开发修完几个 bug 重新出包、一个紧急小补丁要上线、某模块做了小调整
- **测什么**：只围绕本次改动点及其紧邻路径，范围比冒烟更窄。目的不是全面验证，是**快速判断"这个小改动没引入明显新问题，值得进入下一环节"**——值得细测、值得回归、值得上线
- **不通过**：打回继续修，或者暂缓本次发布

### 回归测试：改动的涟漪检查

回归测试（Regression Testing）回归的是**改动的影响面**：开发修了一个 bug 或加了一个功能，代码改动像往水里扔石头，涟漪会扩散到没改过的地方。回归既确认"改的没问题"，更确认"没改的没被改坏"。三种常见策略：

| 策略 | 测什么 | 什么时候用 |
| --- | --- | --- |
| 全量回归 | 所有用例重跑 | 版本末期最后一轮、大改动、发版前 |
| 定向回归 | 改动模块 + 关联模块 | 日常 bug 修复后的验证（最常用） |
| 冒烟级回归 | 只跑核心主流程 | 时间被严重压缩时的保底 |

### 三兄弟五维度对比（本篇核心，背这张表）

| 维度 | 冒烟测试 | Sanity 测试 | 回归测试 |
| --- | --- | --- | --- |
| **目的** | 验证主流程通不通，版本能不能收下来细测 | 验证小改动没引入明显问题，值不值得进入下一环节 | 验证改动没把原来好的功能弄坏 |
| **时机** | 每次提测 / 出包后的第一件事 | bug 修复出新包后、小补丁上线前、细测开始前 | 每轮修复验证后、版本末期、上线前 |
| **范围** | 核心主流程，固定一套，通常 20~50 条 | 只围绕本次改动点和紧邻路径，三者中最窄 | 改动点 + 关联模块，可扩到全量 |
| **耗时** | 半小时到两小时 | 几分钟到半小时 | 数小时到数天，随范围伸缩 |
| **不通过怎么办** | 整个版本打回，修复后重新提测 | 打回继续修，或暂缓本次发布 | 修复后回归范围重跑，问题严重时回到功能测试 |

记忆锚点：**面对的对象不同**——冒烟面对一个新版本，Sanity 面对一个小改动，回归面对"改动扩散出去的影响"。范围从小到大通常排成 Sanity < 冒烟 < 回归。

### 三者在一个版本里先后登场

不是三选一，而是一条时间线上的接力：**提测 → 冒烟（收不收）→ 功能细测 → 开发修复出包 → Sanity（这个包值不值得继续）→ 定向回归（改动周边没坏）→ 版本末期回归（整体确认）**。这条时间线的完整位置见[测试执行全流程](../process/10-test-execution-flow.md)，那篇讲整条河，本篇把河里这三个弯道放大了讲。

补充一句现实：不少团队把 Sanity 合并进"定向回归"里叫，不做区分。面试时把三者的思路说清楚，比死抠名词更显功力。

## 举个例子

电商 App 支付页改版，一个版本完整走一遍三兄弟：

1. **周一提测**：你先跑冒烟，40 分钟——登录、选商品、加购、下单、支付。跑到支付直接白屏。冒烟不通过，版本打回，你半天时间省下来了，只测了 40 分钟而不是两天
2. **周二重新提测**：冒烟通过，进入功能细测。两天里你发现 8 个 bug：优惠券展示错位、指纹支付无响应、支付密码键盘遮挡输入框……逐个提单
3. **周四开发修复出包**：你先做 Sanity——只测支付主路径加上那 8 个修复点，15 分钟全过，确认这个包值得继续，才叫上组里同事一起回归
4. **回归**：改的是支付页，涟漪可能波及下单和订单。你回归了下单流程、订单列表、退款入口，发现退款页金额展示被改坏（展示成了优惠前金额），提单——这就是回归的价值：**改动点之外的 bug，只有回归抓得到**
5. **周五末期回归**：主流程全量用例跑一遍（已自动化的部分脚本执行，手工补漏），全绿，出报告，版本具备上线条件（上线结论怎么下见[准入与准出](../process/11-entry-exit-criteria.md)）

回头看：冒烟止损了一次、Sanity 把关了一个修复包、回归捞出一个改动点之外的 bug——三次出场，三种用途。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 冒烟不过，硬着头皮继续细测 | 主流程都跑不通的版本测了也白测，大概率中途打回全泡汤；打回是标准动作不是找茬 |
| Sanity 就是冒烟的洋名 | 冒烟面对整个新版本，Sanity 面对小改动；范围和目的都不同 |
| 回归＝全部用例重跑一遍 | 全量是最贵选项，日常靠定向回归科学裁剪，全量留给版本末期 |
| 修复包直接开始细测，不先 Sanity | 小包也值得 15 分钟确认，不然细测到一半发现主路径挂了更亏 |
| 回归只测改过的那个功能 | 涟漪会扩散到关联模块，只测改动点等于没回归 |
| 回归范围拍脑袋决定 | 范围要有依据：看代码改动影响面、问开发、参考历史易碎区，三个信息源都过一遍 |

## 上手建议

1. 把团队的冒烟用例单独打标签建成"冒烟集"，每次提测固定执行，别每次临时凑——冒烟集的质量直接决定你的止损能力
2. 给自己定一个修复包验收定式：**先 Sanity 再定向回归**，形成肌肉记忆
3. 每轮回归前先答三问：改了什么、影响哪些模块、历史上哪里容易碎——三问答完，回归范围自然浮出来
4. 优先把回归做成自动化：回归是全流程重复度最高的环节，是自动化的第一现场（怎么起步见[实战教程](../../knowledge/)）
5. 学会写打回邮件 / 冒烟报告：一句话结论加失败清单加截图，打回也打得专业
