# 13｜正向测试与逆向测试：顺毛捋和反着来

> 核心要点：**正向测试**用合法输入走正常流程，验证"说好的都兑现"；**逆向测试**反着来——非法输入、乱序操作、异常环境，验证"被刁难时不崩不坏不吞数据"。线上事故大多出在逆向场景，但正向永远优先：正向挂了，用户连门都进不来。

## 打个比方

验收一台**无人售货机**：

**正向**：投 5 元硬币，按"可乐 3 元"的按钮，掉出可乐，找零 2 元——设计承诺的都兑现，这台机器"会干活"。

**逆向**：只投 1 元就按 8 元的咖啡；连按三次同一按钮；按了不取货转身就走；断电的瞬间按按钮；投一枚游戏币进去；对着按钮泼水。正常用机器的人不会这么干，但真实用户里有手滑的、较真的、赶时间的，还有专找茬的。合格的售货机必须在所有这些情况下**不坏、不吞钱、不装死**：投币不足要有提示，断电要记得刚才投了多少钱，连按不能连出三罐。

正向验证"该会的都会"，逆向验证"不该怂的时候不怂"。只做正向的测试，等于只验了机器在说明书里写的那一页。

## 展开讲讲

### 正向测试：验证设计承诺

用**合法输入、正常操作顺序**，验证系统行为与需求一致：正确账号密码登录成功跳首页；满 300 元用"满 300 减 50"券，实付 250 元。正向用例直接来自需求文档，好写、好执行，是主流程的骨架——通常说"主流程测试"，基本都是正向。

### 逆向测试：验证系统扛得住刁难

逆向测试系统化地做"开发没想到的事"，四类正规军：

| 类别 | 内容 | 例子 |
| --- | --- | --- |
| **非法输入** | 空值、超长、特殊字符、负数、乱码 | 备注栏粘 5000 字、数量填 -1 |
| **异常流程** | 跳步骤、重复提交、回退重做、并发操作 | 不支付直接点"确认收货"、连点两次提交 |
| **异常环境** | 断网、弱网、权限关闭、存储不足 | 断网状态下点提交、拒了相机权限还点拍照 |
| **恶意姿势** | 改参数、重放请求、越权访问 | 抓包改金额、改别人订单号（见[安全测试入门](./10-security-basics.md)） |

### 为什么逆向才是抓 bug 主力

开发按需求写代码，思考路径也是正向的——**bug 藏在"开发没想到"的地方，逆向就是系统化地穷举"没想到"**。但注意两点：一是正向不可省，正向挂了用户根本用不了，逆向挂了用户会骂，严重度排布上正向优先；二是逆向不是越多越好，范围要按风险裁剪——支付和登录值得四类全铺，一个"关于我们"静态页不值得。

### 两者一张表对齐

| 维度 | 正向测试 | 逆向测试 |
| --- | --- | --- |
| 输入 | 合法、需求给的 | 非法、需求没给的 |
| 路径 | 正常操作顺序 | 乱序、重复、中断 |
| 验证点 | 该做的做了，做对了 | 不该崩的没崩，异常处理正确 |
| 典型 bug | 功能缺失、计算错误 | 提示缺失、数据错乱、重复提交 |
| 漏测后果 | 用户进不了门 | 线上事故、用户骂街 |

和用例设计方法的关系：**等价类里的无效等价类、边界值里的离点，就是逆向用例的正规来源**（见[等价类划分法](../testcase-design/06-equivalence-class.md)）；逆向的灵感源泉则是[错误推测法](../testcase-design/13-error-guessing.md)——老手凭经验专挑系统最可能心虚的地方下手。

## 举个例子

登录页，需求写明：账号 6~18 位，密码 8~20 位，密码连错 5 次锁定 15 分钟。

**正向**：正确账号 + 正确密码 → 登录成功跳首页，登录态保持 7 天。

**逆向铺开**：

- **密码错 1 次**：提示"账号或密码错误"（不提示到底哪个错——提示哪个错本身是个安全问题）；**连错 5 次**：提示"密码错误次数过多，请 15 分钟后再试"
- **锁定后再测**：锁定期间输入**正确**密码——居然登录成功了。锁定校验只挡错误密码不挡正确密码，bug。**只有逆向测得出**，正向用例永远碰不到这个状态
- **超长粘贴**：密码框粘贴 30 位——前端提示"密码最多 20 位"；抓包绕过前端直接发 30 位，后端也拦了，双保险通过
- **断网提交**：关 Wi-Fi 点登录——提示"网络不给力，请检查网络设置"，不是白屏转圈到天荒地老
- **快速连点**：狂点登录按钮 5 次——抓包确认只发出 1 个请求，没有重复登录
- **空输入直提**：两个输入框留空直接点登录——提示"请输入账号"，逐个提示

一个登录页，正向用例两三条，逆向用例十几条——这个比例在输入校验密集的页面上是常态。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 正向通过就万事大吉 | 正向只是入场券；线上事故大多出在逆向场景——重复提交、并发、异常状态 |
| 逆向测试＝随便乱点 | 逆向有四类正规军，每类都有系统化的方法；乱点只是其中最没效率的一种 |
| 逆向用例不用写预期结果 | 逆向更需要写清预期：提示什么文案、拦在哪一层（前端 / 接口）、数据回不回滚 |
| 逆向做得越多越专业 | 范围失控、工期爆炸；按风险裁剪，核心链路全铺、边角功能抽查 |
| 逆向 bug 都是低优先级 | 锁定失效、重复扣款、并发超卖这类逆向 bug 常是 P0——比多数正向 bug 严重得多 |

## 上手建议

1. 每个输入框过"四件套"：空值、超长、特殊字符、边界值——这是逆向用例的最小闭环
2. 每个提交按钮过"三连"：快速连点、回退后重做、断网时点——最便宜的三个高产出动作
3. 每个有状态的功能过"乱序"：跳过该做的步骤直接做下一步（不支付去点确认收货）
4. 逆向用例标明**预期拦截层**：该前端拦、接口拦还是数据库兜底，预期写得越具体，测得越有底
5. 收集线上事故和用户投诉，反推每条属于哪类逆向场景，补进用例库——事故是最好的逆向用例教练
