# 01｜测试分类总览：一张图看懂所有测试类型

> 核心要点：测试类型几十种，但分类只有**四把尺子**：按**阶段**分、按**方法**分、按**执行方式**分、按**测试内容**分。任何一个测试名称，都是"某把尺子上的一个刻度"——记住尺子，名词就记不完也认得全。

标题里说"一张图"，本站文章不嵌图，下面用**几张"维度 × 类型"的表加一段分层文字总览**代替，信息一点不少，查起来比图还快。

## 打个比方

图书馆给一本书归架，用的不是一张清单，而是**几个维度**：按**文种**分（中文/英文）、按**体裁**分（小说/传记/工具书）、按**主题**分（历史/科技）、按**出版状态**分（新书/馆藏）。

《人类简史》是"中文 + 历史 + 通俗读物 + 在架"——四个维度各占一格，位置就唯一了。没有人会把所有书排成一条直线记顺序，**维度才是收纳的方式**。

测试类型同理。"单元测试""黑盒测试""性能测试"经常被新人当成同一层的名词混着背，其实它们分属不同维度：**单元测试是"阶段"维度上的一格，黑盒测试是"方法"维度上的一格，性能测试是"内容"维度上的一格**。一次真实的测试活动，往往同时是"系统阶段 + 黑盒方法 + 动态执行 + 功能内容"——就像一本书同时占四个格子。

## 展开讲讲

### 四把尺子：四个分类维度

| 维度 | 回答的问题 | 包含的常见类型 |
| --- | --- | --- |
| **按阶段分**（测的时机和层级） | 测在研发的哪一站 | 单元测试、集成测试、系统测试、验收测试 |
| **按方法分**（看不看内部结构） | 从盒子外面看还是里面看 | 黑盒测试、白盒测试、灰盒测试 |
| **按执行方式分**（跑不跑代码） | 静态审还是动态跑 | 静态测试、动态测试 |
| **按测试内容分**（验证哪种质量属性） | 测的是哪一面 | 功能测试、性能测试、兼容性测试、安全测试、易用性测试 |

还有一个常被单独拎出来的维度——**按执行手段分**：手工测试与自动化测试。它和上面四把尺子正交（任何一类测试都可能手工做或自动化做），通常作为附加属性而非并列类型。

### 交叉定位：给一个真实场景归位

拿"电商大促前的**优惠券压力测试**"来定位，它会同时落在四个格子里：

| 维度 | 归位 | 说明 |
| --- | --- | --- |
| 阶段 | 系统测试阶段 | 整个系统集成完成后开展 |
| 方法 | 黑盒为主 | 从接口/页面施加压力，不关心内部代码 |
| 执行方式 | 动态测试 | 系统真实运行中测量 |
| 内容 | 性能测试（负载/压力家族） | 验证的是性能属性 |

看懂了这张定位表，你就能拆穿一类唬人的说法："我们做的是黑盒测试，不做单元测试"——**黑盒是方法，单元是阶段，两个维度根本不对立**，正确说法是"系统阶段的黑盒测试由测试负责，单元阶段的白盒测试由开发负责"。

### 一张总表：常见类型的完整归位

| 测试类型 | 阶段 | 方法 | 执行 | 内容 |
| --- | --- | --- | --- | --- |
| 单元测试 | 单元 | 白盒为主 | 动态 | 功能 |
| 集成测试 | 集成 | 灰盒常见 | 动态 | 功能/接口 |
| 系统测试 | 系统 | 黑盒为主 | 动态 | 全属性 |
| 验收测试 | 验收 | 黑盒 | 动态 | 业务场景 |
| 代码走查/评审 | 任意 | 白盒 | **静态** | 代码质量 |
| 冒烟/Sanity/回归 | 系统（过程动作） | 黑盒 | 动态 | 功能为主 |
| 探索性测试 | 系统 | 黑盒 | 动态 | 任意 |
| 性能测试 | 系统 | 黑盒 | 动态 | 性能 |
| 兼容性测试 | 系统 | 黑盒 | 动态 | 兼容 |
| 安全测试 | 系统 | 灰盒 | 两者皆有 | 安全 |

这张表不用背——**记住四个维度，任何新名词来了一问"它答的是哪个维度的问题"，自动归位**。后面十二篇就是沿这四把尺子逐维展开：阶段尺（02 篇）、方法尺（03 篇）、执行尺（04 篇），以及内容尺里的高频类型（07~11 篇）。

### 为什么要有分类

分类不是学术洁癖，每类测试对应**不同的人、不同的工具、不同的时机**：单元测试是开发的活（跑得快、定位准），系统功能测试是测试的主场，性能测试要专门的压测工具，安全测试常有专职团队。**分类的实用价值是让你知道"此刻该派谁、用什么工具、在哪个时机上场"**——这也是面试里"测试有哪些类型"的真实考点：考的不是背诵量，是你有没有一张结构化的地图。

## 举个例子

新人小周入职第一周，听同事说了七个名词，有点懵：单元测试、集成测试、冒烟、回归、黑盒、性能、兼容。她按四把尺子整理了一张卡片：

- 单元、集成 → **阶段**尺（开发自测的层级）
- 冒烟、回归 → **阶段**尺上的过程动作（版本流转中的两种范围策略）
- 黑盒 → **方法**尺（不看代码从外面测）
- 性能、兼容 → **内容**尺（验证的质量属性）

周五带教问她"App 大促前要做的事里，哪些是系统阶段的黑盒动态测试"，她答："功能回归是，优惠券压测也是——只是内容一个功能一个性能；而开发的单元测试在阶段尺的更早一格，不归我们派。"带教点头。**一周入门的差距，就是有没有这张维度地图**——名词永远在增加（混沌测试、模糊测试、A/B 测试……），但尺子就那四把，新名词挂上去就行。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 把所有测试名词当同一层并列着背 | 名词分属四个维度，"黑盒 vs 单元测试"这类对比本身就是错的 |
| 想把分类一次背全 | 记四把尺子，不记名词清单——尺子稳定，名词常新 |
| 分类是理论，工作中用不上 | 每类对应不同的人/工具/时机，分类直接决定"派谁、用什么、何时上" |
| 手工测试和功能测试是并列类型 | 手工/自动化是执行手段属性，与内容维度正交 |
| 一个测试活动只能属于一类 | 真实测试活动在四个维度上各占一格，交叉定位才是常态 |

## 上手建议

1. **画一张自己的四维卡片**：照本文第一张表手抄一遍，放进笔记首页，两周内每听到一个新测试名词就往卡片上挂一次
2. **拿当前项目做一次归位**：列出团队正在做的所有测试活动，标出各自在四个维度上的格子，你会对项目全貌有一次清晰俯瞰
3. **面试前用尺子自测**：随机抽五个测试名词，五秒内说出它的维度——过了这关，"测试分类"类面试题就是送分题（怎么组织成答案见[面试题](../../interview/testing-essentials/03-testcase-design-methods.md)）
4. **顺着尺子往下读**：阶段尺读 02 篇、方法尺读 03 篇、执行尺读 04 篇，把地图的经纬线走完
5. **给新名词留个"挂载区"**：笔记里开一栏"新听说的测试类型"，先挂维度再查含义，不让陌生名词吓住你
