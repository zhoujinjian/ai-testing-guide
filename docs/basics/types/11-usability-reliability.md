# 11｜易用性与可靠性测试：好不好用与经不经用

> 核心要点：**易用性**站在新用户这边，问"能不能顺手地把事办成"；**可靠性**站在时间这边，问"用得久、出故障后能不能恢复"。一个考下限体验，一个考长期表现，都是"功能没 bug"之外用户最在意、也最容易被砍掉的两类测试。

## 打个比方

买家电时你其实同时在做这两类测试：

挑微波炉，**易用性**这关你问的是：外婆不看说明书会不会热饭——旋钮一拧就火的 beats 按十二下菜单键的；按键上的字老花眼看不看得清；手滑按错了会不会直接高火两分钟。**可靠性**这关你问的是：这台机器天天用、用五年坏不坏；小区电压不稳的时候它会不会烧；煮到一半停电，来电之后它能不能接着用、时钟要不要重调。

好家电 = 两头都硬。软件一样：**易用性是"第一次用的人能不能顺利办成事"，可靠性是"第一千次用的时候它还活不活得好"**。功能测试管"每一项功能对不对"，这两位管"整个过程顺不顺、撑不撑得久"。

## 展开讲讲

### 易用性测试：站在新用户这边

易用性没有"对错"判据，问的是一组体验问题：

- 首次使用，**不看引导能不能完成核心任务**
- 文案**说人话吗**："鉴权失败，请重试"vs"密码不对，再试一次或点这里找回"
- 操作路径**多长**：完成一件事要点几步、填几项
- 出错时**用户能不能自救**：提示有没有告诉用户哪里错了、下一步怎么办

行业里有一套成熟的**可用性启发式原则**（尼尔森十原则），新手先记三条最常用的：**一致性**（同样的操作，全 App 行为一致——都是左滑删除，不能这个页面左滑、那个页面长按）；**防错**（危险操作有二次确认，删除按钮离常用按钮远一点）；**状态可见**（系统正在干什么要让用户知道——加载有转圈、成功有反馈、网络断了有提示）。

**怎么测**：最朴素也最有效的一招是**新用户走查**——拉一个没用过的同事，给他一个任务（"下单一份奶茶"），全程闭嘴观察，记录他卡在哪、猜错什么。他卡住的地方，就是真实用户流失的地方。

### 可靠性测试：站在时间这边

可靠性问的是**规定条件下持续正常运行的能力**，两个核心度量：

| 指标 | 人话解释 |
| --- | --- |
| **MTBF**（平均无故障时间） | 平均多久出一次故障——值越大越可靠 |
| **MTTR**（平均恢复时间） | 出故障后平均多久能恢复——值越小越抗揍 |

可靠性测试的典型动作都是在**时间和故障上做文章**：**长时间运行**（7×24 小时挂机看会不会变慢、闪退，这正是[性能全家桶](./08-performance-family.md)里稳定性测试的活）；**故障演练**（断网后重试、断电重启后数据丢不丢、杀进程重进状态乱不乱）；**资源压力**（存储快满、内存吃紧时系统是优雅降级还是直接崩）。

两者一张表对齐：

| 维度 | 易用性 | 可靠性 |
| --- | --- | --- |
| 关心什么 | 第一次用顺不顺 | 第一千次用还在不在 |
| 典型问题 | 找不到入口、看不懂提示、路径太长 | 内存泄漏、闪退、断电后数据丢失 |
| 怎么测 | 新用户走查、文案走查、启发式原则逐条过 | 长跑、故障演练、MTBF / MTTR 度量 |
| 产出形态 | 体验问题清单（程度问题，不是对错问题） | 稳定性指标和故障恢复结论 |

### 两兄弟的共同尴尬

这两类测试都没有"功能级 bug"那样非黑即白的判据，最容易被"功能没 bug 就行，先上线"挤掉——然后以**应用商店差评**的形式加倍奉还：翻翻任何产品的差评区，"难用""不会操作""动不动闪退"永远排在最前面。它们是用例穷举不出来、必须靠场景化思维去覆盖的测试类型。

## 举个例子

智能门锁的配套 App，配网功能（让 App 连上家里的门锁）两关一起过：

**易用性**：拉一位没接触过这产品的同事配网，全程观察。她 3 分钟没成功，卡在"请长按设备键 5 秒"——文案没说清是哪个键、长按到什么程度；按错键之后 App 毫无反应，她不知道该等还是重按，干等了 40 秒。走查结论两条：加键位示意图、失败时给出"没检测到设备，请确认指示灯是否在闪烁"的提示。改完再拉一位新同事：90 秒配网成功。

**可靠性**：配网中途手机断网，App 停在"连接中"死循环，既不报错也不超时；配网成功后杀掉 App 重进，设备列表出现两条重复的门锁记录（脏数据）；连续进出设置页 100 次，第 43 次闪退。三条全提单——第三条附上崩溃日志，第一条建议加 30 秒超时加失败提示。

同一套配网代码，易用性考官和可靠性考官各判各的卷：一个判"新用户 3 分钟配不成网"，一个判"断网一次就死循环"。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 易用性＝界面好不好看 | 好看是 UI 设计的活；易用性是"任务能不能顺利办成"，素界面也能很易用 |
| 易用性没标准，没法测 | 有成熟的启发式原则可以逐条走查，新用户走查更是零门槛高产出 |
| 可靠性＝没有 bug | 可靠还包括出故障后能不能自动恢复——崩了能自愈的比不崩但崩了就瘫的更可靠 |
| 可靠性指标是玄学 | MTBF / MTTR 口径明确，可以直接度量、可以直接进验收标准 |
| 这两类是加分项，砍掉不心疼 | 用户卸载和差评的理由里，"难用"和"不稳定"长期排前两位 |

## 上手建议

1. 每个新功能上线前，拉一位没用过的同事走一遍主流程，全程闭嘴观察，记录每一个卡壳点——这是成本最低的易用性测试
2. 检查所有错误提示是否给出路：把"操作失败，请重试"这类无信息提示列成清单，逐条改成"哪里错了 + 怎么办"
3. 给核心场景做一次故障三连演练：断网重试、杀进程重进、重启后数据核对
4. 用三条启发式原则（一致性、防错、状态可见）给自己的模块打一遍分，每条找出一个正面例子和一个反面例子
5. 每周翻一次应用商店差评，把"难用"和"不稳"类差评转成用例或 bug 素材——差评区是免费的可用性实验室
