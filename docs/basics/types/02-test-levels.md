# 02｜按阶段分：单元、集成、系统、验收测试

> 核心要点：按**测试对象的大小**从里到外分四级——**单元**测最小零件、**集成**测零件拼起来的配合、**系统**测整车、**验收**让用户自己说行不行。越靠里修问题越便宜，越靠外越接近真实用户。

## 打个比方

一座汽车厂，质量把关是四道关卡：

**单元测试**是零件进厂质检——每一颗螺丝、每一块钢板都抽检，不合格当场退，绝不让坏零件上流水线。**集成测试**是总成装配检查——发动机由几百个零件拼成，拼完要上台架试运转，看零件之间配合得好不好。**系统测试**是整车下线路试——方向盘、刹车、车机一起工作，上路跑一圈才算整车合格。**验收测试**是用户提车——绕车一圈、试坐、试开，用户点头，这单才算交付。

软件的四级测试就是这四道关卡：零件是函数，总成是模块，整车是整个系统，提车的用户就是产品的真正使用者。

## 展开讲讲

### 单元测试：最小零件逐个检

- **测什么**：单个函数、类、方法。比如"校验手机号格式"这个函数，单独拎出来测
- **谁来测**：开发自己写、自己跑，这是开发的责任田，测试负责督促和看覆盖率
- **怎么测**：因为零件是孤立的，依赖的别的零件常常还没造好，开发会用**Mock**（造一个假的依赖对象）代替，比如测下单函数时 Mock 掉支付接口
- **特点**：跑得飞快（毫秒级）、失败定位极准（挂了就是这一个函数）、数量应该最多

### 集成测试：拼到一起测配合

零件各自合格，拼在一起照样可能出事——螺丝和螺孔的公差不匹配，零件再好也白搭。

- **测什么**：模块之间的**接口**——参数传没传对、数据格式认不认、异常有没有处理好。比如下单模块调用库存模块："扣减库存"接口的参数是 `sku_id` 还是 `product_id`，两边必须对得上
- **谁来测**：开发的联调 + 测试的集成测试。联调是开发自己把两个模块跑通；测试做的集成测试更正式，要验证接口契约、边界值和异常分支
- **典型问题**：字段名对不上、时间格式一边用时间戳一边用字符串、一端改了接口另一端没同步

### 系统测试：整车路试

- **测什么**：整个系统作为一个整体，在尽量接近真实的环境里，按用户的使用方式跑。功能、性能、兼容、安全这些专项都在这一层展开
- **谁来测**：测试团队，这是你入职后接触最多的层——拿到的提测包、执行的用例，绝大多数属于系统测试
- **环境**：独立的测试环境，数据是造出来的，但结构和生产一致

### 验收测试：用户说行才行

- **测什么**：从**用户视角**验证产品满足需求——不再关心实现，只关心"我要的东西你给我了没有"
- **谁来测**：用户代表、产品经理（UAT，用户验收测试），测试负责组织和支持
- **两种变体**：Alpha 测试（自己人先测）和 Beta 测试（真实用户小范围试用），详见[Alpha 测试与 Beta 测试](./12-alpha-beta.md)

四级放一张表里对齐：

| 级别 | 被测对象 | 谁来测 | 典型问题 | 不过时卡在哪 |
| --- | --- | --- | --- | --- |
| 单元测试 | 函数、类 | 开发 | 逻辑写错、边界漏判 | 卡在开发自己手里，根本出不了门 |
| 集成测试 | 模块间接口 | 开发 + 测试 | 参数对不上、异常没处理 | 卡在联调，可能要两个团队一起改 |
| 系统测试 | 整个系统 | 测试团队 | 功能不符、性能不达标 | 打回开发修，修完回归 |
| 验收测试 | 用户视角的整体 | 用户、产品 | 需求理解偏差、体验不达标 | 需求层面返工，代价最大 |

### 顺便认识：测试金字塔

业内有个经典说法叫**测试金字塔**：底座是海量的单元测试，中间是适量的集成测试，塔尖是少量的系统级 UI 测试。越往下跑得越快、修得越便宜；越往上越慢越贵、失败越难定位。理想是金字塔，现实里很多团队是"倒三角"甚至"一锅粥"——你入职后做的系统测试偏多，不代表金字塔错了，只说明这个团队的底座欠账，这正是测试开发后来能补的位（进阶方向见[学习路线](../../roadmap/09-quality-engineering.md)）。

## 举个例子

外卖 App 做一个"新增收货地址"功能，四级各自在忙什么：

1. **单元测试**：开发给"手机号校验函数"写了 6 条单测——11 位合法、10 位拦截、带字母拦截、带空格拦截、空值拦截、`+86` 前缀通过
2. **集成测试**：地址保存接口要调地图服务做坐标解析，联调时发现地图服务返回的坐标系是 WGS84，而 App 用的是 GCJ02，同一个地址偏了 300 米——典型的集成层问题
3. **系统测试**：你在测试环境从"定位当前小区 → 填写门牌号 → 选择标签'家' → 保存"完整走一遍，发现备注超过 50 字时保存成功但列表只显示 50 字且没有省略号提示，提单
4. **验收测试**：产品经理按真实用户场景验收，模拟"公司地址和家地址来回切换下单"，确认交互符合最初的设计稿

同一份代码，四个关卡各拦各的问题，谁也替代不了谁。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 单元测试是测试的活 | 单测是开发的责任田；测试做的是督促、评审覆盖率，别替开发写日常单测 |
| 集成测试＝两个开发联调 | 联调只是跑通；集成测试还要验契约、边界和异常分支 |
| 系统测试只测功能 | 功能是主体，但性能、兼容、安全等专项都发生在系统层 |
| 验收测试走个形式 | 需求做没做对是用户视角说了算，验收打回的需求变更代价最大 |
| 四级必须严格串行进行 | 敏捷迭代里多层并行，但每一层的职责边界不变 |

## 上手建议

1. 入职先摸清团队的四级现状：单测覆盖率大概多少、集成测试谁在做、系统测试占你工作几成
2. 接到系统测试任务时向上问一句：这个模块开发有没有单测兜底，心里对底层质量有数
3. 联调类问题按"契约"提单：把接口文档的参数名、类型、默认值贴进 bug 单，开发秒懂
4. 验收测试前自己先当一次"用户"把主路径走通，别让产品经理当第一个发现问题的人
5. 有空读一读自己模块的单元测试代码，能看出开发对边界值的假设，也是最快的技术学习
