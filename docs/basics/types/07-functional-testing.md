# 07｜功能测试是什么：新手第一份工作做的事

> 核心要点：功能测试是**拿着需求当清单，逐条验证系统的每个功能"做没做、做没做对"**——正常路径走得通、边界值算得对、提示文案说得准、数据存得对。它是你新职业生涯的主业，也是其他一切测试类型的地基。

## 打个比方

超市打烊后的**仓储盘点**：理货员拿着库存清单逐项核对——每件商品名称对不对、数量对不对、货架位置对不对、标签价签和实物一致不一致。

注意盘点不是只看"东西在不在"。货架上有可乐，但价签挂的是雪碧，这是错；数量系统记着 24 瓶、货架上只有 23 瓶，这是差；商品放在"饮料区"但清单归在"日化区"，这是乱。

功能测试就是拿**需求文档当库存清单**，对系统做盘点：需求说的每个功能做了没有（在不在）、行为和需求一致吗（对不对）、界面展示和实际数据一致吗（标签对不对）、存进数据库的值正确吗（数量准不准）。**清单之外的性能、安全，是另外的专项盘点**（后文讲边界）。

## 展开讲讲

### 定义：验证功能与需求一致

功能测试（Functional Testing）验证的是**系统行为与需求文档的约定是否一致**。它不做"这个设计好不好"的价值判断（那是产品的事），只做"说好的有没有做到"的事实核对：

- 需求说"密码 6~20 位"——输入 5 位、6 位、20 位、21 位，逐一核对拦截和提示
- 需求说"库存不足时提示'库存不足'"——把库存清零下一单，看提示到底是这句还是"系统繁忙"
- 需求说"下单后订单状态变为'待支付'"——下单后不只看页面，去数据库查订单表的状态字段

### 功能测试的四个角度

拿到一个功能，从四个角度各过一遍，基本不会漏大项：

| 角度 | 问的问题 | 例子 |
| --- | --- | --- |
| **界面** | 展示的对不对 | 手机号列表页显示 138\*\*\*\*8000 打码 |
| **交互** | 操作顺不顺、状态对不对 | 删除要二次确认，取消后不误删 |
| **数据** | 存取的对不对 | 保存地址后下单页能选到，字段没串位 |
| **提示** | 文案准不准 | 上限 20 条时提示"地址最多保存 20 条" |

四个角度之外还剩一件——**稳**：同样的操作第二次、第十次还灵不灵，这属于可靠性范畴（见[易用性与可靠性测试](./11-usability-reliability.md)）。

### 它不管什么：和专项测试的分界

功能测试管"对不对"，不管"快不快、安不安全、各环境表现一不一致"，这三块各有专项：

- 快不快、扛不扛得住 → [性能测试全家桶](./08-performance-family.md)
- 不同机型、浏览器上表现一致吗 → [兼容性测试](./09-compatibility-testing.md)
- 会不会被攻击、数据会不会泄露 → [安全测试入门](./10-security-basics.md)

但"归专项"不等于功能测试视而不见：**页面 8 秒才出来、低端机上按钮错位，通常最先看到的是做功能测试的你**，你有责任把体感问题转译成量化描述交给专项（"下单页平均 8 秒，接口 6.5 秒"）。

### 为什么新手都从功能测试起步

三重原因：**最贴近用户**——你做的是用户真实会做的事，用户视角从此长在身上；**最练测试思维**——用例设计、边界意识、怀疑精神，全在功能测试里磨；**对系统理解最深**——功能测试要在整个系统里穿行，摸熟每个模块，之后无论转自动化、性能还是安全，这块底子都用得上。别信"功能测试没技术含量"的说法——同样叫点点点，用例设计能力的差距能大到一个人测三天等于另一个人测三周。

## 举个例子

外卖 App"收货地址管理"功能，需求三页纸：新增、编辑、删除、设默认地址。你的功能盘点这样铺：

- **界面**：地址列表手机号打码显示 138\*\*\*\*8000；默认地址有"默认"角标；空列表时显示引导页"还没有收货地址，去添加"
- **交互**：点删除弹二次确认"删除后不可恢复"，点"取消"回到列表不误删；长按地址无隐藏菜单（需求没提的功能冒出来了也算问题）
- **数据**：新增地址带门牌号"3 号楼 2 单元 502"，保存后去数据库查 address 表，字段完整没截断；编辑把标签从"家"改成"公司"，再下一单，结算页能选到改后地址
- **提示**：保存第 21 条地址时提示"地址最多保存 20 条，可删除不常用地址后添加"——需求写了上限 20，你验到 21 这条边界

测出两个 bug：编辑地址改标签后，原来的"默认地址"标记丢了；地址名输入 30 个字保存成功，但列表只显示一行没有省略号，把下一条地址挤出屏幕外。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 功能测试＝点点点，没有技术含量 | 点点点的质量差距极大；用例设计、数据核验、定位能力，每一项都分三六九等 |
| 功能测试就是验收测试 | 功能测试贯穿整个系统测试阶段；验收是用户视角的最后一环（见[按阶段分](./02-test-levels.md)） |
| 照着用例执行完就算测完 | 用例是骨架，执行时的怀疑和顺手探索才是血肉（见[探索性测试](./06-exploratory-monkey.md)） |
| 功能测试不需要懂技术 | 懂接口和数据库能把验证做深一层：页面看着对，库里存错的功能 bug 只有查数据才抓得到 |
| 功能 bug 都长在界面上 | 状态流转错误、落库字段串位，是藏在数据层的功能 bug，界面一团和气 |

## 上手建议

1. 拿到手头的每个需求，拆成"界面 / 交互 / 数据 / 提示"四列各写一遍，这就是你的功能盘点清单雏形
2. 每条功能问自己三遍：做了没、做对没、数据层也对了没——第三问最常被跳过，也最容易漏大 bug
3. 验证关键功能时养成"看一眼数据库"的习惯，SQL 不熟先从 `SELECT` 学起（见[测试必备 SQL](../tech-basics/08-sql-for-testers.md)）
4. 用例执行之外每天留 30 分钟探索时间，把清单之外的巷子走一走
5. 建"功能点 × 用例"的映射表，每个功能点都能点开看到对应用例——防漏测的最硬手段
