# 03｜按方法分：黑盒、白盒、灰盒

> 核心要点：三种盒子说的是**你看不看得见被测对象的内部**——黑盒只看输入输出，白盒看得见每一行代码，灰盒介于两者之间（知道结构、不抠每行）。你的日常以黑盒为主，灰盒是进阶第一步，白盒多是开发在用。

## 打个比方

判断一家餐厅的出品稳不稳，有三种站法：

第一种，**只当食客**：点菜、吃、评价，好吃就是好吃，难吃就是难吃，后厨长什么样你一概不知。第二种，**进后厨**：看菜谱配比、看火候控制、看卫生状况，哪道菜少放了一味料、哪个环节偷了工，看得明明白白。第三种，**站在明档**：这类半开放餐厅，你能看到切配和摆盘的过程，但炒锅那一下看不见——比纯食客多懂一点，比进后厨少看一层。

对应过来：只当食客是**黑盒**，进后厨是**白盒**，站明档是**灰盒**。三种站法没有高下，只是能发现的问题不一样：食客发现"这道菜咸了"，后厨发现"盐勺换大的了"，明档发现"配菜和菜单对不上"。

## 展开讲讲

### 黑盒：只看输入和输出

黑盒测试（Black-box Testing）把软件当成一个黑箱子：**不关心里面怎么实现，只关心"我给什么输入、它给什么输出"**，对照的标准是需求文档。

- **典型方法**：等价类划分、边界值分析、判定表、场景法——用例篇讲的设计方法全是黑盒方法，从[什么是测试用例](../testcase-design/01-what-is-testcase.md)到[方法选型指南](../testcase-design/14-method-selection.md)
- **谁在用**：功能测试的日常就是黑盒。你不需要会写代码就能做，但做得好不好全看用例设计功力
- **擅长发现**：功能错误、界面问题、需求理解不一致、边界处理不当
- **看不见什么**：代码里的隐患路径、没被输入触发的死逻辑

### 白盒：顺着代码逻辑测

白盒测试（White-box Testing）反过来，**内部代码全透明**，按代码的执行路径设计用例，讲究"覆盖率"：

| 覆盖标准 | 人话解释 |
| --- | --- |
| 语句覆盖 | 每一行代码至少被执行过一次（最低标准） |
| 分支覆盖 | 每个 if 的真、假两条路都走过（比语句覆盖严格） |

- **谁在用**：主要是开发写单元测试；测试侧是测开岗在写单测和代码级自动化时用
- **擅长发现**：某条分支从来没被测过、逻辑运算写错、循环边界问题
- **看不见什么**：需求本身错了它测不出来——代码忠实地实现了一个错的需求，白盒照样全绿

### 灰盒：知道结构，不抠每行

灰盒测试（Grey-box Testing）**知道系统由哪些模块组成、数据大概怎么流转，但不逐行读代码**。最常见的形态就是接口测试：你知道登录要调 `/login` 接口、参数有哪些、后端大概分几层服务，但不关心校验逻辑是哪行代码写的。

- **典型活动**：接口测试、抓包分析、按模块和数据流设计用例
- **为什么说是进阶第一步**：它给黑盒加上了"结构感"——出了问题你能猜到该往哪个模块查，而不是只能描述现象

三种视角一张表对齐：

| 视角 | 看不看代码 | 典型活动 | 擅长发现 | 主要是谁 |
| --- | --- | --- | --- | --- |
| 黑盒 | 不看 | 按需求做功能测试 | 功能错、界面错、需求偏差 | 功能测试 |
| 白盒 | 逐行看 | 单元测试、代码级自动化 | 漏测分支、逻辑错误 | 开发、测开 |
| 灰盒 | 看结构 | 接口测试、抓包定位 | 模块间问题、数据流转问题 | 测试进阶后 |

### 三种视角是组合拳，不是三选一

排查一个 bug 的真实过程常常是三段接力：**黑盒发现现象**（提交订单提示"系统繁忙"）→ **灰盒定位环节**（抓包看到订单接口返回 500，而再往里的库存接口正常，问题圈定在订单服务）→ **白盒确认根因**（开发查代码发现是空指针）。你未必亲手做白盒那步，但要看得懂整个接力。

## 举个例子

同一个功能——登录页"密码 6~20 位"校验，三种视角各怎么做：

- **黑盒**：打开登录页，分别输入 5 位、6 位、20 位、21 位密码，看提示和拦截是否符合需求：5 位提示"密码至少 6 位"，21 位提示"密码最多 20 位"，6 位和 20 位正常提交
- **灰盒**：抓包工具直接调登录接口，绕过前端发一个 21 位密码——发现后端没拦、直接登录成功。前端拦了后端漏了，这是个真实高频的 bug（前端限制永远不算真限制）
- **白盒**：开发写单测时检查分支覆盖，发现校验代码只写了 `length < 6` 拦截，`length > 20` 的分支压根没有，补上分支和用例

三种视角合起来，这条校验才敢说测扎实了——这也解释了为什么面试聊"怎么测登录页"时，能说到"绕过前端直接调接口"这一层的候选人，显得明显老练（见[给你一个登录页面怎么设计用例](../../interview/testing-essentials/04-login-page-test-design.md)）。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 黑盒＝不专业的点点点 | 黑盒是用户视角，恰恰最贴近真实使用；黑盒的上限由用例设计能力决定 |
| 白盒比黑盒高级 | 视角不同而非高下：白盒发现不了"需求本身错了"，黑盒发现不了"没被触发的死逻辑" |
| 功能测试必须先会写代码 | 黑盒做扎实能解决八成功能问题；代码是放大器，不是入场券 |
| 灰盒是黑盒白盒各占一半 | 灰盒是"知道结构和数据流"，关注到模块和接口这一层，不逐行读代码 |
| 一个项目只能选一种视角 | 日常是组合拳：黑盒铺面、灰盒定位、白盒兜底，排查 bug 时三段接力 |

## 上手建议

1. 先把黑盒方法（等价类、边界值、场景法）练到熟，这是你的基本盘，别急着跳白盒
2. 学会用抓包工具（Fiddler 或 Charles 入门见[抓包工具入门](../tech-basics/06-capture-tools.md)），这是从黑盒迈到灰盒最实际的一步
3. 请开发给你讲一次系统架构图：有哪几个模块、数据怎么流，灰盒的"结构感"就有了
4. 排查 bug 时练三段式描述：现象是什么、接口层看到什么、怀疑哪一层——开发最认这种提单
5. 有余力时读一读自己模块的接口文档和关键校验代码，读得懂多少算多少，攒半年就是分水岭
