# 04｜按执行分：静态测试与动态测试

> 核心要点：分界线就一条——**被测程序有没有真的跑起来**。不运行程序就挑毛病的叫**静态测试**（评审、走查、扫描），运行起来喂输入看输出的叫**动态测试**（你日常的绝大部分测试）。静态最便宜、越早越值钱，动态最真实、是最终裁判。

## 打个比方

夏天挑西瓜，两派手法。

**静态派**不切开：抱起来看纹路清不清楚、拍一拍听声音脆不脆、掂一掂估分量。速度快、一个瓜能反复看，裂纹、斑点、畸形这类"外观级"问题一眼挑出。但瓤里的事——没熟、过熟、空心——不切开就是看不见。

**动态派**直接切开尝：红不红、甜不甜、沙不沙，一口定论。最真实，但每验证一个瓜就要切开一个，成本高，而且切开的瓜没法退货，一个瓜只能测一次。

软件同理：需求文档里的自相矛盾、代码里的低级笔误，**不运行就能挑出来**，这是静态测试；而接口超时、并发冲突、缓存错乱这类问题，**必须跑起来才现形**，这是动态测试的领地。

## 展开讲讲

### 静态测试：程序不跑，先挑毛病

静态测试（Static Testing）不执行被测程序，对**文档和代码本身**做检查，三种常见形态：

| 形态 | 干什么 | 谁主导 |
| --- | --- | --- |
| 评审（Review） | 一群人围着文档挑错：需求评审、用例评审、测试报告评审 | 全员 |
| 走查（Walkthrough） | 作者带着大家把自己的文档或代码讲一遍，边讲边被提问 | 作者 |
| 工具扫描 | 静态分析工具自动查代码：规范问题、疑似空指针、未使用变量 | 工具 + 人判误报 |

最容易被低估的是**需求评审**——它是最典型的静态测试。需求里"满 200 可用"没写清是 ≥200 还是 >200，在评审会上问一句就解决了；到了上线后才发现，就是一次线上事故加一次紧急发布。**改一个字的成本，从文档阶段的几分钟涨到线上阶段的几天**，这就是静态测试值钱的原因（测试左移的思路由此而来，见[测试左移与测试右移](../concepts/07-shift-left-right.md)）。

### 动态测试：跑起来才算数

动态测试（Dynamic Testing）给定输入 → 运行程序 → 比对实际输出和预期输出。你每天做的功能测试、性能测试、兼容测试全是动态。

- **为什么不可替代**：并发竞争、时序、缓存、真实网络环境，这些**运行时才存在的行为**，静态手段永远碰不到
- **代价**：要环境、要数据、要时间；一个用例跑一遍就要占一份资源，发现问题后定位也更费劲——切开的瓜没法复原

两种测试一张表对齐：

| 维度 | 静态测试 | 动态测试 |
| --- | --- | --- |
| 程序运行吗 | 不运行 | 运行 |
| 典型活动 | 评审、走查、代码扫描 | 功能、性能、兼容等一切"跑起来"的测试 |
| 能发现 | 文档矛盾、规范问题、可疑代码 | 运行时行为：功能错、超时、崩溃 |
| 发现不了 | 运行时才现形的问题 | 需求本身的错（代码忠实实现了错误需求） |
| 成本 | 低，越早做越便宜 | 高，需要环境、数据、时间 |

### 两者怎么配合

一个成熟的节奏是**静态在前动态在后**：需求评审（静态）挡掉需求级问题 → 用例评审（静态）挡掉用例级漏洞 → 测试执行（动态）专注验证运行时行为。静态拦得越多，动态阶段浪费在"这需求本来就有问题"上的时间越少。注意动态有个静态永远替代不了的职责：**最终行为以运行为准**——代码看着再对，跑出来什么样就是什么样。

## 举个例子

电商"优惠券满 200 可用"这个需求，两种测试各自出手：

**静态阶段**（需求评审 + 代码评审）：

- 你在评审会上问出三个问题："满 200 是 ≥200 还是 >200？""和限时券能叠加吗？""整单退货券退不退？"——需求文档当场补了三行，两个潜在线上争议被消灭
- 开发做代码评审时，同事发现优惠判断写成了 `amount > 200`，一行改动当场修掉，这行代码如果漏到动态阶段，你得先下三单（199、200、201）才能撞见

**动态阶段**（测试环境真实下单）：

- 199 元下单：无券可用，提示"差 1 元可用券"
- 200 元下单：券生效，优惠 30 元，实付 170 元
- 201 元下单：同上，验证边界不是只过了 200 一格
- 顺手验了整单退货后券回到账户——评审时补的第三条需求，动态确认兑现

同一个边界 bug，静态阶段修是一行代码，动态阶段修是一轮提单、修复、回归。两条腿都迈开，才知道省了多少事。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 静态测试＝只有代码审查 | 需求评审、用例评审、文档检查全算静态测试，而且是你能深度参与的 |
| 不跑程序的检查不算"真测试" | 静态测试是被正式认可的一类测试活动，性价比还是全流程里最高的 |
| 扫描工具报的都要改 | 静态扫描有误报，需要人来判断；参与判断误报本身就是很好的学习 |
| 动态测试才是真功夫，评审是走过场 | 评审一小时挡掉的 bug，可能省下三天返工；走没走过场取决于你有没有带着问题去 |
| 静态做多了拖慢进度 | 越靠前改问题越便宜，静态恰恰是在给进度买保险 |

## 上手建议

1. 把下一次需求评审当成你的静态测试现场：会前通读一遍，带着至少三个具体问题进场（怎么问见[需求评审：测试左移第一站](../process/06-requirement-review.md)）
2. 用例评审前先自查一轮：每条用例有没有预期结果、有没有覆盖无效场景，别把漏洞留给评审会
3. 找开发要一份代码扫描报告，学着看最常见的几类告警，分不清的当场问
4. 每个动态阶段发现的 bug 追问一句：这个问题静态阶段能不能发现？攒十次就有感觉了
5. 记一笔"静态拦下的问题"：本月评审挡掉了几个需求级问题，季度汇报时这是最硬的左移收益
