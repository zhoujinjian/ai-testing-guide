# 06｜需求评审：测试左移第一站

> 核心要点：需求评审是**测试左移的第一站**——趁需求还停留在纸面上就把问题挖出来；需求阶段改一行字，比上线后修一个模块便宜得多。测试带进会场的两把刀：**用户视角**和**可测性**。

## 打个比方

需求评审就是**给需求做体检**。

30 岁体检查出血脂偏高，调整半年饮食就回来了；拖到 50 岁查出血管堵了 80%，要支架、要长期服药、要改变整个生活。**病是同一个病，发现得早晚，决定代价的大小。**

PRD 写完，产品、开发、测试坐到一起把它"扫"一遍，就是这场体检。你作为测试，是拿"找病灶"的眼光读文档的那个人——逻辑矛盾、异常流程缺失、边界没定义，这些病在纸面阶段只是改几行字，拖到上线就是返工、客诉、资损。体检报告上查出来的每一项，都是给未来的自己省钱。

## 展开讲讲

### 为什么是"第一站"

行业里有个被反复验证的成本规律：需求阶段发现的问题，改起来按小时计；开发阶段发现，按天计；上线后发现，按周计——还要连上数据修复、客诉安抚、舆情处理。而相当一部分线上 bug 的根子就在需求：规则没写、异常流没想、口径含糊。这些锅最后常被甩给测试（"怎么没测出来"），其实病根在纸面阶段没人挑。**评审会上多说一句，比执行期多测三天值钱。**

### 评审前：别空手去

提前半天到一天拿到 PRD，通读两遍：**第一遍当用户**——照着文档把流程在脑子里走一遍，走不通的地方记下来；**第二遍当测试**——逐条挑哪里没说清、哪里没定义失败情况。读的时候顺手列问题清单，每条写清"位置 + 问题 + 为什么重要"。再翻翻旧版本和竞品同类功能，脑里有对照，问题就问得准。

### 会上：照着五个角度问

| 视角 | 典型问题 | 真实例子 |
| --- | --- | --- |
| 异常流 | 失败了怎么办 | 支付超时了订单什么状态？券回退吗？ |
| 边界 | 数字规则定死了吗 | "满 100 可用"，99.9 算不算满？ |
| 数据 | 数据从哪来、到哪去 | 历史订单要迁移吗？旧版本 App 看到新字段显示什么？ |
| 依赖 | 上下游谁受影响 | 券逻辑变了，退款、客服后台、报表要不要跟着改？ |
| 可测性 | 测得了吗 | 灰度开关可配吗？测试环境能造出"库存不足"的场景吗？ |

会上只问"需求说清楚了没有"，不聊"代码该怎么实现"——那是开发设计评审的事。问倒了需求不丢人，是功劳。

### 三种常见的评审形式

不是所有评审都要开会，常见三种：**正式评审会**（人齐、过文档、当场定结论，大需求用）；**轮审**（文档发群里，各方异步评论留痕，中小改动用）；**走查**（两三个人凑一起快速过一遍，紧急小需求用）。三种形式测试都要在场——轮审最容易漏掉测试，别人可能只@开发和设计，你要主动认领评审批注的任务。无论哪种形式，**产出的问题清单和修改结论必须留痕**，截图或文档存档，将来扯皮时它就是证据。

### 评审后：结论要落进文档

会上定的规则当场记，会后盯着 PM 更新进 PRD——**没落进文档的口头共识等于没说**。PRD 定稿叫"需求基线"，之后任何改动走变更流程（谁提的、影响什么、何时生效），测试同步更新用例。另外，现实中口头需求、一句话需求很多见，测试的对策是自己补文档拉开发对齐，[这道面试题](../../interview/testing-essentials/05-testing-without-requirements.md)有完整打法。

## 举个例子

外卖「满 30 减 8 店铺优惠券」的需求评审实录。PM 讲完方案，你照清单提了 6 个问题：

1. **和平台满减能叠加吗？**——定：可叠加，券在满减后结算
2. **退款后券回退吗？**——定：24 小时内整单退款券回退，部分退款不回退
3. **券快过期有提醒吗？**——定：过期前 24 小时推送一次
4. **一个用户一天能领几张？**——定：每人每天限领 1 张
5. **优惠后订单金额是 0 元怎么支付？**——PM 愣了 10 秒，定：0 元单直接成单不进支付（这条差点漏掉，是经典的"0 元单卡死支付页"事故源头）
6. **怎么防批量薅券？**——定：同设备限领，接风控

其中第 5 条如果你会上没问，上线后"0 元单卡在支付页转圈"就是一起 P0 加你的锅。会后 PM 按结论把 PRD 更新到 v1.2，你把这 6 条规则翻译成 18 条测试用例——**评审的产出，直接喂给了用例设计**（怎么翻译见[从需求到用例](../testcase-design/05-requirement-to-testcase.md)）。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 评审会是产品宣讲会，听完就行 | 不发言等于放弃表决权，会后的坑最后都是测试的锅 |
| 怕问"蠢问题"不好意思开口 | 你觉得蠢的问题，往往恰好是 PM 没想到的，问倒是功劳 |
| 看交互稿就够了 | 稿子只画了正常流，文字规则（口径、限制、异常）才是 bug 之源 |
| 评审通过就完事了 | 结论要落回 PRD 形成基线，变更要走流程并同步用例 |
| 需求变更是产品的事 | 每条变更都要过一遍"影响哪些用例"，不然测了个寂寞 |
| 提的问题越多越显水平 | 先问影响流程和数据的硬伤，文案级别的攒着会后单提 |

## 上手建议

1. **建一张"评审问题清单"模板**，按异常流 / 边界 / 数据 / 依赖 / 可测性分五栏，每次评审前照单预填
2. **下次评审至少开口 3 个问题**，从最好上手的"这一步失败了怎么办"开始
3. **评审后 24 小时内对照 PRD 核一遍结论**，漏写的让 PM 补上再归档
4. **遇到口头需求就主动整理"需求确认清单"**，拉上开发和 PM 逐条确认签字
5. **翻一遍项目历史 bug**，挑出需求类问题（规则没定、口径含糊），看哪种最常漏，把对应的问题加进你的清单
