# 09｜测试环境入门：dev、test、staging、prod

> 核心要点：四套环境不是"同一个系统复制粘贴四份"，而是**四个用途不同的战场**——数据、部署节奏、谁有权动，全都不一样；新手手里一半的"诡异 bug"，最后查出来是环境问题。

## 打个比方

四套环境像**一场话剧的四个阶段**。

**dev 是排练厅**：演员（开发）自己练，走位错一百遍无所谓，道具想改就改。**test 是导演连排**：导演（测试）在场，一遍遍抠细节，演砸了推倒重来，成本可控。**staging 是正式剧场的合成彩排**：服装、灯光、音响全部到位，除了没有观众，一切都按正式演出标准走——专门暴露"排练厅里发现不了的问题"（比如灯光和音响打架）。**prod 是正式首演**：观众进场了，说错一句台词都是真事故，改剧本要走流程。

四阶段的差别就两个词：**像不像现场、能不能出错**。排练厅怎么折腾都行，首演不能错一个字——软件环境同理，test 里删库重造没人心疼，生产环境查一行数据都要审批。

## 展开讲讲

### 四套环境对照

| 环境 | 谁在用 | 数据 | 部署节奏 | 离生产多远 |
| --- | --- | --- | --- | --- |
| dev | 开发自测联调 | 造的假数据，随便删 | 一天几十次 | 远 |
| test | 测试团队 | 测试数据 + 脱敏样本 | 每次提测部署 | 较远 |
| staging（预发） | 发布前验证 | 生产脱敏数据，配置尽量同生产 | 每次发布前 | 极近，是生产的"彩排替身" |
| prod（生产） | 真实用户 | 真实数据 | 按发布窗口，走审批 | 它就是标准本身 |

### 每套环境存在的意义

**dev** 让开发敢乱试；**test** 让测试敢破坏——造"库存不足""网络超时""重复提交"这些场景都不心疼；**staging** 专门拦"test 环境测不出来"的问题：配置差异（回调地址、开关阈值）、数据量级（100 条和 1 亿条的查询表现）、第三方依赖（test 里是 mock，这里要过真实网关）；**prod** 只做终极确认，测试通常只有只读权限加一套固定的线上验证清单。

### 复现不一致：按这四步排查

新手最常撞上的怪事：**bug 在 test 复现、staging 不复现**（或反过来）。别急着说"诡异"，按顺序查：

1. **版本一致吗**——两边的构建号是不是同一个（提测包和预发包不是同一次构建的情况很常见）
2. **配置一致吗**——开关、阈值、白名单、回调地址，staging 和生产的已知差异清单里有它吗
3. **数据一致吗**——你在 test 造的数据形态，和生产真实数据长得不一样（比如手机号格式、历史订单数量）
4. **依赖一致吗**——第三方服务在 test 是 mock 还是真调、版本是否相同

四步都排完还不一致，再抓包、看日志往下挖（查日志的方法见[底子篇](../tech-basics/09-linux-logs.md)）。**直接拿 test 环境的结论给生产品票，是很多事故的开头。**

### 不止四套：那些临时环境

除了四大常驻环境，你还会遇到一批**临时环境**：**联调环境**（前后端或多团队接口联调专用，谁改动大谁拉一套）、**压测环境**（性能测试专用，和生产同配置才有效，压完即拆）、**演示环境**（给老板或客户看 demo 用，数据漂亮但功能可能是半成品，千万别拿它测）。临时环境的纪律就一条：**用完还**——占着环境不放的团队，是所有排期延误里最冤的那种。

### 环境纪律

测试数据用完要清理，不然脏数据会让下个版本的用例成片误报（造数思路见[测试数据怎么造](../tech-basics/12-testdata-strategy.md)）；环境出了问题当天报给环境负责人，别默默重启糊弄过去——环境不稳定是测试效率的头号杀手，忍让只会让它更烂。

## 举个例子

外卖 App「支付宝退款」功能在三个环境各拦住一层问题：

**test 环境**：小周造了一笔 19.9 元的订单发起退款，秒到账，逻辑正确——这里拦的是**业务逻辑**问题。

**staging 环境**：轮到验证真实退款网关，用 1 分钱订单过真实通道。发起退款后订单状态半天不变，查日志发现**回调地址配置的还是 test 环境的地址**——支付宝回调打到了测试库，生产订单自然收不到通知。当场改配置再验，回调正常。这种问题在 test 环境（走 mock）永远测不出来，只能 staging 拦截。想想它漏到生产会怎样：用户退款成功、钱退了，但订单永远显示"退款中"，客诉直接爆炸。

**prod 环境**：上线后人工验证 1 分钱退款真实到账，盯 1 小时回调成功率（100%），确认无异常——这里做的是**终极确认**。

三层各司其职：**test 拦逻辑，staging 拦配置和集成，prod 做最后确认**。少哪层，就有一类问题直接漏到用户面前。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 环境就是四台服务器 | 是四套不同规则：数据、权限、部署流程、仿真度全不同 |
| test 能复现就一定是真 bug | 先按"版本→配置→数据→依赖"四步排环境差异，再下结论 |
| staging 通过 = 生产没问题 | staging 只是"尽量像"，真实流量和用户行为模仿不了 |
| 环境卡了就自己重启 | 频繁重启掩盖根因，要报障留痕，让环境问题可见 |
| 造的数据用完不管 | 脏数据会让下个版本成片误报，用例"全红"多半是它的锅 |
| 生产环境"就看一眼"不行吗 | 只读也是权限，任何生产操作走审批留痕，这是红线 |

## 上手建议

1. **建一张环境速查表**：每套环境的地址、账号、部署负责人、数据库连接方式，贴在最顺手的地方
2. **遇到"复现不一致"就按四步走**：版本、配置、数据、依赖，练成肌肉记忆再谈玄学
3. **摸清 staging 和生产的已知差异清单**，验证时心里有数：哪些差异是"知道且接受"的
4. **造数脚本化，用完清理**，给每批测试数据起可识别的名字（如 `test_zhou_1015`），方便事后清扫
5. **学会看部署日志**：谁、什么时候、部署了哪个版本——排查"环境问题还是代码问题"的第一手证据
