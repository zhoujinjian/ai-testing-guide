# 03｜敏捷开发入门：Scrum 与看板

> 核心要点：敏捷是"小步快跑、拥抱变化"的理念，**Scrum 按固定周期一批一批交付，看板让需求像流水一样持续流动**，这是它俩最常用的两种落地框架；测试在其中不是等在终点的关卡，而是跟着每个故事走的随行医生。

## 打个比方

两家奶茶店，两种经营节奏。

**Scrum 式**的店按"上新周期"经营：每两周固定上一批新品。周期第一天开选题会定这批做什么（计划会）；每天开店前 10 分钟店员碰个头，说说昨天做到哪、今天做什么、卡在哪（站会）；新品上架当天请熟客来试喝给反馈（评审会）；当晚关店复盘这批哪些好卖哪些翻车，下批怎么改（回顾会）。

**看板式**的店现点现做：每张小票贴在"点单 → 制作 → 出杯"的三段轨道上，顾客抬头看一眼屏就知道自己的单走到哪一步；关键是**制作段最多同时挂 5 张单，挂满了就不接新单**——防止越堆越多、杯杯做糊。

第一家赢在"按周期集中交付、定期复盘"，第二家赢在"一切可视化、不超载"。软件团队选 Scrum 还是看板，选的就是这两种节奏。

## 展开讲讲

### 先说敏捷是什么

2001 年十几位软件老兵聚在一起发布了《敏捷宣言》，核心就四句话，浓缩成一句人话：**与其花一年憋一个大版本，不如每两周交付一个能用的东西，边交付边听反馈边调整**。注意敏捷是理念不是操作手册，落地靠具体框架——Scrum 和看板（Kanban）就是最常见的两个。

### Scrum：按冲刺交付

**Sprint（冲刺）**：固定 1~4 周、最常见 2 周的开发周期，也叫"时间盒"——时间到了必须收，做不完的挪到下个冲刺。**三个角色**：PO（产品负责人，管需求价值和优先级）、Scrum Master（管流程不管人，更像团队的服务员，帮你清障碍）、开发团队（开发+测试一起算"团队"，共同对交付负责）。**五个事件**里最要记住的三个：

| 会议 | 干什么 | 时长参考 |
| --- | --- | --- |
| 冲刺计划会 | 从产品待办列表里挑出本冲刺要做的故事，定目标 | 1~2 小时 |
| 每日站会 | 每人三问：昨天做了什么、今天要做什么、有什么阻碍 | 15 分钟以内 |
| 评审会+回顾会 | 评审会演示成果给 PO；回顾会复盘流程本身怎么改进 | 各 1 小时 |

站会特别提醒：它是**团队互相同步**，对着队友说而不是对着领导汇报。

### 看板：让工作流动起来

三件套：**卡片**（一张卡一个任务）、**列**（待办 / 开发中 / 待测试 / 完成，按团队实际流程设）、**WIP 限制**（在制品限制，每列设上限）。WIP 限制是看板的灵魂——"开发中"一列上限 4 张，第 5 张想进来就必须先有一张流出去。它逼着瓶颈暴露：哪一列常年堆满，哪一环就是堵点。测试在敏捷团队里最常见的心酸就是"待测试"列常年爆满，这个可视化恰恰是改进的起点。看板没有固定周期，需求随时来随时走，节奏由容量决定。

### Scrum 与看板怎么选

| 维度 | Scrum | 看板 |
| --- | --- | --- |
| 节奏 | 固定时间盒，到期交付 | 持续流动，来一单做一单 |
| 需求变更 | 冲刺内尽量不动，下冲刺再排 | 随时可以插队 |
| 会议 | 五件套齐全 | 站会可选 |
| 适合 | 版本型产品迭代、需求成批次来 | 工单型、运维型、需求零散的团队 |

### 测试在敏捷里意味着什么

两件事改变最大。一是 **DoD（完成的定义）**：一个故事"开发写完代码"不叫完成，"测试通过"才算——测试从流程末梢变成冲刺内的一等公民。二是提测方式：故事做一个提测一个（增量提测），不是攒到冲刺最后一天倒给你。相应的挑战也真实存在：开发第 5 天才交付第一个故事，测试挤压在冲刺后半程——这正是回顾会上该被拿出来改的流程问题，而不是测试默默加班消化掉。

## 举个例子

同一个电商公司，两个团队两种活法。

**搜索团队用 Scrum**：双周冲刺，本冲刺做"搜索历史记录"功能。Day1 计划会认领 8 个故事（记录搜索词、历史列表展示、清空历史、历史点击回搜……）；每天 10 点站会，测试小林昨天说"等'记录搜索词'这个故事的联调，卡了一天"，Scrum Master 当场去催后端；Day4 开发交付第一个故事，小林当天测完提了 2 个 bug；Day10 评审会给 PO 演示全部故事，当晚回顾会得出结论——"故事拆得太大导致测试挤在后半程，下个冲刺故事粒度减半"，写进了下冲刺的改进清单。

**客服工具团队用看板**：需求零散（改一句文案、加个导出按钮、修个 bug），看板四列：待办 / 开发 / 待测试 / 上线，"待测试"列 WIP 上限 3。测试小周负责这一列：卡片流进来就测，当天测完当天流走。某天"开发"列堆了 7 张卡片，站会上一看板子就明白了——两个开发请假，主动从"待办"挪走 2 张低优先级卡，瓶颈当场拆掉。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 敏捷 = 不用写文档 | 该有的 PRD 和用例一样要，敏捷反对的是"为了写而写" |
| 站会是给领导汇报工作 | 站会是团队互相同步，对着彼此说，超时 15 分钟就是开歪了 |
| 把任务贴墙上就叫看板 | 没有 WIP 限制和关注流动，看板只是块告示栏 |
| Scrum Master 是项目经理 | SM 伺候流程不派活，不背交付指标，是服务员不是领导 |
| 冲刺内测试挤压是测试的问题 | 是故事拆分和流转问题，回顾会就该摊开改流程 |
| 用了敏捷就没有流程 | 敏捷的会议和节奏比很多传统流程更密集，只是轻文档重沟通 |

## 上手建议

1. **明天的站会按"三问"准备发言**：提前写在本子上，30 秒内说完，卡点一定说出口
2. **搞清自己团队是 Scrum、看板还是混搭**，找到对应的机制：冲刺待办列表或物理看板在哪
3. 团队有看板的话，**找到"待测试"列并主动认领**，测完当天把卡片挪走
4. **和 PO 确认 DoD 里包不包含"测试通过"**，没包含就去推动加上——这是测试话语权的根
5. **下次回顾会带一个具体流程问题去**，比如"提测集中在冲刺后半程"，带着数据去
