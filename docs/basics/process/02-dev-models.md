# 02｜开发模型：瀑布、迭代、增量、螺旋

> 核心要点：开发模型说的是**"一个项目按什么节奏组织开发"**——一次做完还是分多轮做、每轮做什么。模型决定了测试什么时候进场、按什么节奏干活；不懂模型，你只能被动挨排期。

## 打个比方

四种开发模型，像**写毕业论文的四种写法**：

**瀑布式**：先定大纲交导师审，批完再花两周查文献，憋出一版初稿，改三稿，最后定稿装订——一步走完才走下一步，每步都有签字画押的产出。**迭代式**：先交一版"能看"的粗稿，导师批注哪里不行，第二版加深度，第三版补数据，每版都比上一版更像论文。**增量式**：第一章写完就交一章，交完三章正好答辩，每一章交出去时都是成品。**螺旋式**：动笔写每章之前，先评估"这章最大的坑是什么"——数据拿不到？方法不熟？——先做个小实验探路，确认安全了才正式写。

论文写法不同，你当"审稿人"的节奏就完全不同：瀑布式是最后集中审两周，迭代式是每轮都审一遍。测试一模一样。

## 展开讲讲

### 瀑布模型：一步一关卡

阶段严格串行：需求分析 → 设计 → 编码 → 测试 → 运维，上一阶段评审通过才进下一阶段，靠文档驱动。

- **优点**：阶段清晰、文档齐全、便于按里程碑验收（外包和政企项目爱用它就是这个原因）
- **缺点**：周期长、用户反馈来得晚、**测试排在编码之后**，方向性错误要到最后才暴露，返工成本极高
- **适合**：需求极其稳定、合规要求高的项目——银行核心系统、航天、军工

### 迭代模型：同一产品多轮加深

先把一个"能跑但粗糙"的完整版本做出来，每一轮迭代都针对同一个产品**在深度上打磨**：第一轮能下单，第二轮下单体验变好还加了优惠券，第三轮再加会员体系。每一轮都是"设计→开发→测试"的小循环。

### 增量模型：功能一块块加

先交付**核心可用的最小版本**（这个思路的极致叫 MVP，最小可行产品），再一块一块往上加功能：先上"设置预算"，两周后上"超支提醒"，再两周上"报表"。每个增量交付时都是完整可用的成品。**迭代和增量最容易混**：迭代是同一功能逐轮变深，增量是不同功能逐块变广——一句口诀，**迭代磨深度，增量扩地盘**。

### 螺旋模型：每轮先排雷

每一轮固定四步：**定目标 → 评估风险 → 做原型验证 → 规划下一轮**。风险驱动是它的灵魂，特别适合大型、高风险、需求高度不确定的项目：先花小成本验证"支付网关扛不扛得住"这种致命疑问，确认了再投入正式开发。

### 一张表收拢

| 模型 | 一句话 | 交付节奏 | 测试进场时机 | 适合项目 |
| --- | --- | --- | --- | --- |
| 瀑布 | 一次做完再交付 | 项目末期一次交付 | 编码后集中测试 | 需求稳定、强合规 |
| 迭代 | 同一产品多轮加深 | 每轮一个更完善的版本 | 每轮都测一遍 | 需求会持续演进的产品 |
| 增量 | 功能一块块交付 | 核心先上，逐块追加 | 每块交付前测试 | 想尽早上线占位的产品 |
| 螺旋 | 每轮先验证风险 | 每轮一个原型或版本 | 参与风险验证+每轮测试 | 大型高风险项目 |

### 模型决定测试的活法

瀑布里测试集中在尾部，但**计划、用例、环境必须提前备好**，别真的闲等到提测；迭代和增量里测试每轮都来一遍，**回归是家常便饭**，自动化的价值被放大（每轮手工回归会把人拖垮）；螺旋里测试要参与风险评估，"原型验证"本身就非常像探索性测试。现实中没有纯血模型，多数团队是混搭——整体偏瀑布的大项目里局部敏捷，或者敏捷框架里对高风险模块先做技术验证。而"敏捷"本身，就是迭代思想的现代化身，下一篇展开。

## 举个例子

记账 App 要做「月度预算」功能，四种模型分别是这么干的：

- **瀑布**：产品花 3 周定完所有规则（总预算、分类预算、超支提醒、报表），开发 2 个月，第 3 个月测试团队集中测 3 周——你作为测试在这 2 个月里把 200 条用例写得滚瓜烂熟，但直到第 3 个月才见到真东西，一测发现"用户根本不想设置分类预算"，方向错了，代价巨大
- **迭代**：第 1 轮只有"设总预算+超了弹提醒"，你测 3 天；第 2 轮加分类预算，你测这轮新功能+回归上一轮，4 天；第 3 轮加报表，5 天——每轮用户都在用、都在反馈
- **增量**：预算设置功能先上，两周后提醒功能跟上，再两周报表上线——你每次只测新的一块+核心回归，节奏均匀
- **螺旋**：第一轮先做"预算数据在多设备同步"的原型，你和开发一起验证同步不丢数据（这是最大风险点），确认方案成立，第二轮才放量开发完整功能

同一个需求，你在瀑布里是"末端的集中审稿人"，在迭代和增量里是"每轮都上场的随队队医"。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 敏捷先进，瀑布落后 | 模型没有先进落后，只有合不合适；需求稳定时瀑布依然好用 |
| 迭代和增量是一回事 | 迭代是同一功能逐轮变深，增量是不同功能逐块交付 |
| 瀑布里测试前期没事干 | 计划、用例、环境、造数全要提前备好，闲着才是失职 |
| 螺旋模型早过时了 | "先小成本验证风险再投入"的思想活在每个项目里 |
| 模型是研发经理的事，与我无关 | 模型决定你的测试节奏和回归压力，不懂只能被排期推着走 |
| 我们公司用敏捷，就等于 Scrum | 敏捷是理念，Scrum 只是落地框架之一，还有看板（见下一篇） |

## 上手建议

1. **问 leader 一个问题**：我们项目整体走的是哪种模型？答案往往是"名义敏捷、实际混搭"，追问混在哪里
2. **拿手头一个需求判断节奏**：它是"一次全量交付"还是"分轮/分块交付"？对照本篇归类
3. **统计你最近一个月的回归次数**：每周都在回归，说明迭代节奏快，该认真考虑自动化了
4. **看团队历史版本的发布频率**：拉一张近半年的发布时间表，交付节奏一目了然
5. **花 10 分钟读一遍敏捷宣言**（网上搜"Agile Manifesto"，12 条原则），为下一篇打底
