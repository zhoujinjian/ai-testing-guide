# 11｜准入与准出：什么时候开始测、什么时候能上线

> 核心要点：**准入**决定"这个版本配不配被测"，**准出**决定"这个版本配不配上线"；两条线都要**提前写进测试计划、量化成数字**，发布前夜才不会变成吵架现场。

## 打个比方

一次航班要过**两道关卡**。

第一道在**登机口（准入）**：查票、查证件、量行李——不合格就不让你上飞机。不是地服刁难你，是因为你带上飞机的每一件超规行李，都可能拖累整趟航班。第二道在**驾驶舱（准出）**：机长核对油量、天气、配载、舱门——全部确认才敢推油门。乘客全部登机了，机长也不含糊：**不达标就是不起飞**，延误好过出事。

提测准入同理：开发自测没做、冒烟跑不通，测试有权打回——保护的是整趟"版本航班"，不是跟谁过不去。上线准出同理：用例没跑完、P0 没清零，谁来施压也不放行——**放走一个带病版本，比延误三天贵得多**。

## 展开讲讲

### 准入：提测的门槛

| 准入项 | 标准示例 |
| --- | --- |
| 提测单完整 | 写明改动点、影响范围、自测结论 |
| 开发自测通过 | 附自测记录或截图 |
| 冒烟通过 | 冒烟用例 100% 通过（自动化跑最理想） |
| 单元测试达标 | 核心模块覆盖率不低于 70% |
| 环境就绪 | 测试环境部署成功、版本号与提测单一致 |
| 阻塞问题清零 | 上一轮遗留的阻塞性 bug 已修复 |

不满足怎么办？**打回**，并附一段专业话术："冒烟 12 条挂 4 条（失败清单见附件），按准入标准本次提测打回，预计影响测试启动 1 天。"有标准、有证据、有影响评估，开发没法觉得你在针对他——**打回是流程动作，不是情绪动作**。

### 准出：上线的门槛

| 准出项 | 标准示例 |
| --- | --- |
| 用例执行率 | 100%，未执行的要写明原因 |
| 用例通过率 | 不低于 95%，未过的逐条分析 |
| bug 修复 | P0P1 修复率 100%，P2 不低于 90% |
| 遗留 bug | 每条有风险评估、规避方案和跟进负责人 |
| 回归完成 | 核心模块加关联模块回归通过 |
| 专项达标 | 性能压测、兼容性等专项结论合格 |
| 线上预案 | 回滚方案已确认（见[发布上线](./12-release-process.md)） |

### 准出评审会：结论怎么下

版本末期开 30~60 分钟的会：测试出报告（用例数据、bug 分布、遗留风险，怎么写见[报告篇](../report-metrics/07-release-conclusion.md)），项目干系人共同决策。划清一条界线：**测试给质量结论，上线决策是团队共同拍板**。测试说"不满足准出"，业务可以基于商业判断带风险上线（比如大促窗口必须赶上），但必须记录在案："风险已知悉，决策人签字"——出了问题，追溯的是当时的决策，不是测试的失职。

### 三条铁律

**提前定**——标准写进测试计划（见[测试计划怎么写](./07-test-plan.md)），版本第一天就让所有人知道，事后才定的标准没有公信力。**可量化**——"质量良好"不算标准，"P0P1 清零"才算。**对标准不对人**——标准立在那里，打回和否决都不伤感情；没有标准的打回才是找茬。

### 标准的松紧是调出来的

第一条标准别拍脑袋抄大厂的值。起步阶段可以从宽（比如通过率 90%），每个版本复盘后再收紧——**先有标准，再谈严格**。校验一条标准值不值得留，问一句话："它防的是哪次真实事故？"答不上来的标准可以删，防得住事故的标准谁也不敢删。还有一条隐性收益：数字标准积累三五个版本后，你手里就有了团队的质量趋势线——通过率是不是逐版本在涨、P1 修复时长是不是在缩短，这些正是测试报告和年度总结里最值钱的素材（怎么呈现见[报告篇](../report-metrics/04-core-metrics.md)）。

## 举个例子

电商 App v3.2.0 的两道关卡实录。

**周二提测，卡在准入**：冒烟 12 条挂了 4 条——购物车加购后数量不同步、商品详情页打不开。你按准入标准打回，附失败清单。开发修复后**周三下午重新提测**，冒烟全过，正式开测。打回的这一天没有白费：周四上午你就抓出了 7 个功能 bug，因为版本底子是干净的，不用在"时好时坏"里烧时间。

**下周一准出评审**：用例执行率 100%（286/286）、通过率 96.9%（9 条未过：6 条已修复待回归、3 条转遗留）、P0P1 全清；遗留 P2 两个——列表排序在小概率分页下错乱，规避方案"先按默认排序，下版本修"；P3 三个文案问题。结论：**满足准出，周三发布**，遗留项全部登记跟进。

对照组是隔壁项目组：没定准出标准，发布前夜产品施压"先上了再说"，带着一个未修的 P1 上了线，当晚崩溃率翻倍，全组回滚加班到凌晨三点。第二周，他们老实把准出标准贴在了墙上。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 准入准出是走形式 | 这两条线是测试话语权的来源，数字在手才有的谈 |
| 打回提测得罪开发 | 有标准的打回是流程动作，没标准才像找茬 |
| 准出 = 测试一个人拍板 | 测试出质量结论，上线是共同决策，但风险要白纸黑字 |
| 执行率 100% 就是测完了 | 执行了不等于通过，两个数字要一起看 |
| 有遗留 bug 就一律不让上线 | 带风险上线是常态，关键是评估、记录、有规避方案 |
| 标准定得越高越好 | 定一个达不到的标准等于没有标准，要贴合团队实际逐年收紧 |

## 上手建议

1. **把准入准出的数字标准抄进你的测试计划模板**，从本文的示例值起步，每个版本复盘后微调
2. **经历打回时用"标准 + 证据 + 影响"三段式**写打回说明，练熟这套表达
3. **建遗留 bug 跟踪表**：bug 号、严重级、风险描述、规避方案、负责人、计划修复版本
4. **准出评审前把数据备齐**：执行率、通过率、bug 分布，做到有问必答不翻手机
5. **复盘过往版本的遗留 bug**：后来有没有炸？用真实数据校准你们标准的松紧
