# 01｜一个需求的一生：从想法到上线

> 核心要点：一个需求不是"产品想出来→开发写出来→上线"三步的事，而是要闯过**需求池、评审、排期、开发、提测、测试、准出、发布、线上验证**一整条流水线；越早看清这条线，你越不会把自己活成"末端验货员"。

## 打个比方

一个需求的旅程，像**一箱橙子的快递之路**：

你在网上下单（用户提了个想法），订单先落进商家系统（需求池）；客服确认有没有货、发哪家快递（需求评审）；仓库把这一箱排进今天的打包批次（排期）；打包员装箱贴单（开发）；出库前扫码核对一遍（开发自测与提测）；分拣中心过安检、抽检有没有坏果（测试）；然后干线运输（发布部署）；先到小区驿站（灰度）；你签收开箱验货（线上验证），确认没烂，这单才算完结。

任何一环掉链子，橙子到你手里都是烂的。软件需求一样：你接到的"提测版本"只是这条链上的一站——**往前看清它怎么来的，往后看清它去哪，你这个测试才当得明白**。

## 展开讲讲

### 全流程一张表

| 阶段 | 主角 | 产出物 | 测试在干嘛 |
| --- | --- | --- | --- |
| 需求收集（需求池） | 产品经理 | 需求列表 | 每周扫一遍新需求，提前熟悉方向 |
| 需求评审 | 产品+开发+测试 | PRD 定稿 | 挑逻辑漏洞、评估可测性 |
| 排期 | 项目经理 | 排期表 | 评估测试工作量、申请资源 |
| 开发 | 开发 | 代码+自测记录 | 同步写用例、备环境造数据 |
| 提测 | 开发 | 提测单 | 准入检查，不达标打回 |
| 测试执行 | 测试 | bug 单、执行记录 | 冒烟→功能→回归 |
| 准出评审 | 测试+项目 | 测试报告与结论 | 出具质量结论 |
| 发布 | 开发+运维 | 线上版本 | 盯灰度批次指标 |
| 线上验证 | 测试+运维 | 验证记录 | 生产环境主流程真实走一遍 |
| 复盘 | 全员 | 复盘结论 | 分析缺陷为什么漏到线上 |

几个名词先解释：**PRD**（产品需求文档，说清做什么、做成什么样）、**提测**（开发把版本正式交给测试）、**灰度**（先放一小部分用户用新版本）。

### 三个关键认识

**第一，需求不是评审完就定死。** 评审通过叫"基线"（大家公认的这一版），之后业务变化、开发遇到技术难题，需求都会改。健康的团队有变更流程：谁提的变更、影响什么、什么时候生效，白纸黑字记录，测试照着同步更新用例。没有变更管理的团队，测的经常是"上一版需求"。

**第二，提测之前测试一点不闲。** 对照表里看得到：评审、排期、用例设计、环境准备、数据预埋，全发生在提测前。新手最常见的错觉是"等开发提测我才开始干活"——等你真等来提测再想测什么，三天执行期就废了一天半。

**第三，两个里程碑最重要。** **需求评审**决定你后面测什么（规则错了用例全错），**准出评审**决定版本能不能上线（结论下错就是事故）。这两场会，测试的发言分量最重，别缺席。

## 举个例子

外卖 App 的「餐具份数」需求，完整走一遍：

1. **3 月 1 日进需求池**：用户反馈"十个人团建点餐只送了一副筷子"，PM 判断高频，立项
2. **3 月 8 日出 PRD**：下单页新增餐具份数选择（0 份 / 1 份 / 2 份 / 按人数），默认"按人数"，商家小票同步打印
3. **3 月 10 日需求评审**：你提了三个问题——"按人数"有没有上限？选"0 份"要不要二次确认？旧版本 App 下的单，商家端怎么显示？当场定下规则写进 PRD
4. **3 月 12 日排期**：前端 3 天、后端 2 天、联调 1 天、测试 3 天，你确认 3 天够用，但要一个测试账号提前开好
5. **3 月 13~17 日开发**：你同步写完 32 条用例，在 test 环境预埋了 3 个测试商家账号和一桌"10 人份"的测试商品
6. **3 月 18 日提测**：提测单信息齐全、冒烟 12 条全过，准入通过
7. **3 月 18~20 日测试执行**：冒烟半小时过；功能测试两天，抓到 bug"选 0 份餐具，商家小票仍打印餐具数 1"（P2），修复后定向回归通过
8. **3 月 21 日准出**：用例执行率 100%、通过率 97%、遗留 1 个 P3 文案问题，风险评估可接受，结论"可发布"
9. **3 月 22 日发布**：白名单 20 家内测店 → 10% 用户 → 全量，三批各盯 1 小时指标
10. **线上验证与复盘**：你在生产环境真实下 3 单（分别选 0 份、2 份、按人数），商家端小票全部正确；一周后复盘，"餐具相关客诉"下降了 40%

十步走完，这个需求才算真正交付。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 需求是产品一个人的事 | 评审是三方共同打磨，你不发言，后面的锅测试背 |
| 评审通过 = 需求不再变 | 变更天天有，重点是每条变更要同步到用例 |
| 测试从提测才开始干活 | 用例、环境、数据全在提测前，那是测试的"主场时间" |
| 提测单就是走个形式 | 提测单是准入检查的依据，信息不全按标准打回 |
| 线上发布 = 测试结束 | 线上验证和复盘才是收尾，逃逸 bug 的经验全从复盘长出来 |
| 每家公司的流程都一样 | 骨架八九不离十，细节各家不同，入职先摸清自家节奏 |

## 上手建议

1. **找 PM 要需求池的查看权限**，每周扫一遍新增需求，你会比同事早两周知道方向
2. **画一张自己项目的流程图贴在工位上**，把每个节点的负责人名字标上去
3. **建一张需求跟踪表**：需求名、当前阶段、产品负责人、开发、测试负责人，每天更新
4. **拿最近一个上线需求反推一遍**：它的评审、提测、发布分别发生在哪天、产出物是什么文件，在群里都找得到
5. **报名参加下一次复盘会**，重点记别人怎么分析"缺陷为什么漏到线上"
