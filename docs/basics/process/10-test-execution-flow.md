# 10｜测试执行全流程：冒烟 → 功能测试 → 回归 → 上线验证

> 核心要点：版本提测之后，测试不是拿起手机一通乱点，而是按**冒烟 → 功能测试 → 回归测试 → 上线验证**四步走，每一步都在给下一步把关，顺序乱了就是白干。

## 打个比方

把测试执行想象成**新房装修验收**：

你不会一进房门就趴在地上检查瓷砖缝——先开总闸看看水电通不通（**冒烟**），水电都是断的这房没法验；通了，再一个房间一个房间细看（**功能测试**）；墙裂了让工人补，补完你不能只看那面墙，得顺带敲敲旁边的墙有没有被震裂（**回归**）；最后交房当天，你再整体走一圈确认没问题（**上线验证**）。

顺序为什么不能乱？水电没通就去挑瓷砖缝，挑了半天结果整栋楼要返工，前面的活全白干。测试同理：**冒烟没过就细测，测了一半版本打回，全泡汤。**

## 展开讲讲

### 第 0 步：提测准入检查（门还没进，先看门票）

开发说"提测了"，不等于马上开测。先过一遍**准入检查**：

- 提测单信息齐全：改了什么、影响哪些模块、自测过没有
- 测试环境部署成功，版本号对得上
- 开发自测报告或冒烟记录里有结论

准入不过，直接打回。这一步看着冷酷，实际是在保护测试的时间——**开发五分钟的自测，能省测试半天的不必要排查**。

### 第 1 步：冒烟测试——主流程通不通

冒烟测试（Smoke Testing）这个名字有个真实出处：早年硬件测试时给电路板通电，看冒不冒烟，冒烟就说明有致命问题，后面的细测不用做了。软件沿用了这个思路。

- **测什么**：系统最核心的主流程。电商就是登录、搜索、加购、下单、支付；一条都不多，通常 20~50 条用例
- **多快**：半小时到两小时，快进快出
- **不通过怎么办**：整个版本打回，开发修复后重新提测，冒烟重跑

注意：冒烟不通过打回版本，**不是找开发的茬，是止损**。主流程都跑不通，说明这个版本连"能测"的门槛都没到。

### 第 2 步：功能测试——按用例铺开细测

冒烟过了，才进入真正的细测阶段，这一步占掉整个执行周期的大头：

- **按用例执行**：跟着评审过的测试用例一条条走，通过了标记通过，失败了先确认是不是 bug
- **按优先级排兵**：先 P0 保命用例，再 P1 核心功能，最后 P2P3 边边角角。时间不够砍后面的，不能砍前面的
- **边测边提单**：发现 bug 按规范提交（怎么写一条合格的 bug 单，见[缺陷报告怎么写](../bug-management/03-bug-report.md)），开发边修你边测，两线并行
- **留出探索时间**：用例之外，凭直觉和经验做些自由探索——用例是渔网，探索是下水摸鱼，漏网的 bug 常在这捞着

### 第 3 步：回归测试——改动的涟漪有多大

回归测试（Regression Testing）是新手最容易做拧的一步。先说清楚它回归的是什么：

> 开发修了一个 bug，或者加了一个功能，**代码改动像往水里扔石头，涟漪会扩散**。回归测的就是涟漪波及的范围——既确认"改的没问题"，也确认"没改的没被改坏"。

回归范围怎么定，是个技术活：

| 策略 | 测什么 | 什么时候用 |
| --- | --- | --- |
| 全量回归 | 所有用例重新跑一遍 | 版本末期最后一次、大改动、发版前 |
| 定向回归 | 改动模块 + 关联模块的用例 | 日常 bug 修复后的验证 |
| 冒烟级回归 | 只跑核心主流程用例 | 时间被压缩时的保底方案 |

实际项目里最常见的是**定向回归为主、末期一次全量（或自动化全量）**。怎么判断"关联模块"是哪些？看开发的代码改动范围、问开发改动影响面、参考历史经验——这三个信息源最好都过一遍。

### 第 4 步：上线验证——最后一道确认

版本发布到生产环境（或预发环境），测试还没下班：

- **发布后验证**：生产环境把核心主流程+本次新增功能真实走一遍
- **灰度观察**：如果走灰度发布，盯灰度批次的核心指标（报错率、订单量、崩溃率）
- **留观一段时间**：不是验证完立刻走人，重点盯发布后半小时到几小时的用户反馈和监控

线上验证发现严重问题，要有回滚预案——发布前和开发确认好"能不能回滚、怎么回滚、数据怎么办"。

## 举个例子

拿一个真实迭代走一遍：电商 App 改需求——**购物车加购数量上限从 99 调到 200**。

1. **提测准入**：提测单写明"改动了加购校验逻辑和购物车数量输入框，自测通过"。你确认测试环境包已更新
2. **冒烟**（约 40 分钟）：登录 → 搜索商品 → 加购 → 改数量 → 下单支付，主流程全通，冒烟通过
3. **功能测试**（2 天）：围绕本次改动铺用例——数量上限 200 的边界验证、输入框超限提示、购物车展示三位数、结算金额计算。期间发现一个 bug：数量输 201 时提示文案还是"最多购买 99 件"，提单
4. **回归**：bug 修复后，验证 201 提示正确（定向验证改动点）；同时回归关联模块——下单页数量展示、订单金额计算，确认没被改坏。版本末期跑一次购物车主流程全量
5. **上线验证**：发布后你在生产环境真实下一单，数量输 200，验证通过，同步看 10 分钟订单监控

四步走完，这个需求才算真正交付。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 一提测就闷头细测 | 冒烟没过就细测，版本打回全部白干。永远先冒烟 |
| 冒烟不过不好意思打回 | 打回是标准流程动作，不是针对开发。藏着掖着才会双输 |
| 回归 = 全部用例重跑一遍 | 全量回归是最笨也最贵的选择，日常应该科学裁剪范围 |
| 回归只测改过的那个功能 | 涟漪会扩散到关联模块，只测改动点等于没回归 |
| bug 修完验证通过就关单 | 验证通过还要看周边有没有被改坏，关单前补一圈定向回归 |
| 上线验证随便点点走形式 | 生产环境的验证是最后一道闸，主流程+新功能必须真实走 |

## 上手建议

1. **要一份提测单模板**：向团队要或自己整理一份，把"改了什么、影响什么、自测结论"变成固定字段，准入检查 30 秒完成
2. **冒烟用例单独建集**：把 20~50 条主流程用例打上"冒烟"标签，每次提测一键执行，别每次临时凑
3. **回归范围写进测试计划**：项目开始时就和开发约好"什么样的改动回归到什么范围"，别到回归时才临时拍脑袋
4. **让自动化接手回归**：回归是重复度最高的环节，手上有自动化能力后，第一个该自动化的就是它（怎么起步见[实战教程](../../knowledge/)）
5. **建一张流程卡**：把四步画成一张卡贴工位上，新项目头一个月照着走，形成肌肉记忆
