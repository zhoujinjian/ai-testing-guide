# 05｜DevOps 与 CI/CD：测试在流水线里干什么

> 核心要点：DevOps 是**开发、测试、运维拧成一股绳**的文化与实践，CI/CD 是它的流水线——代码一提交，**编译、单测、扫描、部署、自动化测试**自动接力跑完；测试的活从"人肉守门"升级成"把质量门禁装进流水线"。

## 打个比方

老式发布像**全家手洗碗**：开发把代码这只"碗"端过来，测试一个个摸过去（手工回归），摸完运维再手工上架（部署），谁失手打碎一只碗（线上事故），全家开会互相埋怨。碗越攒越多，洗碗的晚上越来越长。

装了**洗碗机**（CI/CD 流水线）以后：碗一放进水池（代码一提交），机器自动接力——预冲（编译打包）→ 主洗（单元测试）→ 高温消毒（代码扫描）→ 烘干（产出部署包）→ 自动归位（部署环境）。人只干两件事：**设定程序**（写流水线配置和门禁规则）和**处理机器报警**（失败用例的分流治理）。手洗碗没有消失——贵重的水晶杯（新功能的探索测试）还是得手洗——但日常碗盘全交给机器。

## 展开讲讲

### 先拆三个词

**DevOps** = Development + Operations，开发、测试、运维协作的一整套文化加实践，目标是"交付又快又稳"。**CI（持续集成）**：所有人频繁把代码合并到主干，每次合并自动构建加跑单测，几分钟内告诉你"这次合并有没有搞坏东西"。**CD** 有两层：持续交付（Continuous Delivery，随时产出可上线的部署包，上不上线人决定）和持续部署（Continuous Deployment，过了质量门禁自动上线）——一字之差，差在**要不要人按发布键**。

### 流水线长什么样

| 阶段 | 自动做什么 | 挂了会怎样 |
| --- | --- | --- |
| 提交/合并 | 开发 push 代码 | 触发流水线 |
| 编译构建 | 编译、打镜像 | 立即通知提交人 |
| 单元测试 | 自动跑全部单测 | 覆盖率或通过率不达标，红灯挡住 |
| 代码扫描 | 静态检查、安全漏洞扫描 | 高危问题拦截或告警 |
| 部署测试环境 | 自动部署到 test | 环境异常告警环境负责人 |
| 自动化测试 | 接口/冒烟自动化全量跑 | 卡点：失败不准进预发 |
| 人工验证 | 测试做新功能手工测试 | 全流水线唯一的人工环节 |
| 部署预发/生产 | 走发布流程 | 灰度加监控（见[发布上线](./12-release-process.md)） |

### 测试在流水线里干什么

**一，写门禁。** 门禁是流水线上的硬性关卡：单测覆盖率不低于 70%、接口自动化通过率不低于 98%、冒烟全绿才准部署预发。不到就红灯，谁也别想硬闯。它最大的价值是把"能不能上"**从人的争论变成机器的裁决**——门禁规则由测试主导制定，这是测试话语权最硬的来源。

**二，养自动化。** 流水线的火力全靠自动化用例支撑，接口自动化是主力军。用例设计方法不变，变的是执行方式：从人手点变成机器每轮全量跑（自动化起步可参考[实战教程](../../knowledge/)和[路线第 9 章](../../roadmap/09-quality-engineering.md)）。

**三，治理误报。** 流水线最怕"狼来了"——用例三天两头误报（不是 bug 却失败），大家就开始无视红灯。所以失败用例必须当天分流：脚本问题当天修脚本，环境问题当天报环境，真 bug 当天提单。用例不稳定、误报多是流水线的癌症，治理思路可以看[这道面试题](../../interview/testing-essentials/17-flaky-test-governance.md)。

**四，盯指标。** 流水线成功率、平均时长、失败原因分布——这些数字是测试开发的基本盘，也是你推动改进的证据。

## 举个例子

外卖订单服务，一个真实的下午：

- **14:14** 开发小王提交代码，流水线启动
- **14:16** 编译通过
- **14:19** 单测 486 个全部跑完，全绿，覆盖率 74%（门禁线 70%，过）
- **14:21** 安全扫描报一个中危依赖告警，不拦截，记录到待办
- **14:24** 自动部署到 test 环境
- **14:31** 接口自动化 1200 条跑完：1197 过、3 失败。门禁拦截，部署自动回退，流水线@小王
- **14:35** 测试小李对 3 条失败分流：2 条是小王改动影响的接口（转给开发确认），1 条是脚本依赖的测试数据过期（自己修脚本）
- **14:50** 小王修复代码、小李更新脚本，重新提交
- **15:07** 流水线全绿，test 环境部署成功，可以开始手工测试新功能

整个过程没有一个人肉指挥，小李唯一的动作是"分流"。对比手工时代——这套验证要开发打包、运维部署、测试手工回归，两小时起步还不保证每次都全量。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| CI/CD 是运维的事 | 质量门禁的规则要测试主导定，测试是流水线上质量关卡的 owner |
| 全自动化了就不需要手工测试 | 自动化守已知回归，新功能和探索性测试仍然是人的战场 |
| 流水线绿了 = 质量没问题 | 门禁只覆盖自动化范围，范围之外还是要人测 |
| 失败用例先注释掉再说 | 注释掉的用例是流失的覆盖，误报要修而不是逃 |
| 小团队玩不起流水线 | Jenkins、GitLab CI 等开源工具零成本起步，三五人的团队照样用 |
| 装了流水线就算 DevOps 了 | 工具只是壳，出了事故一起复盘而不是互相甩锅，才是 DevOps 的核 |

## 上手建议

1. **找到团队的流水线入口**（Jenkins、GitLab CI 或云效等），从头到尾看懂每个阶段在干什么
2. **问清接口自动化是怎么挂上流水线的**，能读到脚本就读，看不懂配置先记住触发时机
3. **统计一周内流水线的失败次数和原因**，做个三分类小账：代码问题、脚本问题、环境问题——你会立刻知道团队的最大堵点
4. **推动一条最小门禁**：冒烟自动化全绿才能部署预发，先跑起来再谈提高门槛
5. **读一读路线**[第 9 章 CI/CD 与质量平台](../../roadmap/09-quality-engineering.md)，对齐你要学的工具栈
