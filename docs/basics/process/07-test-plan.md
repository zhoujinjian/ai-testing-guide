# 07｜测试计划怎么写

> 核心要点：测试计划是**给整个团队对齐"测什么、谁来测、怎么算测完"的合同**，不是写给领导看的作文；一张骨架表十来个章节，其中**范围和准出标准是命根子**，必须量化到数字，一个字都不能含糊。

## 打个比方

写测试计划就是**做旅行攻略**。

五一去成都玩四天：去哪些景点（**范围**）、明确不去哪些——都江堰这次不去（**排除项**）、几个人怎么分工谁订票谁订房（**人力**）、几号到几号（**排期**）、住哪个区域出行方便（**环境**）、预算怎么分配（**资源**）、下雨了改室内还是改期（**风险应对**）、什么情况算这趟玩好了（**准出标准**）。

没有攻略的旅行，是到了成都现查地图，四天全耗在排队和赶路上；没有计划的测试，是提测了现想测什么，执行期全耗在来回问"这个测不测"。攻略不必写成书，但每一项都得有人认账——**计划的价值不在文档本身，在"所有人看过并同意"那一刻**。

## 展开讲讲

### 骨架表：十章节逐项讲

| 章节 | 写什么 | 写多细 |
| --- | --- | --- |
| 1 概述 | 项目背景、测试目的、术语解释 | 半页纸；术语只解释新人看不懂的 |
| 2 测试范围 | 本轮测哪些模块和需求；**明确写出不测什么** | 全文最重的一章：逐条列需求编号；不测的写清原因 |
| 3 测试依据 | PRD、设计文档、接口文档的链接和版本 | 落到链接加版本号，保证大家看的是同一版 |
| 4 人力与排期 | 谁负责哪个模块、每阶段起止日期 | 表格化：模块 × 人员 × 周期，精确到半天，留 20% 缓冲 |
| 5 环境与工具 | 用哪个环境、账号怎么来、工具清单 | 写清环境地址和数据准备的责任人 |
| 6 测试策略概要 | 测试类型组合、用例设计方法、优先级安排 | 一页以内：功能、接口自动化、兼容性各自的打法；技术细节放测试方案（见下一篇） |
| 7 准入准出标准 | 什么时候开始测、什么条件算测完 | **必须量化**：冒烟全过才开测；用例执行率 100%、P0P1 清零才放行 |
| 8 风险与应对 | 什么可能耽误进度、怎么办 | 每条风险配一个应对动作：造数复杂就提前两天启动 |
| 9 交付物 | 产出什么 | 用例文档、自动化脚本、测试报告的名称和存放位置 |
| 10 变更管理 | 需求变了流程怎么走 | 变更评审 → 评估影响 → 更新计划和用例，谁签字谁通知 |

国际上的 IEEE 829 等标准对测试文档有参考模板，现实项目里按团队习惯裁剪即可——**章节可以砍，范围和准出不能砍**。

### 写多细的分寸

**范围和准出**：越细越好，它们是将来"扯皮"时的依据。**排期人力**：精确到半天，粗到"下周开始"等于没法跟踪。**策略概述**：点到为止，展开是测试方案的事。**概述和术语**：能省则省，没人会读三页的项目背景。一页纸能讲清楚的计划，好过十页没人看的计划。

### 计划是活的

写完不是锁进抽屉：每周对照一次实际进度，偏差和新风险及时更新；遇到大变更（需求加塞、人力被抽走）要正式改版并重新知会团队——**悄悄漂移的计划等于作废**。计划评审会别省：拉上开发和产品过一遍，他们补的每一条（"这个模块改动会影响下单页"）都是你漏算的回归范围。

## 举个例子

电商 App「双 12 大促」版本的测试计划，填空实录：

- **范围**：本版本含 8 个需求（优惠券叠加、购物车改版、大促价展示等，编号 RD-2311-01~08）；**不测**客服系统（无改动）、不测 iOS 14 以下机型（占比 0.3%）
- **人力排期**：小周和小吴共 5 个工作日，小周负责券和购物车、小吴负责下单和支付，每人留 1 天缓冲
- **环境**：test-03 环境；大促价商品 200 个由小周提前 2 天造数（大促价配置复杂，是本计划最大的时间风险）
- **策略概要**：功能测试按模块铺开；券和下单的接口自动化同步补齐；Top10 机型兼容性专项
- **准出**：用例执行率 100%、通过率不低于 95%、P0P1 全清、P2 修复率不低于 90%、支付链路压测达标
- **风险**：两条——造数复杂（应对：提前启动，复用去年双 11 脚本）、提测可能延期（应对：P2P3 用例挪到回归期执行）

计划评审会上开发补了一条："购物车改版影响下单页传参，回归必须覆盖下单页。"——于是排期里多了半天的下单回归。这条如果没被补上，上线后下单页出问题，你说不清是谁的锅。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 计划是写给领导看的 | 第一读者是未来的自己和开发，它是对齐工具不是表功材料 |
| 范围写"全部功能" | 等于没写；明确"不测什么"比"测什么"更防扯皮 |
| 准出标准写"质量良好" | 不可量化的标准在发布前夜一文不值，必须写数字 |
| 计划定完就锁进抽屉 | 每周核对一次，漂移了不更新就等于作废 |
| 一个人闷头写完就交 | 要拉开发和产品评审，计划本身就是对齐的产物 |
| 篇幅越长越专业 | 十页以内讲清楚是本事，细节放附件 |

## 上手建议

1. **按十章骨架建一个空模板存好**，下个项目直接往里填，别每次从头排版
2. **拿手头正在进行的版本试填一遍**，填不出来的格子就是你该去问人的清单
3. **准出标准逐条自问"能不能拿数字证明"**，答不上来的改成数字
4. **找 leader 要一份历史项目的计划对照**，看你比当年的团队漏了什么
5. **计划写完提前 24 小时发出去**，评审会上收意见，而不是会上念稿
