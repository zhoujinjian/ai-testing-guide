# 12｜发布上线：灰度、放量与线上验证

> 核心要点：发布不是"按下部署按钮"的瞬间，而是**发布评审 → 灰度 → 放量 → 线上验证 → 监控观察**的一条链路；核心思想一个字：**稳**——问题越早暴露在越小的人群里，代价越小。

## 打个比方

一次发布像**一家新店开业**。

**内部试营业（白名单）**：员工和亲友先吃三天，后厨磨合流程、菜单试做，问题不外泄。**试营业（小比例）**：门口挂"试营业 8 折"，限流 100 桌——真实顾客进场，但规模可控，差评也来得及改。**正式开业（放量）**：客流逐步放开，前三天老板天天蹲在店里盯翻台率。**开业之后（监控观察）**：盯差评、盯投诉、盯回头率，出问题当天整改。

直接全量开业行不行？也行，就是赌——赌后厨没磨合好也不会崩。软件发布同理：新功能先给 60 个内部账号用，再放 1% 用户、10%、50%、100%，**每一批都盯着指标走，任何一批不对劲就停**。小锅试过再大锅开炒，翻车也只翻一口锅。

## 展开讲讲

### 发布前：评审与冻结

**发布评审**半小时到一小时，过四件事：准出结论最终确认（见[准入与准出](./11-entry-exit-criteria.md)）、发布顺序（先服务端后客户端？先数据库后应用？）、**回滚预案**（能不能回、怎么回、回滚了已产生的数据怎么办）、通知口径（客服和运营要提前拿到新功能说明，用户问起来不能一问三不知）。评审过了进入**代码冻结**：发布窗口前只修阻塞性问题，别让"顺手改个小东西"混上车。**发布窗口**选业务低峰——电商选凌晨一两点，还要避开大促和节假日。

### 灰度：分批放用户

| 批次 | 范围示例 | 盯什么 | 停留时长 |
| --- | --- | --- | --- |
| 白名单 | 内部账号 60~500 人 | 功能可用性、主流程通不通 | 半天到 1 天 |
| 小比例 | 1%~5% 用户 | 报错率、崩溃率、支付成功率 | 1 天 |
| 放量 | 10%~50% | 核心业务指标和大盘对比 | 1~2 天，必须覆盖一个业务高峰 |
| 全量 | 100% | 转入常规监控 | 转日常 |

灰度的判断标准一句话：**新版本的指标不劣于老版本**——报错率不升、下单转化不降、崩溃率持平。另外灰度维度按产品形态选：App 按渠道或应用商店分批，服务端按流量比例切，也可以按地区（先放一个城市）或按账号属性（先放会员）。

### 客户端和服务端，发布逻辑不同

**服务端发布**随时可做、随时可回滚（回滚就是重新部署上一个版本），所以灰度节奏可以快。**客户端（App）发布**要过应用商店审核，审核时长不受你控制，用户还要手动更新——回滚几乎不可能，只能"闭眼提审修复版"再等一轮。所以 App 发布的灰度靠**渠道分批**：先放一个应用市场或先放安卓再放 iOS，用小渠道当灰度批次。这也是为什么 App 的发布前测试要压得更狠：**上线后的纠错成本，客户端比服务端高一个量级**。

### 线上验证：测试的最后一场

发布完成不等于测试下班。三件事：**主流程真实走**——真实下单、真实支付（小额）、真实退款，每条核心链路过一遍；**新功能专项**——本版本改动的功能逐条点；**盯监控**——发布后半小时到几小时是事故高发期，盯错误率、订单量、崩溃率，还有客服群的用户反馈。

### 回滚：最后的保险

发布前必须确认回滚方案：回滚脚本演练过没有、执行要几秒、**回滚后已产生的数据兼容吗**（新版本写入的数据老版本读不读得动）。最难的是**预授权**：提前写明触发条件——"报错率超过 1%、支付成功率跌破 95%，值班人直接回滚，不用请示"。等汇报、拉群、开会一圈走完，事故早就扩大三倍了。

## 举个例子

外卖 App「支付页改版」的灰度实录：

- **周四 16:00 发布评审**：确认回滚脚本 5 秒生效、本次数据库改动向后兼容（老版本读新数据不炸）、客服话术已同步。窗口定在**周五 01:00**
- **01:00 白名单**：产品、测试、开发共 60 人真实下单。你（测试）发现"银行卡图标在旧机型上错位"——P3，记录不拦截
- **02:00 放 1%**：监控 1 小时，支付成功率 98.7%（大盘 98.9%），持平
- **周五白天 10%**：**特意压着午高峰放**——灰度最该验的就是高峰。12:00~13:00 支付成功率 98.8%，崩溃率 0.02%，无异常
- **周日 50%**：晚高峰盯 2 小时，指标持平
- **周二 全量**：转入常规监控
- **周三 复盘**：P3 图标问题排进下版本；灰度期间客诉 0 起

对照组是同城竞品：新版本**全量直发**，支付网关一个配置错误导致 40 分钟无法支付，客诉冲上同城热搜，相关负责人连夜写事故报告。同一个错误，在 1% 灰度里暴露，代价是几百个用户半小时；在全量里暴露，代价是全城用户四十分钟加一条热搜——**这就是灰度的价格差**。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 发布是运维和开发的事 | 线上验证是测试的收官动作，主流程必须真实走一遍 |
| 灰度是浪费时间 | 每多一批就多一次拦截机会，版本越大越要灰 |
| 灰度只看有没有报错 | 业务指标（转化率、支付成功率）和报错率同样重要 |
| 出问题先开会讨论 | 重大指标恶化按预授权直接回滚，复盘留给事后 |
| 回滚了就万事大吉 | 回滚也有代价（数据兼容、二次发布），预案要提前演练 |
| 发布完当天就下班 | 发布后几小时是事故高发期，留观是职业底线 |

## 上手建议

1. **找到团队的发布 checklist 通读一遍**，逐项问自己"这项为什么存在"——多半都对应一次历史事故
2. **争取参与一次发布值班**：盯哪些指标、告警群怎么响应、谁有权拍板回滚，走一遍全懂
3. **建自己的线上验证清单**：核心主流程 10 条 + 本次改动功能逐条，发布当天照单执行
4. **问清回滚预授权条件**：什么指标恶化可以直接回、回滚找谁执行——发布前就该知道答案
5. **找一份公开的线上事故复盘读一遍**（各大厂都发过），看灰度或回滚哪一环缺失、代价多大
