# 04｜用例评审：评什么、怎么评

> 核心要点：用例评审是**在执行之前**把设计缺陷暴露出来的关卡——漏测的场景、想当然的预期、互相矛盾的规则，改一行字的成本远低于上线后改一个事故。评的是**设计本身**，不是给写用例的人打分。

## 打个比方

把用例评审想象成**烹饪比赛里的试菜**。

大厨做完一道菜直接上桌，客人吃了不满意，整桌退菜；上桌前先让主厨、帮厨、老板各尝一口——咸了加水、淡了补盐、摆盘歪了重摆——**花五分钟，救一桌菜**。

评审就是用例的试菜环节。你自己写的时候是"厨子视角"，一切 obvious（理所当然）；别人看是"食客视角"，一眼看出"这道菜没放盐"（缺负向场景）。**写用例的人最不可能发现自己漏了什么，因为他要是想到了，早就写上了**——这不是能力问题，是视角盲区的必然，所以才需要第二双眼睛。

## 展开讲讲

### 评审前：准备做足，会才开得短

评审会效率低，九成是准备不足：

- **提前 1~2 天发材料**：用例文档 + 需求文档（PRD）链接，别指望会上现读
- **圈定参会人**：产品（讲需求预期）、开发（讲实现约束）、其他测试（挑设计盲区）、有条件拉上运营或客服（讲用户真实行为）
- **自己先过一遍自查清单**：把低级错误（错别字、编号断档）提前消灭，别浪费别人的会议时间

### 评审中：按清单逐项过，别信马由缰

会上容易跑偏成闲聊或互相挑格式毛病，拿这六项清单兜住主线：

| 检查项 | 问的问题 | 主要靠谁 |
| --- | --- | --- |
| **正确性** | 用例和需求规则对得上吗？预期结果和 PRD 一致吗？ | 产品 |
| **覆盖度** | 正向、负向、边界、异常场景都有吗？功能之间交互测了吗？ | 测试同行 |
| **可执行性** | 换个人能照着执行吗？前置条件成立吗？ | 测试同行 |
| **优先级** | P0 定得准吗？和核心链路匹配吗？ | 测试 + 产品 |
| **可实现性** | 用例假设的环境、数据、权限，现在做得到吗？ | 开发 |
| **冗余度** | 有没有两条用例在测同一件事？ | 写用例的人自己 |

覆盖度是最核心也最难的一项，靠"大家觉得还有什么场景没覆盖"的自由讨论效率很低——成熟的团队会按方法清单来扫（等价类、边界值、判定表……本系列第 14 篇的方法选型指南就是干这个用的），逐方法过一遍，漏的场景自己跳出来。

### 评审后：纪要与闭环

会上吵得再热闹，没有纪要等于白开。会后要做三件事：

1. **会议纪要当天发出**：改哪些用例、谁负责、什么时候改完
2. **按纪要修改用例**：改完在群里同步"已按评审意见更新"，附文档链接
3. **有分歧的项挂账跟踪**：需求本身有歧义的（比如"数量超限时怎么处理"PRD 没写），单独列成"需求确认项"，催产品给结论，别让它烂在用例里

### 评审其实有三层

按介入时机从早到晚，价值递减、成本递增：

- **需求评审阶段**（最早）：测的其实不是用例，是需求本身——歧义、遗漏、逻辑冲突，这时候发现，改的是一行 PRD
- **用例设计评审**（本文主角）：发现设计缺陷，改的是用例，成本是几分钟
- **执行后复盘**（最晚）：漏测 bug 出来了，回头补用例——这是亡羊补牢，价值在于把教训固化成用例，下不为例

## 举个例子

外卖平台新需求：**下单页新增"准时宝"服务，超时 15 分钟自动赔付 5 元红包**。测试小周写完 23 条用例发起评审。

会上被挑出的问题长这样：

| 评审发现 | 问题类型 | 怎么改 |
| --- | --- | --- |
| 只测了"开了准时宝超时"，没测"用户主动关闭准时宝后超时" | 覆盖度缺口 | 补用例：关闭服务后超时不触发赔付 |
| 预期写"赔付 5 元"，但 PRD 写的是"赔付 5 元无门槛红包，有效期 7 天" | 预期不精确 | 预期改为完整规则，含有效期和门槛 |
| 有一条用例要求"骑手位置停在 3 公里外 30 分钟" | 可实现性不足 | 开发确认无法模拟骑手轨迹，改为用测试后门直接改预计送达时间 |
| 两条用例都在验证"超时后订单状态变为已送达" | 冗余 | 删一条 |
| 没人提"赔付红包能不能叠加同单已有的优惠券" | 需求歧义 | 挂账：找产品确认，PRD 补充"可叠加" |

散会后小周做的第一件事不是改用例，是把"需求歧义"那条单独拉群 @ 产品——**评审挖出需求本身的问题，才是收益最大的时刻**，这一条如果带上线，就是一个客诉工单。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 评审是领导检查我，得防着点 | 评审评的是用例不是人，被挑出问题是收获，被上线事故挑出问题才是耻辱 |
| 会上临时现场读用例 | 等于把准备工作搬进会议室烧大家的时间，下次没人来 |
| 只叫测试同事来评 | 没有产品就没人裁决"预期对不对"，没有开发就没人发现"环境做不到" |
| 挑错别字和格式挑了一小时 | 格式问题自查解决，评审时间要花在**场景和预期**这种高价值区 |
| 评审完就完，纪要不发、用例不改 | 会上达成的共识没有落到文档里，两周后各记各的，等于没评 |
| 用例评审一次管半年 | 每个大需求都该有自己的评审，需求变了用例变了就要再碰 |

## 上手建议

1. **要一份你们团队的评审 checklist**：没有就自己按"六项检查"建一份，每次评审前自查一遍，你会是会上被挑出问题最少的人
2. **给每个需求都发评审邀请，哪怕 15 分钟**：小需求拉产品线上快速过 15 分钟，好过事后漏测开复盘会一小时
3. **被问住时记下来，别当场硬撑**："这条我没想到，会后补"是评审里最专业的回答，比现编一个理由体面得多
4. **把每次漏测 bug 反向塞进评审清单**：出过的事故，问一句"当时评审为什么没拦住"，答案就是清单的新条目
5. **轮流主持评审**：主持人和记录员轮着当，半年后你对"什么是好评审"的理解会甩同侪一条街
