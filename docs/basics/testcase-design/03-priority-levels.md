# 03｜用例优先级 P0~P3 怎么划分

> 核心要点：优先级回答的是**时间不够时先跑谁、砍谁**的问题。P0 是"挂了就没法用"的保命用例，P3 是"坏了也不致命"的长尾——定级的依据是**用户和业务的受损程度**，不是你对这个功能的喜爱程度。

## 打个比方

把一个版本的测试想象成**医院急诊分诊**。

急诊室门口的护士不会按挂号顺序看病，而是按**病情轻重**分诊：心梗的进抢救室（P0），骨折的优先处理（P1），慢性疼痛的排队等着（P2），来开体检报告的可以约明天（P3）。医生不够时，先救最重的——**不是排队的不重要，是此刻救谁收益最大**。

测试同理。版本快上线，时间只够跑 40% 的用例，你跑哪 40%？跑 P3 的文案错别字而放过 P0 的支付流程，就像急诊室先给健康人量血压——忙碌了一天，最该救的没救。

## 展开讲讲

### 四档的判据

P0 到 P3 的叫法各公司略有出入（有的用高/中/低三档），判据是一致的：

| 优先级 | 一句话判据 | 典型例子 | 执行策略 |
| --- | --- | --- | --- |
| **P0** | 主干流程，挂了核心业务直接停摆 | 登录、下单、支付、发消息、核心搜索 | 每次提测必跑，自动化首选对象 |
| **P1** | 重要功能，坏了对主流程有影响但能绕 | 优惠券使用、收货地址管理、订单列表筛选 | 每轮功能测试覆盖，回归必含 |
| **P2** | 次要功能，坏了体验差但业务能走 | 个人资料编辑、消息推送设置、分享文案 | 时间正常就跑，时间紧可后置 |
| **P3** | 边角体验，极端场景或锦上添花 | 页面文案、极小概率的兼容组合、埋点统计 | 抽测或版本末期补测 |

定级时问自己两个问题：**这条挂了，用户还能不能完成核心目的？**（不能 → 至少 P0）；**这条挂了，多少用户会撞上？**（全量用户 → 升一档）。

### 定级最常见的三个依据来源

1. **需求本身分层**：PRD 里的核心故事（Story）对应的功能是 P0 候选，"异常说明""备注"里的规则一般是 P2
2. **用户路径数据**：埋点数据显示 90% 用户从搜索进入、只有 2% 用筛选器——筛选器的用例天然比搜索低一档
3. **历史故障史**：这个模块过去出过线上事故（比如重复扣款），它的用例整体上调一档，这是用脚投票换来的教训

### 优先级和严重程度不是一回事

新手最爱混这两个词，它们一个属于用例、一个属于缺陷，方向恰好相反：

| 对比项 | 用例优先级（P0~P3） | 缺陷严重程度（Fatal/严重/一般/轻微） |
| --- | --- | --- |
| 描述对象 | 测试用例（还没执行的东西） | 缺陷（已经发生的东西） |
| 回答的问题 | 测试时间有限，先测谁 | 出了问题，伤害有多大 |
| 决定谁 | 测试自己定，评审时校准 | 测试初判，和产品/开发对齐 |

同一条 P0 用例能跑出一个轻微缺陷（文案错误），一条 P3 用例也可能挖出致命缺陷（某个罕见操作触发崩溃）——**用例的优先级不预示它找到的 bug 的严重程度**，它只管"先跑谁"。

### 优先级是动态的

用例库不是刻完碑就完了：

- **大促前**：营销活动的用例整体上调，个人中心的 P1 可能降到 P2
- **某个模块刚出过事故**：它的用例临时升档，稳定两三个版本后再降回
- **新功能刚上线**：首批用例按高半档对待，跑顺两个迭代后回归原级

## 举个例子

电商 App 的"购物车"模块，同一批用例按上面的判据分档：

| 用例 | 优先级 | 定级理由 |
| --- | --- | --- |
| 加购成功，购物车数量 +1 | P0 | 加购是下单链路第一环，断了就没法买 |
| 修改数量 199/200/201 边界校验 | P1 | 校验失效会算错钱，但有前端兜底且非每次必现 |
| 勾选部分商品分开结算金额正确 | P1 | 影响下单金额准确性，用户高频使用 |
| 删除商品后"猜你喜欢"推荐刷新 | P2 | 推荐体验问题，不挡下单 |
| 购物车为空时的插画和文案展示 | P3 | 纯展示，坏了不影响任何功能 |
| 划掉商品左滑删除的触感反馈 | P3 | 锦上添花的交互细节 |

时间被压到只剩一天时，你的执行顺序就是从上往下：P0 全跑、P1 全跑，P2 抽一半，P3 基本放弃——并且在测试报告里写明"P2P3 未覆盖，风险自担"，让砍时间的人知道代价。**这句话必须写**，它是测试的保护动作，不是甩锅。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 全部标 P0，显得都重要 | 等于没有优先级。时间紧张时照样无从下手，定级失去意义 |
| 按模块定级，"登录模块都是 P0" | 模块里也有边角，"忘记密码页的文案"和"登录本身"不是一个量级，要逐条定 |
| 定级拍脑袋，不看数据 | 埋点、客诉、故障史都是现成依据，用了才有说服力 |
| 优先级定完永不调整 | 大促、事故、功能下线都会改变风险分布，季度校准一次不嫌多 |
| 拿用例优先级当 bug 严重程度用 | 一个管"先测谁"，一个管"伤害多大"，汇报时混用会被开发当场抓住 |
| 低优先级用例永远不跑 | P3 攒三个版本集中补测一轮，别让长尾区彻底失守 |

## 上手建议

1. **先给手头项目的用例全部打上 P 标**：没有优先级的存量用例库这周就补，先粗标后精调，两小时能干完一个中型模块
2. **拉着产品对一遍 P0 清单**：你定的 P0 和产品心里的核心链路对不齐很常见，对齐后它就是你们共同的契约
3. **把 P0 单独建成执行集**：测试平台里打个"冒烟/P0"标签，提测当天一键执行，这是[测试执行全流程](../process/10-test-execution-flow.md)里冒烟阶段的弹药库
4. **记录定级理由**：每条 P0 旁边写一句"为什么是 P0"，三个月后你忘了当初的判断依据时，它会救你
5. **拿历史线上事故反查定级**：翻去年的线上故障单，看当时漏测的用例现在是什么优先级——标低了就升，这是最诚实的校准
