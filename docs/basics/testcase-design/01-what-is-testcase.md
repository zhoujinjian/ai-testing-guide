# 01｜什么是测试用例：要素、格式与示例

> 核心要点：测试用例就是一份**提前写好的操作剧本**——在什么条件下、做什么操作、系统应该给出什么反应。它把"随手点点点"变成"可执行、可重复、可盘点"的正规军动作。

## 打个比方

把测试想象成**考试阅卷**。

如果阅卷老师拿到一张卷子，脑子里想"我就随便看看这题对不对"，那打出来的分数每次都不一样，谁也不服。所以学校会给老师一份**评分标准**：第几题、答案是什么、答到哪一步给几分、写错别字扣不扣分。换任何一个老师来，照着标准走，分数都一样。

测试用例就是测试这份工作的**评分标准**。没有它，你今天测登录想到什么点什么，明天心情不一样点的顺序也不一样，测没测全自己都说不清；有了它，你和同事能对出同一份答卷——**哪些测过了、哪些没测、哪些失败了，一目了然**。

## 展开讲讲

### 一条用例的八个要素

不同公司用的模板略有差别，但拆到底都是这八样东西：

| 要素 | 它回答的问题 | 写法示例 |
| --- | --- | --- |
| **用例编号** | 这条是谁、怎么找到它 | `REG-001`（模块缩写 + 序号） |
| **所属模块** | 归哪个功能管 | 注册模块 |
| **用例标题** | 一句话说清测什么 | 6 位用户名注册成功 |
| **前置条件** | 开测之前世界长什么样 | 未注册账号可用的手机号 |
| **操作步骤** | 一步步做什么 | 1. 打开注册页 2. 输入 6 位用户名…… |
| **输入数据** | 喂给系统什么值 | 用户名 `abcdef`，密码 `Abc12345` |
| **预期结果** | 系统应该怎么反应 | 注册成功，跳转首页，数据库新增一条用户记录 |
| **优先级** | 这条有多重要 | P0（怎么划分见本系列第 3 篇） |

新手最看不上"前置条件"和"预期结果"，觉得啰嗦——恰恰是这两样在撑用例的价值：**没有前置条件，别人复现不了你的场景；没有预期结果，测出的"失败"到底是不是 bug 都吵不清**（开发问"你觉得应该是什么样"，你答不上来，单子就提不出去）。

### 用例的三种常见载体

- **Excel / 在线表格**：小团队最常见，上手零成本，缺点是关联关系弱、版本容易乱
- **测试管理平台**：禅道、TAPD、TestRail 这类，用例、执行记录、bug 单互相挂钩，团队协作首选
- **代码化用例**：自动化测试脚本本质上也是用例，只是"操作步骤"变成了代码、"预期结果"变成了断言

载体不重要，**要素齐才是硬道理**。面试官问"什么是测试用例"，答出"一组包含前置条件、操作步骤、输入数据和预期结果的测试输入与执行说明"就已经及格，再补一句"它是测试执行的依据，也是度量覆盖率的基础"就漂亮了。

### 用例和测试点的关系

很多新人把这两个词混着用。**测试点**是"要验证什么"的一句话念头，比如"验证密码输错 5 次锁定账号"；**用例**是把念头落成可执行剧本后的完整记录。一个测试点至少对应一条用例，复杂的测试点可能拆出好几条。设计用例的过程，就是把需求拆成测试点、再把测试点写成用例的两级放大——怎么拆，本系列第 5 篇会完整演练。

## 举个例子

需求：电商 App 注册页，**用户名 6~18 位、只允许字母数字，密码 8~16 位且必须同时含字母和数字**。

把其中"用户名校验"这个测试点写成用例，一条合格的成品长这样：

| 字段 | 内容 |
| --- | --- |
| 用例编号 | REG-001 |
| 用例标题 | 输入 6 位纯字母用户名，注册成功 |
| 优先级 | P0 |
| 前置条件 | 手机号 13800001111 未注册，可正常接收验证码 |
| 操作步骤 | 1. 打开注册页；2. 用户名输入 `abcdef`；3. 密码输入 `Abc12345`；4. 输入正确验证码；5. 点击"注册"按钮 |
| 输入数据 | 用户名 `abcdef`，密码 `Abc12345`，验证码正确 |
| 预期结果 | 注册成功，跳转到首页并自动登录，数据库 users 表新增一条记录，username 字段值为 `abcdef` |

注意三个细节：标题里直接写了 **6 位、纯字母**，而不是"输入合法用户名"——翻表格的人不看步骤就知道这条在测什么；预期结果写到了**数据库**，不只写"注册成功"四个字，界面成功但落库字段错了，也是 bug；验证码写"正确"而不是随手填，**前置条件和输入里不能埋不确定因素**，否则用例换个环境就跑不通。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 没有用例，拿到版本直接点 | 点完说不清测了什么、漏了什么，版本质量全凭感觉，出了漏测责任说不清 |
| 步骤写成"输入用户名密码，点注册" | 输入什么值都没写，别人执行时只能猜，预期结果也对不上号 |
| 预期结果只写"成功"或"失败" | 成功长什么样（跳转？提示？落库？）、失败提示什么文案，都要写清 |
| 用例写得一次比一次细，最后像写小说 | 用例是给执行者看的剧本，写到**换个人也能执行出同样结果**就够了 |
| 一条用例塞五六个检查点 | 一个检查点失败，后面的全执行不下去，用例挂了也说不清挂在哪。一况一条 |
| 写完用例从不更新 | 需求改了用例还躺在那儿，执行时才发现在测一个不存在的世界 |

## 上手建议

1. **找你们团队的用例模板**：入职第一周就问导师要团队现成的用例模板和一条历史用例，格式跟着团队走，别自创
2. **拿注册页练手**：找个你天天用的 App 注册页，按八要素写 20 条用例，写完对照本系列第 15 篇的登录用例查漏
3. **预期结果写"看得见摸得着"的**：界面文案、跳转页面、数据库记录、接口返回码——能验证的才叫预期，"体验流畅"这种不算
4. **编号规则定好再动笔**：模块缩写 + 三位序号（如 `LOGIN-001`），插入新用例插在尾号段，别中途重排打乱别人的引用
5. **每条用例自己先跑一遍**：写完的用例自己在测试环境过一遍，前置条件不成立、步骤走不通的，当场修——没跑过的用例只是草稿
