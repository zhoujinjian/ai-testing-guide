# 14｜方法选型指南：什么需求用什么方法

> 核心要点：方法没有高低，只有**对口不对口**——选型的唯一依据是**需求的形状**：有范围找边界值、有组合找判定表、有流程找场景法、有状态找迁移表。本文这张总表，就是你的对号入座速查卡。

## 打个比方

把方法选型想象成**五金工具墙上挑扳手**。

墙上一排扳手：活动扳手、套筒扳手、扭力扳手、内六角。老师傅拧一个螺丝前，先看**螺丝的形状**——外六角上套筒、精密件上扭力、异形件上活动扳手。新手不看螺丝抡起最大的那个就上，结果拧花了螺丝口还怪扳手不好使。

**七个设计方法就是那面工具墙**。没有一个方法能包打天下，也没有"最高级"的方法——只有"这个需求长什么样、该拿哪把"。面试官最爱问"给你一个 XX 你怎么测"，考的其实就是你**扫一眼需求形状就能摸到对工具**的能力。

## 展开讲讲

### 总表：需求特征 → 首选 → 辅助

| 需求特征（看到这些词/形状） | 首选方法 | 辅助方法 | 典型需求 |
| --- | --- | --- | --- |
| 有取值范围（长度、金额、次数、天数） | **等价类** | 边界值 | 密码 8~16 位、满 199 减 30 |
| 边界明确（刚好、差一点的位置） | **边界值** | 等价类 | 数量上限 200、有效期 3 天 |
| 多条件组合决定结果（且/或/同时满足） | **判定表** | 因果图 | 三条件都满足才发券 |
| 条件间有约束（互斥、要求、屏蔽） | **因果图** | 判定表 | 选了 A 禁止选 B |
| 因素多、组合爆炸（多机型/多浏览器） | **正交实验法** | 错误推测 | 5 机型 × 4 版本兼容矩阵 |
| 有操作流程（步骤一环扣一环） | **场景法** | 状态迁移 | 下单、退款、注册流 |
| 对象有状态流转（状态会变身） | **状态迁移法** | 场景法 | 订单、审批单、优惠券 |
| 老模块、有历史 bug 沉淀 | **错误推测法** | 全部 | 购物车改版、支付重构 |
| 纯展示型（文案、样式、布局） | 无固定方法，用 UI 检查清单 | 错误推测 | 活动页、空状态插画 |

### 选型三步口诀

1. **扫形状**：通读需求，标记每段文字的形状——数字范围？条件组合？操作步骤？状态变化？
2. **对总表**：每种形状对号入座，选出首选方法；一个大需求往往有**好几种形状混着**，那就几种方法各上一段
3. **补一刀**：所有系统方法铺完后，拿[错误推测法](./13-error-guessing.md)的雷区清单扫一遍做补刀

### 一个需求通常不止一个方法

新手常见错觉是"一个需求选一个方法"。真实需求是混合形状的：一个下单需求里——金额满减是范围（边界值）、券叠加规则是组合（判定表）、下单流程是路径（场景法）、订单变更是状态机（状态迁移法）。**方法跟着需求形状走，一个需求混三四个方法太正常了**。

### 别忘了方法之外的通用件

无论什么方法都绕不开的**横切检查**，选完方法后统一补：

- **兼容性**：这功能在不同浏览器/机型/系统上表现一致吗（因素多时上[正交](./10-orthogonal-array.md)）
- **安全**：输入能注入吗、越权能操作别人的订单吗、明文传密码了吗
- **易用性**：错误提示人看得懂吗、操作步骤能不能更少
- **网络**：弱网、断网、网速抖动时体面吗
- **数据一致性**：界面显示的和库里存的一致吗（尤其[场景法](./11-scenario-method.md)和[状态迁移](./12-state-transition.md)的终态）

## 举个例子

四个真实需求片段，演示对号入座：

**片段一**：「会员积分商城，500 积分起兑，单次最多兑 3000 积分。」
形状：取值范围。首选**等价类**（有效：500~3000；无效：不足 500、超 3000、非数字、空值），辅助**边界值**（499、500、501、2999、3000、3001 六个值钉死切口）。

**片段二**：「开启"到货通知"需同时满足：商品已入库、用户已收藏、通知开关打开，三者缺一不可。」
形状：三条件组合。首选**判定表**——2 的 3 次方 = 8 列铺开再合并成 3 条规则（全满足/缺任一/开关关）；条件之间还藏着约束（未收藏的用户看不到开关），值得再画一张**因果图**把"要求"关系标出来。

**片段三**：「用户在订单列表可对'已发货'订单申请退货，退货审核通过后退款，退款到账订单关闭。」
形状：状态流转 + 流程。首选**状态迁移法**（状态：已发货→退货中→退款中→已关闭；把"已发货订单直接申请退款"这类非法迁移标红），辅助**场景法**（用户路径：申请退货→填原因→审核通过→退款到账，再挂"审核驳回"备选流）。

**片段四**：「直播间点赞动画，需覆盖 8 款主流机型 × 2 档系统 × 3 种网络环境。」
形状：组合爆炸（8×2×3=48 种）。首选**正交实验法**挑出十几行均匀组合，辅助**错误推测法**（低端机 + 弱网 + 高频连点这个"三差"极值组合人肉必测）。

四个片段，四种形状，四套组合——**没有一个需求需要你"从头到尾只用一招"**。把总表贴在手边，练习两三个迭代，选型会变成下意识动作。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 迷信"高级"方法，什么需求都上正交/因果图 | 方法对口才值钱，单一输入框上正交表是杀鸡用牛刀还切不干净 |
| 一个需求从头到尾只用一个方法 | 需求是混合形状的，金额段用边界值、流程段用场景法，各管各的 |
| 方法选完就完，不做横切检查 | 兼容、安全、弱网、数据一致性是所有方法的公约数，漏了照样漏测 |
| 正向用例铺满，负向靠猜 | 负向场景藏在每个方法的"无效类/拒绝格/备选流"里，选了方法就要走完该方法的负向侧 |
| 面试时背方法名却不会对号入座 | 考官问"怎么测 XX"时，正确姿势是先说形状再说方法："这里有范围，我上边界值；这里是流程，我铺场景" |
| 照搬别的项目的用例不重新选型 | 同名功能在不同项目需求形状不同（这里的购物车有拼团状态，那边的没有），方法要跟着本需求重选 |

## 上手建议

1. **把总表打印贴在工位**：至少贴一个月，每个需求设计前扫一眼，形成"先看形状再伸手"的习惯
2. **做一次"形状标注"练习**：拿你们项目最近的一个大需求，通读一遍只做一件事——把每段标成范围/组合/流程/状态/组合爆炸，标完对着总表选方法
3. **用例里标注所用方法**：每条用例加一列"设计方法"，评审时同事能直接看出你的方法覆盖，也是面试讲方法论的好素材
4. **错题本升级成"形状-方法"错题本**：每次漏测记一笔"当时需求是什么形状、我该用什么方法没用到"，比记 bug 本身更能涨选型能力
5. **拿[经典实战篇](./15-classic-pages.md)自测**：登录、搜索、购物车三个经典页面，先自己写方法组合，再对照那篇的打法找差距
