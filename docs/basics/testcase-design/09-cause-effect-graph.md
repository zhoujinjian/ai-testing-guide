# 09｜因果图法：给条件关系画出电路图

> 核心要点：当条件之间不只是简单组合，还有**互斥（有他没我）、要求（有他必须有他）、屏蔽（有他禁止有他）**这类关系时，先用因果图把关系画出来，再机械地翻译成判定表——**图管关系，表管组合**，两步合起来才不漏。

## 打个比方

把因果图想象成**门禁保安脑子里的访问规则图**。

公司门禁不是一个简单的"刷卡就进"：工卡有效则放行；访客必须先登记才发访客证——**登记是访客进入的"要求"**；消防通道钥匙刷了就锁死正门——**两种进入方式互斥**；黑名单里的人，任何证都无效——**屏蔽掉其他所有条件**。

保安脑子里的这张关系图，画在纸上就是因果图：**左边原因（刷卡、登记、黑名单），右边结果（放行、拒绝、报警），中间连线写着关系符号**。规则一多，人脑就开始"想当然地简化"，图不会——它把每条关系都摆在明面上，谁跟谁冲突一眼看见。

## 展开讲讲

### 基本符号：恒等、非、或、与

原因和结果之间的连线只有四种基本关系，跟电路图一个道理：

| 符号含义 | 人话 | 例子 |
| --- | --- | --- |
| **恒等** | 原因出现，结果就出现 | 输入了正确验证码 → 通过校验 |
| **非** | 原因出现，结果就不出现 | 账号已注销 → 无法登录 |
| **或** | 多个原因任一出现，结果就出现 | 手机号或邮箱任一注册过 → 提示"账号已存在" |
| **与** | 多个原因同时出现，结果才出现 | 密码正确**且**未锁定 → 登录成功 |

### 约束符号：关系图里真正值钱的部分

光有四种连线还不用专门学，因果图的杀手锏是**约束**——需求文字里最容易被吞掉的逻辑关系：

| 约束 | 管的是 | 例子 |
| --- | --- | --- |
| **E（互斥）** | 两个原因不能同时为真 | "微信登录"和"手机号登录"不能同时勾选 |
| **I（包含）** | 多个原因至少一个为真 | 查询条件：按订单号、按手机号、按日期，至少选一个才查 |
| **O（唯一）** | 有且仅有一个原因为真 | 三种支付方式只能选一种 |
| **R（要求）** | 一个为真，另一个必须为真 | 勾选"开具发票"就必须填抬头 |
| **M（屏蔽）** | 一个为真，另一个禁止为真 | 选"包邮"就禁止再选"运费险" |

**为什么这些符号值钱**：判定表裸铺组合时，"互斥"的两列是根本不存在的组合（微信 + 手机号同时登录），不标出来你就会写出永远执行不了的用例；反过来"要求"的列里藏着隐性规则（勾发票没填抬头的拦截提示），不画出来就漏测。

### 标准走法：因果图 → 判定表 → 用例

因果图法很少直接产出用例，它是一个**前置加工工序**：

1. 从需求里列出所有**原因**（输入/条件）和**结果**（输出/动作）
2. 画图：用四种连线连因果，用约束符号标注关系
3. 把图翻译成判定表（约束直接决定哪些组合列该删、哪些列必须补）
4. 按判定表每列写用例

和[判定表法](./08-decision-table.md)的关系一句话说清：**判定表是成品图纸，因果图是画图时的思考草稿**——条件少关系简单（就"与/或"）直接上判定表；条件之间有互斥、要求、屏蔽这类约束，先画图再转表。图和[等价类](./06-equivalence-class.md)的配合也顺：原因自身取值的有效无效先切类，图的节点上直接写"有效/无效"，一举两得。

## 举个例子

需求：网盘文件上传功能。

> C1 上传的是单个文件；C2 文件大小 ≤ 500MB；C3 文件类型属于白名单（doc/pdf/zip/jpg）；C4 用户会员未过期。
> 结果：E1 上传成功；E2 提示"文件类型不允许"；E3 提示"超过单文件大小上限"；E4 提示"请开通会员"。
> 另有约束：单文件和文件夹上传入口互斥；选了"上传文件夹"（C5）时禁止同时选"单文件"（E/M 约束）。

**第一步，把关系画成图**（文字版因果图）：

- C2、C3、C4 与 E1：**与**关系（三个都满足才成功）
- C3 为假 → E2；C2 为假 → E3；C4 为假 → E4
- C1 与 C5：**互斥**（两个入口只能走一个）

**第二步，按图铺判定表**（C5 与 C1 互斥，删掉两者同真的组合；C2/C3/C4 的组合按"哪个先拦"整理成优先级列）：

| 组合 | C1 单文件 | C2 ≤500MB | C3 白名单 | C4 会员 | 结果 |
| --- | --- | --- | --- | --- | --- |
| 1 | Y | Y | Y | Y | E1 上传成功 |
| 2 | Y | Y | N | Y | E2 提示"文件类型不允许"，列表无变化 |
| 3 | Y | N | Y | Y | E3 提示"超过单文件大小上限 500MB" |
| 4 | Y | Y | Y | N | E4 提示"请开通会员"，弹出会员购买页 |
| 5 | N（走文件夹入口） | — | — | — | 走文件夹上传逻辑，另测 |

**第三步，翻译成用例**（节选）：

| 用例 | 输入 | 对应组合 | 预期结果 | 优先级 |
| --- | --- | --- | --- | --- |
| 01 | 上传 `测试报告.pdf`，120MB，会员有效 | 1 | 进度条走完，列表新增该文件，大小显示 120MB | P0 |
| 02 | 上传 `工具.exe`，100MB，会员有效 | 2 | 弹红色提示"文件类型不允许"，列表无新增 | P0 |
| 03 | 上传 `设计稿.zip`，501MB，会员有效 | 3 | 弹提示"超过单文件大小上限 500MB"，上传中断 | P1 |
| 04 | 上传 `合同.doc`，10MB，会员已过期 | 4 | 弹提示"请开通会员"并跳转会员购买页 | P1 |
| 05 | 同时点"上传文件"和"上传文件夹" | 互斥约束 | 只响应先点的入口，另一个按钮置灰 | P2 |

用例 05 是因果图独有的贡献——它是从**约束符号**直接翻译来的，不看图的话，"两个入口互斥"这半句需求谁会想起来专门测？还有一个隐藏收益：组合 3 里文件 501MB **恰好超上限 1MB**，这是[边界值](./07-boundary-value-analysis.md)顺手钉进去的，三个方法在同一个例子上合流了。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 把因果图当成最终交付物画得极精美 | 图是思考工具，评审交付的是翻译后的判定表和用例，草图就够 |
| 简单组合也硬画因果图 | 三个纯"与"条件，直接上判定表更快，图是给**有约束的关系**用的 |
| 约束符号只在图上标、不落到表里 | 互斥的列要删、要求的列要补，不落进表，图的功夫就白费了 |
| 原因列不完整（漏掉隐性条件） | "会员是否过期"这种藏在开头的条件最易漏，读需求时前置状态也算原因 |
| 结果只列成功不列各种失败 | 每种失败提示是一个独立结果，漏了结果就漏一整类用例 |
| 以为因果图和判定表是两套并行的方法 | 它们是一条流水线的两站：图定关系、表定组合、用例落地 |

## 上手建议

1. **下次 PRD 里看到"不可同时""必须""则不能再"，立刻开画**：这些连接词就是约束符号的中文原形，E/R/M 三种约束十有八九藏在里面
2. **原因清单对照输入项清单数一遍**：界面有几个输入项/开关/入口，原因至少有几个，少一个就是漏
3. **图转表时先删互斥列、再补要求列**：这两个动作做完，表才真正"忠实"于业务规则
4. **跟判定表法配成连招**：本系列两篇对照着读一遍，下次遇到组合逻辑先判断"有没有约束"，再决定走哪站
5. **把画过的因果图归档**：同类功能（上传、支付、权限）的图高度相似，归档的旧图就是新需求的设计模板
