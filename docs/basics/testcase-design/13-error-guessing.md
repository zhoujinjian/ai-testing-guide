# 13｜错误推测法：老手的经验直觉

> 核心要点：前几个方法都讲"怎么系统地推"，错误推测法反着来——**直接猜哪里容易错**。猜不是玄学：空值、重复提交、并发冲突、脏数据这些雷区，是历年 bug 库反复验证过的高发带，**老手的直觉其实是踩坑史压缩包**。

## 打个比方

把错误推测法想象成**老交警设卡**。

路口事故数据看得多了，老交警不用教科书，也知道早高峰电动车爱从左侧钻、雨天追尾集中在下坡弯、周五晚上酒驾多。设卡时他**专挑这些点位**，一查一个准。新手交警按手册站位，一天拦不住几个。

但注意：老交警的"直觉"不是天赋，是**事故台账读出来的规律**。错误推测法也一样——它看起来最不系统，实际上**完全可以从历史 bug 里系统化地养出来**。你不是没有直觉，是还没攒够案例库。

## 展开讲讲

### 为什么它是方法而不是玄学

测试界叫它"error guessing"（错误猜测），列为正式设计方法之一，原因在于：**软件错误在分布上高度重样**。空字符串打崩校验、重复点击下两单、并发减库存减成负数——不同项目、不同团队、不同语言，翻车姿势出奇一致。既然错误重样，"哪里容易错"就可以列表、可以传授、可以积累，这就是它的方法论内核：**基于经验和历史数据的缺陷定向打击**。

### 四类高发雷区（新手可以直接背）

| 雷区 | 为什么高发 | 典型攻击动作 |
| --- | --- | --- |
| **空与清空** | 空值是最常见的"没人想"输入 | 输入框清空后直接提交；搜索词删光再回车；购物车清空瞬间点结算 |
| **重复与连点** | 网络有延迟，用户会连点，后端没有幂等（重复请求只算一次的机制）就是事故 | 提交按钮连点 5 次；同一请求抓包重放；双击"确认收货" |
| **并发与时序** | 两个人同时动一份数据，谁后写谁覆盖 | 两个端同时改收货地址；抢 1 件库存的商品发 10 个并发请求 |
| **脏数据与残留** | 上一次操作留下的数据干扰这一次 | 删了地址马上下单（默认地址还挂着旧 ID）；退出登录后用回退键回到订单页 |

再补三个个人私藏：**字符集**（emoji、空格、繁体字放进昵称）、**极端长度**（一个字的地址、200 字的收件人名）、**跨模块边界**（优惠券在下单页能用、在秒杀页忘了禁）。

### 和其他方法的关系

错误推测法是**最后一道补刀**：[等价类](./06-equivalence-class.md)、[边界值](./07-boundary-value-analysis.md)、[场景法](./11-scenario-method.md)铺完主覆盖之后，拿着雷区清单对设计做一遍"定向扫描"——**每个输入点、每个按钮、每条流程**问一句"这里会不会踩四类雷"。它不替代系统方法（直觉有盲区，重样的雷拦得住、没见过的雷拦不住），但能在系统方法的网眼上再缝一层。

### 直觉怎么攒：把踩坑变成资产

老手的直觉是可以工程化复制的：

1. **记 bug 日志**：自己测出的、同事测出的、线上爆的，每条记"模块 + 错误类型 + 复现姿势"
2. **按雷区归类**：月底把日志按四类雷区分堆，你会发现你们项目的 bug 高度集中在两三类
3. **固化成检查清单**：归类结果变成项目专属的"错误推测清单"，新需求设计用例时照单扫一遍
4. **清单定期更新**：每出一次线上事故，问"这个姿势在清单里吗"——不在，加进去

这份清单就是你区别于"只会点按钮的测试"的核心资产，跳槽都带得走。

## 举个例子

电商"确认收货"按钮，系统方法（场景法 + 状态迁移）已经测过基本流。上错误推测清单扫描：

| 用例 | 推测依据 | 操作 | 预期结果 | 优先级 |
| --- | --- | --- | --- | --- |
| 01 | 重复雷区 | 确认收货按钮在弱网下连点 5 次 | 只触发一次状态变更，不重复触发售后窗口计时 | P0 |
| 02 | 重复雷区 | 抓包拿到确认收货请求，重放 3 次 | 后端幂等拦截，返回"订单状态已变更"，订单仍只有一个售后单 | P0 |
| 03 | 时序雷区 | App 和小程序同时打开同一订单，各自点确认收货 | 只有先到的生效，后到的返回错误提示，状态不回退 | P1 |
| 04 | 脏数据雷区 | 确认收货后 1 秒内立刻申请退款 | 售后流程正常受理，不出现"已完成的单不能售后"的死锁 | P1 |
| 05 | 边界雷区 | 确认收货瞬间断网再恢复 | 恢复后刷新，状态正确同步，不出现"永远转圈"的中间态 | P1 |

这五条没有一条来自等价类或场景图的推导——**全是"这里我见过翻车"的下意识**。其中 01 和 02 这类重复提交问题，在真实电商项目的 bug 库里出场率高到几乎每个新手都该主动交一次学费，不如在测试阶段就交掉。

再给一个凑清单的过程示范：某次上线后爆出"用户删除默认地址后下单，订单的收货地址显示为空白"——把"删除关联对象后，引用它的功能还正常吗"写进清单，下个版本你会主动去测"删除优惠券模板后，已发出去的券还能用吗"。**一次线上事故，换一整类用例**，这就是错误推测法的复利。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| "我经验少，用不了这方法" | 雷区清单是可以直接背的公共知识，四类雷区就是前人替你踩好的坑 |
| 拿直觉替代系统方法 | 直觉有盲区，没见过的错误类型根本猜不到，主覆盖必须靠等价类场景法，直觉只管补刀 |
| bug 过去了就过去了 | 每个 bug 都是一张彩票，不归档就等于作废——bug 日志是直觉的原料车间 |
| 清单写好就束之高阁 | 清单要当工具用：每次设计用例的最后一步，照单扫一遍，别当装饰品 |
| 只记自己的 bug | 团队历史 bug 库、线上事故复盘、甚至别人公司的故障公告，全是你的清单素材 |
| 推测不验证就写进用例 | 猜出来的点要写清复现步骤再进用例库，"我觉得会有问题"不是用例 |

## 上手建议

1. **今天就开始记 bug 日志**：格式就三列——日期、模块与姿势、错误类型（归四类雷区），每天两分钟，三个月后清单初具规模
2. **把四类雷区打印出来贴屏幕边**：每写完一个模块的用例，对着扫一遍，先背公共知识再攒私有经验
3. **翻你们项目的历史 bug 库**：按错误类型分个堆，找出你们项目的 Top2 雷区，下个版本重点扫
4. **盯住每次线上事故复盘**：复盘会上问一句"这类问题以后怎么拦在测试阶段"，答案进清单，这是最贵也最值的学习材料
5. **主动找老测试讨三个"必测点"**：问问带你的人"这个模块你每次必测但别人总漏的是什么"，一次对话顶你试错一个月
