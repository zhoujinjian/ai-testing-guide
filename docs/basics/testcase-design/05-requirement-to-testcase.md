# 05｜从需求到用例：完整演练一遍

> 核心要点：从需求到用例不是灵感，是**流水线**——通读圈规则、拆测试点、按需求特征选设计方法、落成用例表，四步走完，新手也能产出老手水准的覆盖。

## 打个比方

把这段转化过程想象成**做一桌宴席**。

食材（需求文档）不会自己变成菜。你得先**把食材全倒出来清点**（通读需求，一条规则都不许漏），再**按菜式分类**（这个是荤菜那个是汤，对应拆测试点），然后**选烹饪手法**（爆炒还是清蒸，对应选设计方法），最后**动手颠勺**（写成用例表）。

新手最大的事故是"看到食材就下锅"——读到"满 200 减 30"就兴冲冲写了一条"验证满减"，锅热了才发现没问：不满 200 呢？刚好 200 呢？多张券叠加呢？**宴席的翻车从来不在颠勺，在清点食材这一步**。

## 展开讲讲

### 第 1 步：通读需求，把规则全圈出来

拿到 PRD 先通读一遍，第二遍拿着笔圈**所有带条件和数字的句子**。圈出来的每一条都是一条"规则"，它们是用例的原料。

顺手做两件事：**给规则编号**（R1、R2……后面用例要反向引用它们）；**标出疑问**（"优惠券可叠加使用"？和谁叠加？叠几张？）——疑问当场找产品确认，别揣着疑问写用例。

### 第 2 步：从规则拆测试点

一条规则至少拆出一个测试点，复杂的规则拆多个。拆的口诀是**每个规则问三遍**：

- 正向：规则满足时，正确响应是什么？
- 逆向：规则不满足时（少一点、多一点、类型不对），怎么拦截？
- 关联：这条规则和别的规则相遇时（叠加、互斥、先后顺序），谁说了算？

### 第 3 步：按需求特征选设计方法

测试点有了，怎么把它撑成具体的用例值？看测试点的特征选工具（完整对照表见本系列第 14 篇）：

| 需求特征 | 选用方法 |
| --- | --- |
| 有取值范围（金额、长度、次数） | 等价类 + 边界值 |
| 多个条件组合决定结果 | 判定表 / 因果图 |
| 有流程、有步骤顺序 | 场景法 |
| 有状态流转（订单、审批单） | 状态迁移 |
| 组合爆炸，全测测不完 | 正交实验法 |
| 老模块、有历史 bug 沉淀 | 错误推测法 |

### 第 4 步：落成用例表

按第 1 篇讲的八要素写，每条用例标上**来源规则编号**——这条链路（用例 ← 规则 ← 需求）是覆盖率的底气：需求有 8 条规则，每条规则都有用例挂着，覆盖就是全的；有规则没挂用例，那就是漏测的洞。

### 第 5 步：自查一遍再提交评审

拿三个问题扫一遍成品：每条规则都有用例吗？每个输入都有负向和边界吗？流程类需求把主流程和异常分支都画出来了吗？过了这三问，再去发起[用例评审](./04-testcase-review.md)。

## 举个例子

需求原文（电商 App，新功能"复活优惠券"）：

> R1：用户 7 天内未登录 App，回来后弹窗发放一张 30 元优惠券；R2：优惠券面额 30 元，**满 199 元可用**；R3：有效期 3 天，过期作废；R4：**每人每月最多领 2 次**；R5：可与店铺券叠加，不可与平台券叠加。

**拆测试点**（每条规则问三遍后得到）：

| 来源 | 测试点 |
| --- | --- |
| R1 | 距上次登录 7 天内回来不弹窗；恰好第 7 天回来弹窗；超过 7 天回来弹窗 |
| R2 | 订单满 199 可用 30 元券；订单 198.99 不可用 |
| R3 | 有效期内使用成功；第 3 天 23:59:59 可用；过期 1 秒不可用 |
| R4 | 当月第 1 次领取成功；第 2 次成功；第 3 次拦截 |
| R5 | 叠店铺券金额计算正确；叠平台券被拦截 |

**选方法**：R1、R3 是时间条件 → **边界值**（7 天、3 天的临界时刻）；R2 是金额范围 → **等价类 + 边界值**（198.99 / 199）；R4 是次数上限 → **边界值**（2、3）；R5 是组合条件 → **判定表**（券种 × 是否允许叠加）。

**落用例表**（节选 R2 + R4 的成品）：

| 编号 | 标题 | 前置条件 | 步骤与输入 | 预期结果 | 优先级 |
| --- | --- | --- | --- | --- | --- |
| CPN-006 | 订单实付 198.99 元，30 元券不可用 | 持有一张满 199 可用的复活券 | 选商品合计 198.99，去结算，选择该券 | 券置灰不可选，提示"满 199 元可用" | P1 |
| CPN-007 | 订单实付 199 元，30 元券抵扣成功 | 同上 | 选商品合计 199.00，去结算，选择该券 | 券可用，应付 169.00 元 | P0 |
| CPN-011 | 当月第 3 次触发复活券，不发放 | 当月已领 2 次复活券 | 再次隔 7 天以上未登录后回来 | 不弹窗，领券中心无新增券 | P1 |

看 CPN-007 那行：输入值 199.00 精确到分、预期"应付 169.00 元"精确到金额——**这就是从需求文字走到可执行用例的样子**，每个数字都有出处（R2），失败时开发看一眼就知道差在哪。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 读完需求凭感觉直接写用例 | 跳过圈规则和拆测试点，写到哪算哪，回头一看一半规则没碰过 |
| 只拆正向测试点 | "满足规则时成功"只是一半，负向和边界才是 bug 高发区 |
| 疑问不确认，按自己的理解写 | 你理解的和产品想的不一致时，用例在验证一个不存在的需求，测了等于白测 |
| 用例不标需求出处 | 需求变更时找不到要改哪些用例，覆盖率也算不出来 |
| 一次想把方法用全 | 先用最对口的 1~2 个方法铺骨架，再拿别的方法补漏，别为了炫技堆方法 |
| 写完不自查直接上评审 | 把低级缺口留到评审会上，浪费的是全组的会议时间 |

## 上手建议

1. **下次拿到需求，先别写用例**：先做"圈规则 + 编号 + 列疑问"三件事，一小时内做完，再开工设计
2. **建一张"规则-测试点-用例"三列底稿**：这张表既是设计底稿，也是评审材料，还是覆盖率的证据，一表三用
3. **疑问清单当天清零**：找产品确认不完的，把"待确认"标注进用例草稿，评审会上一并解决
4. **拿本系列的方法篇当字典查**：拆完测试点不知道套什么方法，翻[方法选型指南](./14-method-selection.md)那张对照表，对号入座
5. **每做完一个需求复盘十分钟**：数一数用例数 ÷ 规则数的比例，和上次比——这个比值稳定上涨，说明你的拆解在变细
