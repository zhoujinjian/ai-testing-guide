# 12｜状态迁移法：给会变形的功能画出状态机

> 核心要点：有些对象不是静止的——订单会从"待付款"变成"已发货"，审批单会一路"提交-审批-通过"。**状态迁移法把"当前状态 × 触发事件 → 新状态"列成表**，专测两条线：合法的跳转都跳得对，**非法的跳转都被拦住**。

## 打个比方

把状态迁移想象成**交通灯控制器的检修**。

路口的灯有四个状态：红、绿、黄、全灭。检修工要验证的从来不是"灯亮不亮"（这算功能测试），而是**跳变规则**：绿只能跳黄、黄只能跳红、红只能跳绿——绿直接跳红，司机就懵了；任何状态都**不允许**跳到"全灭"（除非断电，那是另一个合法事件）。

他会拿一张表逐格打钩：当前是绿，来一个"倒计时结束"事件，应该变黄，实测变黄，过；当前是绿，来一个"手动强制红灯"事件（紧急车辆优先），应该变红，实测……还是绿，**抓到一个 bug**。这张"状态 × 事件"的打钩表，就是状态迁移表——**它把灯的每一条变身路径、连同不该存在的变身，全部圈进了射程**。

## 展开讲讲

### 状态机的三要素

| 要素 | 人话 | 订单的例子 |
| --- | --- | --- |
| **状态** | 对象在某一刻的"形态" | 待付款、已付款、已发货、已完成、已取消 |
| **事件** | 促使状态改变的动作或信号 | 付款成功、商家发货、用户确认收货、用户取消 |
| **迁移** | 状态 A + 事件 → 状态 B 的规则 | 已付款 + 商家发货 → 已发货 |

外加一个概念：**非法迁移**——需求不允许的跳转，比如"已发货 + 用户取消"应该被拒绝（只能走退货流程）。**非法迁移是状态迁移法的金矿**：开发漏写校验、前端按钮没置灰，用户点一点就把订单从"已发货"直接砍到"已取消"，钱货两清的账就乱了——这类 bug 靠场景法顺路撞到靠运气，靠状态迁移表是**一格一格扫出来的**。

### 走法四步

1. **挖状态**：从需求里列出对象的所有状态（找名词："待付款""已发货"这些词）
2. **挖事件**：列出所有能触发变化的事件（找动词：付款、发货、取消、确认收货、超时）
3. **画迁移表**：行放状态、列放事件（或直接列"当前状态 + 事件 → 新状态"三列清单），把合法迁移填上新状态，非法迁移标"拒绝"
4. **逐行写用例**：每条合法迁移至少一条用例；每条高风险非法迁移也要用例——**直接调接口触发非法事件**，验证后端拦得住（前端置灰不是安全边界）

### 和场景法的分工

[场景法](./11-scenario-method.md)和状态迁移法都管流程，刀口不同：

- 场景法从**用户的路径**出发——一条路走到底，眼里是"操作顺序"
- 状态迁移法从**对象的状态**出发——一个状态的所有出口，眼里是"每个状态能去哪、不能去哪"

用户路径只覆盖状态机里的一部分迁移（多数用户不会尝试从"已取消"订单去点确认收货）；状态机里那些**只有异常操作才触达的迁移**，必须靠状态迁移表主动扫。两法连用：场景法扫主干，状态迁移法补全图。

另外别忘了**时间类事件本身就是边界**——"15 分钟超时自动取消""30 分钟后解锁"这类定时迁移，临界时刻要按[边界值](./07-boundary-value-analysis.md)取法验证：14 分 59 秒不取消、15 分 00 秒取消，两个时刻各来一条用例，别只等 15 分钟看一眼了事。

## 举个例子

电商订单的状态集合：**待付款、已付款、已发货、已完成、已取消**。事件集合：付款成功、商家发货、用户确认收货、用户/系统取消、申请退款。

**第一步，画出状态迁移表**（行 = 当前状态，列 = 事件，格 = 新状态）：

| 当前状态 ＼ 事件 | 付款成功 | 商家发货 | 确认收货 | 取消 | 申请退款 |
| --- | --- | --- | --- | --- | --- |
| **待付款** | 已付款 | —（拒绝） | —（拒绝） | 已取消 | —（拒绝） |
| **已付款** | —（拒绝） | 已发货 | —（拒绝） | 已取消（需退款） | 退款中 |
| **已发货** | —（拒绝） | —（拒绝） | 已完成 | —（拒绝，只能退款） | 退款中 |
| **已完成** | —（拒绝） | —（拒绝） | —（拒绝） | —（拒绝） | 售后中 |
| **已取消** | —（拒绝） | —（拒绝） | —（拒绝） | —（拒绝） | —（拒绝） |

"—（拒绝）"格子和实心格子**同等重要**，每个拒绝格都是一条潜在的非法迁移测试。

**第二步，逐迁移写用例**（节选六条，含两条非法迁移）：

| 用例 | 当前状态 | 触发事件 | 预期结果 | 优先级 |
| --- | --- | --- | --- | --- |
| 01 | 待付款 | 支付宝付款成功 | 状态变"已付款"，支付流水号落库，触发商家发货通知 | P0 |
| 02 | 待付款 | 用户点"取消订单" | 状态变"已取消"，提示"订单已取消"，释放占用的库存 | P0 |
| 03 | 已付款 | 商家点击"发货"填入运单号 | 状态变"已发货"，用户侧显示物流单号 | P0 |
| 04 | 已发货 | 用户点"确认收货" | 状态变"已完成"，触发售后窗口期（7 天）开始计时 | P1 |
| 05 | 待付款 | 已取消的订单再发起支付（用旧支付单继续付） | 支付被拦截，提示"订单已取消，无法支付"，**钱不入账** | P0 |
| 06 | 已发货 | 绕过前端直接调取消接口（抓包重放） | 接口返回错误码，订单状态保持"已发货"，不产生退款流水 | P0 |

用例 05 是真实事故的高发区——用户下单后取消，但支付页面还开着，点一下"付款"钱扣了、订单却是已取消，**钱货两失**。用例 06 是非法迁移的标准测法：前端把"取消"按钮藏了不算数，**后端接口必须自己拦**。这六条用例对应表格里六个格子，一张 5×5 的表扫完，订单状态机的合法迁移和危险非法迁移就全部在控。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 只测合法迁移 | 非法迁移（已取消再支付、已发货直接取消）才是资金类事故的主产区，拒绝格比实心格更值钱 |
| 只从前端点按钮验证拦截 | 前端置灰只是装饰，必须抓包/直连接口发非法事件，后端拦得住才算数 |
| 状态漏挖 | "退款中""售后中"这类中间态最容易被漏掉，翻需求时把所有状态名词列全再动笔 |
| 事件漏挖 | 系统事件（超时自动取消、定时关闭售后窗口）没有用户点击，但会改状态，定时任务必须算事件 |
| 迁移表画完只测一遍新状态 | 新状态对了还要查**伴随动作**：库存回滚、退款流水、通知推送——状态是壳，数据是里子 |
| 状态机和场景法混为一谈 | 一个从用户路径出发、一个从状态出口出发，先场景铺主干、再状态机补全图，顺序别反 |

## 上手建议

1. **给你手头项目找一个"有状态"的对象**：订单、审批单、优惠券、会员卡、优惠券模板都算，先画出它的状态迁移表，贴进测试设计文档
2. **拒绝格单独标红**：把非法迁移按风险分级（涉及资金 > 涉及库存 > 纯展示），高危的先写用例
3. **定时事件列进事件清单**：超时取消、过期作废这类系统事件，用查库或等真实触发验证，别只在代码里"看起来有"
4. **非法迁移测试固定走接口**：抓包工具或 Postman 直接发请求，这是把"后端校验"测出真话的唯一姿势（接口怎么发见[底子篇](../tech-basics/07-postman-quickstart.md)）
5. **状态机变更时先改表再改用例**：需求给订单加一个"拼团中"状态，先改迁移表，对照表增删用例——表是用例的账本
