# 02｜用例怎么写才算好：规范与常见问题

> 核心要点：好用例只有一条金标准——**换一个没写过它的人来执行，也能得出和你一样的结论**。标题具体、步骤可循、预期可验，三样都占才算合格。

## 打个比方

把用例想象成**快递分拣中心的操作手册**。

流水线天天换人、分拣员从不认识写信的人，但包裹照样不出错，靠的是手册写得狠：包裹朝哪面朝上、条码对准哪个窗口、异形件放哪个筐，一步一张图。新人上午报到，下午就能上岗——**手册替老师傅把经验固化下来了**。

写得差的用例就是口头带教："这个你到时候看着办"。老师在，包裹分得挺好；老师休假，错分率翻倍。测试用例也一样：它在替未来的你、休假的你、接手你模块的同事干活，**它的质量下限，就是团队在你不在场时的质量下限**。

## 展开讲讲

### 判据一：标题具体到不用翻正文

用例标题是给人扫一眼用的。评审、执行、回归排范围，第一眼看的全是标题列。

| 差的标题 | 问题 | 改成 |
| --- | --- | --- |
| 验证登录功能 | 测哪个分支？ | 输入正确账号密码，登录成功并跳转首页 |
| 密码错误测试 | 错几次？什么反应？ | 密码连续输错 5 次，第 5 次提示"账号已锁定，请 30 分钟后重试" |
| 异常输入 | 哪个输入框、什么异常 | 手机号输入框输入字母 `abc`，提示"请输入正确的手机号" |

一个粗暴的自测办法：把标题列单独复制出来发给同事，让他猜这条用例会怎么执行——**猜不中，就是标题不合格**。

### 判据二：步骤是"可复制"的，不是"可意会"的

操作步骤要满足三个"可"：

- **可复现**：值写死（密码输 `Abc12345`），别写"输入一个正确密码"
- **可排序**：步骤编号，1、2、3 排下去，别把两步揉在一句里
- **可交接**：页面上叫什么按钮就写什么按钮，写"点击【立即注册】按钮"，别写"点那个注册的玩意"

### 判据三：预期结果是"可判定"的

预期结果决定执行的人能不能独立判断"通过还是失败"。合格的写法要能对上**一个可观察的现象**：

| 维度 | 写法示例 | 能查到吗 |
| --- | --- | --- |
| 界面 | 提示"用户名至少 6 位"，红色 toast，2 秒消失 | 能，看得见 |
| 跳转 | 跳转到首页，底部 tab 高亮"首页" | 能 |
| 数据 | orders 表新增一条记录，status = 10（待付款） | 能，查库 |
| 接口 | 返回 HTTP 200，code = 0，msg = "success" | 能，抓包 |

反例是"系统表现正常""体验良好"——**没有判定标准的预期，等于没有预期**，执行的人只能拿自己的感觉当标准，同一条用例两个人能测出两个结论。

### 一条用例只测一个况

"况"指一个独立的验证场景。把"用户名合法 + 密码合法 + 验证码正确"塞一条里测注册成功，没问题；但把"用户名过长"和"密码过短"塞同一条，用户名先报错，密码那条检查点根本执行不到——这条用例挂了，你只能说"挂了"，说不清挂在哪。**用例是主谓宾清晰的句子，不是段落**。

## 举个例子

需求：购物车页"修改商品数量"，规则为数量范围 1~200。同一个测试点，差写法和好写法各来一版：

**差版本**：

| 字段 | 内容 |
| --- | --- |
| 标题 | 修改数量异常测试 |
| 步骤 | 修改数量为不合法的值 |
| 预期 | 修改失败，有提示 |

执行的人当场要问你三个问题：不合法是几？在哪改？提示写什么？这条用例把三个问题全甩给了执行现场。

**好版本**：

| 字段 | 内容 |
| --- | --- |
| 用例编号 | CART-012 |
| 标题 | 数量输入框输入 201，提示"最多购买 200 件"，数量保持 200 |
| 前置条件 | 购物车中有 1 件商品"无线机械键盘"，库存 500 |
| 步骤 | 1. 打开购物车页；2. 定位该商品数量输入框；3. 清空后输入 `201`；4. 点击页面空白处触发校验 |
| 预期 | 输入框下方红色提示"最多购买 200 件"，数量自动回填为 200，商品小计金额按 200 件计算，页面不刷新 |

两版的差距不在文采，在**信息量**：好版本执行起来零提问，失败时开发照着步骤就能复现。这就是"可执行"的全部含义。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 用例越细越好，一步拆三步 | 过细的用例维护不动，需求一改几百条跟着改，**写到别人能执行就停笔** |
| 预期结果凭开发实现的现状倒填 | 那是在记录行为不是在验证需求，需求说上限 200、实现拦的是 99，照实现填预期等于放过 bug |
| 写完不执行第一遍 | 没跑过的用例里混着前置条件不成立、路径走不通的"死用例"，真上线执行时才暴雷 |
| 用例覆盖正向，负向靠临场发挥 | 负向场景（空值、超长、非法字符、断网）恰恰是 bug 高发区，必须成条入库 |
| 复制粘贴改两个字符凑数量 | 评审一眼识破，且容易改漏字段——同模板批量生成后要逐条校对输入值 |
| 文案口头约定不写进用例 | 需求没写提示文案时，用例里写清你预期的文案，评审时拉产品当场确认，事后少吵一轮 |

## 上手建议

1. **写完做"交接测试"**：随机挑三条用例发给没接触过这个需求的同事执行，他卡壳的地方就是你下一版要改的地方
2. **建立自己的"预期结果词库"**：把项目里常见的提示文案、状态码、落库表字段整理成一页速查，写用例时预期直接引用，准确又快
3. **差版本先写草稿，好版本再誊抄**：允许自己第一遍写糙的，第二遍按三条判据（标题、步骤、预期）逐条抛光，比憋着一次写好顺畅得多
4. **每条用例标上需求出处**：加一列"关联需求"，比如"PRD-3.2 购物车规则"，需求变更时按这列反查要改的用例，不靠脑子记
5. **每月清理一次死用例**：跑不通的、需求已删的、重复的，定期归档，用例库膨胀到没人愿意翻，比没有用例更糟
