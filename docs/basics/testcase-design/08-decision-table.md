# 08｜判定表法：条件组合的全覆盖打法

> 核心要点：当**多个条件的组合**决定一个结果时，靠脑子枚举组合必漏——判定表把所有条件和所有动作画进一张矩阵，每个组合占一列，**漏没漏一眼看穿**。

## 打个比方

把判定表想象成**机场安检的处置手册**。

安检员判断一个箱子开不开箱，看的不是单一因素：有液体吗？超量吗？有锂电池吗？单独装的（没托运）吗？手册直接给出一张速查表——**"有液体 + 超量"开箱倒掉，"有液体 + 不超量"放行，"无液体 + 有超规锂电池"移交柜台**。安检员不用现场推理，查表对号入座。

测试里的组合逻辑一样：一个功能要不要发券、能不能提交、弹不弹窗，往往是三个条件叠加的判决。**人脑对"两两组合"还行，到 3 个条件 8 种组合就开始丢三落四**，判定表就是那张替你穷举的处置手册。

## 展开讲讲

### 判定表的四个部件

| 部件 | 管什么 | 例子（自动发券） |
| --- | --- | --- |
| **条件桩** | 列出所有影响结果的条件 | 是新用户？订单满 99？当月未领过？ |
| **动作桩** | 列出所有可能的结果 | 发 20 元券 / 不发 |
| **条件项** | 每列给出各条件的取值（Y/N） | 第 3 列：Y、Y、N |
| **动作项** | 每列给出该组合下的结果 | 第 3 列：不发（领过） |

N 个条件（每个取真假两值）就有 **2 的 N 次方**种组合，每列一种——判定表的本质是**把组合空间钉在表格里**，谁也别想溜。

### 制作四步

1. **列条件桩**：从需求里挖出所有影响结果的输入条件（漏一个条件，整张表就是错的）
2. **列动作桩**：把所有可能的输出列全
3. **填组合**：2 的 N 次方列，逐列填 Y/N
4. **简化合并**：找出"某条件取值不影响结果"的列（比如新用户 N 时，另外两个条件怎么样都不发券），把这两列合并成一列写"—"（任意）

第 4 步是判定表的精髓——**合并是它对组合爆炸的还手**。3 个条件 8 列，简化后常常只剩 4~5 列，测的还一点不少。

填表前后还有两个容易忽略的细节。一是**拦截优先级**：多个条件同时不满足时，系统提示哪一个？比如"非新用户 + 订单不满 99 + 已领过"，弹哪个提示？需求没写就要当场找产品定下来，并把答案写进对应列的预期里——不然开发各写各的，用例跟着打架。二是**条件先过等价类**：条件取值本身未必只有真假两值，"满 99"就还藏着"恰好 99"和"98.99"两个边界，先按[等价类划分法](./06-equivalence-class.md)把每个条件的取值切细，判定表的列才立得住。

### 什么需求该用判定表

信号词很明确，PRD 里出现**"同时满足""且""并且""以下条件均""在……的情况下"**，结果又是开关型的（发/不发、通过/拒绝、显示/隐藏），就是判定表的主场。单条件、范围型的需求别硬上——那是[等价类](./06-equivalence-class.md)和[边界值](./07-boundary-value-analysis.md)的活儿。判定表和它们怎么配合：先用等价类把**每个条件自身**的有效无效切干净，再用判定表管**条件之间**的组合，两层叠完才叫严丝合缝。

## 举个例子

电商需求：**下单后自动发 20 元红包。规则：新用户、且订单满 99 元、且当月没领过这个红包，三个条件都满足才发，否则不发。**

**第一步，列桩**：

- 条件桩：C1 新用户？C2 订单满 99 元？C3 当月未领过？
- 动作桩：A1 发 20 元红包；A2 不发

**第二步，铺 8 列填组合，再简化**：

| 组合 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| C1 新用户 | Y | Y | Y | Y | N | N | N | N |
| C2 满 99 | Y | Y | N | N | Y | Y | N | N |
| C3 未领过 | Y | N | Y | N | Y | N | Y | N |
| A1 发券 | √ | | | | | | | |
| A2 不发 | | √ | √ | √ | √ | √ | √ | √ |

**第三步，合并**：第 5~8 列（C1 = N），不管另外两个条件怎样都是"不发"，可合并为一列"C1 = N，C2/C3 任意"。同理第 2、3、4 列（C1 = Y 但 C2、C3 至少一个不满足）也合并。简化后：

| 规则 | R1 | R2 | R3 |
| --- | --- | --- | --- |
| C1 新用户 | Y | Y | N |
| C2 满 99 | Y | —（任意） | — |
| C3 未领过 | Y | — | — |
| 动作 | 发 20 元红包 | 不发 | 不发 |

8 列收成 3 条规则，**一条不多一条不少**。

**第四步，把每条规则翻译成用例**：

| 用例 | 前置条件与输入 | 对应规则 | 预期结果 | 优先级 |
| --- | --- | --- | --- | --- |
| 01 | 老张是新用户，下单 129 元，当月未领过 | R1 | 下单成功页提示"恭喜获得 20 元红包"，卡包可见该红包 | P0 |
| 02 | 老张是新用户，下单 129 元，本月已领过 1 次 | R2 | 正常下单，无红包提示，卡包无新增 | P1 |
| 03 | 老用户（注册 2 年），下单 500 元，当月未领过 | R3 | 正常下单，无红包提示，卡包无新增 | P1 |

三用例覆盖全三条规则。如果不用判定表，第 2 条这种"满足两个就差一个"的组合，是人工枚举时最容易漏的——**它看起来跟 R1 好像差不多，结果却完全不同**。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 条件桩挖不全就开填表 | 漏一个条件，整张表的组合空间就是残缺的，先把需求里所有"且/或"挖干净 |
| 满怀敬畏地测全 2 的 N 次方列 | 该合并就合并，"—（任意）"是判定表的正规写法，不是偷懒 |
| 条件超过 4 个还硬上判定表 | 表会大到没人看，先拆子功能，或改用[正交实验法](./10-orthogonal-array.md)抽样 |
| 把动作项写成过程描述 | 动作桩只要"发/不发"这种终态，过程细节属于用例的步骤字段 |
| 只测 Y 组合不测 N 组合 | 全 Y 的那列人人记得测，"差一点"的列才是拦错的关键 |
| 表格画完用例不翻译 | 判定表是设计工具不是交付物，最终落进用例库的必须是翻译后的用例 |

## 上手建议

1. **下次看到"且/同时满足"就地画表**：别等评审，需求里每个逻辑连接词都是判定表入口，五分钟一张草表
2. **先画全再合并**：宁可先老老实实铺 8 列，做完再缩成 3 列——直接画简化版容易把"任意"标错地方
3. **拿历史 bug 反查组合缺口**：翻出组合逻辑出过的线上 bug，看它落在哪个组合列里、当时那张表缺了哪列
4. **每个条件先过一遍等价类**：条件自身的有效无效切干净了，判定表管组合才有意义，两个方法连着用
5. **简化列里抽边界值加测**：R2 的"—（任意）"里藏着一个边界——满 99 刚好差 1 元（98.99），补一条用例把[边界值](./07-boundary-value-analysis.md)钉进去
