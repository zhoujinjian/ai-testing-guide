# 01｜什么是软件缺陷：定义与产生原因

> 核心要点：软件缺陷（bug）就是**软件的实际表现和预期表现不一致**。判定的钥匙不是"我觉得不对"，而是**需求**。缺陷不是凭空冒出来的，从需求到编码每个环节都可能埋雷。

## 打个比方

你在餐厅点了一份**微辣的鱼香肉丝，不要香菜**。

菜端上来，你筷子还没动就发现问题：上面铺满了香菜，尝一口还辣得跳脚——这盘菜和你下的单不符，它就是一盘"有缺陷"的菜。

注意三个细节。**第一**，判断的依据是你下的单（需求），不是厨师的手艺好不好——厨师火候再棒，做错了单子照样是错的。**第二**，缺陷是在菜端上桌（软件运行）时才暴露的，厨师忘了你的备注（代码里埋的雷）在灶台阶段看不见。**第三**，"不好吃"和"上错菜"是两回事——前者是主观体验问题，后者是和订单明确不符，测试抓的是后者为主。

软件缺陷就是这盘上错的菜：**用户/需求"下的单"，和软件"端上来的菜"对不上。**

## 展开讲讲

### 缺陷的判定标准：四条口诀

国际上有份经典标准（IEEE 829 语境下被广泛引用），判断一个现象是不是缺陷，看四条，满足任意一条就算：

| 判定标准 | 人话版 | 例子 |
| --- | --- | --- |
| 少做了 | 需求要求的功能没实现 | 需求说优惠券满 200 可用，实际输入满减券下单，优惠没生效 |
| 做错了 | 实现的功能和需求不符 | 需求说"最多购买 99 件"，实际 99 件也被拦截 |
| 多做了 | 软件做了需求没要求的事 | 需求没说取消订单要发短信，用户取消后却收到了营销短信 |
| 难以接受 | 虽然需求没写，但明显不合理 | 手机号输入框里能粘贴进去 500 个字符，界面直接撑破 |

第四条最微妙——需求不可能把所有细节写死，**"测试人员站在用户角度认为不可接受"也是判定依据**，但这通常要和产品确认后再定，不能全凭个人口味。

### 错误、缺陷、失效：一条因果链

三个词在日常口语里都叫 bug，严格说是一条链上的三站：

| 术语 | 英文 | 是什么 | 发生在哪 |
| --- | --- | --- | --- |
| 错误 | Error | 人犯的错：理解偏了、手滑了 | 人的脑子里 |
| 缺陷 | Defect/Bug | 错误被写进了代码或文档，静态躺着 | 代码/文档里 |
| 失效 | Failure | 缺陷在特定条件下被执行触发，表现出来了 | 运行中的系统里 |

比如开发把 `>` 写成了 `>=`（错误），这行代码进了仓库（缺陷），只有用户恰好输入边界值 99 时才会被拦（失效）。**测试直接看到的是失效，往前追是缺陷，再往前追才是错误。**你平时提的"bug 单"，严格说是缺陷报告。

### 缺陷从哪来：每个环节都会埋雷

新手容易以为 bug 都是开发代码写错，实际上缺陷的出生地分布很广：

| 来源环节 | 典型缺陷 | 占比观感 |
| --- | --- | --- |
| **需求** | 需求本身有矛盾、漏了异常场景、表述有歧义 | 不低，且最贵——发现越晚修改成本越高 |
| **设计** | 架构没考虑并发、接口定义不清、数据库字段长度给小了 | 藏得深，常在压测或放量时爆 |
| **编码** | 边界符号写错、空指针、多线程竞争、复制粘贴改漏 | 数量最多，最容易修 |
| **集成** | 前后端对同一规则理解不一致、上下游接口参数对不上 | 联调阶段集中出现 |
| **环境与数据** | 测试环境配置和生产不一致、脏数据、缓存未失效 | 常被误报成功能 bug |
| **沟通** | 口头说好的改动没写进文档、需求变更没同步到测试 | 改三处只改了两处 |

看清这张表的意义在于：**发现 bug 之后别只盯着开发**。一个"下单金额算错"的缺陷，可能是需求写错了满减规则，也可能是设计时金额字段用了单精度浮点。定位来源，才能让同类问题下次少发生。

## 举个例子

拿一个真实场景走一遍：电商 App 上线了**"满 200 减 50"优惠券**。

用户反馈"券用了但没省钱"。你作为测试复现：账号 A 购物车合计 **220 元**，结算页选择该优惠券，应付金额显示 **220 元**——优惠没生效。再看账号 B 合计 260 元，同样用券，应付 210 元，正常。

单看现象只能确认"失效"发生了。往后追：抓包看账号 A 的下单请求，发现她的购物车里有一件"预售商品"，后端算优惠券时**把预售商品金额排除在满足门槛的计算之外**（只算了 120 元，不满足 200 门槛）——这是缺陷所在。再往后追根因：需求文档里压根没写"预售商品是否参与满减门槛"，产品口头说"都算"，后端按自己的理解排除了预售——错误发生在**需求环节**，一个字没写清楚，最后变成了用户看到的不省钱。

四种判定对号入座：这是"做错了"（实际规则和产品意图不符）；因果链对号入座：需求没写清（错误）→ 后端排除逻辑（缺陷）→ 账号 A 用券失效（失效）。一张 bug 单提给后端之前，先拉产品把规则补进文档，才是真正的止血。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| bug 都是开发代码写错的 | 需求、设计、集成、环境、沟通都会产缺陷，编码只是其中一站 |
| "我觉得不好用"就是 bug | 主观体验问题要先和产品对齐，用四条判定标准说话 |
| 现象=缺陷本身 | 你看到的是失效，缺陷躺在代码里，中间还隔着触发条件 |
| 需求没写的就不管了 | "明显不合理、用户难以接受"也是判定依据，但需产品确认 |
| 一个 bug 修掉就结束了 | 不追问"它从哪个环节漏进来的"，同类 bug 会换个面目再来 |

## 上手建议

1. **把四条判定口诀贴进笔记**：少做了、做错了、多做了、难以接受——下次和开发争论"这是不是 bug"时，先对号入座再开口
2. **提单前先定位归属**：简单抓个包、看眼日志，判断像前端还是后端的问题（怎么判断见相关阅读的面试题），能大幅减少 bug 单被退回
3. **读需求时主动找歧义**：每句有歧义的表述当场问产品并落进文档，需求阶段的缺陷最便宜也最容易被新手漏掉
4. **给 bug 记"出生地"**：自己维护一张表，记录每个 bug 最终定位到哪个环节（需求/设计/编码/环境），一个月后你就知道团队的质量洼地在哪
5. **区分"缺陷"和"失效"再沟通**：和开发交流时说清触发条件，等于帮他把失效回溯到缺陷，沟通效率翻倍
