# 03｜缺陷报告怎么写：要素、模板与反面教材

> 核心要点：bug 单是写给**三个月后的陌生人**看的——开发靠它定位问题，你自己靠它回忆问题。八要素写全，**让看到单子的人不用来找你问第二句**，就是合格线。

## 打个比方

你给**物业报修**："我家水管坏了，来人看看。"

师傅上门问你：哪里的水管？厨房还是卫生间？漏水和不出水是一回事吗？从什么时候开始的？拍张照片给我看看。你一句"坏了"，师傅白跑一趟，你也白等半天。

会报修的业主这么写：**"3 号楼 2 单元 502 厨房水槽下方的软管接口渗水，今早 6 点发现，地面已积水约一盆，关总阀后停止，附照片和 15 秒视频，家里下午 4 点后有人。"**师傅带上软管和扳手，一次上门修好。

bug 单就是这张报修单。区别只是，报修单写得差损失的是一趟路，bug 单写得差损失的是**开发的排查时间、你的来回扯皮、甚至 bug 本身被拒收**。

## 展开讲讲

### 八要素：一张单子的合格线

| 要素 | 写什么 | 反面写法 |
| --- | --- | --- |
| **标题** | 哪个模块 + 什么条件下 + 什么现象。"订单页选西藏地址运费显示 0 元" | "运费不对" |
| **前置条件** | 账号、环境、数据状态。"test 环境，账号 A 已领满 200 减 50 券，购物车合计 220 元" | "正常登录" |
| **复现步骤** | 编号步骤，具体到输入值。"1. 进入结算页 2. 选择优惠券…" | "下单试一下就知道了" |
| **预期结果** | 需求怎么规定的。"运费应显示 15 元" | "应该是对的" |
| **实际结果** | 看到什么，含提示文案原文。"显示 0 元" | "不正常" |
| **附件** | 截图/录屏/日志，标注关键处 | 无图无真相 |
| **严重程度/优先级** | 按团队标准评（见第 04 篇），给理由 | 全部无脑最高级 |
| **复现概率** | 必现写"必现"；偶现写"10 次出现 3 次"（见第 07 篇） | 偶现不标注，开发复现不出来 |

其中**标题**最值钱：开发扫一眼标题列表就要能分流，你自己的周报统计也靠标题分模块。一个好标题的公式是**"模块 + 条件 + 现象"**，三段缺一不可。

### 完整模板：照抄就能用

```text
【标题】订单结算页-选择西藏拉萨地址时运费显示 0 元
【严重程度】高    【优先级】P1    【复现概率】必现
【测试环境】test 环境（test-03），App 版本 2.8.1（Android），账号 13800001111
【前置条件】
  1. 账号已实名，默认收货地址为上海
  2. 购物车含商品 A×1（99 元）+ 商品 B×1（121 元），合计 220 元
【复现步骤】
  1. 进入购物车，点击"去结算"
  2. 在地址栏选择"西藏 拉萨市 城关区"作为收货地址
  3. 进入订单确认页，查看运费
【预期结果】运费显示 15 元（按需求文档 PRD-1024 运费模板：西藏 15 元）
【实际结果】运费显示"免运费"
【附件】截图 1（运费区域）、录屏 15 秒、下单接口抓包（freight=0）
【初步定位】抓包看下单请求 freight 字段为 0，前端展示与接口一致，
  疑似后端运费模板未配置西藏，请后端同学确认
```

最后一条"初步定位"是加分项：抓个包、看眼日志，把"前端还是后端"的判断写进去（怎么做见相关阅读），开发少走一半弯路——注意写"疑似"，定位是帮忙不是越权。

### 反面教材：同一个 bug 的两张单

烂单（真实新手风格）：

```text
标题：运费 bug
内容：下单的时候运费有问题，你们看看吧，我这边是好的之前。
```

开发的回复往往是："哪个页面？哪个地址？哪个账号？之前是好的是多久之前？必现吗？截图呢？"——五个问题等回复，半天没了。

好单就是上面那份模板。两相对比，差距全在**信息密度**：

| 对比点 | 烂单 | 好单 |
| --- | --- | --- |
| 能否直接复现 | 开发要自己猜条件 | 步骤+账号+数据照抄即现 |
| 能否直接定位 | 不知道查前端还是后端 | 抓包结论指明疑似后端 |
| 会被拒收吗 | 大概率以"无法复现"打回 | 不会被拒，只会被接单 |
| 三个月后回看 | 没人记得这是什么 | 单子自己会说话 |

### 写单的三条心法

1. **写给没在场的人**：假设读单的人不了解这个需求，所有缩写、黑话都展开写
2. **事实和推断分开写**：现象（运费显示 0 元）是事实，定位（疑似后端模板）是推断，别混在一句里
3. **一单一缺陷**：一张单只写一个问题。三个问题挤一张单，修好两个关单，第三个跟着陪葬

## 举个例子

社交 App 迭代，你测"**修改昵称**"功能，发现改完昵称回到个人主页，昵称还是旧的，要杀进程重进才刷新。

按模板提单——标题：**"个人主页-修改昵称保存成功后返回主页昵称未刷新（重进 App 恢复）"**；复现步骤写清"1. 我的-设置-昵称 2. 输入'测试喵'点保存，提示'修改成功' 3. 返回个人主页查看"；预期"昵称即时显示'测试喵'"；实际"仍显示旧昵称'张三'，杀进程重进后正常"；附件贴对比截图和录屏；复现概率"必现（Android 2.8.1），iOS 未复现"。

开发接单十分钟定位：保存接口成功后主页未发刷新通知，**而且只在 Android 端**。你那句"iOS 未复现"帮他把排查范围直接砍掉一半——这就是一张好单省下的时间。反过来说，如果标题只写"昵称 bug"，这个"仅 Android"的关键信息就根本没机会被发现。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 标题写"XX 功能有 bug" | 等于没写，模块+条件+现象三段式才算标题 |
| 步骤写"先正常登录" 一笔带过 | 账号、数据状态是复现的一半，缺了开发就是盲猜 |
| 预期结果写"应该正常" | 预期要引用需求的具体规定，"正常"没有信息量 |
| 所有 bug 都标最高级 | 全是紧急等于没有紧急，评级要有区分度（见第 04 篇） |
| 偶现 bug 不标概率 | 不标概率的偶现单 100% 被退回（见第 07 篇） |
| 一张单塞三个问题 | 修一个关一张，剩下两个陪你一起沉底 |

## 上手建议

1. **把八要素模板存成个人 snippet**：用输入法自定义短语或笔记工具存下模板，提单时直接唤出，比每次回忆格式快十倍
2. **写完标题自检一句**：开发只看标题，能不能猜到八成问题？不能就重写
3. **提单前自己照单复现一遍**：开个新会话，只按单子上写的步骤走，走不通就是步骤漏了
4. **截图上画框标重点**：满屏截图里的问题区域用红框圈出来，别让开发玩找茬
5. **被退回的单记一笔**：每次被打回的原因（缺步骤？没概率？）记进笔记，两周后你会发现退回率断崖式下降
