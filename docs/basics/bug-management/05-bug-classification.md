# 05｜缺陷怎么分类：功能、界面、数据、性能、兼容

> 核心要点：给 bug 打上**类型标签**，统计才有意义。功能、界面、数据、性能、兼容五大类各有所指，**标签打得准，季度末那张"哪类问题最多"的分布图才不会骗人**。

## 打个比方

小区实行**垃圾分类**：可回收物、厨余、有害、其他，四色桶一字排开。

分类的目的不是仪式感，而是**后端处理线不同**——可回收的去再生工厂，厨余的去堆肥，有害的要专门无害化。要是居民随手乱扔，电池混进厨余，整条堆肥线被污染，分类就白搞了。

bug 分类同理。开发组长看"**本迭代功能类缺陷占 62%**"会得出"自测不足，要加强提测门槛"；看"**兼容类占 40%**"会得出"机型覆盖不够，要补适配测试"。**每张标签背后连着一条不同的改进动作**，标签乱打，改进就走错路——这就是分类的全部意义。

## 展开讲讲

### 五大类：定义与高发场景

| 类型 | 判定核心 | 高发例子 | 主要责任方 |
| --- | --- | --- | --- |
| **功能** | 系统行为和需求不符 | 满减券不生效、提交订单无反应、状态流转错乱 | 前后端开发 |
| **界面（UI）** | 展示层瑕疵，功能本身对 | 文案错别字、图标错位、间距和设计稿不符、深色模式颜色错误 | 前端/UI 走查 |
| **数据** | 存取的数不对 | 金额精度丢失、列表分页第 2 页重复第 1 页数据、时区差 8 小时 | 后端/DBA |
| **性能** | 快慢与稳定问题 | 页面加载 8 秒、高并发下接口报错、内存泄漏越用越卡 | 后端/架构 |
| **兼容** | 特定环境才出问题 | iOS 正常 Android 闪退、Chrome 正常 Safari 样式乱、特定机型按钮点不到 | 前端/客户端 |

判断口诀：**先问"功能对不对"，再问"长得对不对"，再问"数对不对"，再问"快不快"，最后问"是不是只在特定环境"**。前两问筛掉大半，剩下的按特征归位。

### 五类各自的排查路数

分类不只是贴标签，每类的排查路数也不同，顺手记住能少走弯路：

- **功能类**：对照需求文档逐条核（需求文档没有的先找产品补），抓包看请求参数和返回值，多数能定位到前后端谁的问题
- **界面类**：拿设计稿逐像素对，注意设计稿版本是不是最新的——"和设计稿不符"经常是设计师改了稿没同步，不算开发 bug
- **数据类**：直接查数据库（测试环境你有权限），比对"接口返回值、库里存的值、页面显示值"三方是否一致，断点在两两比对之间现形
- **性能类**：先看监控和日志定位慢在哪一段（接口耗时还是前端渲染），再区分是"一直慢"还是"数据量大了才慢"
- **兼容类**：锁定变量——同一步骤在不同浏览器/机型/系统版本上各跑一遍，把出问题的环境矩阵画出来，环境特征就是定位线索

### 分类字段在工具里怎么配

成熟团队的缺陷单上，"类型"之外还有几个配套维度，一起构成统计骨架：

| 字段 | 作用 | 常见取值举例 |
| --- | --- | --- |
| 缺陷类型 | 本篇主题，指向改进方向 | 功能/界面/数据/性能/兼容/安全/易用性 |
| 所属模块 | 定位问题聚集地 | 订单中心/购物车/登录/个人中心 |
| 发现阶段 | 衡量测试左移成效 | 需求评审/冒烟/功能测试/回归/线上反馈 |
| 责任归属 | 流转与考核 | 前端/后端/客户端/测试/第三方 |

**模块 × 类型**交叉统计是最有杀伤力的一张表："订单中心 × 数据类 12 个"——下一轮迭代测试重点、开发的着重自查范围，全出来了。

### 分类的两条纪律

1. **一类为主，不贪多**：一个 bug 同时像功能又像数据时，按根因归类，别打两个标签（除非工具支持主次标签），否则统计会重复计数
2. **边界争议团队约定**：前端展示错误的数据（后端返回就错了）算功能还是数据？建议按**根因**归：根因在后端就算数据类，前端只是背锅侠。这类边界每个团队都要写进自己的判定说明，一次约定长期执行

## 举个例子

外卖 App 一个迭代，测试报了 6 个 bug，逐个归类：

| Bug | 归类 | 判定理由 |
| --- | --- | --- |
| 下单选"准时宝"后，订单详情不显示准时宝标识 | 功能 | 需求明确要求展示，行为不符 |
| 商家列表页"月售"数字显示为"月售 1024.0" | 界面 | 数据本身对（1024），展示格式化错了，多了个 .0 |
| 修改收货地址后，历史订单的配送费按新地址重算了 | 数据 | 老订单费用被波及，数据一致性被破坏 |
| 商家列表滚动加载到第 5 页越来越卡 | 性能 | 功能都对，快慢和流畅度问题 |
| 鸿蒙系统上"去结算"按钮点击无响应 | 兼容 | 仅特定 OS 出现，其他环境正常 |
| 优惠券列表"已使用"标签在深色模式下看不见 | 界面 | 特定显示模式下的展示问题（若团队细分"兼容"含深色模式，归兼容也可——按团队约定执行） |

最后一条恰好踩在分类边界上——**同一现象在不同团队的归类可能不同，这不是谁对谁错，约定一致比定义精确更重要**。迭代复盘时这张表一拉：界面类 2 个、功能/数据/性能/兼容各 1 个，前端走查和深色模式适配被点名，下个迭代测试计划里"UI 走查 + 深色模式专项"就有了数据依据。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 分类是给领导看的仪式 | 标签连着改进动作，打错标签改进就走错路 |
| 一个 bug 打好几个类型标签 | 统计重复计数，分布图失真，一类为主 |
| 按现象分类而不是按根因 | 后端算错的金额在前端展示，根因归数据类，不是界面类 |
| "兼容"只想到浏览器 | 机型、OS 版本、App 版本、分辨率、深色模式、弱网，全是兼容战场 |
| 性能问题当功能问题提 | "页面打不开"要先量时间（超时 8 秒还是接口报错），两类排查路数完全不同 |
| 工具里类型字段空着不填 | 空标签 = 统计盲区，季度分析时这些 bug 全部蒸发 |

## 上手建议

1. **提单时必填类型字段**：给自己立规矩，每个 bug 单归类后再提交，犹豫不决的按"根因优先"裁决
2. **整理一张团队判定速查表**：把五大类定义 + 边界判例（如深色模式归哪类）写成一页纸，贴在缺陷工具的项目说明里
3. **每月拉一次模块×类型交叉表**：两个下拉框筛选就行，看看问题聚集在哪一格，那就是你下个月测试火力该覆盖的地方
4. **归类存疑就当场问**：拿不准的 bug 在群里问一句"这个算数据还是功能"，五分钟的讨论换来全团队口径统一，最划算
5. **把分类喂给用例设计**：上迭代"数据类"集中爆发，本迭代设计用例时就多造几组数据边界和并发写场景——分类的价值最终回到测试本身
