# 07｜偶现 bug 与无法复现的 bug 怎么处理

> 核心要点：偶现 bug 的处理原则是**先抢救现场，再缩小变量**——日志、录屏、账号、时间点立刻固定下来，然后用"控制变量法"一轮轮逼近触发条件。复现不了不等于不存在，**降级跟踪而不是销单**。

## 打个比方

家里**电闸每隔几天半夜跳一次**。

你的第一反应绝不是"跳的时候我在睡觉，算了"——你会先做两件事：**记下来**（几点跳的、当时开着哪些电器）和**留证据**（拍下跳闸的是哪个空开）。然后开始排查：昨晚跳闸时空调+电热水壶同时开着？今晚只开空调试试，还跳吗？不跳了，再单开热水壶……一轮轮**缩小变量**，最后锁定是老热水壶漏电。

要是排查三轮也没抓到现行呢？你会在配电箱装个**监控插座记录电流**（相当于给系统加日志埋点），让它替你蹲守——人等不到的条件，让记录仪等。

偶现 bug 完全一样：**它不是随机的，只是触发条件你没找全**。时序、并发、缓存、网络、数据状态，总有一个变量在悄悄作祟。

## 展开讲讲

### 第一步：现场抢救清单

bug 现出来的那一刻，别急着复现第二遍——**很多现场只有一次**。按顺序做四件事：

| 动作 | 做什么 | 为什么 |
| --- | --- | --- |
| 1. 截图/录屏 | 立刻截当前页面，有时间戳更好 | 复现失败时它是唯一"目击证词" |
| 2. 记录四要素 | 时间点、账号、环境（test-03/版本号）、当时的操作序列 | 开发查日志全靠这几项定位请求 |
| 3. 保全现场 | 别刷新、别退出，先抓包、看控制台报错、必要时保留会话 | 一刷新，内存里的状态全没了 |
| 4. 再试复现 | 以上都留好了，才动手按原步骤再走 | 顺序反了，证据先被你毁掉 |

### 第二步：缩小变量的五个方向

现场留好了，开始"控制变量"。偶现 bug 的触发条件逃不出这几个方向，逐个排查：

| 方向 | 典型变量 | 试验方法 |
| --- | --- | --- |
| **时序/竞态** | 快速连点、双击提交、两步操作间隔极短 | 把操作速度拉到极限试；故意慢速操作对比 |
| **数据状态** | 特定数据组合、脏数据、首次使用/老用户差异 | 换新账号、换不同数据组合各试一组 |
| **环境** | 网络（弱网/切换 WiFi 到 4G）、机型、系统版本 | 用弱网工具模拟、换设备交叉验证 |
| **缓存与埋点** | 冷启动/热启动、缓存命中与否 | 杀进程重来 vs 直接重进，分别试 |
| **并发** | 多端同时操作、多人同时改同一数据 | 开两个浏览器/两台设备同时下单、同时改 |

方法就是初中生物课的**控制变量法**：一次只动一个变量，出问题的那轮变量就是嫌疑犯。每轮试验**记录尝试次数和出现次数**——"10 次出现 3 次"和"10 次出现 0 次"是完全不同的信息。

### 第三步：找开发要"眼睛"——日志与埋点

你自己复现不动了，别硬扛，让系统替你蹲守：

- **给开发提供四要素换日志**：时间点+账号+环境能唯一定位那次请求，开发拉服务端日志，异常堆栈直接写在那儿的情况太常见了
- **申请加埋点/日志级别**：关键路径加详细日志（或临时放开 debug 级别），下次它再犯，日志自动记下案发经过
- **测试侧的蹲守**：有条件的话写个循环脚本反复执行可疑操作 500 次跑一晚上，第二天看日志——**人蹲不到的，脚本蹲得到**，这也是不少"偶现"最后被证实为"必现但概率低"的路子

### 提单怎么写：偶现单的标准写法

处理到这一步还复现不了？照样提单，但**必须写清你已排除和已怀疑的范围**，在 bug 单上这样呈现：

```text
【标题】订单页-点击"提交订单"偶现无响应（约 10 次 3 次，test 环境）
【复现概率】10 次操作出现 3 次
【已排除】换 Chrome/Firefox 均出现；换测试账号 A/B 均出现
【已怀疑】快速连续点击时高发，慢速点击 10 次未出现
【现场材料】录屏 8 秒（异常那次）、正常次抓包对比、时间点 14:32:05/14:36:41
【建议排查方向】疑似按钮防重与请求竞态，请开发结合服务端日志核对这两次请求
```

这样的单子开发没法拒收：你给的不是"我复现不了你看着办"，而是**缩小后的包围圈**。

### 降级跟踪：销单是最后的选择

真到版本结束还复现不了，处理分三档：

1. **有伤害证据（截图/用户反馈）**：单子保留，状态挂起，写清"已收集材料+已排除项"，流转到下版本继续跟
2. **线上用户报来的**：让客服引导用户提供机型、时间、录屏，用真实用户数据继续缩小包围圈
3. **彻底石沉大海**：归档但**不删除**，标注"长期未复现，关闭跟踪"——下个同事再撞见，翻出你的单子就省了一半排查

## 举个例子

你测出行 App 的**打车叫车**功能，出现一次怪事：点"立即叫车"，按钮转了两秒圈，然后**什么都没发生**——没弹出司机匹配页，也没报错。再点一次，好了。之后再没撞见。

按流程走：先翻当时有没有留证据——有，你录屏了（起手就开着录屏是老测试的习惯）。记下四要素：14:32、账号 13800002222、test-04 环境、iOS 2.9.0。然后缩小变量：慢速点击 10 次没出现；把网络切到弱网（用工具限速 200ms 延迟）再点 20 次，**出现了 2 次**——包围圈缩到弱网。拿四要素找后端拉日志，发现在 14:32:05 有一次请求**超时后前端没有处理失败回调**：接口其实失败了，但前端只在成功时跳转，失败分支漏了提示。复现条件就此锁定：**弱网下叫车接口超时 > 2 秒必现**——所谓"偶现"，只是你办公室的网太好了。

这张单最后按必现收尾：弱网工具模拟 3 秒延迟，复现步骤一步到位，开发补上失败提示后关闭。"偶现"变"必现"的那一刻，是这个行当里最爽的瞬间之一。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 复现不了就不提单 | 有证据就要提，偶现单写清概率和已排除项照样有效 |
| 现场第一时间反复重试 | 先保全证据再复现，一刷新日志和状态就没了 |
| "我这边没问题"就关用户的单 | 环境差异正是偶现的温床，用户的环境你替代不了 |
| 不记概率只写"偶现" | 10 次 3 次和 10 次 0 次（只撞见过一次）信息量差很远 |
| 一个人闷头试三天 | 带上四要素找开发拉日志，服务端堆栈常直接写着答案 |
| 长期未复现就直接删单 | 归档留痕，下个撞见的人需要你这份"已排除清单" |

## 上手建议

1. **养成起手录屏的习惯**：测任何功能前先开录屏（QuickTime/系统录屏），代价几乎为零，偶现现场值千金
2. **建一张"偶现追捕表"**：每撞见一次偶现就记一行（时间、账号、操作、已排除项），同一现象攒到第二行时，交叉比对两行的共同点
3. **装一个弱网工具**：Charles 的 Throttle 或手机开发者选项，很多"偶现"一上弱网立刻现形
4. **学一套拉日志的流程**：知道团队的日志平台在哪、按什么字段（时间/账号/traceId）检索，你排查偶现的效率翻倍（查日志三件套见底子篇）
5. **偶现单提完就跟踪到底**：每轮新试验把"已排除"更新进单子备注，这张单子最终会成为团队的问题知识库
