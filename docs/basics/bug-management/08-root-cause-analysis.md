# 08｜缺陷根因分析：5Why 与鱼骨图

> 核心要点：**直接原因**解释"这次为什么错"，**根本原因**解释"为什么会允许这次错发生"。5Why 负责**纵向深挖**，鱼骨图负责**横向穷举**，修掉根因，同类 bug 才不会换个面目再来一遍。

## 打个比方

你开车，右前方总有**一声若有若无的异响**。

路边快修店的搞法：哪儿响敲哪儿，垫块胶皮，响声小了，交钱走人——三天后又在别处响。**这是修现象。**

老修车师傅的搞法：先问"什么时候响？过减速带响还是踩刹车响？"（**定位条件**），再上架拆检，发现是变速箱支架的一颗**螺丝松了**（直接原因），再追问"螺丝为什么会松"——上次保养时师傅没按扭矩上紧（根因），最后店里把"扭矩扳手复查"加进保养流程（**改流程**）。从此这辆车再没响过。

修 bug 同理：改一行代码是垫胶皮，问出"螺丝为什么松"并改掉上螺丝的手法，才算断根。**根因分析（RCA，Root Cause Analysis）分析的从来不是这一行代码，而是让这行错误代码活着走到线上的流程漏洞。**

## 展开讲讲

### 先分清：现象、直接原因、根本原因

| 层次 | 是什么 | 例子（金额算错的 bug） |
| --- | --- | --- |
| 现象 | 用户看到的问题 | 订单应付金额 220.00000001 元 |
| 直接原因 | 哪行代码错了 | 金额用了单精度浮点计算，精度丢失 |
| 根本原因 | 什么让这个错误发生并被放行 | 金额计算没有团队规范约束，评审时没人看数据类型，测试用例没覆盖小数场景 |

只修直接原因，下次同样的坑换个模块再踩——那个团队后来又在积分计算上栽了同一个浮点的跟头，因为**根因（无规范、评审不查类型、用例无覆盖）一个都没动**。

### 5Why：纵向挖到哪层该停

5Why 源自丰田生产方式：对一个问题连问五次"为什么"，每层答案必须是**上一层的事实性解释**，不是甩锅。还用运费那个例子（第 01 篇的后续）：

| 层 | 问 | 答 |
| --- | --- | --- |
| Why 1 | 为什么西藏订单运费显示 0 元？ | 后端计算运费时没查到西藏的运费模板，返回了默认值 0 |
| Why 2 | 为什么查不到西藏的模板？ | 运费模板配置表里没有西藏这条数据 |
| Why 3 | 为什么配置表漏了西藏？ | 运营按 Excel 模板逐省填写，漏了一行没人发现 |
| Why 4 | 为什么漏了没人发现？ | 配置保存后没有完整性校验，也没有 checklist 核对环节 |
| Why 5 | 为什么没有校验环节？ | 配置类操作没有纳入发布流程，被视为"运营随时改的数据"，游离在质量流程之外 |

挖到 Why 5，改进动作自然浮出水面：**给运费配置加"34 个省级行政区全覆盖"的保存校验**，再给配置变更加一次核对——这是流程级修复，修一行代码永远到不了这个深度。

**什么时候停**：答案落到"流程/规范/机制缺失"这一层，且改进动作能**阻断一类问题**而不只是这一个问题，就停；如果答案开始指向"某个人的失误"（运营手滑），别停——**继续问"为什么手滑能造成线上事故"**，人总会手滑，挡住手滑的机制才是根因。追问变成追责，团队以后就没人敢配合分析了。

### 鱼骨图：横向铺开穷举

5Why 适合**顺着一条线深挖**，但根因有时不止一条线，这时用鱼骨图（又名石川图，因形似鱼骨得名）：鱼头是问题，大骨是原因类别，小骨是具体猜测，**先穷举、后验证**。

软件研发常用的六大骨（借用制造业"人机料法环测"改造）：

| 鱼骨（类别） | 软件语境 | 典型小骨 |
| --- | --- | --- |
| 人 | 技能、经验、沟通 | 新人不熟悉模块、口头需求无确认 |
| 机 | 机器、环境 | 测试环境数据与生产不一致、环境版本落后 |
| 料 | 输入物料 | 需求文档有歧义、第三方接口文档过期 |
| 法 | 方法、流程 | 无评审、无自测标准、分支管理混乱 |
| 环 | 外部环境 | 弱网、高并发、跨时区、节假日流量 |
| 测 | 测试自身 | 用例遗漏场景、冒烟未覆盖、自动化未接入 |

用法三步：① 团队头脑风暴往骨上钉小骨，**只列不辩**；② 每根小骨标注"可验证/待验证/无法验证"；③ 对高嫌疑小骨逐一用数据或实验验证（查日志、查记录、复现实验），**验证过的才能进结论**——鱼骨图上一切没验证的都只是假设，这是新手最容易跳过去的纪律。

### 两个工具怎么配合

实战里两个工具是**先后关系**：先用鱼骨图把可能的原因铺满（防止只盯着第一条想到的线索），再对高嫌疑分支用 5Why 逐条深挖到流程层。鱼骨防漏，5Why 防浅。

## 举个例子

社交 App 年度复盘，有个问题被拎出来：**三季度"消息丢失"类线上反馈 17 起**。测试牵头做了一次 RCA。

先画鱼骨：人（新开发不熟悉消息队列）、机（MQ 集群偶发重启）、料（消息协议文档没写重试语义）、法（发送失败无兜底路径）、环（弱网高发）、测（用例没覆盖发送失败场景）。逐一验证：查 17 起的日志，14 起是 **MQ 偶发重启瞬间发送失败且无重试**，3 起是弱网超时同样无重试——"机"和"环"两根骨验证成立，"人""料"两根骨证据不足，剔除。

再对验证成立的分支问 5Why：为什么发送失败没有重试 → 客户端发送逻辑没实现失败重试 → 为什么没实现 → 需求文档只写了"发送消息"，失败语义没定义 → 为什么没定义 → 消息类需求的模板里没有"异常分支"必填栏 → 为什么没有 → 消息模块从未出过线上事故，需求模板一直没更新。

改进动作三层落地：代码层补发送重试+失败红感叹号（修现象）；需求模板给消息类需求加"异常分支"必填栏（修流程）；用例库补"消息发送失败"标准场景集（补测试盲区）。四季度同类反馈降到 2 起。**那张鱼骨图后来贴在团队 Wiki 上，成了新需求评审时的自查清单**——根因分析的产出从来不止一份报告。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 修掉直接原因就叫闭环 | 换个模块再犯同类错时，你会看到只修现象的账单 |
| 问到"某人失误"就停 | 人总会手滑，让手滑穿不透的机制才是根因 |
| 5Why 硬凑满五层 | 停在"能阻断一类问题的流程层"即可，两三层挖透也行 |
| 鱼骨图钉完骨就下结论 | 没验证的小骨只是假设，结论必须靠日志/数据/实验支撑 |
| RCA 只在重大事故后做 | 高频小问题同样值得轻量分析，攒到季度一起算账更难还原 |
| 分析变追责大会 | 一旦和绩效挂钩，下次没人给你真实信息 |

## 上手建议

1. **给手头的 bug 补一次 5Why**：挑一个你最近提的重复出现的 bug，在笔记本上连问五个为什么，写到"流程层"为止，练三次就有手感
2. **存一张团队鱼骨模板**：把本文六大骨做成共享画板模板，复盘会直接往上钉，比每次重画快
3. **验证优先于罗列**：分析会上每钉一根小骨就问一句"这个怎么验证、谁去验"，避免变成想象力的聚会
4. **把 RCA 结论喂给用例**：每个根因对应的"测试盲区"，当场转成用例清单补进用例库——这是根因分析对测试自己最直接的回报
5. **报告里分三层写**：现象/直接原因/根本原因各一段，改进动作和根因一一对应，领导最认这种结构
