# 02｜缺陷生命周期：从新建到关闭的完整旅程

> 核心要点：bug 单不是提完就完了，它像快递一样在**测试、开发、产品**之间流转，每个状态都有明确的**触发人和去向**。看懂状态机，你才知道自己的单子此刻归谁、下一步等谁。

## 打个比方

你寄出一个**快递包裹**，它的旅程你其实很熟悉：

下单揽收（**新建**）→ 网点揽件发出（**确认接收**）→ 分拣中心处理（**修复中**）→ 派送签收前你要验货（**待验证**）→ 验货没问题签收（**关闭**）。

中间还有分支：卖家说"你拍错规格了，这不是质量问题"，申请拒收走**拒绝**流程，得找平台客服（产品）仲裁；"双十一人手不够，下周发"，这是**延期**；你验货发现尺码还是不对，**拒签重新派送**——这就是**重新打开**。

快递每个节点都有人负责、有状态可查，你不会对着一个"运输中"的包裹干着急。bug 单一样：**状态告诉你"球在谁脚下"**，生命周期管理就是保证每个球都有人踢、不丢球。

## 展开讲讲

### 主线：六站走完才算交付

不同团队的状态命名略有出入，但主线大同小异：

| 状态 | 谁触发 | 含义 | 下一步去向 |
| --- | --- | --- | --- |
| 新建 New | 测试 | 提交 bug 单，附复现步骤 | → 确认/分配（开发） |
| 已确认 Open | 开发（或组长分配） | 开发看过单子，承认是 bug、接下活 | → 修复中 |
| 修复中 In Progress | 开发 | 定位、改代码、自测 | → 已修复 |
| 已修复 Fixed | 开发 | 改完并自测通过，等测试回归 | → 待验证（测试） |
| 待验证 Verified/待回归 | 测试 | 测试按原步骤复现验证 | 验证通过 → 已关闭；不通过 → 重新打开 |
| 已关闭 Closed | 测试 | **只有测试有权关单**，验证通过才关 | 终点（理论上） |

两个岗位边界要记牢：**开发把单子改成"已修复"，代表他说"我修好了"；测试把单子改成"已关闭"，才代表"我确认修好了"。**关单权在测试手里，这是质量把关的最后防线。

### 分支一：拒绝——"这不是 bug"

开发看完单子直接把状态改成**拒绝（Rejected）**，理由通常三类：

| 拒绝理由 | 真实含义 | 测试怎么接 |
| --- | --- | --- |
| 按设计如此 | 和产品确认过的行为 | 拉产品当面对需求，产品站开发就关单 |
| 无法复现 | 开发照你的步骤走不出来 | 补充复现信息：环境、账号、录屏（见第 07 篇） |
| 重复提交 | 和别的单子是同一个问题 | 确认后关联到主单，别急着删，留关联痕迹 |

**拒绝不是终局，是"踢回来协商"**。协商不成找产品或测试经理裁决，双方都不许悄悄把对方的状态改掉了事。

### 分支二：延期——"这个版本修不了"

有些 bug 大家都认，但本版本来不及修：改动静太大、依赖第三方、或者触发概率极低。走**延期（Deferred/Postponed）**流程：

- 必须有**有决策权的人**（产品/项目经理）审批同意，不能开发单方面延
- 延期单要写清：延到哪个版本、规避方案是什么、风险谁承担
- 延期 ≠ 关闭。下个版本开始时，延期单要**重新捞出来**进入待办，最常见的烂账就是延期单石沉大海，谁都不捞

### 分支三：重新打开——"你修的那个没修好"

测试在待验证环节复现，发现**问题还在**，或者引出了新问题，把单子从"已修复"改回**重新打开（Reopened）**。此时单子回到开发手里，流程重新走一轮修复→验证。

重新打开率高不是好事：它说明"已修复"的含金量不足——要么开发自测敷衍，要么修复引入了新问题。**一张单被反复打开三次以上，就该拉上开发当面复现对齐，而不是继续在状态里打乒乓球。**

### 特殊状态：挂起

还有一种**挂起（Pending/Hold）**：bug 本身有效，但被外部条件卡住——等第三方接口修复、等测试数据、等需求澄清。挂起单要写清"卡在等什么"，条件解除立刻捞回，否则它会和延期单一起变成陈年烂账。

## 举个例子

电商 App 提测，你提了一张单：**"提交订单页，收货地址选西藏拉萨后，运费显示 0 元，预期运费 15 元"**（严重程度：高）。

1. **新建**：你 16:20 提单，附操作步骤、账号、截图
2. **已确认**：开发小李 17:00 接单，回复"运费模板漏配了西藏，确实是 bug"
3. **修复中 → 已修复**：次日上午小李配好模板，自测通过，改状态留言"配置已更新，请在 test 环境验证"
4. **待验证**：你按原步骤重测——拉萨运费显示 15 元，通过；顺手又点了个新疆乌鲁木齐（16 元）和上海（免运费），都正常
5. **已关闭**：你关单

一周后用户反馈又来了：**青海的运费也是 0**。你找到原单，确认青海当时也没验证到，把单**重新打开**，注明"补青海，运费模板同类区域请全量自查"。开发这次不只补青海，把全国 34 个省级行政区的运费模板全对了一遍——这就是生命周期里"重新打开"真正的作用：**逼着问题按类修，而不是按下葫芦浮起瓢。**

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 提完单就等，不追踪状态 | 单子卡在"已确认"三天没人动，你要去催，状态机不是许愿池 |
| 开发说修好了就关单 | 关单权在测试，没亲手复现验证过的单一个都不能关 |
| 被拒绝了就默默认栽 | 拒绝是协商的开始，找产品对需求，别自己消化 |
| 延期单记在心里 | 延期必须走审批留痕，版本启动时逐条捞出，靠记性必丢 |
| 重新打开 = 关系闹僵 | 重新打开是正常流程动作，对事不对人，反复打开才需要升级沟通 |
| 挂起的单从此不管 | 挂起要写清解除条件，每周巡一遍挂起列表 |

## 上手建议

1. **画一张自己团队的状态机**：打开公司缺陷工具，把实际用的状态和流转规则抄成一张表贴工位上，第一天就对齐"我们团队怎么流转"
2. **每天上班先巡单**：待我处理（待验证、被拒绝、待补充信息）的单子过一遍，别让球停在自己脚下超过一天
3. **关单前跑一圈定向回归**：验证修复点之外，顺带测紧邻功能，防止"修 A 坏 B"被关单埋掉
4. **给延期和挂起建专属看板视图**：在工具里存一个过滤器，每周五扫一遍，版本启动时逐条捞回
5. **状态备注必写**：每次改状态都留一句话（为什么拒、延到哪版、验证了哪些值），半年后回看这张单的人才不用靠猜
