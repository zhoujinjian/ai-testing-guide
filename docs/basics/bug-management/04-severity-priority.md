# 04｜严重程度与优先级：不是一回事

> 核心要点：**严重程度（Severity）衡量的是 bug 对系统伤害多重，优先级（Priority）衡量的是修它有多急**。前者看技术影响，后者看业务排期，两个维度一组合，"严重但不急""轻微但很急"就都解释得通了。

## 打个比方

医院**急诊分诊台**每天在干的就是这件事。

一位车祸重伤员被抬进来——**伤得很重**（严重程度：致命），分诊护士立刻叫抢救室（优先级：马上）。一位糖尿病患者来复查，情况稳定但病根不轻——伤得重，但今天不用抢救，排到下午专科门诊（**严重但不急**）。一位小伙子手指划了个口子，血看着吓人——伤得轻，但他疼得受不了且处理只要五分钟，医生顺手就给缝了（**轻微但急**）。

护士心里有两把尺子：**这病本身多重**，和**该排在谁前面**。两把尺子量出来的结果经常不一样，医院从来不混着用。测试评级也一样：Severity 是医生看伤情，Priority 是分诊台排顺序。

## 展开讲讲

### 两个维度各自怎么分级

先看严重程度，主流分四级（有的团队三级，逻辑一致）：

| 级别 | 名称 | 判定标准 | 例子 |
| --- | --- | --- | --- |
| S1 | 致命 | 系统崩溃、主流程走不通、数据丢失、安全漏洞 | 支付环节 App 闪退，用户无法完成付款 |
| S2 | 严重 | 主要功能错误、结果错误 | 下单金额计算错误，多扣了钱 |
| S3 | 一般 | 次要功能异常、有替代路径 | 订单列表筛选项失效，但搜索仍可用 |
| S4 | 轻微 | 界面瑕疵、提示文案、体验问题 | 按钮图标错位、错别字 |

再看优先级，衡量的是**修复排期的先后**：

| 级别 | 含义 | 典型决策 |
| --- | --- | --- |
| P0 | 立即修，阻塞发布/影响上线 | 当天拉人加班修，修不完不发版 |
| P1 | 本版本必须修 | 排进本迭代修复计划 |
| P2 | 时间允许就修 | 本版修不完可带病上线，下版修 |
| P3 | 待办池里排队 | 和需求一起排期，随缘修 |

### 四象限：组合起来才是真实世界

Severity 和 Priority 是两个独立旋钮，组合出四种真实场景：

| 组合 | 场景 | 典型例子 |
| --- | --- | --- |
| **严重 + 急**（S1×P0） | 正在伤害用户，立刻止血 | 支付页崩溃、线上资损、用户密码明文展示 |
| **严重 + 不急**（S1/S2×P2） | 伤害大，但触发条件很窄 | 深夜灰度期间才暴露的致命缺陷——影响面被灰度比例压着，修复可排到放量前 |
| **轻微 + 急**（S4×P0/P1） | 伤得不重，但等不起 | **首页错别字**——技术上只是个文案问题（S4），可它在首页每天被几百万用户看到，公关影响大，必须当天改 |
| **轻微 + 不急**（S4×P3） | 小瑕疵，排队 | 设置页某个图标颜色和设计稿差一个色号 |

**首页错别字**是讲烂了但最经典的教学案例：新手里最常见的行为是"错别字嘛，S4，不急，扔待办池"；而懂业务的人会评 S4×P1——Severity 忠实反映技术伤害（轻微），Priority 反映业务紧迫性（首页脸面，得快改）。**两个字段各说各的话，这才是这套评级的设计意图。**

### 谁定 Severity，谁定 Priority

分工有惯例，也有弹性：

- **Severity 通常测试定**：你发现的问题，你对技术影响判断最直接，按标准照评
- **Priority 通常由开发负责人/产品定或确认**：修不修、先修谁，牵扯排期和业务判断，是资源决策
- 两者都可以协商，但**改动要有理由并留痕**：开发觉得你评高了，可以说理；单方面悄悄改低你评的级别，是流程事故

### 为什么会"严重但不急"

新手最难理解的就是这一格，多给两个例子帮你看透：

- 某致命崩溃**只在安卓 4.4 及以下机型触发**，而产品早已不再适配 4.4，活跃用户占比 0.01%——伤害确实致命，但几乎没有用户够得着，降优先级合理
- 某资损漏洞需要**同时满足**三个条件才触发（特定商品 + 特定组合券 + 凌晨跨天时刻），当天有运营手段兜底（先下架问题商品），修复可缓一天

注意逻辑：**"不急"永远是因为伤害有客观的隔离带（灰度、版本占比、触发概率、运营兜底），不是因为你不想修。**隔离带消失的那一刻（灰度放量、兜底下架），优先级必须立刻升回去。

## 举个例子

电商大促前三天，测试报出四个 bug，评完级排期长这样：

| Bug | Severity | Priority | 处理 |
| --- | --- | --- | --- |
| 支付页在 iOS 18 上白屏 | S1 | P0 | 当晚修复，次日回归 |
| 凑单页"满减"写成"满尖" | S4 | P1 | 大促前随包修文案——大促页面每天千万级曝光 |
| 积分商城兑换后积分未扣减 | S2 | P2 | 大促期间先下架积分商城入口兜底，大促后修 |
| 收藏夹图标在深色模式下偏灰 | S4 | P3 | 进待办池 |

看这份排序就明白两把尺子怎么配合：**白屏和错别字都是"马上修"，但理由完全不同**——一个靠 Severity 拿到 P0，一个靠业务曝光拿到 P1。积分那个最妙：S2 够重，但用"下架入口"这一运营兜底把紧迫性压了下来，给开发腾出人手修白屏。评级从来不只是打标签，**它是排兵布阵**。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| Severity 高 = Priority 必须高 | 灰度、机型占比、触发概率都能把急迫性压下来，四象限都真实存在 |
| 错别字都是最低级等下版 | 位置决定紧迫性，首页/大促页的文案问题常是 S4×P1 |
| 全部评 S1P0 引起重视 | 全是紧急等于没有紧急，狼来了三次后你的评级就没人信了 |
| Severity 由开发说了算 | 技术影响测试评最直接，Priority 排期开发/产品确认，协商改要有痕 |
| 评完级就不管了 | 兜底下架、灰度放量时优先级要重估，评级是动态的 |
| 拿 Severity 当奖金筹码虚高评 | 一次两次有效，长期看毁掉的是自己的评级公信力 |

## 上手建议

1. **入职第一周要两份量表**：找测试主管要团队的 Severity/Priority 判定表，没有就主动照本文表格式起草一份，评审一次全组共用
2. **提单时两个字段分开写理由**：各写一句话（为什么这个伤害等级、为什么这个急迫程度），评审和撕扯减少八成
3. **背下四象限各一个自己的例子**：拿团队真实 bug 各配一例，面试被问"严重度和优先级的区别"时直接讲案例
4. **盯"严重但不急"的单子**：给自己建一个 S1S2×P2P3 的过滤器，每周扫一遍隔离带是否还在（灰度是否放量了、兜底是否下架了）
5. **参加一次排期会**：争取旁听开发排修复顺序的会，亲眼看 Priority 是怎么被人力和版本节点掰弯的，比读十篇文章都明白
