# 09｜测试必备 Linux：查日志三件套

> 核心要点：测试环境的服务几乎都跑在 **Linux 服务器**上，bug 发生的"现场"就是日志文件。查日志三件套——**cd + less（翻）、grep（搜）、tail（盯）**——覆盖测试查日志九成的场景，最核心的招数是**按时间戳定位一次请求，再用单号或 traceId 把全程串起来**。

## 打个比方

超市丢了货，经理调**监控录像**：没人会从 24 小时前的第一帧开始看——先**按时间点跳到 14:32**（grep 时间戳），再看那几分钟的前后画面（上下文），还不死心就**实时盯着屏幕**等它再发生一次（tail -f 跟踪）。

日志就是系统的监控录像：每行带着时间戳，谁来过、干了什么、哪里报了错，全都录着，而且**页面看完就没了、日志永远留着**。三件套就是你手里的遥控器：跳转、回放、快进。测试的环境通常不允许你装图形界面，一条条命令就是你唯一的遥控器。

## 展开讲讲

### 第 0 步：先进"监控室"——cd 和 ls

用账号 ssh 登录测试服务器后，日志一般在 `/var/log/` 或应用自己的目录下：

```bash
cd /var/log/mall-app
ls -lh
```

`ls -lh` 的 `-h` 把文件大小显示成人能读的格式（200M 而不是一长串字节数）。**看"最后修改时间"最新的那个文件**——正在被写入的就是它。顺带认识两个常见命名：`app.log.1`、`app.log.20261026` 是被切走的旧日志，`.gz` 结尾的是压缩归档。找日志前先想清楚：要找的那天，落在哪个文件里。

### 件套一：less——翻着看

```bash
less app.log
```

进去之后靠按键操作，常用的就四个：

| 按键 | 作用 |
| --- | --- |
| `/关键字` 回车 | 向下搜索，`n` 跳下一个、`N` 跳上一个 |
| `G` | 跳到文件末尾（排查刚发生的问题从尾部看起） |
| `g` | 回到文件开头 |
| `q` | 退出 |

几百 M 的大文件 less 也不卡，因为它按页加载——这是它比 cat 强的地方。

### 件套二：grep——按条件搜

```bash
grep 'ERROR' app.log                  # 搜出所有 ERROR 行
grep '2026-10-27 14:32' app.log       # 按时间戳搜
grep -i 'timeout' app.log             # -i 忽略大小写，Timeout 也命中
grep -c 'ERROR' app.log               # 不看内容，只数有几条
grep -C 5 'TD20261027001' app.log     # 命中行前后各带 5 行上下文
```

`-C 5` 是排障神器：单号那一行前后发生了什么，一屏看全，等于监控回放里"往前倒五分钟"。

### 件套三：tail——盯实时

```bash
tail -n 200 app.log                          # 只看最后 200 行
tail -f app.log                              # 实时滚动，新日志立刻刷出来
tail -f app.log | grep --line-buffered 'ERROR'   # 只盯新增的 ERROR
```

第三条里的 `--line-buffered` 必须带：grep 默认攒够一批缓冲才输出，不加它，你会盯着一个纹丝不动的屏幕误以为"没有报错"。退出跟踪按 `Ctrl + C`。

### 进阶两招：多文件搜与压缩日志

**跨文件搜**：日志常按天切成多个文件（app.log、app.log.20261026……），一个个切进去 grep 很烦，用 `-r` 对整个目录递归搜：

```bash
grep -r 'TD20261027001' /var/log/mall-app/
```

**搜压缩的历史日志**：更早的日志通常打包成了 `.gz`，grep 直接搜会漏，要换 `zgrep`：

```bash
zgrep 'ERROR' app.log.2026-10-20.gz
```

这两招解决的是同一个问题：**线索未必在今天这个文件里**——用户投诉的可能是三天前下的单，今天的日志里当然搜不到。

### 串起来：从时间戳定位一次请求

单条命令是零件，排障套路是整机。用户反馈"14:32 下单失败"，五步走：

| 步骤 | 命令 | 目的 |
| --- | --- | --- |
| 1. 拿线索 | 问清用户账号和大致时间 | 锁定时间窗口 |
| 2. 按时间搜 | `grep '2026-10-27 14:32' app.log` | 找到那几秒的所有日志 |
| 3. 拿单号 | 从结果里找 orderId / traceId | 拿到贯穿全程的线索 |
| 4. 搜全程 | `grep -C 10 'TD20261027001' app.log` | 这次请求前后 10 行上下文 |
| 5. 跨服务 | 拿 traceId 去订单、支付服务的日志再 grep | 微服务架构下串起全链路 |

第五步值得多说一句：现在的系统动辄拆成网关、订单、支付、库存好几个服务，一次请求的日志散落在好几台机器上。traceId 就是贯穿全链路的"行李牌"——网关收到请求时生成，一路上每个服务都带着它打日志。拿 traceId 把各服务的日志各 grep 一遍，按时间戳排起来，这次请求的完整旅程就复原了。

## 举个例子

电商项目，用户反馈下单提示"系统繁忙"。按五步走：`grep '2026-10-27 14:32' app.log` 搜到十几行，其中一行是 `INFO orderId=TD20261027001, traceId=7f3a9c, userId=10086`——单号和 traceId 到手；`grep -C 10 'TD20261027001' app.log` 一看，紧接着一行：

```text
2026-10-27 14:32:15 ERROR StockService: 扣减库存失败 skuId=SK9981
java.sql.SQLIntegrityConstraintViolationException: Duplicate entry 'SK9981-10086'
```

真相大白：并发扣库存时唯一键冲突。你把**时间、单号、traceId、这段 ERROR** 四样东西贴进 bug 单——后端不用再问"什么时间、哪个用户、日志呢"，直接对着堆栈修。这就是测试亲手查日志的价值：**提单自带现场，一来一回的沟通全省了**。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 用 cat 打开大日志 | 几百 M 直接刷屏卡死终端，翻看一律 less、看尾部一律 tail |
| tail -f 接管道不加 --line-buffered | grep 攒缓冲不输出，活日志看着像死日志 |
| 见到 ERROR 就认定是 bug | 有些 ERROR 是正常业务拦截（参数校验拒绝），要结合上下文判断 |
| 只在网关一个服务里搜 | 微服务架构下请求层层转发，拿 traceId 把链路上的服务都搜一遍 |
| grep 不加时间、不加条件全量搜 | 全库大海捞针又慢又刷屏，先时间戳后单号是铁律 |
| 日志里翻不到就说"没线索" | 线索要先从页面、接口响应里拿（单号、traceId），再回日志里搜 |

## 上手建议

1. **要一个日志路径说明**：问开发或运维要测试服务器地址、账号、各服务日志路径，记进自己的小抄，别每次现问
2. **less 四个按键练到肌肉记忆**：`/`、`n`、`G`、`q`，一天就熟，终身受用
3. **把三件套命令存成模板**：按时间搜、按单号搜、盯 ERROR 三条，用的时候改个参数就发
4. **下一个 bug 亲手查一次日志**：把时间戳和 ERROR 段落贴进 bug 单，你会发现开发回单速度快了一倍
5. ** Ctrl + C 记牢**：tail -f 不会自己退出，看完记得按它放终端自由
