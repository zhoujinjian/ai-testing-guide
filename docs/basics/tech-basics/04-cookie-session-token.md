# 04｜Cookie、Session 与 Token

> 核心要点：HTTP 是无状态的，服务器记不住你是谁，于是有了三种"认人"方案——**Cookie 是装凭证的袋子（载体），Session 把账记在服务端，Token 把凭证发给你自己保管**。三者不是三选一的并列关系，Cookie 和 Session 是配合关系，Token 是另一套思路。

## 打个比方

想象一个景区，门口要验票才能玩每个项目。HTTP 的规矩是"每个项目入口都不记人"，所以要发凭证：

**方案一（Cookie + Session）**：你在售票处报身份证（登录），售票员在**登记本上**记下"张三 = 0088 号"，然后给你一个**手环**，上面只写了 0088（Set-Cookie）。之后你玩任何项目，把手环递给检票员，检票员**翻登记本**查到"0088 是张三，票到下午 6 点"——放行。手环本身没有信息，账都在登记本上，登记本就是 Session（存在服务端），手环就是 Cookie（存在你浏览器里）。

**方案二（Token）**：景区升级了，发一种**自带防伪芯片的手环**：里面直接刻着"张三、VIP、有效期到 18:00"，还有景区的**激光防伪标**（签名）。检票员扫码，防伪标对得上就放行——**不用再翻登记本**。这个手环就是 Token：信息自己带着，服务端只验签名、不查账。

两种方案的命门不同：登记本丢了（Session 服务重启）所有人都得重新买票；防伪手环一旦发出去，**退票很难**——你退了票（退出登录），手环在过期前理论上还能扫，这正是 Token 的测试点。

## 展开讲讲

### 三者各是什么

| 名称 | 存在哪 | 是什么 | 一句话 |
| --- | --- | --- | --- |
| Cookie | 浏览器（客户端） | 一小段随请求自动带上的数据 | 装凭证的袋子，机制本身不带业务 |
| Session | 服务器 | 以 sessionId 为 key 的用户状态记录 | 账记在服务端，客户端只拿编号 |
| Token | 客户端保管、内容自包含 | 带签名的凭证字符串（常见 JWT） | 凭证发给你，服务端只验真伪 |

### 一次登录的完整过程

**Cookie + Session 模式：**

```http
# 1. 你提交账号密码
POST /api/login HTTP/1.1

# 2. 服务器验证通过，登记 Session，下发手环
HTTP/1.1 200 OK
Set-Cookie: sessionId=abc123; Path=/; HttpOnly

# 3. 之后每个请求，浏览器自动带上
GET /api/cart/list HTTP/1.1
Cookie: sessionId=abc123
```

**Token 模式：**登录成功后响应体里返回 token（常见 JWT，形如 `eyJhbGciOi...` 的三段式长串），前端把它存起来，之后每个请求放在头里带上：

```http
GET /api/cart/list HTTP/1.1
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.eyJ1aWQiOjEwMDg2fQ.x7Kq
```

顺手拆开 JWT 看看长什么样：它用两个点分成**三段**——头部（声明签名算法）、载荷（uid、过期时间这类信息）、签名（防篡改的防伪标）。前两段只是 base64 编码，**解码就能看**，所以载荷里绝不该出现手机号、密码这类敏感信息；签名保证的是"内容没被人改过"，不保证"没人看得见"。

### 为什么要从 Session 走到 Token

Session 的账本只有一本，服务器一多就麻烦：

| 痛点 | Session | Token |
| --- | --- | --- |
| 多台服务器 | 账本要共享（通常搬进 Redis），不然第 2 台不认你 | 哪台都能验签名，天然支持横向扩容 |
| App / 小程序 | 未必有 Cookie 机制，得模拟 | 就是个字符串，放头里即可，端无关 |
| 服务端压力 | 每个用户占一条存储 | 不存，只做签名校验 |
| 主动踢人下线 | 删账本那一行即可，很干脆 | 要额外加黑名单才办得到 |

所以现在的 App 和前后端分离系统多用 Token，传统网页系统 Cookie + Session 依然大量存在——测试两种都得会认。

### 登录态测试的五个检查点

1. **过期表现**：凭证过期后再操作，应返回 401 并引导重新登录，而不是报 500 或直接静默失败
2. **篡改防护**：把 token 改一个字符再发，服务器必须拒绝——验签失败的用例不能漏
3. **退出登录**：退出后旧凭证再调接口应被拒（Token 模式重点测，很多系统这步做不干净）
4. **多端互踢**：手机和网页同时登录，改密码后另一端应被踢下线
5. **越权**：拿 A 的凭证去请求 B 的订单详情，必须 403——凭证只证明"你是谁"，不等于"你能看所有数据"

## 举个例子

测电商 App"我的订单"页，怀疑登录态有问题：页面偶发提示"登录信息已失效"。排查就按这条链走——F12 抓包看"我的订单"接口：请求头里 Authorization 带的 token 和登录时拿到的是不是同一个？失效场景下服务器回了什么码？如果回的是 **401 且前端没处理**（没跳登录页，只在页面上留了一句失效提示），那就是前端 bug；如果 token 明明没过期却 401，抓包把 token 复制到 Postman 里单独重发（见第 07 篇）——还 401 就是后端校验问题，排查方向立刻从"前端"切到"后端"。这套"看凭证 → 看状态码 → 单独重发"的套路，是登录态问题的标准三步。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| Cookie、Session、Token 三选一并列 | Cookie 是载体，常和 Session 搭配；Token 是另一套方案，不是同一维度的东西 |
| Session 就存在浏览器里 | Session 的账在**服务器**，浏览器里只有 sessionId 这个编号 |
| Token 是加密的 | JWT 默认只是**编码 + 签名**，内容 base64 一解就能看，别把 token 里的信息当保密的 |
| 退出登录就万事大吉 | Token 没过期前可能仍有效，退出后旧 token 还能用是真实存在的高频 bug |
| 凭证有效就能访问一切数据 | 还要过越权这一关：A 的 token 访问 B 的数据必须被拒 |
| Cookie 被禁了系统就完了 | 现代接口多用 Header 带 token，不依赖 Cookie，App 尤其如此 |

## 上手建议

1. **看一次自己的登录响应**：F12 抓登录请求，看清楚你们系统发的是 Set-Cookie 还是 body 里的 token——这决定你后续所有接口测试怎么带凭证
2. **在 Postman 里配全局凭证**：把 token 存成变量，所有请求自动带，别每条手抄（第 07 篇有操作步骤）
3. **改一个字符做篡改测试**：token 尾部改一位重发，确认返回 401 而不是 200
4. **把过期时间问清楚**：问开发测试环境 token 多久过期，别把"过期了"当 bug 提
5. **背下三步排障口诀**：看凭证、看状态码、单独重发——登录态问题按这个顺序走，不绕路
