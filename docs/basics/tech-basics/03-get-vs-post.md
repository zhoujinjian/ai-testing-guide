# 03｜GET 与 POST 的区别

> 核心要点：GET 和 POST 的区别要**分三层答**——表面区别（参数在哪、长度、缓存）、语义区别（GET 是取数据、幂等，POST 是交数据、会改状态）、安全误区（"POST 比 GET 安全"只是相对"不被人一眼看到"而言，**和加密、和防篡改完全无关**）。

## 打个比方

把这两个方法想象成去**政务大厅**办两件不同的事。

**GET 是在大厅的自助查询机上查社保记录**：你输入身份证号，机器打出结果给你。查一次和查一百次，记录都不会变；你查询的条件就显示在屏幕上，排在你后面的人瞄一眼就能看见你查了什么。因为只是"看"，不改任何数据，**查坏了系统这种事不存在**。

**POST 是向窗口提交一份申请表**：办居住证、改名字，交上去之后你的档案就真的变了。所以表格要装进信封（请求体）、同一份表不小心交两次就可能办出两张证（重复提交）、表上可以写很长的内容，也不怕后面的人看见（但信封没上锁，想看还是能拆）。

对应关系：查询机 = GET（参数挂在明面上、只读、可随意重复），申请表 = POST（参数装在体里、改变状态、要防重复提交）。

## 展开讲讲

### 第一层：表面区别（一眼能看到的）

| 对比项 | GET | POST |
| --- | --- | --- |
| 参数位置 | 拼在 URL 后面 `?key=value` | 放在请求体里 |
| 参数长度 | 受 URL 长度限制（浏览器约 2KB~8KB） | 理论上大得多，常用于传文件 |
| 编码 | 只支持 URL 编码 | 支持多种，application/json 最常见 |
| 浏览器行为 | 可收藏成书签、有缓存、会留在历史记录 | 不可收藏、默认不缓存 |
| 请求体 | 一般没有 | 有 |

这层区别是**实现层面的习惯**，不是铁律——技术上 GET 也能带 body（很多服务端直接忽略），POST 也能把参数放 URL 上。面试只答到这层，会显得像背书。

### 第二层：语义区别（真正该记住的）

按 HTTP 的设计意图，两者是**不同的动作**：

- **GET 是"获取"**：只读不写，理论上**幂等**（同一个请求发一次和发一百次，服务器上的数据都不变），也**安全**（这里的"安全"专指"不会改动服务器数据"，不是防偷看）
- **POST 是"提交"**：目的就是让服务器**改变状态**——下单、改密码、发帖。它既不幂等也不"安全"：点两次"支付"可能扣两次钱

语义决定了用法：查询列表用 GET，创建订单用 POST。REST 风格接口还延伸出 PUT（整体更新，幂等）、DELETE（删除，幂等）、PATCH（部分更新）——判断标准都是"重复执行同一请求，结果变不变"。

### 什么场景该用哪个方法

| 场景 | 该用 | 为什么 |
| --- | --- | --- |
| 搜索、看列表、查详情 | GET | 只读、可收藏成书签、可缓存 |
| 登录、下单、发帖 | POST | 改变服务器状态，要防重复提交 |
| 全量更新一条资料 | PUT | 幂等：发多少次结果都一致 |
| 删除一条记录 | DELETE | 幂等：删一次和删多次结果都是"没了" |

选法口诀就一句：**这个请求重复发一次，服务器数据会不会变**——不会变选幂等的方法，会变就用 POST，并把防重复提交测到位。

### 第三层：安全误区（面试的加分点）

流行说法"POST 比 GET 安全"，**半对半错**，要拆开说清楚它对在哪、错在哪：

| 说法 | 对错 | 实际情况 |
| --- | --- | --- |
| GET 参数在 URL 里，会被看到 | 对 | 会进浏览器历史、服务器访问日志、用户随手截图 |
| POST 参数在 body 里，别人看不到 | 错 | 抓包工具看得一清二楚，HTTP 是明文传输 |
| POST 比 GET 难攻击 | 错 | SQL 注入、XSS 对 GET、POST 一视同仁 |
| 想安全就用 POST | 错 | 想防偷看要上 **HTTPS**，想防篡改要**签名**，和 GET/POST 无关 |

一句话总结：**POST 的"安全"只是相对"不被路过的人一眼瞄到"而言的遮羞布，不是保险柜。**密码用 POST 传是为了不留在浏览器历史里，但如果不走 HTTPS，它在中途照样是明文。把这句说清楚，这道题就从"背过"变成"懂了"。

## 举个例子

电商 App 的搜索和下单，正好各用一种方法。在 F12 的 Network 里搜一次"手机壳"：

```http
GET /api/search?keyword=手机壳&page=1&pageSize=20 HTTP/1.1
```

参数全在 URL 上：搜什么、第几页。你把这条 URL 发给同事，他直接打开就是同样的搜索结果——GET 的参数自包含、可分享、可缓存。

再看点"提交订单"：

```http
POST /api/order/create HTTP/1.1
Content-Type: application/json

{"addressId":301,"skuId":"SK9981","count":2,"couponId":"C200"}
```

参数装在请求体里。测试时这里有两个经典检查点：一是**参数从 URL 挪到 body 后，后端还认不认**（联调常见问题）；二是**快速连点两次"提交订单"**，会不会生成两笔订单——POST 不幂等，前端必须加防重，这正是"语义区别"落到测试上的样子。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| POST 传数据加密了 | HTTP 下 POST 一样是明文，加密靠 HTTPS，跟方法无关 |
| GET 不能传中文/长参数 | 能传（URL 编码后），只是别超 URL 长度限制 |
| GET 一定没有请求体 | HTTP 没禁止，只是语义上不该用，服务端通常忽略 |
| 幂等就是"返回结果一样" | 是"服务器状态不变"，不是响应内容一样 |
| 所有查询都用 GET、所有写入都用 POST | 还有 PUT/DELETE/PATCH，语义更细，见 REST 风格接口 |
| POST 比 GET 慢 / GET 比 POST 快 | 差异可忽略，性能问题不从这里找 |

## 上手建议

1. **F12 对比两条请求**：找一条 GET（搜索）和一条 POST（登录），对照 URL 和请求体的位置，把第一层区别看进眼里
2. **测一次重复提交**：找项目里任何"提交"按钮连点 5 次，看会不会产生重复数据——这是 POST 不幂等最直观的代价
3. **检查密码走没走 HTTPS**：登录请求的 URL 是 http 还是 https，GET 还是 POST，两个维度分开判断
4. **面试按三层背骨架**：表面区别 → 语义与幂等 → 安全误区，每层两三句，比背十几条对比表更出彩
5. **看接口文档对方法**：前端调用的方法和文档不一致（文档写 POST、实际发 GET）时，多半有坑，值得提出来
