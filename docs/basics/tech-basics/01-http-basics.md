# 01｜HTTP 协议入门：请求与响应

> 核心要点：HTTP 就是浏览器（或 App）和服务器之间**一问一答的通信规矩**——客户端发一个**请求**，服务器回一个**响应**，两边都按固定的三段式格式说话。测试天天说的"抓包""调接口""看返回"，看的都是这一对请求和响应。

## 打个比方

HTTP 就是**寄快递**的规矩。

你在网上买了东西要寄退换货：先填一张快递单——寄给谁（地址）、你是谁（寄件人）、里面是什么（品名），再把货装进箱子交给快递员。这一整套动作就是浏览器发出的**请求**：地址是 URL，寄件人信息是一堆"头"，箱子里的货是**请求体**。

卖家收到包裹，处理完给你回一张**回执**：签收成功还是拒收（结论）、回执上的备注（说明）、有时还附带给你的东西（你要的数据）。这就是服务器的**响应**。

快递单和回执的格式是全行业统一规定的，所以任何快递员和任何卖家都能对接——HTTP 之所以叫"协议"，就是这份**双方约定好、谁都必须遵守的格式**。浏览器和服务器可能隔着半个地球、用着完全不同的技术，照样能通信，靠的就是都按这张"单子"说话。本分类后面的内容——状态码、GET 与 POST、Cookie——其实都是在这张快递单的各个栏目里做文章。

## 展开讲讲

### 请求的三段式

一个 HTTP 请求由三部分组成，顺序固定：

| 部分 | 人话 | 里面有什么 |
| --- | --- | --- |
| **请求行** | 单子上的核心栏 | 方法（GET/POST）、路径（/api/login）、协议版本 |
| **请求头**（Headers） | 寄件人信息栏 | Content-Type、Cookie、Authorization、User-Agent 等 |
| **请求体**（Body） | 箱子里的货 | 表单、JSON 数据；GET 请求通常没有这段 |

这三段在 F12 里怎么对上号：点开 Network 里的一条请求，**Headers** 页签上半是请求头、下半是响应头，**Payload** 页签是请求体，**Response** 页签是响应体——报文里的每一块，软件都替你摆好了位置。

### 响应的三段式

| 部分 | 人话 | 里面有什么 |
| --- | --- | --- |
| **状态行** | 回执结论 | 协议版本 + 状态码（200、404、500）+ 结果短语 |
| **响应头**（Headers） | 回执备注 | Content-Type、Set-Cookie、Content-Length 等 |
| **响应体**（Body） | 附带给你的东西 | HTML 页面、JSON 数据 |

### 测试最常打交道的几个头部字段

| 字段 | 谁发给谁 | 管什么 |
| --- | --- | --- |
| Content-Type | 双方 | 内容格式：application/json、text/html |
| Cookie | 客户端 → 服务器 | 带上"我是谁"的凭证 |
| Authorization | 客户端 → 服务器 | 登录令牌，接口鉴权用 |
| User-Agent | 客户端 → 服务器 | 我是什么设备、什么浏览器 |
| Set-Cookie | 服务器 → 客户端 | 下发凭证，登录成功的响应里常见 |

### 顺手把 URL 和常用方法也认了

`https://www.mall.com/api/search?keyword=手机壳&page=1` 拆开看三段：`https://` 是协议（加了 TLS 加密的 HTTP）；`www.mall.com` 是主机（服务器门牌）；`/api/search` 是路径（服务器里的哪个窗口）。`?` 后面是**查询参数**，`key=value` 用 `&` 连接——GET 请求的参数就住在这里。抓包时说"看下 URL 和参数"，看的就是这几段。

请求行的第一个词是**方法**，常见五个：

| 方法 | 语义 | 例子 |
| --- | --- | --- |
| GET | 查 | 搜索商品、查看订单列表 |
| POST | 增 | 下单、登录、发评论 |
| PUT | 改（整体替换） | 修改整条收货地址 |
| DELETE | 删 | 删除购物车里的商品 |
| PATCH | 改（部分更新） | 只改订单备注 |

其中 GET 和 POST 的区别是测试面试的常客，单独展开在下一篇。

还有一条要记住：HTTP 本身是**无状态**的——服务器不记得上一个请求是谁发的，每次都要靠请求头里的凭证认人。这正是 Cookie、Session、Token 要解决的问题（见本系列第 04 篇）。

## 举个例子

电商网站登录，点"登录"按钮的那一瞬间，浏览器发出的请求长这样（浏览器按 F12 打开 Network 面板就能看到）：

```http
POST /api/login HTTP/1.1
Host: www.mall.com
Content-Type: application/json
User-Agent: Mozilla/5.0 (iPhone; CPU iPhone OS 17_0 like Mac OS X)

{"username":"test001","password":"Aa123456"}
```

服务器回的响应：

```http
HTTP/1.1 200 OK
Content-Type: application/json
Set-Cookie: sessionId=abc123; Path=/; HttpOnly

{"code":0,"msg":"success","data":{"userId":10086,"nickname":"测试小王"}}
```

逐行对着三段式看：请求行写了"POST /api/login"，请求头声明"我发的是 JSON"，请求体就是账号密码；响应的状态行告诉你"200 成功"，Set-Cookie 给你发了张凭证，响应体里是用户信息。**测试时说的"接口返回了"，指的就是响应体；说"看下请求带没带 Cookie"，指的就是请求头。**排障时前端说"页面没数据"，你抓包看这条报文，一眼就知道是请求没发对，还是服务器没回对。

再看一眼响应头里其他值得认识的线索：`Content-Type` 标明返回的是 JSON 还是网页，`Content-Length` 是返回内容的字节数，`Cache-Control` 管缓存策略。排障时先扫一眼头部，经常比逐字看响应体更快发现问题。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| HTTP 太底层，功能测试不用懂 | 天天在用：F12、抓包、bug 单里写"接口返回 500"，全是 HTTP |
| 请求和响应混着说 | "返回 404"说的是**响应**；"参数传错了"说的是**请求**，提 bug 要分清 |
| 响应体就是页面 | 接口返回的 JSON 是数据，页面是浏览器拿到数据后**渲染**出来的 |
| 状态码 200 就等于业务成功 | 200 只代表通信成功，业务失败常藏在响应体的 code 字段里（如 code:1001 密码错误） |
| 头部不重要 | 登录态、鉴权、格式全靠头部，少带一个 Cookie 就是 401 |
| HTTPS 是另一套协议 | 还是 HTTP，只是传输过程加了密（TLS），报文结构不变 |

## 上手建议

1. **今天就开一次 F12**：任意网站按 F12 → Network → 刷新页面，随便点一条请求，把它的请求行、请求头、响应体三块找出来
2. **盯一条登录请求**：在自己常用的网站登录一次，在 Network 里找到那条 login 请求，看请求体里密码是明文还是加密的
3. **把 Content-Type 认熟**：看到 application/json 知道是接口、text/html 知道是网页，后面用 Postman 少踩一半坑
4. **装个抓包工具备用**：手机 App 的请求 F12 看不到，提前装好 Fiddler 或 Charles（怎么装、怎么用见第 06 篇）
5. **趁热看状态码**：状态码是状态行的核心，读完这篇紧接着看第 02 篇
