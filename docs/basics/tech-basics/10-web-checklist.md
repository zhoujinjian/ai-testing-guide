# 10｜Web 测试要点清单

> 核心要点：Web 测试最怕的不是难，而是**漏**——盯着功能点测完，刷新回退、多标签、低分辨率这些边角一碰就碎。这份清单把要点按**八个维度**列全，每轮测试照着过一遍：**漏测从靠运气变成靠清单**。

## 打个比方

飞行员开飞机前要过**起飞检查单**：副驾驶念一条，机长核对一条，哪怕飞了两万小时也不凭记忆省步骤——因为**人脑记不住所有项目，而漏掉一条可能机毁人亡**。

历史上有名的空难里，相当一部分不是技术故障，而是**老手跳过了检查单**。Web 测试同理：测了两年的人照样会漏掉"断网时点提交"这种项，不是不会，是没想到。所以成熟的测试团队都有自己的检查单：**每轮测试像过检查单一样逐条核对，测完的不是"我感觉测完了"，而是"清单上每一项都有结论"**。清单不会累、不会烦、不会因为周五下午想下班而偷懒。

## 展开讲讲

### Web 测试八维度检查大表

| 维度 | 检查点 |
| --- | --- |
| **功能主流程** | 核心路径走得通（注册→登录→搜索→下单→支付）；每个入口都能到达（首页导航、直链 URL、扫码）；上下页数据传递正确 |
| **输入与校验** | 必填项为空、格式错误（手机号 10 位/12 位）、长度边界（6 位、18 位、19 位）；特殊字符（空格、emoji、`<script>`）；**前端拦了，绕过前端直接调接口再测一遍** |
| **交互细节** | 按钮连点不重复提交；回车键能否触发提交；Tab 键跳转顺序合理；翻页快速连点；弹窗点遮罩、按 Esc 的表现 |
| **UI 展示** | 主流浏览器（Chrome、Edge、Safari）各过一遍；常见分辨率（1920×1080、1366×768、H5 手机宽度）不错位；文案无错别字；图片加载失败时有占位不破版 |
| **数据一致性** | 列表页数量与实际条数一致；列表金额与详情金额一致；分页第 1 页和最后一页；操作后刷新，状态已更新；**页面显示与数据库落库一致**（用 SQL 核对，见第 08 篇） |
| **网络与刷新** | 弱网下加载提示、按钮防重；断网时操作有友好提示；**浏览器回退/前进**后页面状态正确；F5 刷新后登录态、表单内容的表现；重复提交同一表单 |
| **登录态** | 凭证过期后操作引导重新登录而非报错；多标签页一边退出登录另一边的表现；A 账号退出后 B 账号登录无残留数据 |
| **安全意识** | 未登录直接输 URL 访问受限页应被拦截；改 URL 参数越权（把 orderId=201 改成 orderId=202）应返回无权限；输入框试注入 `' or 1=1 --` 不应报数据库错误 |

### 清单怎么用才不是摆设

三条使用纪律：

1. **逐条核对、留下痕迹**：每条测完标记通过/失败/不适用，测试报告里"不适用"也要写清理由（如本项目无 Safari 用户则记"不适用，依据 xxx"）
2. **每轮裁剪、随 bug 生长**：新迭代按功能裁出子集；每出一个线上漏测 bug，分析它属于哪个维度，**补一条新检查点回去**——清单越用越厚，漏测越来越少
3. **按风险标优先级**：主流程和登录态是 P0 必测，UI 文案类可排在时间充裕时——清单是防漏的，不是无限加量的

## 举个例子

电商"领券中心"活动页提测，拿清单八个维度过一遍，每维度各挑两三条真实执行：

- **功能**：从首页横幅、直链 `?activityId=88`、扫码海报三个入口进入都正常；领券后"立即使用"正确跳到可用商品列表
- **输入校验**：新用户输手机号领券——输 10 位提示"请输入正确的手机号"；输 12 位同样拦截；**Postman 直接调接口发 10 位**，后端也拦（双层校验通过）
- **交互**：领取按钮快速连点 5 次，只领到 1 张券；回车键触发领取
- **UI**：1366×768 分辨率下优惠券卡片不错位；图片挂掉时显示默认占位图
- **数据一致**：领券后查 `coupon_record` 表确实新增一行；页面"已领取 3 张"与列表实有 3 条一致
- **网络**：Charles 限速 3G，领取按钮转圈 3 秒后成功，且连点不重复；断网点领取，提示"网络开小差了"
- **登录态**：token 过期后点领取，跳登录页，登录后回到领券页而非首页
- **安全**：把 URL 改成 `?activityId=89`（未上线活动），返回"活动不存在"而非堆栈报错；改别人的券记录 ID 访问，返回 403

一轮过完提了 3 个 bug（连点重复领取、断网无提示、过期报 500），**没有一个是"感觉测完了"能兜住的**——这就是清单的价值。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 清单写一次就封笔 | 清单要随每个漏测 bug 生长，静态的清单半年后就跟不上业务 |
| 只用自己顺手的浏览器测 | 用户用什么就得测什么，至少 Chrome + 一款非 Chromium 内核（Safari/Firefox） |
| 刷新、回退、断网不算测试点 | 前端状态类 bug 的高发区恰恰在这，用户天天按回退键 |
| UI 错位是小事不用提单 | 错位影响可用性就是缺陷，提了由产品定严重程度，不是测试替人做主 |
| 安全测试归安全团队，我不碰 | 越权、注入尝试是功能测试随手能做的基本盘，见安全常识篇 |
| 清单越长越好，不分轻重 | 无优先级的清单会在时间紧时被整体抛弃，分层才能保命 |

## 上手建议

1. **把上面的大表抄成自己的模板**：存进笔记或用例管理工具，作为每轮 Web 测试的起手式
2. **本周就拿它过一次存量页面**：挑自己项目一个老页面完整过一遍，大概率能捞出被漏了很久的 bug
3. **给高发维度加星标**：哪个维度历史上出 bug 最多（多数团队是交互细节和网络刷新），标星优先过
4. **漏测复盘时回填清单**：每次漏测分析"属于哪个维度、清单里有没有"，没有就加一条——这是清单变厚的唯一正道
5. **和 App 清单配成一套**：Web 与 App 清单七成相通三成互斥，两份对照维护，比各记各的省力（App 专有部分见第 11 篇）
