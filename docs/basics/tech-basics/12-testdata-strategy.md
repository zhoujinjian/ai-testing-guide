# 12｜测试数据怎么造：造数思路与工具

> 核心要点：测试一天里相当多的时间耗在"等一份数据就位"上。造数先想清楚**要什么状态的数据**（状态矩阵），再从**五种造法**里挑最省力的一种，守住**唯一、可重复、可清理、不污染**四条原则——造数效率，直接就是测试效率。

## 打个比方

大厨开炒之前先**备菜**：该洗的洗、该切的切、按菜谱分装摆盘，灶上一开火，抓起来就下锅——**备菜备得好，炒菜才不慌**。

测试同理：用例写好了，执行时才发现"没有一张已发货的订单""没有库存为 0 的商品"，于是现场下单、支付、喊运营发货，十五分钟过去菜还没下锅。成熟的测试**头一天就把数据备齐**：各种状态的订单、各种余额的账号、正常和异常的商品，像备好的一盘盘菜，第二天开测直接抓用。**备菜是工序的一部分，不是耽误工夫**——这个观念转过弯，效率就上了一个台阶。

## 展开讲讲

### 第一步：画状态矩阵，想清楚要什么

别上来就造，先列"本轮测试需要的 数据类型 × 状态"清单。比如订单测试：

| 数据类型 | 需要的状态 |
| --- | --- |
| 订单 | 待支付、已支付、已发货、已取消、**售后中** |
| 账号 | 正常、禁用、无绑定手机、余额 0、**新注册 1 天内** |
| 商品 | 在售、下架、库存 1（边界）、**库存 0** |

矩阵列完，造数需求一目了然——**正常状态往往一条就够，异常状态才是 bug 高发区**，别只备"好菜"。

### 第二步：五种造法，挑最省的

| 造法 | 适用场景 | 优点 | 坑 |
| --- | --- | --- | --- |
| **界面手工造** | 少量、流程短的数据 | 零门槛、最真实 | 慢；深状态要一步步走完 |
| **SQL 直插或 UPDATE** | 深状态、历史数据 | 秒级把订单改到任意状态 | 要懂表结构；漏改关联表会造出"半套数据"；只在测试库动手（见第 08 篇） |
| **调接口造** | 批量、自动化前置 | 快、走真实业务链路最干净 | 依赖接口稳定；造完记得清理 |
| **复制改造已有** | 一批相似数据 | 快 | 唯一性字段（单号、手机号）忘改就成了脏数据 |
| **开发造数工具/后台** | 团队高频需求 | 一键、人人可重复 | 需要推动建设，值得为它提需求 |

选法口诀：**一次性的用界面，改状态的用 SQL，要复用的走接口，团队常用的推动做工具**。

团队里最好的状态，是把高频造数沉淀成**造数脚本或后台按钮**：测试提需求，开发做个"一键造已发货订单"的入口，人人可点、随时可重复。这步投入不大，回报是整个团队每轮迭代省下的等待时间——值得你在迭代回顾会上认真提一次。

### 第三步：守住四条原则

1. **唯一**：命名带时间戳或姓名缩写（`test_zhou_1027`、`TD_TEST_售后_1027`），自己的数据一眼可认，和别人的不打架
2. **可重复**：能脚本化就脚本化（Postman 前置请求、SQL 模板），下次改个参数重来，别每次手工重走
3. **可清理**：造的时候登记（放哪张表、什么标记），测完删除或复原——**造完不管的数据，下个迭代就变成别人排查半天的脏数据**
4. **不污染**：不用真实用户的手机号和身份信息，不动共享账号里的数据，别把测试单混进统计报表

## 举个例子

要测"已发货订单申请售后"，需要一笔 `status=2`（已发货）的订单。手工造：下单→支付→找运营在后台点发货，15 分钟起步。换造数思路，十分钟备齐：

1. **SQL 造**：挑自己昨天下的测试单 `TD20261026005`，`SELECT` 确认后 `UPDATE orders SET status = 2 WHERE order_no = 'TD20261026005' AND user_id = 10086;`——两秒到位（先查后改的纪律见第 08 篇）
2. **加唯一标记**：备注字段写上 `售后测试-1027-小王`，日志和表里都能认领
3. **批量备货**：同一招再造 `status=0/1/3` 各一笔，四个状态一次备齐，后续回归直接复用
4. **登记清理**：在团队的"测试数据登记表"里记一行；当天测完，把这四笔单删掉或标记作废

第二天执行用例时，同事还在等运营发货，你四个状态已经开测——**省下来的每一分钟，都是造数思路换的**。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 造数是浪费测试时间 | 恰恰相反，一次备货多轮复用，是效率投入回报最高的动作 |
| 每次都从零手工造 | 手工造只适合一次性的，高频数据要沉淀成 SQL 模板或接口脚本 |
| 造完不清理 | 数据越积越脏，最后报表对不上、排查寸步难行，买单的是整个团队 |
| 从生产库导真实数据来测 | 手机号、地址都是用户隐私，导数据要走合规审批，测试默认只用脱敏数据 |
| 只造正常状态 | 待支付、库存 0、已禁用这些异常态才是 bug 高发区，矩阵里别漏 |
| 造数靠记忆不登记 | 三个月后没人说得清那几万条测试单是谁的，登记表就是防这个 |

## 上手建议

1. **给当前项目画一张状态矩阵**：按"数据类型 × 状态"列一遍，你会立刻发现下轮测试缺哪几份
2. **存三条 SQL 造数模板**：改订单状态、改库存、改账号状态，配上"先 SELECT 后 UPDATE"的注释，随取随用
3. **跟开发约一个造数接口或后台按钮**：高频造数需求值得工程化，这是测试推动效率建设的好切入点
4. **建一张团队数据登记表**：谁、什么时间、什么标记、放哪里，一列清清楚楚
5. **命名规范定死**：`test_名字缩写_日期` 从今天用起，让每条测试数据都有主人
