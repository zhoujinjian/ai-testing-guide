# 05｜接口测试是什么：零基础版

> 核心要点：**接口就是系统内部各部分之间约定好的"对话方式"**——前端把请求发给后端，后端把数据回给前端。接口测试就是**绕过页面，直接模拟前端去和后端对话**，专门考后端：参数传对了吗、异常输入拦住了吗、返回的数据对吗。

## 打个比方

想象一家**餐厅**。

你（**前端页面**）坐在大厅看菜单点菜，后厨（**后端服务器**）负责炒菜。大厅和后厨之间隔着一堵墙，全靠**窗口里的服务员（接口）**传话：你喊"一份宫保鸡丁，微辣"，服务员把话递进后厨；几分钟后服务员端出一盘菜（**返回的数据**）。

平时你通过菜单点菜，这相当于用户在页面上点点点——这是 **UI 测试**。但菜做得好不好，其实取决于你和服务员之间这段对话：你说"微辣"她听成"特辣、快上"，菜就废了。

**接口测试就是你不看菜单，直接站到窗口跟前考服务员**：

- 正常话能不能听懂："宫保鸡丁，微辣" → 上对菜
- 含糊话怎么办："来个……那个鸡" → 应该礼貌追问，而不是端上来一盘错的
- 故意刁难："来 999 份" → 该说"一次最多 10 份"，而不是把后厨压垮
- 不存在的菜："来盘凤凰蛋炒饭" → 该说"没有这道菜"，而不是报 500 错误

菜单（页面）可以慢慢装修，但窗口的对话**今天就可以开始考**——这就是接口测试最大的价值：**不等前端**。

## 展开讲讲

### 接口到底长什么样

"接口"听起来玄，落到纸上就是一份**约定文档**，通常包含这些内容：

| 要素 | 人话 | 示例 |
| --- | --- | --- |
| URL | 在哪个窗口点 | `POST https://api.mall.com/api/order/create` |
| 方法 | 什么动作 | POST（提交） |
| 请求参数 | 你递进去的话 | addressId、skuId、count |
| 返回数据 | 端出来的菜 | code、msg、订单号 |
| 约定规则 | 话怎么算说对了 | count 范围 1~99，超了返回 400 |

前端开发和后端开发开工前先谈好这份约定，之后各写各的——**只要双方都守约，页面和后端拼起来就能跑**。接口测试，就是验证后端有没有守约。

### 为什么不满足于点点点

页面测试和接口测试的关系，像隔着菜单点菜和站在窗口考服务员的关系：

| 对比 | 只测页面 | 加上接口测试 |
| --- | --- | --- |
| 时间 | 必须等前端做好 | 后端一出来就能测，**测试左移** |
| 覆盖 | 只能点到页面露出的入口 | 参数可以随便构造：超长、为空、非法值，页面做不出来 |
| 定位 | 页面错了不知道谁的锅 | 直接验证后端，前后端责任一刀切开 |
| 速度 | 一条条点，慢 | 一条请求毫秒级，容易做成自动化 |

页面点不出来的例子最说服人：注册页用户名限制 6~18 位，前端输入框会拦住 3 位的。但**跳过页面直接调接口发 3 位用户名**，后端拦不拦？不拦的话，绕过页面攻击的用户就注册成功了——这类用例只有接口层测得到。

### 一条接口用例的五个要素

写接口用例，就是把点菜的话填进表格：

| 要素 | 填什么 | 例子（下单接口） |
| --- | --- | --- |
| 前置条件 | 凭证、数据准备 | 已登录，购物车有商品，库存 10 件 |
| 请求 | 方法 + URL + 参数 | POST /api/order/create，count=11 |
| 预期返回 | 状态码 + 业务码 + 数据 | 200 + code:1005 + "库存不足" |
| 后端落库 | 数据库里该是什么 | 不生成订单，库存不变 |
| 清理 | 测完收拾现场 | 删除测试数据（思路见第 12 篇） |

注意第三、四条：**接口测试不只看"回了什么"，还要看"数据库里落了什么"**——返回说成功但没落库，是真实存在过的 bug。

## 举个例子

电商 App 做个"领优惠券"功能，页面还要两周才能提测，但后端接口已经就绪。你用 Postman（第 07 篇教）直接开测 `POST /api/coupon/receive`，参数 couponId：

1. 正常领 C200 → 200 + code:0，数据库 coupon_record 表多一行——通过
2. **重复领**：再发一次同样请求 → 预期 code:1001"已领取"，实际又发了一张——**bug，后端没做防重**
3. **领不存在的券**：couponId=99999 → 预期"活动不存在"，实际返回 500——**bug**
4. **参数为空**：不发 couponId → 预期 400 提示"参数缺失"，实际返回空指针 500——**bug**

页面还没影，三个后端 bug 已经提走了。等页面上线，后端早就修干净了——这就是接口测试"左移"的实在好处，也是它成为面试必问（怎么答见面试题库）的原因。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 接口测试是"高级技能"，功能测试用不上 | 入行头一年就会接触：抓包看请求、提 bug 附接口返回，都是接口测试动作 |
| 会用 Postman 就等于会接口测试 | 工具只是"能发请求"，**用例设计**（参数组合、边界、异常）才是核心，方法与页面用例同源 |
| 接口测试只看返回值 | 还要查数据库落库结果，返回与落库不一致是高发 bug |
| 接口测试能替代 UI 测试 | 不能：页面渲染、交互、兼容性接口层测不到，两者互补 |
| 必须会写代码才能做 | 手工接口测试 Postman 就够；自动化阶段才需要代码（路线第 6 章） |
| 把 URL 当成接口的全部 | 方法、参数、返回、**约定规则**合在一起才是一份接口 |

## 上手建议

1. **找开发要接口文档**：问后端要 swagger 或 apifox 地址，挑一个查询接口，把 URL、参数、返回对着文档读一遍
2. **装上 Postman 发第一条请求**：从最简单的 GET 查询接口开始，收到 JSON 返回就算入门（第 07 篇一步步带）
3. **对一条接口写五条用例**：正常 1 条 + 参数异常 4 条（为空、超长、非法格式、不存在的值），体会"页面点不出的用例"
4. **练习看三样东西**：状态码、业务 code、data 内容——每条请求都把三样说出来，形成习惯
5. **和 UI 测试对照着想**：每测一个页面功能，想一句"它的后端接口是什么、我能不能直接测"——左移意识就是这么养成的
