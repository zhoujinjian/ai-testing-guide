# 12｜好测试的标准：快、全、准怎么权衡

> 核心要点：评价测试好坏不是"用例多、耗时长"，而是**在时间和资源的约束里，把版本风险压到最低**。快（反馈及时）、全（覆盖够广）、准（命中关键）三个标准天然打架——**好测试不是三样拉满，是按风险把钱花在刀刃上。**

## 打个比方

一家连锁超市每月要**盘点**，三个要求摆在一起：

要**快**——盘点期间货架不能正常卖，停一天就是一天的营业额；要**全**——漏盘的货架下个月对不上账；要**准**——数了没用，数出来的数得和账面、和实物对得上。

但这三样同时拉满是不可能的：停业三天全店细数，准和全满分，快零分；营业中抽几个货架数数，快满分，全和准不及格。所以真实世界长出了**分层盘点**：高价值货架（烟酒、数码）双人细数（准），普通货架循环抽盘（全），快消品靠系统库存自动对账（快）。**预算固定时，盘点水平的高低不在于数得多仔细，而在于精打细算地分配仔细。**

测试的快、全、准，就是这三种盘点。好测试不是无限投入，是聪明分配。

## 展开讲讲

### 先定义三个字

| 标准 | 人话解释 | 反面教材 |
| --- | --- | --- |
| **快** | 缺陷被发现的周期短，反馈及时 | bug 提测三天才发现，修复窗口早过了 |
| **全** | 该测的范围都碰到了，没有明显盲区 | 上线后发现整块功能压根没人测过 |
| **准** | 测到点上：关键缺陷被抓住，误报少 | 一堆用例全过，线上炸的是没测的那条路径 |

三者为什么打架：时间预算固定时，**求全必然变浅**（每处碰一下），**求准必然变慢**（关键处反复抠），**求快必然舍弃**（只跑冒烟）。新手常犯的错是默认"全"优先——用例铺得满满当当，每条都浅尝辄止，结果看着忙了两周，资损场景一条没抠。

### 按场景选侧重

| 场景 | 侧重 | 怎么做 |
| --- | --- | --- |
| 日常迭代回归 | 快为主，全靠自动化兜 | 冒烟集 + 自动化回归保广度，人力抠改动点 |
| 紧急线上修复（hotfix） | 快 + 准，主动砍全 | 只验证修改链路及其直接涟漪，其余明确放弃 |
| 大版本 / 大促前 | 全 + 准，时间预算给足 | 提前扩容测试排期，全量回归加专项（性能、兼容） |
| 排期被临时压缩 | 风险驱动裁剪 | P0 精测保准，P1 抽测保全，P2P3 明示不测并留风险记录 |

注意最后一行的措辞：**"明示不测"本身就是专业动作**。测试不可能全测（穷举不可能原则，见[软件测试的 7 条原则](./02-seven-principles.md)），把没测的说清楚和把测过的做扎实，同样是质量信息。

### 权衡的裁判是风险

往哪里分配"准"，不看模块大小，看**出事代价**：

- **资损类**（支付、退款、优惠计算）：出事直接赔钱，必须准，逐条抠边界
- **合规与数据类**（隐私展示、数据覆盖）：出事上新闻，必须准
- **主链路体验类**（登录、下单、搜索）：出事掉单量，快 + 适度准
- **长尾界面类**（设置页、帮助中心）：出事容忍度高，全的冒烟级即可

这套分配写下来，就是团队的**测试策略**。而"准"不止靠人力堆，自动化做回归的"快和全"，人力专注新功能的"准"，人机分工本身就是最大的权衡艺术（自动化怎么选型见[什么项目适合做自动化](../../interview/testing-essentials/15-automation-adoption-criteria.md)）。

### 快全准之外，还有两个隐含标准

**稳定**：同样的用例今天过明天挂（不稳定用例），快全准都成笑话——误报会侵蚀团队对测试结论的信任（治理见[用例不稳定误报多怎么办](../../interview/testing-essentials/17-flaky-test-governance.md)）。**可维护**：用例和脚本改起来省力，半年后的人能看懂。快全准描述一轮测试的水平，稳定和可维护描述的是十年如一日的水平。

## 举个例子

同一个电商团队，隔了两周的两件事，权衡完全相反：

**场景一：大促前全量回归**（提前两周排期）。侧重**全 + 准**：全站 1800 条用例自动化回归跑三轮（快让位于覆盖），优惠券叠加、价格计算、库存扣减三个资损模块人工逐条精测（准），补一轮兼容性专项（全）。反馈周期长没关系——离上线还有两周，发现什么都来得及修。

**场景二：大促开始前夜紧急 hotfix**——发现优惠券并发领取会超发，每超发一张赔 15 元。侧重**快 + 准**：只测修复链路——并发领取拦截的 6 种组合场景逐条验证（准），领取入口及订单使用券的直接影响面 12 条定向回归（涟漪），其余几百条回归**明确不跑**，并在发布说明里写清"未回归范围与依据：改动限定在发放接口，历史回归数据该接口缺陷率为零"。两小时完成验证上线，快是硬指标，因为每晚一分钟都在赔钱。

两件事里测试都称职，因为**衡量标准从来不是动作本身，而是和当下风险的匹配度**。这也是[怎么判断版本测完了可以上线](../../interview/testing-essentials/18-release-exit-criteria.md)这道面试题的底层逻辑。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 用例越多、耗时越长越专业 | 投入不讲产出是浪费，好测试看风险压降了多少 |
| 默认全覆盖优先，每处浅浅过一遍 | 全而浅是漏测重灾区，关键路径必须抠深 |
| 时间不够就加班硬扛全量 | 硬扛出的疲劳测试反而误判率高，裁剪加明示才是解 |
| "没测完"不能说出口 | 明示未测范围是质量信息，藏着才是隐患 |
| 三样可以同时拉满 | 约束固定时三样互斥，权衡本身就是测试功力 |

## 上手建议

1. **给当前版本画一张风险地图**：把模块按"出事代价"分成四档，标出必须精测的 P0 区，下次排期先保它
2. **写一次"未测清单"**：版本报告里主动加一段"本轮未覆盖范围与理由"，练习把取舍亮出来的专业表达
3. **测前先回答三问**：这个版本最快要什么时候给反馈、哪里绝对不能错、哪些可以只碰一下——三问答完，侧重点自然浮出
4. **统计自己用例的命中率**：过去三个月你提的 bug 集中在哪些用例设计方法上，往命中率高的方法加码，就是提"准"
5. **复盘一次排期被压缩的经历**：如果重来一遍，砍什么、保什么、怎么明示——把这个答案写成自己版本的权衡模板
