# 03｜软件质量是什么：质量模型通俗版

> 核心要点：**"质量高"不是一句话能说完的事**——质量模型把"好软件"拆成功能性、性能、兼容、易用、可靠、安全、可维护、可移植八个维度，每个维度都能单独检验、单独打分，测试就是照着这张图逐项收质量货的。

## 打个比方

怎么评价一桌宴席**质量高不高**？你脱口而出的"好吃"，其实混了八件不同的事：

菜对不对菜单、点的菜上齐没有（**功能性**）；上菜快不快、分量足不足（**性能效率**）；鱼香肉丝在明火灶和电磁炉灶做出来是不是一个味（**兼容性**）；菜名看不看得懂、筷子夹不夹得动（**易用性**）；连开二十桌，每桌咸淡稳不稳定（**可靠性**）；吃完了会不会拉肚子（**安全性**）；做法写成菜谱没有，换个厨师能不能复刻（**可维护性**）；换到另一个厨房、用当地食材还做不做得出来（**可移植性**）。

一桌菜可能功能性满分、安全性砸锅——后厨卫生不达标，前面全白搭。软件同理：功能全对但一输特殊字符就崩、高峰期转圈、手机号明文展示，你能说它质量好吗？**质量模型的价值就是逼你把"好"说具体**。

## 展开讲讲

现行国际标准 ISO/IEC 25010（前身是 ISO 9126）把软件质量拆成八大特性：

| 质量特性 | 一句话解释 | 对应的测试活动 |
| --- | --- | --- |
| **功能性** | 功能齐不齐、对不对、合不合适 | 功能测试——新手每天做的事 |
| **性能效率** | 单位时间干多少活、占多少资源 | 性能测试：响应时间、并发、资源占用 |
| **兼容性** | 和别的系统、别的环境处不处得来 | 浏览器/机型/版本兼容测试 |
| **易用性** | 用户好不好学、好不好用、犯没犯迷糊 | 易用性测试、UI 走查 |
| **可靠性** | 出了状况能不能扛住、恢复 | 稳定性测试、容错与恢复测试 |
| **安全性** | 该拦的拦得住，数据守得住 | 安全测试：越权、注入、敏感信息 |
| **可维护性** | 改起来费不费劲，别人看不看得懂 | 代码评审、静态检查（多由开发承担） |
| **可移植性** | 换环境安装迁移费不费劲 | 安装升级测试、多环境验证 |

三个新手必须想明白的点：

**一，维度之间会打架。** 加密全开安全性上去了，性能可能掉下来；界面元素堆满功能性齐全了，易用性反而下降。所以质量不是八个维度都拉满，而是**按产品定位做取舍**——银行 App 把安全和可靠压倒一切，小游戏把易用和性能放前面。这也是"测试依赖场景"原则的落点。

**二，不是每个维度都归你测。** 功能、兼容、易用、性能的外围验证是测试主业；可维护性主要靠开发代码评审和静态工具；安全深度测试有专门的安全测试岗。知道边界，才不会新手期就想一口吃成胖子。各测试类型详细介绍见[测试分类总览](../types/01-classification-overview.md)。

**三，质量是分层的。** 代码有内部质量（可维护、可读），产品有外部质量（运行时表现），用户感受到的是使用质量（好不好用、满不满意）。测试报告里说的"质量"通常指外部质量，但内部质量差会慢慢漏成外部问题——临时方案堆三个月，bug 就开始从里面渗出来。

## 举个例子

拿一个**电商 App 的购物车改版**，按八个维度过一遍，你会看到"质量"立刻变得具体：

1. **功能性**：加购、改数量、删除、勾选合计，需求文档 12 条验收标准逐条验证，全对
2. **性能效率**：购物车塞 99 件商品，打开页面耗时 0.8 秒，达标（要求 2 秒内）
3. **兼容性**：iOS 16 的 Safari 内嵌页、安卓 8 的千元机、微信小程序版各走一遍主流程
4. **易用性**：观察两位真实用户操作，发现"左滑删除"没人发现——手势太隐蔽，提了易用性建议
5. **可靠性**：弱网下加购转圈 10 秒，重试机制生效，数据没丢没重
6. **安全性**：抓包看购物车接口，商品价格从响应里带出来而不是请求里传回去——防止改价攻击，验证通过
7. **可维护性**：和开发聊了改版后的接口设计，新旧字段并存有注释，半年内可下线旧字段，可维护
8. **可移植性**：平板端购物车布局自动适配，横竖屏切换正常

最后你给这版质量的结论是："功能性、兼容性、可靠性达标；性能达标但余量小；易用性有一条改进建议。"——**每句话都有落点**，比"质量还行"值钱一百倍。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 质量就是"功能对不对" | 功能只是八分之一，性能安全易用一样能毙掉一个版本 |
| 八个维度都要拉满才叫好 | 维度会互相冲突，好质量是按产品定位取舍后的平衡 |
| 质量模型是背给面试官的 | 它是你列测试点、写测试计划的现成检查清单 |
| 上线出事一定是功能测试的锅 | 安全、性能、可靠性问题各有归属，按维度定位比拍脑袋定责快 |
| 易用性是产品经理的事 | 测试天天操作产品，是最有条件发现"别扭"的人 |

## 上手建议

1. **拿八个维度套手头项目**：给当前负责的模块按八维度各写一条测试点，写不出来的维度就是你当前的盲区
2. **报告里用维度说话**：下份测试报告把"质量情况"按维度分段写，让读的人一眼看到哪块强哪块弱
3. **找产品问一次取舍**：问你的产品经理"咱们产品这八个维度最不能妥协的是哪两个"，把答案记进测试计划的重点
4. **建一张维度检查卡**：把八个特性做成卡片贴在显示器边，设计用例卡壳时扫一眼，常能补出漏掉的类型
5. **对照分类总览扩视野**：读一遍[测试分类总览](../types/01-classification-overview.md)，把八个维度和具体测试类型对上号
