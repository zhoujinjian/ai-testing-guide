# 02｜软件测试的 7 条原则

> 核心要点：这 7 条是几十年测试实践沉淀的**底层规律**——穷举不可能所以要有取舍，bug 爱扎堆所以要重点进攻，用例会失效所以要持续更新。理解了它们，你日常的每个测试动作都有出处。

## 打个比方

你是果商雇的**果园验虫员**，任务是在收购前判断这批苹果能不能要。

- 你验了一千个苹果没见着虫，敢说整园没虫吗？不敢，树上还挂着几万个呢（**穷举不可能**）
- 但你验出一箱有虫，就能下结论："这批果确实有虫"（**测试只能证明缺陷存在**）
- 果农要是从套袋、打药阶段就按规范来，虫果率早就降了；等摘下来再挑，费劲十倍（**尽早测试**）
- 挑出的虫果，十有八九集中在靠山那几棵树——虫子是扎堆的（**缺陷集群**）
- 你一直只用"对着光转一圈看虫眼"这一招，藏得深的虫永远漏网（**杀虫剂悖论**）
- 这批果出口要验农残，榨汁厂只验霉变，鲜食店最在意外观——验收标准完全不同（**测试依赖场景**）
- 最后满车苹果零虫，但品种不对、口感发酸，收购商照样不收（**无缺陷谬论**）

七条原则，就是这七件事在软件里的原样复刻。

## 展开讲讲

| # | 原则 | 人话版 | 对应的日常动作 |
| --- | --- | --- | --- |
| 1 | 测试显示存在缺陷 | 测出 bug 能证明有 bug；测不出证明不了没有 | 别在报告里写"测试通过，无缺陷" |
| 2 | 穷举测试不可能 | 输入组合是天文数字，全测完太阳都下山了 | 用等价类、边界值科学取样 |
| 3 | 尽早测试 | 需求阶段的错，上线才发现，修复成本翻几十倍 | 参加需求评审，别等提测才见需求 |
| 4 | 缺陷集群 | bug 爱扎堆，20% 的模块贡献 80% 的 bug | 逮住一个模块的 bug，就往死里挖 |
| 5 | 杀虫剂悖论 | 同一批用例反复跑，发现新 bug 的能力会枯竭 | 用例要迭代，别一套用例跑三年 |
| 6 | 测试依赖场景 | 医疗系统和休闲游戏，测法、标准完全不同 | 接手项目先问"这软件给谁用、错不起什么" |
| 7 | 无缺陷谬论 | 零 bug 不等于好产品，做错方向照样没人用 | 验证之外还要确认"做的是用户要的" |

三条新手最容易吃亏的，单独说透：

**缺陷集群**是最好用的一条。统计规律确实存在：历史 bug 密集的模块、刚入职开发写的模块、赶工赶出来的需求，都是虫子扎堆的"那几棵树"。实操上，翻出项目的历史缺陷清单，按模块统计一下，把 top 3 模块设为每次回归的必测重点——这是数据，不是玄学。

**杀虫剂悖论**不是让虫产生抗药性（bug 不会进化），说的是**你的检查手段固化了**：同一批用例跑第十遍，对这套用例覆盖的场景当然还是有效，但对用例之外的场景，它的发现能力从第一遍起就没变过。解法是定期注入变化：补充探索性测试、换设备换网络、按新需求改造旧用例。探索性测试怎么玩，见[探索性测试与猴子测试](../types/06-exploratory-monkey.md)。

**无缺陷谬论**最隐蔽：团队把"零 bug"当唯一目标，测得无比严格，最后上线一个"没有 bug 但也没人用"的功能——因为需求本身就理解偏了。所以测试除了"验证做得对"（照需求做没错），还要"确认做的是对的"（需求本身对不对），这对概念展开见[验证与确认：V&V 是怎么回事](./05-verification-validation.md)。

## 举个例子

外卖 App 迭代：**商家搜索支持"配送时长排序"**。七条原则怎么在这一个小需求里现形：

1. **尽早测试**：需求评审会上你就问了"配送时长怎么算，商家出餐时间算不算"——评审阶段就拦下一个口径模糊的需求，省掉后面一整轮返工
2. **穷举不可能**：搜索词 × 城市 Hundreds 个商圈 × 排序方式，组合无穷，你按等价类取样：有配送时长商家、无时长商家、时长相同的商家各挑代表
3. **测试显示存在缺陷**：你测出"时长相同的商家排序随机跳变"，提了 bug；没测出的排序一致性场景你不下"没问题"的结论，只在报告里写"已测范围"
4. **缺陷集群**：bug 集中在排序服务这一个模块，一口气挖出 5 个——你判断这模块有坑，追加了一轮探索测试，又捞出来 2 个
5. **杀虫剂悖论**：搜索旧用例跑了几十遍从没失手，这次你补了"配送时长为空""商家休息中"两类新场景用例
6. **测试依赖场景**：这个功能在高峰期商圈的数据量是普通商圈十倍，你额外做了高峰数据量的排序验证
7. **无缺陷谬论**：bug 清零后，你又和产品确认了一遍"用户真的会用时长排序吗、入口埋点数据如何"——零 bug 不是终点，有人用才是

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 把七条原则当背诵题 | 每条都对应日常动作，背下来不落地等于没学 |
| 认为漏测是自己不细心 | 穷举不可能，漏测只能降低概率，靠方法和方法论改进，不靠自责 |
| 缺陷集群是迷信 | 历史缺陷数据可统计、可验证，用数据找出你项目的"虫子树" |
| 杀虫剂悖论是 bug 变聪明了 | 固化的是你的用例，不是虫子；定期翻新用例就破 |
| 追求零 bug 就万事大吉 | 方向错了零 bug 也会被市场毙掉，验证之外还有确认 |

## 上手建议

1. **统计一次项目缺陷分布**：把近三个月 bug 按模块拉个表，找出 top 3 集群模块，下个迭代把它们设成回归重点
2. **给老用例做次体检**：挑一组跑了半年没更新过的用例，对照新需求补 5 条新场景，体会杀虫剂悖论的破解
3. **需求评审抢着去**：下个迭代的需求评审会主动参加，争取提出至少一个"口径模糊"的问题，这是尽早测试最便宜的落地
4. **接手项目先问三句话**：给谁用、错不起什么、发布节奏多快——把"测试依赖场景"变成开场的固定动作
5. **报告里练习写"已测范围"**：结论别写"无问题"，写"上述 60 条用例范围内未见缺陷"，措辞的严谨就是原则一的落地
