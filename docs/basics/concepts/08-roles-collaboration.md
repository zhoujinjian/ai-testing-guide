# 08｜测试与产品、开发的分工协作

> 核心要点：产品定**做什么**，开发负责**做出来**，测试负责**照出来做得怎么样**——质量是三方共造的，**测试是最后一道防线，但从来不是唯一一道**。协作的本质不是不吵架，是把分歧放进正确的沟通机制里解决。

## 打个比方

一支足球队怎么保住球门？

**前锋**是开发：负责把球打进对方门里（把功能做出来）。但好前锋丢球后要就地反抢——开发写完要自测，别把明显没跑通的版本甩出来。

**中场**是产品：决定打法、给前锋喂球（定义需求、排优先级）。传球质量差（需求口径模糊），前锋脚法再好也进不了球；打法频繁变（需求反复改），全队来回折返跑。

**门将**是测试：最后一道防线，扑出必进之球（拦住致命缺陷）。但门将扑救再神，后场天天漏人照样输球——**好的球队防守是全队的，好的软件质量是整个团队造的**。门将还有个常被忽略的价值：站位最高、看得最全，能提前喊"左边空了"——这就是测试的风险预警：把自己看到的质量信息喊出来，让全队提前布防。

输球只骂门将，是外行；上线出事只怪测试，同理。

## 展开讲讲

### 三个角色各管什么

| 角色 | 主场职责 | 对质量的贡献 | 高频摩擦点 |
| --- | --- | --- | --- |
| 产品 | 定义需求、排优先级、验收 | 需求本身想清楚，口径无歧义 | 需求文档含糊、中途频繁变更 |
| 开发 | 技术方案、编码实现 | 自测充分、代码可测、及时修缺陷 | 不写自测记录就提测、说"这不是 bug" |
| 测试 | 用例设计、执行、缺陷管理、质量评估 | 用专业检查照出问题、给出风险判断 | 打回版本被嫌事多、结论没人听 |

摩擦不可怕，可怕的是用错解决方式——口头吵、群里@、私下憋着，都不如放进机制里。

### 三个高频冲突，标准解法

**冲突一：开发说"这不是 bug，需求就这么写的"。** 别急着争，分两步：拿需求文档对——真写清楚了且实现一致，那是需求问题，转给产品；文档没写或写得含糊，按**用户视角的实际影响**判断要不要紧，把"用户会遇到什么"讲清楚再和产品确认。冲突的解法永远是**回到共同的上游依据**，而不是比谁嗓门大（展开见面试题[开发说"这不是 bug"怎么办](../../interview/testing-essentials/09-dispute-with-developers.md)）。

**冲突二：产品说"时间不够，先上线再说"。** 测试不拦发布，但要把**风险说清楚并留下书面记录**：哪些没测、可能出什么问题、出了怎么办。同时主动给出裁剪方案——"砍 P2 边角功能、保支付主链路"，比一句"测不完"有用得多。决定是团队的，信息必须是全的。

**冲突三：提测质量差，一提测就冒烟不过。** 解法不是群里抱怨，是把**准入标准前置约定**：自测记录、冒烟清单、影响范围三件套齐了才收。机制挡在前面，人对人就没那么难看（见[测试执行全流程](../process/10-test-execution-flow.md)的准入检查一节）。

### 让协作顺起来的四个机制

1. **评审三方到场**：需求评审有测试和开发，口径当场对齐，别让三方各自理解
2. **bug 单是正式渠道**：口头说的 bug 不算数，单据里的缺陷才可跟踪、可度量——怎么写好见[缺陷报告怎么写](../bug-management/03-bug-report.md)
3. **站会只说三件事**：昨天做了什么、今天做什么、有什么阻塞——阻塞说给能解决的人听
4. **准出标准提前约定**：什么样算"测完了、能上线"在版本开始就说定，别在最后一天吵架式谈判

## 举个例子

外卖 App 迭代：**满 30 减 8 的商家满减活动**。三个角色怎么配合，看全程：

**需求评审会**：产品讲完方案，你提了两个问题——"满减和平台券能不能叠加""商家改菜单导致满减门槛变化时，已加购的订单怎么算"。第一个产品当场拍板"不叠加"并补进文档；第二个开发说"按下单时刻快照"，三方确认写清。**两分钟的提问，省掉后面两天的扯皮。**

**提测**：周三开发提测，冒烟跑挂了 2 条——满减金额展示为 0。你按准入标准打回，附上冒烟记录截图；开发一小时修复重提。打回时你补了一句"不针对人，主流程没通细测全是白干"，开发回了句"应该的"。

**执行中**：你提了一个单："满减活动页在 iPhone SE 小屏上'去结算'按钮被遮挡"。开发回复"低优先级，小众机型不算 bug"。你没吵，把用户影响讲清楚："小屏用户点不到结算，等于这批用户下不了单"，并 @产品确认。产品定级 P1，开发当天修了。

**上线前**：时间被压缩半天，你给出裁剪方案：P2 的"活动页分享文案校验"移到下版本，支付与满减计算链路 46 条用例保量完成，遗留项写进版本报告的风险段，产品签字确认。

全程没有一次争吵，但每个分歧都有了出口。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 测试和开发天然对立 | 对立的不是人，是信息差；机制对齐后大多是顺畅合作 |
| 上线出事都是测试背锅 | 质量是三方共同产出，定责看过程证据不看岗位 |
| 打回版本会得罪开发 | 按约定标准打回是流程动作，藏着掖着才真伤关系 |
| 分歧靠嗓门和职级解决 | 回到需求文档和用户影响这两个共同依据，比谁都有用 |
| 需求变更只能被动接受 | 变更要走确认：改了什么、影响多大、测试时间是否重排，问清楚再接 |

## 上手建议

1. **下个迭代的三方评审都到场**：带着问题去需求评审，一次真实拦截胜过读十篇文章
2. **把"这不是 bug"的案例记下来**：每次争议记一行——争议点、依据、最终结论，两个月后你就有了自己团队的判例库
3. **打回时附证据不附情绪**：冒烟失败截图、日志、复现步骤三样摆出来，打回就是纯技术动作
4. **练一句风险话术**：把"测不完"换成"按当前时间，我可以保证 A 链路，B 链路只能抽查，风险是某某"——方案思维是协作的硬通货
5. **每季度请开发吃顿饭**：不是玩笑——非工作场景建立的关系，会让工作场景里的分歧成本低很多
