# 07｜测试左移与测试右移

> 核心要点：**左移是把质量活动往研发早期挪**——问题越早发现修复越便宜；**右移是把关注延到上线之后**——线上真实反馈是最诚实的一手测试数据。一前一后，测试从"中间挨压的环节"变成"贯穿全程的活动"。

## 打个比方

快递公司保证"包裹完好送达"，检查放在哪最划算？

**最差的放法**：一路不管，用户签收时才发现碎了——赔付、补寄、差评三连，最贵。这就是传统瀑布里测试压在最后的样子：上线前夜才发现严重缺陷，代价最大。

**往左挪**：揽收时就验包装是否合规、分拣线上抽查易碎品、装车前再复核一遍——破损在前端网点就被拦下，退回成本几十块；漏到用户手里，成本几百上千。**越早发现越便宜**，这就是左移的全部动机。

**往右延**：签收不是终点——物流全程可追踪、破损率每周统计、用户评价回访，把"哪条线路、哪种包装易碎"摸清楚，反过来改进包装标准和分拣规则。**线上真实反馈是最诚实的数据**，这就是右移。

一句话：左移管"别让问题流下去"，右移管"流下去的问题别再发生"。

## 展开讲讲

### 为什么要移：被三明治夹住的测试

传统流程里测试夹在中间：需求定了、开发排好了，测试时间 = 上线日 − 提测日，前面任何延期都直接吃掉测试。更糟的是，**缺陷发现得越晚，修复成本越高**——需求阶段的笔误，改一行文档；上线后才发现是需求理解错了，开发、测试、发布全要重来。左移的本质不是"测试多干活"，是把发现问题的时机抢到修复最便宜的位置。

### 左移做什么

| 左移实践 | 发生时刻 | 在拦什么 |
| --- | --- | --- |
| 需求评审 | 开发动手前 | 需求矛盾、口径模糊、漏考虑的异常 |
| 设计与接口评审 | 开发中期 | 接口约定不清、异常码缺失 |
| 静态代码检查 | 提交代码时 | 低级代码问题、规范违反 |
| 开发自测 + 冒烟准入 | 提测时 | 明显没自测就提测的版本 |
| 单元测试前移 | 编码阶段 | 函数级缺陷，最便宜的位置 |

新手要扭转一个认知：这些活动不是"帮开发打工"，是**测试把自己的专业判断前置变现**——你在需求评审会上拦下一个口径模糊，等于省掉了未来三天的无效测试和一个线上隐患。需求评审这一站怎么打，展开见[需求评审：测试左移第一站](../process/06-requirement-review.md)。

### 右移做什么

| 右移实践 | 发生时刻 | 在要什么 |
| --- | --- | --- |
| 灰度发布 | 上线中 | 小流量先探路，炸也只炸 5% |
| 线上监控告警 | 上线后持续 | 报错率、成功率、耗时阈值 |
| 日志巡检 | 上线后头几小时 | 用户还没投诉时先看到异常 |
| 用户反馈回收 | 持续 | 应用商店评论、客服工单里的隐性缺陷 |
| 线上复盘 | 每次事故后 | 根因进用例库，同类问题不再漏 |

右移补的是测试环境永远补不了的一块：**真实流量、真实机型、真实数据量**。你在测试环境造不出的并发、想不到的组合，线上每天都在发生。灰度与发布流程展开见[发布上线：灰度、放量与线上验证](../process/12-release-process.md)。

### 左右移之后，测试变了吗

变的是活动范围，不是责任边界：测试仍是质量信息的生产者，只是采集点从"提测到上线"这一段，拉长到"需求到线上"全程。也不必焦虑"是不是要我什么都会"——左移靠的是评审提问的功力，右移靠的是看监控、读日志的功力，都是功能测试能力的自然延伸（查日志底子见[测试必备 Linux：查日志三件套](../tech-basics/09-linux-logs.md)）。

## 举个例子

外卖 App 迭代：**新客立减 15 元首单券**，一次左右移都到位的完整打法：

**左移三步**：需求评审会上，你问出"已注册老用户用新手机号注册算新客吗、同一设备算不算"——拦下口径漏洞，产品补充了设备维度判重，这是最便宜的一次拦截；接口评审时确认券发放接口对并发领取返回什么错误码，为后面自动化留好断言；提测时执行冒烟准入，开发自测记录齐全才收包。

**中间**：常规功能测试 + 回归，正常推进。

**右移三步**：上线走灰度，先放 10% 用户，盯两小时——发放成功率 99.2%、客诉 0，再全量；全量后首日巡检日志，发现凌晨批量任务有 37 条"重复发放被拦截"的记录，确认判重逻辑在真实脏数据下也扛住了；上线一周回收客服工单，把"优惠券说明页看不懂规则"的 5 条反馈整理给产品，说明页文案下迭代优化——**这 5 条反馈，比任何测试环境都真实**。

一个需求，测试的动作从评审桌一直跟到客服工单，这才是左右移完整的样子。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 左移是测试抢开发的活 | 左移是测试把质量判断前置，各角色共同受益 |
| 右移是运维的事 | 监控读得出业务异常、反馈提炼得出缺陷，是测试的专长 |
| 左移后功能测试就不重要了 | 中间的执行测试仍是主战场，左右移是延长线不是替代品 |
| 上线了测试就下班 | 右移的头几个小时恰恰是测试最该在线的时候 |
| 左移就是早点开始写用例 | 写用例只是形式之一，评审拦截才是性价比最高的左移 |

## 上手建议

1. **下个需求评审会坐到前排**：提前读文档，带上 3 个"口径模糊"的问题去，先练习最便宜的左移动作
2. **把提测标准写成检查单**：和开发约好自测记录、冒烟清单、影响范围三件套齐了才提测，把左移落成制度
3. **上线当晚留一小时看监控**：盯发布后的报错率曲线和核心指标，体验右移最浓缩的一课
4. **每周翻一次用户反馈渠道**：应用商店评论或客服群里捞和功能相关的反馈，攒出自己的"线上缺陷线索库"
5. **给每个线上问题补一条用例**：复盘时把暴露的场景翻译成用例入库，让右移的收获回流到左边的用例资产
