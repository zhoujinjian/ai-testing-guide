# 05｜验证与确认：V&V 是怎么回事

> 核心要点：**验证（Verification）问"系统是不是照规格做的"，确认（Validation）问"做出来的东西是不是用户真正要的"**——一个对照图纸，一个对照人心。V&V 就是这两类活动的合称，缺了哪半，质量都会从不同方向漏掉。

## 打个比方

一场考试牵扯两件完全不同的"对"：

**判卷**是判卷老师拿着评分细则逐题核对：这道题步骤分给得对不对、加分加错了没有、总分算对了没。判卷保证的是"**这份卷子按标准判得对**"——至于卷子出得好不好，不归他管。这是**验证**：对照既定标准，检查每一步做得对不对。

**复核考卷设计**是另一回事：哪怕判卷零失误，如果考纲要求考应用能力、卷子却全是名词默写，这份满分卷也说明不了学生学得好——**考的东西本身就错了**。这是**确认**：跳过中间标准，直接问最终结果有没有达到真实目的。

软件里最典型的翻车：团队照着需求文档开发得一丝不苟，测试按文档验证得严丝合缝，最后上线没人用——因为**文档本身理解偏了用户要的东西**。判卷满分，考卷错题。

## 展开讲讲

### 一张表分清两个 V

| 对比维度 | 验证 Verification | 确认 Validation |
| --- | --- | --- |
| 核心问题 | 做对了吗（构建方式正确） | 做的是对的吗（构建了正确的东西） |
| 对照什么 | 需求文档、设计稿、接口约定这些**规格** | 用户的真实目的和**实际使用效果** |
| 看什么 | 中间产物和过程：文档、代码、系统行为 | 最终结果：产品价值、用户能否达成目标 |
| 典型活动 | 需求评审、设计评审、代码评审、各阶段测试 | 验收测试、UAT（用户验收测试）、Beta 试用 |
| 谁主导 | 测试 + 开发 + 评审各方 | 用户/产品代表拍板，测试提供证据 |
| 出错的样子 | 精确实现了错误的需求 | 方向错了，做得越对浪费越大 |

记的窍门就一个：**验证向"规格"负责，确认向"用户"负责**。

### 为什么两个都要有

只做验证不做确认：系统是文档的完美复刻，但文档是错的——方向性浪费，通常在验收或上线后才爆雷，损失最大。

只做确认、跳过验证更离谱：连"照着说的做对了"都没保证，拿给用户验收的东西到处是低级 bug，用户根本体验不到"方向对不对"就被劝退了。

所以 V&V 是**接力**关系：验证一层层把"做对"垒实，确认在出口处问"这东西值得吗"。这也是 V 模型右半边为什么对着用户验收——开发和测试的每个阶段都有对应验证，最末端收口在确认。V 模型展开见[V 模型与 W 模型](../process/04-v-w-model.md)。

### 测试工程师日常里哪些是 V、哪些是 &

你干的大多数活是**验证**：功能测试对照需求逐条核对、接口测试对照接口文档核对字段、UI 对照设计稿走查——都是"拿产物对规格"。

但确认的影子也在：需求评审时你问"用户会这么用吗"，探索性测试时你以用户身份感受"这流程顺不顺"，验收阶段你陪着 UAT 用户走查并收集反馈。也就是说，日常说的"对照需求做测试"本身就兼有两面：对着文档逐条核对是验证在干活；一旦发现文档和用户习惯打架、把疑点主动抛出来，就是确认在干活。**测试是团队里少数同时贴着规格和用户两头的人**，这是这个岗位独特的价值位。

## 举个例子

连锁便利店的小程序需求：**会员消费 1 元积 1 分，积分抵现**。

**验证这条线**你很熟：消费 15.8 元到账 15 分（向下取整）、积分抵现比例 100 抵 1 元、积分有效期 365 天、退单积分回收——需求文档 18 条规则逐条测试，全过；接口返回的积分字段和页面展示一致；设计稿上的积分入口位置逐像素核对。验证结论：**系统与文档一致**。

**确认这条线**在 UAT 阶段出事了：试点门店的店长用了一周反馈——这套线上积分和门店用了三年的线下会员卡**两套体系不互通**，顾客在店里攒的分线上看不到，线上攒的分店里用不了，店长只好劝顾客别用小程序。需求本身没考虑到线上线下打通，做得再对也没用。最后项目回炉，需求改成"积分统一走会员中台"。

回头看：验证做得无可挑剔，确认在 UAT 才拦住一劫。如果连 UAT 都省了直接全量上线，返工成本再翻十倍——这就是"尽早确认"值钱的地方。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 验证和确认是同义词 | 一个对规格，一个对用户目的，出错的方向完全不同 |
| 功能测试通过 = 产品没问题 | 只完成了验证，方向对不对要靠确认类活动兜底 |
| 确认是产品和用户的事 | 测试提供的证据和用户视角反馈是确认的燃料 |
| V&V 是 V 模型的别名 | V&V 是验证与确认活动合称，V 模型是阶段与测试的对应关系图 |
| 需求评审走走形式就行 | 需求评审是最便宜的验证 + 确认关口，方向性错误大多能在这拦住 |

## 上手建议

1. **需求评审必带两个问题**："这条规则用户实际会怎么用""和现有体系冲突吗"——前者是确认思维，后者是验证思维
2. **用例里区分两个预期**：功能预期（按文档该怎样）之外，偶尔写一句用户预期（用户期望什么），不一致时就是提给产品的确认线索
3. **主动蹭 UAT**：验收阶段申请陪用户走查，记下用户皱眉的每一步——这是最便宜的确认教育
4. **把这张对比表讲给同事听**：能给别人讲清 V&V，面试这题你就有了肌肉记忆
5. **读一遍 V 模型**：对照[V 模型与 W 模型](../process/04-v-w-model.md)看每层验证怎么排布，把 V&V 放进流程坐标系
