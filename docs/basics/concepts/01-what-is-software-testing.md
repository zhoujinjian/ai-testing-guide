# 01｜什么是软件测试：不只是"找 Bug"

> 核心要点：软件测试不是"找 Bug"这个动作本身，而是**收集质量信息、评估发布风险**的一整套活动——找 bug 只是手段，帮团队**判断这个版本能不能上线**才是目的。

## 打个比方

把测试想象成**一次体检**。

你去做体检，医生抽血、拍片、量血压，最后给你一份报告：哪些指标正常、哪些偏高、脂肪肝要不要紧、建议三个月复查还是马上治疗。注意，医生的工作不是"找出你所有的病"——没人能做到——而是**用有限的项目，尽量准确地回答"你现在健康状况如何、有哪些风险"**。

软件测试一模一样：你在有限的时间里对系统做检查，最后交付的不是一堆 bug，而是一份"质量体检报告"——主流程通不通、新功能稳不稳、遗留问题有哪些、上线风险有多大。找到了 bug（查出了病）当然重要，但**没查出大病不等于你健康，更不等于体检没价值**。

比喻和概念的对应：抽血拍片 = 执行测试用例，查出的异常指标 = 发现的缺陷，那份结论报告 = 测试报告，"能不能正常上班" = "能不能上线"。

## 展开讲讲

### 一个能站住的定义

ISTQB（国际软件测试资格认证委员会）给的定义大意是：测试包括**验证软件是否满足需求**、**确认软件是否适合使用**，以及**发现缺陷**等活动。拆开看，测试其实在同时干四件事：

| 测试在做什么 | 人话解释 | 对应体检里的动作 |
| --- | --- | --- |
| 验证需求满足 | 需求说"满 100 减 20"，到账就得真减 20 | 按体检套餐逐项检查 |
| 发现缺陷 | 把藏着的问题尽可能翻出来 | 查出脂肪肝、血糖偏高 |
| 评估质量与风险 | 这个版本整体什么水平，上线可能炸哪里 | 报告里写"血脂偏高，建议复查" |
| 建立信心 | 用通过的用例证明核心功能真的能用 | 指标全部正常，放心出差 |

新手最容易只看见第二行，觉得测试就是"提 bug 的"。老手会把四行看全——尤其第三行，**测试是团队里离质量信息最近的人**，上线前大家问的往往是测试那句"你觉得能发吗"。

### 为什么"证明没 bug"做不到

很多人以为测试的目标是"证明软件没有缺陷"。逻辑上这不成立：你测了 1000 条用例全过，只能说明这 1000 条场景没问题，第 1001 条没人知道。就像体检全部正常，也不能证明你没有未来会发的病。

所以行业的共识是：**测试只能证明缺陷存在，不能证明缺陷不存在**。这也直接决定了测试的干活方式——既然穷举不可能，就得动脑子挑最值得测的：先测主流程，先测改动点，先测历史上爱出事的模块（这些原则展开见[软件测试的 7 条原则](./02-seven-principles.md)）。

### 测试和质量的关系

测试能**度量**质量、**暴露**质量问题，但**不能直接提高**质量——就像体检不能替你减肥。质量是设计出来的、开发出来的，测试负责把它照出来。所以别背"质量是测试的职责"这口锅，也别信"测不出 bug 就是测试不行"，这话和不治病怪体检报告一个逻辑。团队里每个人怎么分担质量责任，见[测试与产品、开发的分工协作](./08-roles-collaboration.md)。

## 举个例子

外卖 App 出新需求：**订单满 30 元送 5 元无门槛券**。测试接手后干的活：

1. **验证需求满足**：下一单 35 元的麻辣烫，支付完成后查优惠券列表，5 元券到账、有效期 7 天、无门槛字段正确——需求文档写的每一条都要对上
2. **发现缺陷**：测出 29.9 元的订单也发了券（边界判断写错，把 `> 30` 写成了 `>= 30` 的反例）、退款后券没回收、同一账号重复领券没拦截——提了 3 个 bug 单
3. **评估风险**：回归时发现优惠券列表页加载变慢，判断是本需求新增查询导致，标记为上线前必须确认的风险项
4. **建立信心**：主流程 45 条用例全通过，其中支付链路 12 条重点用例双环境各跑一遍

最后你在版本报告里写的不是"我测完了"，而是："需求功能全部实现，发现 3 个缺陷已修复，1 个性能风险项已确认影响可控，**建议按期上线**。"——这句话，就是测试真正的产出。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 测试就是找 bug 的 | 找 bug 是手段，交付质量信息、支撑上线决策才是目的 |
| 测完没发现 bug 就是白干 | 没发现问题本身就是有价值的信息，证明这轮场景下功能可用 |
| 测试能证明软件没有缺陷 | 测试只能证明缺陷存在，不能证明不存在，穷举不可能 |
| 发现 bug 越多测试越厉害 | bug 多说明开发质量差；测试的水平看关键 bug 抓得多不多、漏得少不少 |
| 质量不好是测试的责任 | 测试度量质量、暴露问题，质量是整个团队造出来的 |
| 上线后出问题一定是测试漏测 | 可能是漏测，也可能是没测的环境、没覆盖的时间点，先做根因分析再定责 |

## 上手建议

1. **每天写测试日志**：今天验证了什么需求、发现了什么问题、还有什么风险，一周后回看，你对"测试在干什么"的感觉会完全不一样
2. **主动看测试报告**：找组里最近一份版本报告，看老测试怎么组织"通过情况、缺陷情况、风险、结论"四段，比自己闷头猜快十倍
3. **把"建议"说出口**：下次版本收尾，试着对师傅说一句"我觉得主流程稳了，可以上"，练习给出质量判断，这是从执行者到测试工程师的分水岭
4. **给发现的 bug 分分类**：按功能、边界、数据、兼容归档，一个月后你会发现自己对"哪里爱出 bug"有了直觉
5. **读一遍需求的验收标准**：拿手上项目的需求文档，把验收标准逐条翻译成检查动作，体会"验证需求满足"这四个字落地是什么样
