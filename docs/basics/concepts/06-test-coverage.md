# 06｜测试覆盖率是什么

> 核心要点：测试覆盖率衡量的是**"被测对象里有多大比例被你的测试碰过了"**——它是照出盲区的手电筒，不是考核分数。**覆盖率 100% 不等于没 bug，覆盖得再全也不等于测得准。**

## 打个比方

你在一间黑屋子里找东西，手里只有一支手电筒。

**覆盖率就是你的光扫过了这间屋子的多大比例。** 光扫到的地方，你看清了摆放的东西（测过的部分心里有底）；光没扫到的地方，不是"没有东西"，是"你不知道有没有东西"——**未覆盖不等于没问题，只等于没看过**。

再想一层：光扫过一遍，就等于看清了吗？未必。你晃着手电筒一路小跑扫完全屋（用例空跑，没做断言），跟蹲下来逐个角落细看（每步都校验结果），扫过的面积一样，收获天差地别。所以老测试嘴边有句话：**覆盖率度量的是"碰没碰过"，不度量"看得细不细"**——它告诉你哪里是黑的，不保证亮处都看清楚了。

## 展开讲讲

### 覆盖率不止一种

新手一说覆盖率就想到代码，其实按"被测对象"不同，常见的有四种：

| 覆盖率类型 | 统计什么 | 怎么算 | 典型场景 |
| --- | --- | --- | --- |
| **需求覆盖率** | 需求点有多少被用例覆盖 | 已覆盖需求点 ÷ 总需求点 | 用例设计完自查漏没漏需求 |
| **用例执行率** | 写了的用例有多少真的跑了 | 已执行用例 ÷ 应执行用例 | 版本报告里的基础数字 |
| **代码覆盖率** | 代码有多少行/分支被跑到 | 被执行代码 ÷ 总代码 | 开发单元测试、自动化回归评估 |
| **接口覆盖率** | 接口有多少被用例调用过 | 已测接口 ÷ 应测接口 | 接口测试进度盘点 |

代码覆盖率内部还分粗细：语句覆盖（每行跑过没有）、分支覆盖（每个 if 的真假两边都走过没有）、条件覆盖（组合条件逐个看过没有）。同一套用例，语句覆盖 80% 时分支覆盖可能只有 60%——分支口径更严，也更能暴露"只走了正路"的用例。工具方面，Java 有 JaCoCo，Python 有 coverage.py，前端有 Istanbul，流水线里都能接。

### 覆盖率的正确打开方式：找盲区，不是刷数字

覆盖率最大的价值是**当镜子**：拿未覆盖清单反问自己"这块为什么没测"——是防御性代码确实到不了？是异常分支懒得构造场景？还是压根没想到？三种答案对应三种动作，第三种最危险，那就是你测试设计的漏洞。

反过来，把覆盖率本身当目标就会跑偏：为了数字好看写一堆没有断言的空跑用例，覆盖率上去了，发现 bug 的能力一点没涨。**指标一旦成为目标，就会被人优化到失真**——这在家代码覆盖率被当 KPI 硬性考核的团队里反复上演。

### 多少合适

没有万能数字。粗略的业内感受：核心支付链路分支覆盖率要求 80% 以上不嫌高，边缘工具类代码 40% 也够用。合理的问法不是"覆盖率要到多少"，而是"**哪些代码没被覆盖，我能接受吗**"——逐块给出理由，比一个总数诚实得多。把这句问话连同答案写进测试计划，比抄一个行业百分比更有说服力，评审时也站得住。

## 举个例子

电商 App 迭代：**优惠券到期前 3 天 App 站内提醒**。三步用覆盖率照了一次盲区：

1. **需求覆盖自查**：需求 22 条验收点，对照用例矩阵逐条打勾，发现"用户关闭推送权限时的降级处理"没有对应用例——漏了 1 条，补上。这就是需求覆盖率最朴素的用法：一张对照表，30 分钟抓出一个设计遗漏
2. **代码覆盖率验证**：开发提供的单元测试语句覆盖率 76%，你看未覆盖清单，发现"券已冻结时不发提醒"的分支没人碰——和开发确认这是上线新逻辑，不是死代码，补了 2 条手工用例：冻结账户到期前查收，验证 App 无提醒且后台记录跳过原因
3. **报告里如实呈现**：版本报告写"需求覆盖率 22/22，用例执行率 100%，主流程自动化分支覆盖率 71%，未覆盖部分为支付回调重试的异常模拟（下版本补）"——每一个数字后面跟着说明，读的人才知道边界在哪

注意第 3 步的写法：**数字 + 未覆盖的说明**。只写"覆盖率 71%"，别人不知道那 29% 是什么；写清"没测什么、为什么、什么时候补"，覆盖率才从数字变成了质量信息。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 覆盖率 100% 就没 bug 了 | 碰过不等于验过，空跑也算覆盖；边界值错、规则理解错照样漏 |
| 覆盖率越高测试越好 | 高覆盖可以是空跑刷出来的，要看断言质量和用例设计 |
| 代码覆盖率是测试专属指标 | 单测覆盖率主要归开发，测试拿它当盲区线索而非考核表 |
| 只盯代码覆盖率 | 需求覆盖率常被忽略，而方向性遗漏恰恰藏在那 |
| 未覆盖的代码都是死代码 | 很多是异常分支和防御逻辑，恰是线上事故的高发地 |

## 上手建议

1. **建一张需求覆盖对照表**：拿当前迭代的需求验收点做行、用例编号做列，逐格打勾——这是新手成本最低、收益最快的覆盖实践
2. **找开发要一次覆盖率报告**：看流水线上有没有接覆盖率工具，拿一次未覆盖清单，挑两块问"这是什么逻辑"，练读代码盲区的眼力
3. **报告里写"未覆盖说明"**：养成数字后面跟一句边界说明的习惯，"覆盖率 100%"永远是可疑的
4. **别用执行率美化报告**：执行率 100% 但通过率 60%，问题更多——几个指标连着看才不会骗自己
5. **给断言做次抽查**：随机抽 10 条自动化用例，检查每条是否真的校验了结果而不是只跑不判，体会"碰过"和"验过"的差距
