# 10｜新手术语词典：中英对照速查

> 核心要点：测试圈的"黑话"不是门槛，是**老手为省时间造的压缩包**——每个词背后是一段固定的协作含义。这份按场景分组的词典帮你解压，听懂站会，只要这一篇。

## 打个比方

你初到一座**说方言的城市**生活。

本地人聊得飞快，不是故意排外，只是那些词从小就说，顺嘴。你插不上话，不是能力差，是**没带方言手册**。而且学方言最快的路子不是背词典，是按场景学——买菜学菜的叫法、坐车学站点的叫法，一周就能听懂大半。

测试团队的黑话同理：站会有站会的词、提单有提单的词、报指标有指标的词。按场景分组记，比按字母背快十倍。下面这本手册，按你一天会遇到的五类场景整理。

## 展开讲讲

### 第一组：流程黑话——站会和群里天天飞

| 术语 | 英文 | 一句人话解释 |
| --- | --- | --- |
| 提测 | submit for testing | 开发说"可以测了"，把版本交给测试 |
| 冒烟测试 | Smoke Testing | 主流程快速过一遍，不通就整包打回 |
| 回归测试 | Regression Testing | 改动之后，确认改的没坏、没改的也没被殃及 |
| 准入/准出 | Entry/Exit Criteria | 开始测要满足什么条件、测到什么程度能放行 |
| 联调 | Joint Debugging | 前后端把接口接起来一起调通 |
| 串讲 | Walkthrough | 需求或方案由作者当面讲给团队听 |
| 封版 | Code Freeze | 到点不许再改代码，之后的改动走下个版本 |
| 灰度发布 | Gray Release | 先放一小部分用户试用，没问题再全量 |
| 上线验证 | Production Verification | 发布后在生产环境真实走一遍核心流程 |
| 留观 | Monitoring Window | 发布后盯着监控和反馈的一段时间 |
| 回滚 | Rollback | 新版本出事，退回上一个稳定版本 |
| 迭代 | Iteration/Sprint | 固定周期的一轮开发交付，常见两周一轮 |

### 第二组：用例相关——设计执行时绕不开

| 术语 | 英文 | 一句人话解释 |
| --- | --- | --- |
| 测试用例 | Test Case | 一条完整的"什么条件下做什么、期望看到什么" |
| 前置条件 | Precondition | 开测前必须准备好的状态和数据 |
| 预期结果 | Expected Result | 按需求应该看到的结果，不写就等于没测点 |
| 优先级 P0~P3 | Priority | P0 保命主流程，P3 边角锦上添花 |
| 正向/逆向用例 | Positive/Negative | 按规矩操作的用例 / 专门捣乱的用例 |
| 冒烟集 | Smoke Suite | 挑出来的主流程用例集合，每次提测先跑它 |
| 用例评审 | Case Review | 团队一起挑用例的漏和错 |
| 等价类 | Equivalence Class | 把输入按"同一种处理"分组，每组挑代表 |
| 边界值 | Boundary Value | 范围的临界点及其两侧，bug 最爱藏的地方 |
| 场景法 | Scenario Method | 按用户完整使用流程串起来的设计方法 |
| 用例矩阵 | Traceability Matrix | 需求和用例的对照表，查漏需求神器 |

### 第三组：缺陷相关——提单吵架必备

| 术语 | 英文 | 一句人话解释 |
| --- | --- | --- |
| 缺陷 / bug | Defect / Bug | 实际结果和预期不一致的问题 |
| 复现步骤 | Repro Steps | 别人照着做就能再看到 bug 的操作序列 |
| 严重程度 | Severity | 对系统伤害多大：崩溃、资损是最高档 |
| 优先级 | Priority | 多急着修：和严重程度不是一回事 |
| 打回 | Reject | 版本或缺陷单被退回，不合收单标准 |
| 偶现 bug | Intermittent Bug | 时有时无、不能稳定复现的 bug |
| 无效缺陷 | Invalid Defect | 查下来不是 bug（环境、配置或理解偏差） |
| 缺陷密度 | Defect Density | 单位规模（千行代码或一个需求）里的 bug 数 |
| 漏测 / 逃逸缺陷 | Escaped Defect | 测试没拦住、流到线上的 bug |
| 根因 | Root Cause | 问题真正的病根，修它才能断根 |

### 第四组：环境与版本——"环境问题"家族

| 术语 | 英文 | 一句人话解释 |
| --- | --- | --- |
| dev / test / staging / prod | 四套环境 | 开发自用 / 测试主战场 / 预发布彩排 / 真实用户的生产环境 |
| 测试包 | Test Build | 装到测试环境用的安装包，和生产包不是同一个 |
| 分支 | Branch | 代码的平行副本，feature 分支开发完才合入主干 |
| mock | Mock | 用一个假实现替掉真依赖，比如假装支付成功 |
| 造数 | Test Data Preparation | 手工或脚本制造测试要的数据 |
| 脏数据 | Dirty Data | 环境里残留的、会影响判断的旧数据 |
| 数据回滚 | Data Rollback | 把数据恢复到操作前的状态 |
| 埋点 | Tracking Point | 代码里预埋的数据上报点，用来统计行为 |
| 抓包 | Packet Capture | 截获网络请求看实际发了什么、回了什么 |
| 打点日志 | Instrumented Log | 为排查特定问题临时加的日志输出 |

### 第五组：指标术语——报告和复盘里出现

| 术语 | 英文 | 一句人话解释 |
| --- | --- | --- |
| 执行率 | Execution Rate | 应测用例里实际跑了多少 |
| 通过率 | Pass Rate | 跑了的用例里过了多少 |
| 崩溃率 | Crash Rate | 用使用次数一除，App 质量的命门指标 |
| 成功率 | Success Rate | 核心操作（如支付）成功的比例 |
| P95 响应时间 | P95 Latency | 95% 的请求都快于这个时间，比平均值诚实 |
| 逃逸率 | Defect Escape Rate | 线上 bug 占全部 bug 的比例，越低拦截越有效 |
| DRE | Defect Removal Efficiency | 测试拦住的 bug 占总 bug 比例，和逃逸率是一体两面 |
| MTTR | Mean Time To Repair | 从发现故障到修复的平均耗时 |

## 举个例子

入职第一天，新人小周在站会上的真实体验——组长语速正常地说：

> "昨天 test 环境的 **4.1.2 测试包**部署好了，今天大家先跑**冒烟**，过了再铺 **P0 用例**。支付那 3 条先别跑，**联调**没完，用例挂 **block** 状态。昨晚那个**偶现 bug**开发还没复现，**提测单**里加了**打点**，今天观察。下午 staging 有**灰度演练**，别占环境。周五**封版**，**回归**必须周四收尾，报告里**执行率、通过率**都补齐。"

小周一头雾水，但会后她没装懂，而是拿着本子逐个问。问完翻译成人话就是：今天先验主流程再测最要命的场景；支付那三条被别的进度挡住了先跳过；昨晚那个时有时无的问题正在等新线索；下午预发环境有安排别去动；周四之前必须确认改动没伤到旧功能，并且报告的两个数字要填全。**一段 30 秒的黑话，信息密度是一段三分钟白话的量**——这就是团队爱用黑话的原因，也是你要尽快解压它的原因。

一周后，小周在站会上说出了第一句完整黑话："block 的那 3 条解了，今天补测，顺便把 mock 支付切回真实通道。"——她入乡随俗了。

## 新手常见误区

| 误区 | 实际情况 |
| --- | --- |
| 听不懂是自己的问题 | 黑话是团队内部的压缩包，新人听不懂天经地义，问就完了 |
| 装懂点头混过去 | 一个词理解偏，后面一串任务做错，代价远大于当场问 |
| 背词典式学术语 | 按场景分组、在实际任务里确认一遍，才真正学会 |
| 学了黑话拿来显摆 | 术语是为了沟通省力，和外部人员沟通该切回白话 |
| 以为严重程度就是优先级 | 两个词含义不同，混用会在提单时吃大亏 |

## 上手建议

1. **把五张表打印贴在工位**：第一周抬头可见，听到陌生词当场对号，比翻聊天记录快
2. **听不懂的当场问一句**："这个 block 是指卡住了吗？"——没有人会笑，两周后才问才是问题
3. **建自己的生词本**：每天记 2~3 个新词，写下"我理解的含义"，一周后找老测试对答案纠偏
4. **每个词绑定一个真实场景**：学"准入"就去看一次真实的提测检查；学"灰度"就去盯一次灰度发布，词和事绑住才忘不掉
5. **对团队外的人切白话**：给客服、给用户解释问题时把术语翻译掉，这个切换能力本身就是专业度
