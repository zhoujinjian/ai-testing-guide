# 12｜测试和开发经常有冲突，作为管理者怎么协调？

> 开场先讲冲突的根源认知：**大多不是人的问题，是机制的问题**——从机制找根子，改造机制比教育人性有效。

## 回答思路

### 第一步：冲突的三个机制根源

1. **交付压力下的目标错位**（开发求快测试求稳，屁股决定脑袋）
2. **质量责任边界模糊**（「提测质量差」和「测试太苛刻」互相埋怨）
3. **沟通机制缺失**（bug 单上吵架，因为平时没有对话渠道）

### 第二步：讲预防性的机制建设

- **共同目标的对齐**：版本质量是共同 KPI 的一部分，**考核设计上绑定**
- **流程接口的清晰**：提测标准的 checklist、bug 处理的 SLA——**规则先于冲突**
- **日常关系的建设**：联合技术分享、非工作社交——有交情的人冲突有缓冲

预防做足，冲突自然少。

### 第三步：讲冲突发生时的处理艺术

- **就事论事的规则**：拿数据和需求说话（合集二 09 题的方法论在管理者视角的放大）
- **及时介入的时机**：小摩擦让团队自己解决练协作；升级到互相攻击或影响交付时管理者出手
- **私下沟通优先**：公开会议上的对立要会后分别聊，给台阶
- **极端情况**：屡次沟通无效的恶意对立，升级到双方上级或 HR——管理者的兜底责任

### 第四步：讲几个高发冲突的具体解法（干货）

| 冲突 | 解法 |
| --- | --- |
| 提测质量差 | 用**打回率数据**说话，推开发自测门禁——而不是测试兜底养出惯性 |
| bug 优先级分歧 | 定级标准的**事先共识**，争议走产品仲裁而不是扯皮 |
| 修复慢影响测试 | bug 处理 **SLA** 加每日修复同步会——把等待显性化 |

### 收尾：给立场

测试和开发的根本利益一致（都想产品好）——冲突是**协作系统的摩擦力**，不是敌我矛盾。管理者的角色是「**润滑和设计系统**」，而不是「帮测试打架」。团队长期看的是你处理冲突的公心。

## 考察重点

| 维度 | 说明 |
| --- | --- |
| 企业动机 | 考察的是机制思维（改造系统）还是人治思维（做个和事佬）——前者是管理者，后者是居委会 |
| 过线标准 | 机制找根子 + 预防机制 + 冲突时的处理艺术 |
| 区分度 | 给高发冲突具体解法（提测差、优先级分歧、修复慢）的是带着经验来的 |
| 加分项 | 「共同 KPI 绑定」的考核设计 |
| 减分项 | 「我脾气好大家都能聊」或「该吵吵不影响工作」——没有管理动作的放任 |
