# 07｜项目要延期，测试时间被压缩，你怎么办？

> 开场先讲判断的第一层：**时间被压缩的原因不同，对策不同**——一上来就「砍测试范围」是放弃管理的表现。

## 回答思路

### 第一步：先归因再应对

| 原因 | 对策 |
| --- | --- |
| 开发延期挤占测试 | 开发的问题——谈开发提测质量 + 测试时间重排 |
| 需求变更 | 产品的问题——评估变更影响 + 范围谈判 |
| 整体工期提前 | 市场的问题——全面的质量风险重新评估 |

### 第二步：讲应对的完整工具箱（按代价从小到大用）

1. **范围裁剪**：按风险分层——核心主流程保、边缘场景降级为线上观察加监控。**裁剪清单显式给项目组确认**，不是测试默默兜下
2. **效率压缩**：自动化回归顶上、并行测试、加班做短时冲刺（但要有补偿和期限）
3. **质量前置**：提测标准提高，减少测试期返工
4. **外部求助**：临时借人集中攻坚

### 第三步：讲风险显性化（管理者的核心动作）

压缩后的质量风险**书面化**（砍了什么、可能漏什么、上线后要观察什么），邮件给项目组和管理层确认——测试专业性的体现不是「扛住一切」，而是「**让选择被知情地做出**」（合集二 10 题的个人版在这升级成管理者版）。

### 第四步：讲底线思维

**哪些不能砍**：资金安全、数据正确性、核心合规项——时间再紧这几类的测试底线守住。底线失守的事故是灾难级且不可逆的，**管理者的价值就在守底线时的坚定**。

### 收尾：讲复盘预防

这次为什么被压缩（排期没留 buffer、上游质量差、还是测试自己报的时间虚高）——根因改进让下一版的谈判筹码更足。**老是被动挨打，说明复盘缺失。**

## 考察重点

| 维度 | 说明 |
| --- | --- |
| 企业动机 | 时间压缩是测试管理的永恒场景——既要能落地（有工具箱）又要有底线（敢说不），只会妥协或只会硬顶的都不行 |
| 过线标准 | 先归因再应对 + 风险显性化 + 底线思维 |
| 区分度 | 讲裁剪清单显式确认、讲事后复盘预防的是管理者级答案；「和领导争取一下时间」是个人贡献者思维 |
| 加分项 | 提测标准提高的 upstream 手段 |
| 减分项 | 无条件压缩按期交付（没底线）或无条件拒绝上线（没方案），两个极端都是不称职 |
