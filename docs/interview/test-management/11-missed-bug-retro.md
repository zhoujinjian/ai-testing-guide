# 11｜这次漏测了，你怎么复盘和改进？

> 开场先讲漏测复盘和事故复盘的差别：漏测是「测试没拦住」（**内部复盘，深挖自己的问题**）——一上来就找外部原因（需求没写、开发代码烂）的复盘没有成长价值。

## 回答思路

### 第一步：漏测原因的解剖框架（本题核心，三层解剖）

**第一层：用例层**

- 根本没设计到（场景遗漏还是设计方法没用够）
- 设计了没执行到（时间压缩还是优先级误判）
- 执行了没发现（断言缺失还是环境差异掩盖）

**第二层：流程层**——需求评审时没识别风险、排期时低估了测试量

**第三层：能力层**——业务理解不足、对新技术的风险认知不够

三层解剖下来，真因浮出。

### 第二步：讲每类原因对应的改进动作（对因开方）

- 用例缺失 → 补用例进回归库 + 「**同类型场景扫描**」（这个漏了，同类的一起补）
- 设计方法 → 边界值场景法的复盘性补课
- 执行问题 → 流程上保核心场景的优先级机制
- 环境差异 → 推环境一致性建设 + 线上仿真测试
- 认知不足 → 业务知识的考核和分享机制

### 第三步：讲个人的责任担当和团队的改进氛围

自己审核过的用例漏了，**管理者先担责**（「我在评审时也没看出来」），再带团队改——改进是团队的事，不是追某个人的责。

**漏测复盘的心理安全氛围，决定未来漏测是「藏」还是「报」**——藏起来的漏测会变成更大的线上事故。

### 收尾：讲度量的跟踪

漏测复盘后的改进项执行率、**同类漏测的复发率**（这个指标恶化，说明复盘是形式主义）——把「漏测分析」做成团队例行动作（每个逃逸 bug 都走轻量归因），而不是出了大事故才开会。

## 考察重点

| 维度 | 说明 |
| --- | --- |
| 企业动机 | 漏测是测试团队的「原罪」场景——浅层复盘（补个用例了事）和深层复盘（解剖到设计和流程层）的差距，就是团队质量能力进化速度的差距 |
| 过线标准 | 三层解剖框架 + 对因开方的改进 |
| 区分度 | 讲「同类场景扫描」、讲心理安全氛围、讲复发率跟踪的是复盘专家级 |
| 加分项 | 管理者先担责的姿态 |
| 减分项 | 漏测原因归结为「开发代码太烂」「时间太紧」——全外部归因的复盘等于没复盘 |
