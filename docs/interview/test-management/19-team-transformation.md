# 19｜手工测试为主的老团队，怎么推动自动化和 AI 转型？

> 开场先讲**转型失败的常见原因**再讲怎么推——三个失败样本先摆出来，说明你见过转型死掉的样子。

## 回答思路

### 第一步：三个失败样本

1. **命令式强推**（没意愿没能力硬上——产出垃圾自动化然后草草收场）
2. **大跃进目标**（三个月自动化率 80%——数字游戏）
3. **没有梯度的任务**（让业务测试直接写框架级代码——劝退）

### 第二步：讲转型的正确顺序（人先于事）

- **意愿的建设**：转型的 why 讲透——不是裁人，是把人从重复劳动里解放去做更有价值的事；配合**职业路径的重新设计**，让转型和个人利益挂钩
- **能力的梯度培养**：分层课程（工具使用 → 脚本编写 → 框架设计），**按基础分班**而不是一锅炖
- **保护期的设计**：转型期绩效不按产出量考核——**给学习留空间**

人转过来了，事才能成。

### 第三步：讲技术路径的低门槛起步

- **从接口自动化切入**（比 UI 简单且回报快——合集三的知识在转型场景的应用）
- **低代码工具过渡**（让不会代码的人先参与编排——合集八 16 题的逻辑复用）
- **AI 工具的借力**（用例生成和脚本生成降低起步门槛——合集六的方法论）

**门槛一低，转型的阻力减半。**

### 第四步：讲节奏和标杆

小步试点（一两个项目先转，跑出效果和数据）→ **标杆示范**（转型成功的人现身说法，比管理者宣讲有力十倍）→ 渐进推广（每步都有数据验证）→ **容错机制**（转型初期的效率下降要被接受；确实转不了的人安排合适的岗）。

### 收尾：讲转型中的个体关怀（管理者的人性面）

年龄大学习慢的员工（一对一帮扶、发挥其业务经验优势**转业务专家岗**，而不是硬逼 coding）；转型焦虑的疏导（把「会不会被淘汰」的恐惧谈开）；最终的人岗匹配——**转型的目的地不是全员码农**，是「测试策略、业务专家、自动化、AI 应用」的多元分工。**把人当目的不当工具的转型才走得远。**

## 考察重点

| 维度 | 说明 |
| --- | --- |
| 企业动机 | 传统测试团队的转型是企业当下最普遍的管理课题（AI 浪潮放大了紧迫性），转型失败率极高——企业要能带团队「软着陆」的管理者 |
| 过线标准 | 失败样本认知 + 人先于事的顺序 + 节奏设计 |
| 区分度 | 讲保护期设计、讲标杆示范、讲人岗多元分工的是有变革实操的 |
| 加分项 | 个体关怀的人性面（年龄大员工的转岗安排） |
| 减分项 | 「下指标限期学会不然淘汰」——威胁式转型只会逼走能干的人，留下躺平的人 |
