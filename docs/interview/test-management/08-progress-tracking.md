# 08｜测试进度滞后了，你怎么发现和追赶？

> 开场先讲**怎么发现**——滞后的发现靠日常数据，不靠版本末的惊觉。

## 回答思路

### 第一步：进度管理的数据化

- **每日执行进度对计划的偏差跟踪**（计划执行一百条实际六十条，偏差四成**当天就要预警**，不是到版本末才发现）
- **关键路径的监控**（哪些用例块在卡测试主线）
- **依赖项的跟踪**（环境好了吗、bug 修复及时吗——**等依赖是测试滞后的隐形主因**）

### 第二步：讲滞后的归因（不同病因不同追赶法）

| 病因 | 追赶法 |
| --- | --- |
| 执行效率低 | 人手或技能问题——加人或换人 |
| 阻塞太多 | 环境或 bug 修复慢——**向上游推动解除**，测试自己解决不了 |
| 范围变大 | 需求加了或修复引入新测试量——重新谈判范围 |
| 估时偏差 | 本来就没估准——修正预期 |

**先诊断再开药，追赶方案对着病因去。**

### 第三步：讲追赶的手段排序（追赶也是资源决策）

1. **低代价先上**：并行执行、优先级重排先跑高风险、用例合并去重、自动化顶重复回归
2. **中代价次之**：借调人手、加班冲刺带补偿
3. **高代价最后**：砍范围（走 07 题的裁剪流程）

### 第四步：讲向上和向外的管理

- **滞后要早报告**（周报里显性化，附追赶方案——最忌管理者自己扛到瞒不住）
- **需要支持明确提**（要人要环境要上游配合，具体到人和事）

**滞后的报告时机是管理信任的分水岭——坏消息早说是职业素养。**

### 收尾：讲滞后后的复盘

估时方法校准（用历史数据修正估时模型）、流程改进（阻塞的预防机制）、教训进团队的 checklist——**同一类滞后反复出现，说明复盘是走过场。**

## 考察重点

| 维度 | 说明 |
| --- | --- |
| 企业动机 | 进度失控是测试团队最常见的失职形态——「发现得早、归因得准、追得上、报告得及时」四个能力一次考全 |
| 过线标准 | 数据化的发现机制 + 归因分类 + 追赶手段排序 |
| 区分度 | 讲「等依赖是隐形主因」、讲坏消息早说的报告时机的是有带队智慧的 |
| 加分项 | 估时校准的复盘闭环 |
| 减分项 | 发现滞后就「让团队加班赶进度」——单一手段且归因缺失，管理工具箱是空的 |
