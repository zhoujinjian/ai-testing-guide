# 01｜性能测试的目的是什么？什么样的项目需要做性能测试？

> 开场先给目的的三层表述——性能测试的**终点是容量结论，不是一份报绿的数据**。

## 回答思路

### 第一步：目的的三层表述

| 层 | 回答什么 |
| --- | --- |
| **验证层** | 系统在预期负载下能不能达标（响应时间、吞吐、资源） |
| **探索层** | 系统的极限在哪、拐点在哪；过载后会不会崩、崩了能不能恢复 |
| **容量层** | 给扩容和预算提供依据——当前配置撑多少量、加机器收益多大 |

### 第二步：什么项目要做，按信号列

1. 有明确高并发场景的（大促、秒杀、开售）
2. 用户量增长期的
3. 架构大改后的（换了中间件、拆了服务）
4. 有 SLA 承诺的（To B 交付合同里写了指标）
5. 出过线上性能事故的

### 第三步：反着讲什么项目可以不做

内部低频管理系统、用户量个位数的工具、一次性的活动页——性能投入没有回报，**明确说「不做」也是专业判断**。

### 第四步：补一个时机认知

性能测试不是上线前才想起来跑一把——**架构评审阶段就该介入**（技术方案里有没有缓存、异步、扩容设计）。上线前才测等于考试前夜抱佛脚，发现问题已经没时间改。

### 收尾：给定位

性能测试的价值一半在验证达标，一半在**找到系统短板推动优化**——只报数字不给结论的性能测试等于白做。

## 考察重点

| 维度 | 说明 |
| --- | --- |
| 企业动机 | 考察对性能测试的价值认知。企业要的是能判断「什么时候该投入性能测试」的人，而不是逢项目就压一把的流水线操作员 |
| 过线标准 | 目的讲到验证和容量两层 + 能列需要做性能的项目信号 |
| 区分度 | 讲「架构阶段介入」和「终点是容量结论」的是有体系认知的 |
| 加分项 | 明确说什么项目不做，敢做减法的判断力 |
| 减分项 | 说「性能测试就是用 JMeter 压一下」，把目的和工具混为一谈 |
