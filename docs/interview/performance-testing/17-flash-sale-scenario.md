# 17｜秒杀或大促场景的性能测试怎么设计？

> 开场先**刻画流量特征**再谈方案——秒杀是典型脉冲流量：开售瞬间流量是平时的几十上百倍、持续几秒到几分钟、库存极少导致大量请求注定失败、热点集中（一个商品一个 SKU）。先讲特征再讲方案，是分析型选手的标志。

## 回答思路

### 第一步：场景设计三层

| 层 | 测什么 |
| --- | --- |
| **入口层** | 开售瞬间的瞬时洪峰（spike 模型，零点几秒内打满目标并发）、页面刷新风暴、按钮防抖前的重复提交 |
| **服务层** | 库存扣减的并发正确性（超卖少卖）、请求排队和削峰（消息队列的积压和消费能力） |
| **兜底层** | 超过容量后的限流表现（被拒请求的友好提示）、熔断降级链路、恢复过程 |

### 第二步：讲正确性验证这个特殊维度

秒杀测试不只是性能，要验证高并发下：

- **库存不超卖**（数据库行锁或 Redis 原子操作的并发正确性）
- 订单和扣减的一致性
- 重复支付幂等

**性能和正确性双线并行。**

### 第三步：讲预期外行为的观察

缓存击穿（热点 key 过期瞬间）、热点账户问题（一个卖家的账户成热点）、黄牛脚本的特征识别——把**攻防视角**带进来的候选人极少。

### 收尾：给体系依赖

秒杀保障从来不是单靠测试，是**限流 + 排队 + 降级 + 扩容的体系工程**——性能测试的角色是验证这套体系在目标流量下的有效性。

## 考察重点

| 维度 | 说明 |
| --- | --- |
| 企业动机 | 秒杀是性能面试的皇冠题（腾讯云真题盘点里有秒杀场景优化原题），电商和出行类业务必考——能系统性讲清的人，专项能力毋庸置疑 |
| 过线标准 | 脉冲流量特征 + spike 场景设计 + 超卖正确性验证 |
| 区分度 | 讲削峰队列、限流降级验证、缓存击穿的是有高并发实战的 |
| 加分项 | 黄牛攻防视角或热点账户这类深水区问题 |
| 减分项 | 只说「把并发数调大压一下」，完全没理解秒杀场景的特殊性 |
