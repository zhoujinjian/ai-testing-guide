# 10｜JMeter 的线程模型是什么？怎么做分布式压测？

> 开场讲线程组这个核心概念——JMeter 的虚拟用户就是线程。

## 回答思路

### 第一步：线程组三参数

- **线程数** = 并发虚拟用户数
- **Ramp-up** = 启动这些线程的爬坡时长
- **循环次数** = 每线程执行几遍

这三个参数是脚本的第一配置。

### 第二步：讲单机瓶颈这个关键认知

JMeter 单机的施压能力受限于 CPU 和内存（线程是重资源），**大约一两千线程就把施压机自己压满了**——这时候看到的吞吐下降是施压机不行，不是被测系统不行。识别「施压瓶颈」和「被压瓶颈」是压测工程师的基本功，这个认知讲出来本题过半。

### 第三步：分布式压测的架构

一台**控制机（master）**调度，多台**负载机（slave）**执行——脚本分发到各负载机，结果回汇总，施压能力随负载机线性扩展。原理一句话：**把线程摊到多台机器上**。

### 第四步：讲分布式实践细节（全是实操坑）

- 各负载机**环境版本一致**
- 参数文件每台都要放，且注意**数据切分**（避免每台压同一批数据）
- **时间同步**（聚合数据的时间戳要对齐）
- 内网部署减少网络干扰

### 收尾：给延伸

更大规模的压测会转向 gossip 协议的轻量施压引擎或云上弹性压测服务——JMeter 分布式是入门主流但不是唯一形态，显示技术视野。

## 考察重点

| 维度 | 说明 |
| --- | --- |
| 企业动机 | JMeter 是国内性能岗的主流工具，考的是真用过还是看过教程——施压机瓶颈这个坑没踩过的人答不出来 |
| 过线标准 | 线程模型 + 单机瓶颈认知 + 分布式架构 |
| 区分度 | 讲数据切分、时间同步、施压机自身监控的是带过分布式压测的 |
| 加分项 | 对施压工具生态的延伸认知（轻量引擎、云压测） |
| 减分项 | 不知道 JMeter 自身会成为瓶颈，压不动就无脑加线程数 |
