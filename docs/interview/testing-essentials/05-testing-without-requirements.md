# 05｜需求文档不全，甚至没有需求文档，你怎么测？

> 开场先表态再给方法：**需求不全是常态不是例外**。正确姿势不是停下等文档，而是把「明确需求」变成测试工作的一部分。

## 回答思路

### 第一步：需求从哪来，给四条路

1. **找产品当面确认**，把问答结果整理成文档反过来发给产品确认，逼模糊变清晰
2. **参考竞品**，同类产品的成熟交互就是隐性需求标准
3. **抓包看同类老功能**的行为，历史行为就是既定需求
4. **从开发和代码里挖**，接口定义、代码逻辑就是当前最准的规格

### 第二步：测试策略要匹配

文档不全时加大**探索性测试**比重，用「功能漫游」的方式把整个功能过一遍，边测边记录形成测试点清单，测完**反向沉淀出一份需求文档**留给后人。

### 第三步：讲风险同步

文档缺失导致的理解偏差要显式同步给项目组——测试结论里注明「基于某某确认的理解」，出了分歧有据可查。

### 收尾：给认知升华

测试人员在需求模糊时承担的是「**需求澄清推动者**」的角色。这个立场讲出来，你就和被动等喂的需求执行者拉开了差距。

## 考察重点

| 维度 | 说明 |
| --- | --- |
| 企业动机 | 真实项目里文档缺失是常态，尤其中小公司和紧急项目。企业要的是不等不靠、自己能把模糊变清晰的人 |
| 过线标准 | 说得出至少三种替代需求来源 |
| 区分度 | 讲「反向沉淀文档」「测试结论注明理解依据」的是真趟过泥潭的；只说「找产品问」的是没被文档坑过 |
| 加分项 | 主动提探索性测试这个术语并会用的，方法论和实操都有 |
| 减分项 | 抱怨「没有文档没法测」，直接出局——暴露被动等待的执行者心态 |
