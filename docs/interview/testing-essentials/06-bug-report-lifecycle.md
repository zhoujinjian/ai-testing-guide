# 06｜一条合格的 bug 报告要包含哪些要素？说说 bug 的生命周期

> 开场先给标准：要素按「**让开发零沟通成本复现**」讲——开发拿到单子不用来回问就能复现，这条单子就合格。

## 回答思路

### 第一步：报告要素

- 标题一句话说清现象
- 前置条件、复现步骤、实际结果、预期结果
- 附件三件套：截图、日志、录屏
- 环境信息：版本号、设备、账号
- 严重程度和优先级建议

### 第二步：讲两个容易漏的

- **出现概率**：必现还是偶现，概率多少
- **影响范围**：仅此功能还是连带其他模块

### 第三步：生命周期主线

**新建 → 确认 → 已分配 → 已修复 → 待回归 → 关闭**，用状态流转讲。

### 第四步：三个分支状态是区分度所在

- **拒绝**：开发认为不是 bug，走分歧处理流程（见 09 题）
- **延期**：本版本不修，挂到后续版本并评审确认
- **重新打开**：回归没通过打回

把分支讲全，说明你真**管理过** bug 而不只是提 bug。

### 收尾：严重程度和优先级的区别

严重程度看对系统的影响，优先级看修复的紧急程度，两者不总是一致——**轻微的界面错字在首页就是高优先级**。这句话是本题的经典加分句。

## 考察重点

| 维度 | 说明 |
| --- | --- |
| 企业动机 | bug 单是测试和开发最日常的交付物，单子质量直接决定协作效率。企业通过这题看你有没有职业化的输出习惯 |
| 过线标准 | 要素齐全 + 主线状态讲清楚 |
| 区分度 | 讲分支状态和严重程度优先级区别的是老手；只报要素清单的是背的 |
| 加分项 | 「开发拿到单子不用来回问」这句标准，或者一个因为描述不清被打回的真实教训 |
| 减分项 | 漏掉预期结果或环境信息还振振有词，说明没体会过被开发追问「你用的什么环境」 |
