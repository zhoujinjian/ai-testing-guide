# 15｜什么样的项目适合做自动化？什么时候引入？

> 开场先给判断标准再谈场景——这题考察的是 **ROI 判断力**，不是脚本能力。

## 回答思路

### 第一步：三个条件

1. **需求稳定**（界面和流程不常变）
2. **重复执行多**（每次回归都要跑）
3. **人工耗时大或人力做不到**（并发、大数据量、长时间浸泡）

三条都占才值得投入。

### 第二步：反面也讲清楚

频繁变动的 UI、探索性测试、一次性项目、纯视觉主观判断的——**不适合自动化**。这段反面清单体现的是投入产出意识，比正面清单更值钱。

### 第三步：讲分层的自动化策略——测试金字塔

- 单元自动化：开发做
- **接口层：性价比最高，优先投入**
- UI 层：只覆盖核心主流程冒烟
- 三层比例参考**七二一**

别把自动化等同于 UI 自动化——这个认知能避开企业最怕的「UI 自动化维护不动最后烂尾」的坑。

### 第四步：引入时机给落地节奏

项目功能基本稳定后的**第二个版本**开始：先冒烟集，跑顺了再扩回归集。自动化是长期资产建设不是一次性项目，人力按「专人维护加全员贡献」排。

### 收尾：算账

用「替代的人工回归小时数」和「用例维护成本」一起算 ROI——**账算得清的自动化才能活下来**。

## 考察重点

| 维度 | 说明 |
| --- | --- |
| 企业动机 | 自动化是企业近两年对测试岗的第一诉求，但大量团队上过自动化又烂尾。企业最怕招来一个闷头写脚本三个月维护不动的人 |
| 过线标准 | 给出选择标准 + 说出测试金字塔分层 |
| 区分度 | 能讲「不适合自动化的场景」和「维护成本账」的是有全局观的；只说「领导让做就做」的是没思考过 |
| 加分项 | 接口优先的策略认知，或一个自动化烂尾的教训复盘 |
| 减分项 | 认为所有项目都该全面自动化，暴露没算过成本账 |
