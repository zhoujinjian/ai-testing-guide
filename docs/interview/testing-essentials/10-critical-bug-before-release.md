# 10｜上线前一天发现一个严重 bug，时间不够了，怎么办？

> 开场先评估再决策，别急着给答案——这个顺序体现的是**风险评估先行**的职业习惯。

## 回答思路

### 第一步：评估三件事

1. **严重程度**：影响主流程吗？会造成资损或数据错误吗？
2. **影响范围**：全量用户还是特定场景、触发概率多大？
3. **修复风险**：改动多大、能不能测得完？

### 第二步：按评估结果分路

| 级别 | 处理 |
| --- | --- |
| **致命级**（崩溃、资损、数据错乱） | 必须处理：要么修复加定向回归，要么项目组决策延期上线——这种级别**测试的态度必须硬** |
| **严重但可规避** | 走技术规避三板斧：配置开关屏蔽该功能、灰度放量控制暴露面、降级方案兜底 |
| **一般级** | 带病上线加遗留清单，进下个版本修复计划——但必须**项目组知情确认**，不是测试自己默许 |

### 第三步：讲清测试的角色定位

测试不做上线决策，但必须**把风险讲透给决策者**——用数据说话（触发概率、影响面、规避方案的成本），让决策有依据。上线后测试要做的，是紧盯监控和用户反馈，准备好回滚预案。

### 收尾：给立场

时间不够时测试的价值不是扛下所有压力，而是**让团队在充分知情的情况下做风险决策**——这个定位讲出来，面试官看到的是质量负责人思维。

## 考察重点

| 维度 | 说明 |
| --- | --- |
| 企业动机 | 压力测试题，考察质量立场和风险决策能力。赶工期是企业常态，企业要知道你在高压下是坚持质量底线还是顺势躺平 |
| 过线标准 | 先评估再分级处理 + 风险同步项目组 |
| 区分度 | 讲得出「配置开关、灰度、降级」规避三板斧的是实战派；只说「看领导决定」的是没立场也没方法 |
| 加分项 | 明确说「致命级我的态度是拦」——敢扛压力的质量立场本身就是加分项 |
| 减分项 | 两个极端：无条件放行（没有质量底线）和无条件拦截（不给方案不给数据），都暴露不了决策参与能力 |
