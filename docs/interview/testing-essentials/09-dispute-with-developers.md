# 09｜开发说「这不是 bug」，你怎么办？

> 开场先亮原则：**对事不对人，用证据说话，不放情绪**——这九个字是这题的态度分。

## 回答思路

### 第一步：永远是自查

复现步骤清不清楚、环境对不对、是不是数据或配置问题被当成了代码问题——先排除自己提错单的可能。这一步体现的是自省，跳过它直接去争会显得莽。

### 第二步：按分歧原因分情况

| 分歧原因 | 处理 |
| --- | --- |
| 需求没写清楚 | 找产品确认，三方对齐，以产品结论为准 |
| 对需求理解不一致 | 拿需求文档和原型对线，逐条对照 |
| 站在用户角度的问题 | 用「用户会怎么想」论证——这类「**需求之外的 bug**」最能体现测试的用户立场 |

### 第三步：都谈不拢的收尾

- 升级到测试负责人和产品组织**三方评审**，把分歧摆到台面由产品拍板
- 确认不修的，在缺陷库记录并写明风险，邮件或文档**留痕**，责任链清晰

### 收尾：给平衡感

测试的职责是**把风险讲透并推动决策**，不是把每个分歧都变成战争——尊重最终决议但确保风险被看见。这个分寸感是面试官真正想听的。

## 考察重点

| 维度 | 说明 |
| --- | --- |
| 企业动机 | 测试和开发的冲突是日常，这题考察沟通能力和职业成熟度。企业怕招到两种人：一碰就炸的杠精，和一推就软的老好人 |
| 过线标准 | 自查 + 分情况处理 + 升级机制 + 风险留痕，链条完整 |
| 区分度 | 能讲「需求之外的 bug」这个灰色地带并给出用户视角论证的，是真理解测试立场的人 |
| 加分项 | 一句「对事不对人，用证据说话」，或者一个真实的三方评审案例 |
| 减分项 | 两个极端都扣分：直接找领导告状显得不会沟通；开发说不是就默默关单显得没原则 |
