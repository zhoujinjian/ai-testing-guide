# 20｜讲讲你做过的平台，最有成就感和最坑的各一件事。

> 开场先明确**选材标准**——平台经验是测开面试的终极验证区：前面十九题的理论对不对，一问实战就现形。

## 回答思路

### 第一步：讲成就感的选材标准

挑「从 0 到 1 的关键转折」或「数据验证的价值时刻」（第一版上线被真实使用、采纳率爬升的曲线、替代人工工时的账）——成就要落在「**用户价值和数据**」上，而不是「技术多炫」。**选材的价值取向本身就是考察点。**

### 第二步：成就故事的结构

背景（什么痛点立项）→ 过程（关键决策和攻坚，突出「你」的角色和判断）→ 结果（**三个数字**：用户规模、效率替代、质量改善）→ 沉淀（留下了什么可复用的资产）。

**数字和角色诚实是底线**——夸大被追问就塌。

### 第三步：讲最坑的事（本题真正的考察重心）

挑「**有认知升级的坑**」而不是「纯背运的事」：

| 坑型 | 教训 |
| --- | --- |
| 技术坑 | 过度设计——一上来微服务，三个人维护不动。教训：**架构匹配团队规模** |
| 运营坑 | 做完没运营，用户流失后重启的艰难。教训：**三分开发七分运营** |
| 数据坑 | 数据模型没想清楚，中期推倒重来。教训：**地基设计值得多花一周** |
| 组织坑 | 没拉齐需求就开干，做出来的不是用户要的。教训：**种子用户共建** |

**坑 + 反思 + 后续改进**的结构，一个坑讲透。

### 第四步：讲坑的态度管理

- 坑要**真实**（编的坑没有细节和情绪记忆）
- 反思要**具体**（「以后更仔细」不算反思——「数据模型评审提前到设计期，用例和执行解耦的检查清单」才算）
- **不自毁**（坑的责任表述对事不对人，不甩锅同事也不过度自责）

### 收尾：把坑和成就串起来

最好的表述是坑和成就**在同一个故事线上**（那个过度设计的教训，直接催生了后来 MVP 模式的成功）——**成长叙事的完整弧线，比两个孤立故事高一个段位**。

## 考察重点

| 维度 | 说明 |
| --- | --- |
| 企业动机 | 双题设计（成就加坑）分别考察价值判断和反思能力——「最坑」的回答质量通常高于「成就」的鉴别力（编造的坑最容易穿帮），这题往往决定最终定级 |
| 过线标准 | 成就有数据 + 坑有反思有改进 |
| 区分度 | 坑选「认知升级型」且反思落到机制上的（检查清单、流程改进）是高级的；坑是「需求老变」「时间不够」这类外部归因的是低级的 |
| 加分项 | 坑和成就串成成长弧线 |
| 减分项 | 说「没什么坑都挺顺的」（没反思能力或没真做过）或坑全是别人的责任（甩锅型）——两个都是红旗 |
