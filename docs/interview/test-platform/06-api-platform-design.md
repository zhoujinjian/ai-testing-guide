# 06｜接口自动化平台的核心功能怎么设计？

> 开场先给**功能地图**——接口自动化平台是测试平台里使用率最高的形态（各厂自研平台的标配）。

## 回答思路

### 第一步：五大功能块

1. **用例编排**：接口定义、参数、断言的在线编辑
2. **场景编排**：多接口串联的流程测试，上下文传递
3. **环境管理**：多环境配置切换
4. **执行调度**：单跑、批量、定时
5. **报告分析**：结果、失败详情、历史趋势

### 第二步：讲接口定义的设计

- 支持从 **swagger 或抓包导入**（别让用户手填——导入是体验的分水岭）
- 参数和头部的模板化
- **变量提取**：上一个接口的返回喂下一个（正则或 jsonpath 提取存变量）——**变量提取是串联场景的核心机制**，讲透它说明懂接口测试的本质

### 第三步：讲断言的分层设计（专业性的直接体现）

| 层 | 断言什么 |
| --- | --- |
| **状态码断言** | 基础 |
| **响应体断言** | jsonpath 取值 + 比较符（等于/不等/包含/大于） |
| **业务断言** | **数据库校验**——接口返回对了库没写对也要抓 |
| **脚本扩展** | 复杂逻辑用脚本写 |

### 第四步：讲环境管理的多环境设计

- 域名、账号、数据库连接的**环境级配置**
- **用例和环境解耦**（一套用例多环境跑）——这两点是团队级使用和玩具的分界
- 加密签名的**前置处理**（接口要签名的场景，平台内置签名插件）

### 收尾：讲和代码仓库的关系

平台适合**场景编排和轻量维护**，复杂逻辑还是代码仓库管理（pytest 项目）——平台提供「从仓库拉用例执行」的集成模式。**两种形态并存而不是互斥**，这个边界认知避免平台走火入魔。

## 考察重点

| 维度 | 说明 |
| --- | --- |
| 企业动机 | 平台开发面试的最高频场景设计题——考察对接口测试业务的抽象能力 + 平台功能架构能力 |
| 过线标准 | 功能地图完整 + 变量提取和三层断言的机制设计 |
| 区分度 | 讲 swagger 导入、签名插件、仓库集成边界的是真做过平台或深度用过的 |
| 加分项 | 「用例和环境解耦」这类平台级设计原则 |
| 减分项 | 只有「发请求看返回」，断言体系和场景编排缺失，业务理解太浅 |
