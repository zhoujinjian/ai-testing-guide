# 01｜为什么要自研测试平台？市面上的工具满足不了什么？

> 开场先摆正回答的姿势：**不是「自研比采购高级」，而是「自研是特定条件下的理性选择」**——这个不贬低开源工具的姿态本身是加分项。

## 回答思路

### 第一步：讲市面工具的三类不满足

| 痛点 | 说明 |
| --- | --- |
| **流程整合** | 公司有自己的研发流程和工具链——禅道 Postman Jenkins 各自割裂、数据不通，平台要的是把它们串起来的一层 |
| **场景定制** | 内部协议、鉴权方式、特殊的造数逻辑——通用工具覆盖不了 |
| **规模治理** | 几百人的用例资产、多团队隔离、统一度量——单机工具管不了 |

### 第二步：讲自研的前提条件

1. 有**持续投入的人力**（哪怕一个人长期维护）
2. 有**真实的高频痛点**（天天用的场景才值得平台化）
3. 团队有**工具文化**（愿意迁移到平台上来）

三个前提缺一个，自研平台大概率沦为「**毕设工程**」。

### 第三步：给替代方案的对比（三档）

| 档位 | 方案 |
| --- | --- |
| 轻量级 | 开源工具 + 二次封装 + 脚本粘合（成本最低，先跑这个） |
| 中量级 | 基于开源平台魔改（MeterSphere 这类） |
| 重量级 | 全自研（只有大团队和特殊需求才值得） |

**按需求烈度选档位，不是只有自研一条路。**

### 收尾：给价值判断

平台的价值不在「有」而在「**被用**」——一个解决真痛点的小工具，胜过一个没人用的全功能平台。

## 考察重点

| 维度 | 说明 |
| --- | --- |
| 企业动机 | 企业被自研烂尾坑过（建了平台没人用、维护断档）——拍脑袋喊自研和只会用现成工具的都不是最优解 |
| 过线标准 | 三类不满足 + 自研前提条件 |
| 区分度 | 给出三档替代方案、讲「被用比有重要」的是有平台价值观的 |
| 加分项 | 不贬低开源工具的姿态 |
| 减分项 | 「自研才体现技术实力」，为了建而建，工程判断不成熟 |
