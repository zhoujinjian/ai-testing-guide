# 03｜测试平台的技术选型怎么做？架构怎么设计？

> 开场选型原则先立三条——技术选型是**工程决策**，不是个人偏好秀。

## 回答思路

### 第一步：选型三原则 + 主流组合

| 原则 | 说明 |
| --- | --- |
| **团队熟悉度优先** | Python 团队选 Django/FastAPI，不硬上 Java 系 |
| **生态匹配** | 要接的工具链有现成 SDK 的优先 |
| **招聘友好** | 主流栈好招人好交接 |

主流组合参照：后端 **FastAPI 或 Django**（Python 系，测试开发生态最顺）、前端 **Vue + Element**（管理后台的标准高效组合）、数据库 **MySQL + Redis**、任务执行 **Celery 或自研调度**、部署 **Docker + Nginx**——**每个选择附理由**，选型能力就是「选择加理由」的展示。

### 第二步：架构讲分层

| 层 | 职责 |
| --- | --- |
| **接入层** | Web 界面 + OpenAPI——平台功能**全部 API 化**为集成留口 |
| **业务层** | 用例管理、任务调度、报告分析 |
| **执行层** | 独立的执行节点（跑测试任务的 worker 集群） |
| **数据层** | 业务库 + 执行结果的存储 |

关键设计是「**执行和平台分离**」——执行节点可以弹性扩缩、挂了不影响平台本身。

### 第三步：讲两个架构关键点

1. **异步化**：执行测试是长任务——全程异步 + 状态轮询或推送，接口秒回任务后台跑
2. **多租户意识**：哪怕现在一个团队，数据模型里**预留团队维度**，后期加权限不伤筋动骨

### 收尾：讲演进而非一步到位

先单体（所有模块一个服务），用户量或团队数上来了再**按瓶颈拆**（执行服务先独立、然后报告分析）——架构跟着规模走，用复杂度换当下的简单。

## 考察重点

| 维度 | 说明 |
| --- | --- |
| 企业动机 | 腾讯真题明确考平台架构与技术选型的考量——背答案的人给不出「为什么这么选」 |
| 过线标准 | 选型带理由 + 分层架构 + 执行与平台分离 |
| 区分度 | 讲异步化、多租户预留、单体先行的演化观的是有架构实战的；堆微服务术语的是跟风 |
| 加分项 | 功能 API 化的集成前瞻 |
| 减分项 | 选型理由是「这个技术比较火」，没有工程权衡 |
