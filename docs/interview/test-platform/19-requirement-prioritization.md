# 19｜用户提了一堆需求，怎么排优先级？

> 开场先讲需求的**第一道过滤**——不是所有「需求」都要做，先过滤再排序。

## 回答思路

### 第一步：三辨过滤掉伪需求

1. **辨别真伪**：用户说想要 A，深挖发现痛的是 B（A 只是他自己想的解法）——平台方要**挖到痛点层再选解法**
2. **辨别频次**：一人一次的诉求还是群体高频的痛点
3. **辨别价值**：解决后省多少时间、多少人受益

### 第二步：排序的框架（给两个参照）

- **价值矩阵**：价值高低 × 实现成本的二维四象限——高价值低成本先做、高价值高成本规划做、低价值低成本顺手做、低价值高成本不做
- **RICE 评分**：到达率 × 影响 × 信心 ÷ 成本，量化打分

**框架不重要，重要的是「有框架」**——凭感觉排序的迭代一定跑偏。

### 第三步：讲平台特有的一票否决项（不进常规排序，特事特办）

1. **架构级需求**（数据模型、权限体系这类晚改伤筋动骨的——哪怕不紧急也优先）
2. **安全红线**（数据隔离、权限漏洞——立即修）
3. **稳定性问题**（bug 修复插队机制）

### 第四步：讲需求的沟通管理

- **所有需求进池子**：哪怕不做的也记录在案给回复——**需求黑洞是用户流失的开始**
- **排期透明**：路线图公示，用户知道自己的需求在哪个版本
- **说不的艺术**：拒绝要给理由和替代方案（「这个场景用现成的 X 工具更合适」）

需求管理一半是排序，一半是**期望管理**。

### 收尾：讲迭代的节奏纪律

**固定发版节奏**（双周或每月，用户形成预期）、每期**主题聚焦**（一个版本解决一类问题而不是撒胡椒面）、需求池的**定期清仓**（季度盘点，过期需求关闭）——节奏感是平台可靠形象的一部分。

## 考察重点

| 维度 | 说明 |
| --- | --- |
| 企业动机 | 排序能力决定平台是「越做越好用」还是「越做越臃肿」——考察产品经理式的判断力，测开转平台 owner 的必经修炼 |
| 过线标准 | 需求过滤 + 排序框架 + 平台特有的一票否决项 |
| 区分度 | 讲真伪需求辨别、讲需求黑洞问题、讲说不的艺术的是有需求管理经验的 |
| 加分项 | 固定发版节奏的纪律性 |
| 减分项 | 谁声音大听谁的（会哭的孩子有奶吃），没有框架没有原则 |
