# 18｜平台开发用什么技术栈？前后端怎么分工协作？

> 开场给主流测开技术栈的**组合和理由**——平台开发本质是 Web 全栈开发（轻量），技术栈的合理选择暴露真实的开发经验。

## 回答思路

### 第一步：主流组合（每个选择附一句为什么）

- **后端**：Python（FastAPI 或 Django——测试生态亲和，脚本工具可以直接复用）或 Java（Spring Boot——工程规范强，大厂平台主流）
- **前端**：Vue3 + Element Plus（管理台开发效率最高的组合，组件丰富）
- **数据库**：MySQL + Redis
- **任务**：Celery
- **部署**：Docker Compose 起步

### 第二步：讲前后端的协作契约

- **API 先行**的协作模式：先定接口文档再并行开发（Swagger 或 Apifox 做契约，前后端不互相等）
- **数据格式的规范**：统一响应结构、分页约定、错误码体系
- **联调的纪律**：mock 数据先行、接口变更提前通知

契约意识是团队协作开发的分水岭。

### 第三步：讲测试开发的客观分工现实

多数测开平台团队**前端偏弱**——务实策略：

- 选**组件化**的前端方案（Element 这类现成组件库降低前端门槛）
- 或者页面用**低代码后台框架**（Amis 这类 JSON 配置生成页面，后端同学也能维护页面）

**用工具补短板，而不是硬练前端。**

### 第四步：讲代码质量的协作规范

code review 的机制（平台代码也要评审，尤其数据模型和核心逻辑）、简单的分支策略（主干 + 特性分支）、文档同步。

### 收尾：给学习路径建议

测开做平台的技术深度要求（数据库设计、API 设计、异步编程、部署运维）比写测试脚本深一层，但远低于专业后端——方向是「**广而够用**」，不是「深而专精」。

## 考察重点

| 维度 | 说明 |
| --- | --- |
| 企业动机 | 考察候选人的工程基本功（是否真做过 Web 开发还是只会脚本）——技术栈的合理选择和协作规范暴露真实的开发经验 |
| 过线标准 | 技术栈组合带理由 + API 先行的协作契约 |
| 区分度 | 讲 Amis 低代码补前端短板、讲统一响应规范的是有团队协作开发经历的 |
| 加分项 | 对「广而够用」的测开技术定位认知 |
| 减分项 | 技术栈答不上来或明显没有 Web 开发概念（不知道前后端怎么分离），平台经验存疑 |
