# 05｜回归测试的范围怎么定？每次都全量回归吗？

> 开场先亮观点：**全量回归是奢侈品不是必需品**。时间成本撑不起每版全量（几百上千条用例的手工全量要一周），**回归范围的确定本质是风险和成本的权衡艺术**。

## 回答思路

### 第一步：给范围判定的方法

- **变更分析**：这次改了什么，变更说明是回归范围的起点
- **影响面分析**：改动涉及哪些模块、调用了哪些公共组件、数据结构变了吗（精准测试是它的进阶形态）
- **风险分级**：核心链路必回归、受影响模块重点回归、无关联模块抽查或不测

三步从变更推出范围，方法论就立住了。

### 第二步：讲回归集的分层组织

- **核心回归集**：主流程，每次必跑，自动化首选
- **模块回归集**：按受影响调用
- **全量集**：大版本或架构变更才上

分层的集配合不同版本类型调用，这是回归范围管理的标准工程解。

### 第三步：讲两个特殊场景的判断

- **缺陷修复后的回归**：修哪测哪加周边影响，不是全量
- **紧急线上修复**：只验证修复点加最核心主流程，速度优先但要留风险评估记录

场景化的判断说明真做过不同的版本。

### 收尾：讲趋势

回归范围的精准化（精准测试、AI 影响面推荐）正在把「拍脑袋圈范围」变成**数据驱动**——讲出这个方向显示视野。

## 考察重点

| 维度 | 说明 |
| --- | --- |
| 企业动机 | 回归范围是版本节奏里测试最大的成本变量——圈大了拖死版本、圈小了漏出事故，企业要的是「有方法圈范围」的人而不是「凭感觉圈」的 |
| 过线标准 | 变更到影响面的推导方法 + 回归集分层 |
| 区分度 | 讲特殊场景（缺陷修复、紧急修复）的差异化处理、讲精准测试方向的是有实践加视野的 |
| 加分项 | 核心回归集自动化的落地 |
| 减分项 | 「每次都全量，安全」或「只测改的部分」，两个极端都不专业——前者不懂成本后者不懂风险 |
