# 11｜测试左移说说你自己的实践，个人能落地哪些？

> 开场先把左移从口号落到动作：左移的核心是「**问题发现的时间点前移**」（需求期发现比测试期发现便宜十倍，测试期发现比线上发现便宜百倍）——个人层面的一切左移动作都围绕「更早介入」展开。

## 回答思路

### 第一步：讲个人可落地的清单

- **需求评审的质量把关**：模糊点当场澄清（01 题的动作）
- **用例先行**：开发编码时用例已评审完，提测即测试
- **技术方案的参与**：听开发讲实现设计，提前知道影响面和风险点，测试策略跟着设计走
- **开发的单测协助**：帮开发梳理单测场景清单，单测覆盖的 bug 不用测试来抓
- **提测前的前置验证**：分支阶段就开始冒烟，不等合并提测

五件事都是个人权限内能做的，**可操作性是这题的命**。

### 第二步：讲左移的自身建设

- **读懂代码的能力**：能看 diff 圈影响面——测试的代码能力在左移里的直接变现
- **业务知识的深耕**：越懂业务越能在需求期发现逻辑漏洞
- **和开发的信任关系**：开发愿意让你参与他的技术讨论，靠日常积累

### 第三步：讲效果的证据

左移后测试期 bug 密度的变化（需求期拦截的问题多了，提测后的 bug 少了，返工少了）、版本周期的缩短——**用前后对比证明左移不是空转**。

### 收尾：给克制的边界

左移不等于测试什么都管（左移是补充不是替代，测试期的系统验证依然不可少），个人实践要**选团队接受的度**——先从需求评审发言和用例先行做起，别一上来就要参加所有技术评审，落地有节奏。

## 考察重点

| 维度 | 说明 |
| --- | --- |
| 企业动机 | 左移是企业质量策略的标配方向（概念人人会说），企业要看你「真做过哪些动作」——五件套清单讲不出的左移是纸面认知 |
| 过线标准 | 至少四个可落地的个人动作 + 效果证据 |
| 区分度 | 讲分支阶段前置冒烟、讲帮开发梳理单测场景的是有深度实践的 |
| 加分项 | 落地有节奏的边界感（从团队接受的度起步） |
| 减分项 | 左移就是「早点开始测试」——时间维度的理解有了但动作层面是空的 |
