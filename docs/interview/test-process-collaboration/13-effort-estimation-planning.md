# 13｜迭代排期时，测试工作量怎么估？怎么参与排期？

> 开场先讲估时被低估的严肃性：估不准的连锁反应（估少了测试被压缩质量埋雷、估多了团队竞争力弱项目流失）——**估时是测试在项目组的专业信用**，先立这个态度。

## 回答思路

### 第一步：给估时的方法

- **分解估**：把测试工作拆成需求分析、用例设计、执行、回归四段分别估，比拍一个总数准
- **类比估**：参照历史同类需求的实际耗时——「上个月类似的功能实际用了五天」是最硬的依据
- **风险系数**：新功能乘复杂度系数、依赖多的加缓冲、新技术领域加学习时间

三种方法交叉验证，**估时是估算科学不是猜**。

### 第二步：讲估时的合理构成

- **别只估执行**：用例设计、环境准备、bug 验证回归的时间常被漏估，实际执行只占一半
- **隐性工作要算**：需求澄清、会议、联调等待都是真实工时
- **并行任务打折**：同时测两个项目，实际产能按七折估

构成的完整度是被毒打过的经验。

### 第三步：讲参与排期的姿态

- **测试估时要有依据地坚持**：拿历史数据和分解明细支撑，被砍时说「砍哪段，砍了风险是什么」——**把选择的代价留给项目组**
- **给排期的约束条件**：提测质量影响测试工时，**测试结束时间 = 提测时间 + 估时**——这个等式让开发工期和测试工期联动
- **备选方案**：时间不够时主动给裁剪方案而不是只有「不行」

### 收尾：讲估时的校准闭环

每轮迭代复盘估时偏差（估五天实际七天的原因分析），偏差数据反过来校准估时模型——**估时能力是迭代出来的不是天生的**。

## 考察重点

| 维度 | 说明 |
| --- | --- |
| 企业动机 | 估时是测试参与项目管理的主要接口，估不准的测试永远是排期博弈里的弱势方——企业要的是「有方法估、有依据扛」的人 |
| 过线标准 | 分解加类比的估时方法 + 估时的完整构成 |
| 区分度 | 讲隐性工作、讲「测试结束时间」等式、讲估时校准闭环的是有项目管理颗粒度的 |
| 加分项 | 被砍时的应对话术（把代价留给决策方） |
| 减分项 | 「凭经验拍个数」，无方法无依据，专业信用为零 |
