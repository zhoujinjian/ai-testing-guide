# 20｜讲一个你印象最深的版本，从需求到上线的完整过程。

> 开场先选好故事，这题考的是你经历的「**真实密度**」：选一个有起伏的版本（有挑战有转折有结果的）——大促保障、紧急上线、重大重构后的版本、出过事故的版本都是好素材，平平无奇的常规版本讲不出细节密度。

## 回答思路

### 第一步：用时间线结构讲

- **需求期**：需求是什么、评审时发现了什么问题、测试怎么介入的
- **设计期**：用例规模、评审插曲、自动化准备
- **执行期**：提测质量、发现的典型 bug、最大的阻塞、时间压力的应对
- **上线期**：发布过程、验证、上线后的观察

时间线让面试官跟着你走一遍，**流程感的展示是这题的主线**。

### 第二步：讲出「你的角色和判断」

团队都做了什么之外，**你的关键决策和动作**——「我发现需求里两个模块的状态定义矛盾，评审时拦下来了」「时间压缩时我提出核心集加边缘抽查的方案」。**个人贡献的颗粒度决定故事的说服力**，全是「我们」的故事会被追问「你具体做了什么」。

### 第三步：讲结果和沉淀

- **版本的结局**：按期上线、质量结果如何
- **你的收获**：这个版本让你建立了什么认知或方法
- **后续的复用**：那个版本的应急方案后来成了团队的常规流程

有沉淀的故事才完整。

### 第四步：讲得失的平衡

**印象最深不等于最成功**——一个出过事故的版本加上诚实的复盘，往往比一个顺利的版本更显真实和成长。敢讲失败版本并讲出认知升级的候选人，比只讲成功故事的更让面试官信任。

## 考察重点

| 维度 | 说明 |
| --- | --- |
| 企业动机 | 这是流程题的收经验和综合题（前面十九题的知识点有没有真实经历托底，一个故事全暴露）——项目流程讲述是测开面经的必问环节，背来的流程和活过的流程在细节密度上一耳就能分辨 |
| 过线标准 | 时间线完整 + 个人角色和判断的颗粒度 |
| 区分度 | 有具体数字（用例数、bug 数、时间点）、有转折和决策点的是真经历的；平铺直叙全是「我们」的是道听或包装的 |
| 加分项 | 敢讲有事故的版本加真诚复盘 |
| 减分项 | 故事是「大家齐心协力按时上线了」的流水账——没有问题没有判断没有数字，经历的密度可疑 |
