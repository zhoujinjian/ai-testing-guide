# 03｜提测流程怎么设计？提测标准怎么定？

> 开场先讲门禁的必要性：没有标准的提测是「**垃圾进垃圾出**」的开始（测试花两天发现根本跑不起来，双方时间全废）——**提测标准是保护测试产能的第一道闸**。

## 回答思路

### 第一步：标准清单给具体项

- **冒烟自测通过**：开发自己把主流程跑一遍并提供自测记录
- **部署可成功**：测试环境能部署起来，包是对的
- **已知问题声明**：哪些功能没做完、哪些坑已知，不许藏着
- **变更说明**：这次改了什么、影响哪些模块，给测试圈回归范围
- **单测通过**：有单测文化的团队加这条

五项清单报出来，**标准的颗粒度就是经验的颗粒度**。

### 第二步：讲不达标怎么处理

- **冒烟不过直接打回**——打回不是惩罚是止损，带着数据反馈给开发「提测三天打回两次」比抱怨有用
- **打回率数据公开**——连续打回的开发自己会重视，数据比情绪有效

### 第三步：讲流程的完整性

- **提测前的预沟通**：开发提前两三天说大概哪天提测，测试排好资源和环境
- **提测时的正式交接**：邮件或工具记录，冒烟结论和测试启动时间有据
- **提测后的变更管理**：提测后开发改代码要走流程知会，防偷偷改

头中尾三段都有规矩。

### 收尾：讲标准的度

标准要和团队成熟度匹配（新团队先执行冒烟自测一条，跑顺了再加）——一上来五条全卡会变成对抗，**门禁是逐步建起来的**。

## 考察重点

| 维度 | 说明 |
| --- | --- |
| 企业动机 | 提测质量差是测试团队最大的产能漏斗，企业要看你有没有门禁意识和推动执行的手腕，被动接垃圾提测的人永远在救火 |
| 过线标准 | 标准清单具体 + 打回机制 |
| 区分度 | 讲打回率运营、讲提测后变更管理的是把流程跑成体系的人 |
| 加分项 | 标准逐步建设的节奏感 |
| 减分项 | 提测标准是「开发说提好了就提好了」，无门禁无动作 |
