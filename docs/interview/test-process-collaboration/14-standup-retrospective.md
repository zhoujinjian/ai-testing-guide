# 14｜每日站会和迭代回顾，测试要怎么参与？

> 开场先讲测试在站会的价值定位：站会不是汇报会是**同步会**，测试的输入常常是最关键的信息（昨天发现的高危 bug、被阻塞的用例、环境的异常）——**测试在站会沉默等于团队少了一双眼睛**。

## 回答思路

### 第一步：站会讲什么给清单

- **昨天**：执行进度、发现的重要 bug、遇到的阻塞
- **今天**：计划、需要的支持
- **风险**：进度风险、质量风险提前亮黄牌

三段话各一两句，重点是「**阻塞和风险的及时抛出**」——站会是测试把困难变成团队共同问题的最快通道。

### 第二步：讲站会的纪律

- **说事实不说细节**：「登录模块三条用例阻塞，等 bug 修复」而不是现场讲 bug 来龙去脉，细节会后单聊
- **抛问题带方案或求助**：「被阻塞了，需要开发今天优先修 233 号 bug」——有明确请求的发言才有推动力

### 第三步：迭代回顾讲测试的深度参与

- **带着数据来**：本迭代的 bug 分布、逃逸、阻塞统计——回顾会有数据的发言有分量
- **提改进不只吐槽**：「回归时间不够」后面接上建议「核心集自动化先建起来」，建设性的提议才会进改进项
- **跟进改进项的落地**：认领和自己相关的改进项——回顾会的产出三个月没动静，下次就没人认真开了

### 收尾：讲文化敏感度

站会和回顾是「**团队自我修正**」的机制，测试在里面既是质量信息的提供者也是流程改进的推动者——把这两个会开成走流程还是开成机制，测试的参与质量影响很大。

## 考察重点

| 维度 | 说明 |
| --- | --- |
| 企业动机 | 敏捷团队的面试官天天和你开站会（这题是敏捷协作日常的抽样检查），考察你在团队机制里的「信息贡献度」——站会只会说「昨天测了今天继续测」的人，面试官会推断他在团队里是隐形人 |
| 过线标准 | 站会三段清单 + 回顾会的数据参与 |
| 区分度 | 讲「抛问题带明确请求」、讲认领改进项的是敏捷团队的核心成员姿态 |
| 减分项 | 站会「轮到我就说说进度」，回顾会「听听大家怎么说」——机制里的旁观者 |
