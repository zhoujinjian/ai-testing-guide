# 06｜版本发布流程里，测试参与什么？上线验证做什么？

> 开场先纠正一个常见错觉：**测试不是「测完就退场」**。发布是把测试环境验证过的东西搬到生产，**环境差异本身就是风险**——测试在发布现场是质量的最后一双眼睛。

## 回答思路

### 第一步：发布前给测试的参与清单

- **发布内容评审**：这次上什么、有没有临时的配置变更、回滚方案是什么
- **上线检查单**：checklist 的逐项确认——数据变更脚本、开关配置、依赖服务就绪
- **灰度方案的确认**：放多少量、观察什么指标、异常怎么回

发布前的功课决定发布时的从容。

### 第二步：发布中和发布后的动作

- **发布过程跟进**：部署有没有报错、关键服务起没起来
- **上线验证**：生产环境的核心流程验证，冒烟集在生产跑一遍，配置类变更重点核对
- **灰度观察期的监控盯守**：错误率、核心指标、用户反馈渠道——首小时首日最关键

三段动作有头有尾。

### 第三步：讲一个关键的意识

**生产验证不是「再测一遍」**——它是抽样确认（环境对了、版本对了、关键链路通了）。深度的功能测试发生在测试环境，生产验证**重广度轻深度、重链路轻细节**。定位讲清说明真理解这个环节。

### 收尾：讲异常处理

发布后发现问题，第一时间反馈并给出判断（回滚还是修复，用影响面数据支持决策），参与复盘——**发布问题回流进发布检查单**，这是发布闭环的最后一环。

## 考察重点

| 维度 | 说明 |
| --- | --- |
| 企业动机 | 发布是质量风险的高压时刻（大量事故出在发布环节的环境差异），成熟团队都要求测试在发布流程里在场——这题筛掉「测完就撤」的传统型测试 |
| 过线标准 | 发布前三项（评审、检查单、灰度方案）+ 上线验证的定位理解 |
| 区分度 | 讲「生产验证是抽样不是重测」、讲灰度观察期盯守的是真跟过发布的 |
| 加分项 | 发布问题回流检查单的闭环 |
| 减分项 | 「上线是开发和运维的事测试不去」，流程视野缺了最后一段 |
