# 01｜需求评审阶段，测试要做什么？怎么评审才算到位？

> 开场先立角色定位：**不是旁听者，是质量的第一个把关人**——需求阶段的缺陷是所有缺陷里修复成本最低的（改一行字和上线后返工的差距是百倍量级）。

## 回答思路

### 第一步：评审的具体动作分三层

- **理解层**：需求讲的是什么、用户故事完整吗、异常流程和边界条件写了吗
- **挑战层**：站在用户和测试视角挑毛病（这个状态没定义流转、两个模块的需求互相矛盾、这个字段没说超长怎么处理）
- **可测性层**：验收标准可度量吗——「加载要快」不可测，「P95 小于两秒」可测

三层动作讲出来，评审就不是走过场。

### 第二步：讲输出物

- 评审后的**测试视角问题清单**（要求逐条闭环）
- **影响面初判**（这个需求动了老功能吗，回归范围早有数）
- 测试资源和**工作量的初步估算**

带着产出物参加评审是职业化的标志。

### 第三步：讲评审不通过怎么办

需求模糊或有矛盾时明确表态打回——「这个点不一致，建议对齐后再过」，而不是「先过了边测边问」。**带病过评审的需求后面全是坑，敢打回是这题的态度分。**

### 收尾：讲左移的衔接

评审阶段就开始写测试点——**需求定稿即测试点成型**，开发还没写完代码测试已 ready，这是需求评审价值的最大化。

## 考察重点

| 维度 | 说明 |
| --- | --- |
| 企业动机 | 需求评审是测试左移的第一现场（「能在需求阶段提出可测试性建议」被列为初级和高级的分水岭），企业通过这题看你是不是「提测后才动手」的被动型测试 |
| 过线标准 | 三层评审动作 + 可测性意识 |
| 区分度 | 讲「带产出物参会」「敢打回」的是真在评审桌上发过言的；说「听产品和开发讨论」的是旁听者 |
| 加分项 | 缺陷成本百倍差的量化意识 |
| 减分项 | 需求评审「主要是听，有疑问再问」，角色定位完全缺失 |
