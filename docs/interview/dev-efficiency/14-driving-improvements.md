# 14｜效能数据分析了发现问题，怎么推动改进落地？

> 开场先讲从数据到问题的转化——**数据只给信号不给结论**：交付周期长是信号，为什么长要做下钻分析。

## 回答思路

### 第一步：用价值流分析定位真瓶颈

把需求从「提出」到「上线」切成阶段（需求评审、排期等待、开发、提测等待、测试、发布等待），统计每段的停留时长，画成时间轴找最长块——**数据下钻找到真瓶颈，这步做不对，后面的改进全是打地鼠**。

### 第二步：讲改进的立项纪律

- **一次只改进一两个瓶颈**（同时铺开十个改进项等于一个也做不成）
- 改进项有明确 **owner 和时间点**
- 改进效果**预挂在某个指标上**（这项改进预期让前置时间降多少）

像管理研发项目一样管理改进项。

### 第三步：讲推动的技巧（多数改进卡在组织不在技术）

1. **用数据讲故事**：「需求在测试环节平均等待五天，这五天里测试同学在并行三个版本，瓶颈是人力峰值不是效率」——让数据和因果说话
2. **找共赢联盟**：改进项帮开发省事才推得动——只帮测试的改进开发没动力
3. **借助管理层背书**：跨团队的流程改动需要行政推动力

### 第四步：讲改进的验证闭环

- 改进落地后**复测指标**（前置时间真的缩短了吗）
- **unintended consequence 检查**（快了但失败率涨了吗）
- 验证有效的**固化为流程**，无效的回滚或换方向

### 收尾：讲改进的节奏观

效能提升是**持续的长跑不是一次会战**——季度一个重点、复盘一次、滚动下一个。追求「每个月都比上个月好一点」的复利，不追求「三个月脱胎换骨」的奇迹。

## 考察重点

| 维度 | 说明 |
| --- | --- |
| 企业动机 | 度量不是终点，改进才是价值兑现——大量组织的效能度量止步于「有了看板」，把数据变成改变的能力比度量知识更稀缺 |
| 过线标准 | 下钻找真瓶颈 + 改进立项纪律 + 验证闭环 |
| 区分度 | 讲价值流分析、讲组织推动技巧（数据讲故事、共赢联盟）的是真推过跨团队改进的 |
| 加分项 | unintended consequence 的检查意识 |
| 减分项 | 改进手段就是「发邮件通报数据排名」，用施压代替改进设计 |
