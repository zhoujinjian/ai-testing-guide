# 13｜效能度量平台（看板）怎么建设？

> 开场先讲平台的**数据架构分层**——四层架构报出来，平台的技术形态就立住了。

## 回答思路

### 第一步：四层架构

| 层 | 职责 |
| --- | --- |
| **采集层** | 对接 Git、CI、项目管理、缺陷系统的 API——事件流拉取和清洗 |
| **数据层** | 指标计算的逻辑集中在这一层——**口径统一定义** |
| **展示层** | 看板和报表 |
| **分析层** | 趋势对比、下钻定位 |

### 第二步：讲指标口径的管理（平台成败的隐藏关键）

- **指标定义代码化**：每个指标的计算逻辑有唯一实现和文档，杜绝「同名不同义」
- **口径变更走评审**：改口径等于改历史可比性，要慎重和公示
- **指标字典对外公开**：用数的人查得到定义

口径混乱是效能平台**被弃用的头号原因**。

### 第三步：讲看板的设计原则

- **按受众分层**：管理层看趋势大屏、团队看迭代细节，下钻路径打通（从指标到明细）
- **少而精**：一屏核心指标——几十个指标的大杂烩没人看
- **指标配解读**：光有数字没有健康度参考，看的人不知道好坏

### 第四步：讲建设的节奏

**先用现成工具拼**（项目管理工具自带报表 + BI 工具连数据源，两周出第一版验证价值），价值验证了再自研平台——别一上来立项大平台（半年的开发周期里热度早凉了）。

### 收尾：讲平台的运营

有 **owner** 维护（数据断了脏了有人管）、有**迭代节奏**（用的人提需求持续优化）、有**使用率观测**（看板没人打开，要么设计差要么没价值，迭代或砍掉）——**平台是产品不是项目，交付只是起点**。

## 考察重点

| 维度 | 说明 |
| --- | --- |
| 企业动机 | 效能平台是效能团队的旗舰交付物（京东行云、阿里云效都是这个方向的产品化）——这题是测开转效能平台方向的核心技术题 |
| 过线标准 | 分层架构 + 口径管理 + 按受众分层设计 |
| 区分度 | 讲口径代码化和变更评审的是踩过数据混乱坑的；讲「先拼现成工具再自研」的是有落地智慧的 |
| 加分项 | 平台当产品运营（owner、迭代、使用率）的认知 |
| 减分项 | 平台方案就是「画几个 Dashboard」，把平台等同于报表页面 |
