# 13｜你的自动化框架是什么架构？从 0 搭建一个框架怎么搭？

> 开场自上而下讲自己的框架，再给从 0 搭建的实施顺序——讲架构时拿自己项目的真实模块名举例，可信度完全不同。

## 回答思路

### 第一步：五层架构

| 层 | 内容 |
| --- | --- |
| **基础层** | driver 封装、等待、截图、日志 |
| **页面对象层** | 页面元素与操作的封装 |
| **业务流程层** | 跨页面业务流封装 |
| **用例层** | pytest 组织、断言 |
| **数据层** | 参数文件、环境配置 |

再加横切的报告和 CI。

### 第二步：从 0 搭建给实施顺序

1. 先跑通**最小闭环**——一条端到端用例从执行到出报告
2. 补基础封装（driver 管理、显式等待、失败截图）
3. 建 PO 层沉淀页面
4. 接数据驱动和配置分离
5. 进 CI 和通知

这个「**先闭环后完善**」的顺序是项目经验的体现——很多人一上来就搭底层憋大招，憋到项目黄了。

### 第三步：讲配置和环境管理

多环境（测试、预发）用配置文件或环境变量切换，账号、域名、数据库连接**全部外置**——用例代码里不写死任何环境信息，这条是框架能不能多人共用的关键。

### 第四步：讲失败处理三件套

失败自动截图、自动重跑（标记 flaky）、失败原因初步归类（环境失败和断言失败分开统计）——这三件套决定 CI 报告有没有人看。

### 收尾：讲演进

框架是**长出来的不是设计出来的**——先服务一个项目跑稳，再抽象通用能力服务多项目。过度设计是 0 到 1 阶段最大的坑。

## 考察重点

| 维度 | 说明 |
| --- | --- |
| 企业动机 | 测开岗的核心大题——企业要判断你能不能独立扛起来一条自动化线，从架构到实施顺序到工程细节，一题看全 |
| 过线标准 | 分层清晰 + 有配置分离和失败处理 |
| 区分度 | 讲「先闭环后完善」实施顺序的是真从 0 搭过；张口就是完美架构图的是没落地过的理想派 |
| 加分项 | 真实模块名、真实数字、演进式设计观 |
| 减分项 | 只报工具名（pytest 加 selenium 加 allure）没有架构思想——工具堆不是框架 |
